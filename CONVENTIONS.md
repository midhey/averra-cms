# Соглашения

Короткий свод правил, чтобы код оставался нормальным, а не криво-косым. Меняем осознанно и сразу записываем сюда.

## Общее

- TypeScript в строгом режиме везде. `any` — только с комментарием, почему иначе нельзя.
- Форматирование и линт — Biome: 2 пробела, одинарные кавычки, без точек с запятой. Перед коммитом — `pnpm check`.
- Имена: типы и компоненты — `PascalCase`, функции и переменные — `camelCase`, файлы — `kebab-case` (кроме файлов компонентов, например `App.tsx`).
- Комментарии пишем по-русски и только там, где неочевидно, почему сделано так. Что делает код, должно быть видно из самого кода.

## Версии

- Node закреплена в `devEngines.runtime` каждого пакета (24 LTS). pnpm скачивает её сам, поэтому глобальная Node и PATH не важны.
- pnpm закреплён в двух местах: в `packageManager` (им запускается установка) и в `devDependencies` (его вызывают корневые скрипты). Версии в обоих местах должны совпадать.
- Общие зависимости (`typescript`, `hono`, `zod`, `@types/node`) подключаются через `catalog:` в `pnpm-workspace.yaml`: одна версия на весь репозиторий. Для `hono` это особенно важно: API и админка должны видеть одни и те же типы.
- Скрипты установки у зависимостей запрещены по умолчанию. Разрешённые перечислены в `allowBuilds`.
- Образ API (`deploy/Dockerfile`) — на той же Node, что в lockfile (`devEngines.runtime`): поменялась версия Node в проекте — меняется и `NODE_IMAGE`. Версии базовых образов (Node, Caddy, Postgres) пишем точно, без `latest`.

## Схемы

- Zod — единственный источник правды о данных. Типы выводим из схем (`z.infer`), руками не дублируем.
- Схемы входа API (тела запросов и параметры вроде адреса страницы) лежат в `@averra/schema`: ими же проверяют ввод формы админки и инструменты MCP. Одна схема — одно сообщение об ошибке везде: русские сообщения Zod включает `setupZodMessages()` из `@averra/schema`, и вызывает её при старте каждый процесс — админка, API (`index.ts` и `createTestApi`), команды терминала (`run` в `cli/common.ts`) и MCP. Новый процесс, который проверяет ввод, вызывает её тоже.
- Адрес страницы: новую создают только по `PageSlug`, а уже существующую ищут по мягкой `ExistingPageSlug` — в базе бывают адреса, созданные до строгой схемы.
- Id (uuid) во входе — только `Uuid()` из `@averra/schema`, не голый `z.uuid()`: он приводит id к строчным. Postgres сравнивает uuid без учёта регистра, а код — строки (ключи файлов, ссылки в JSON, права токена), и один id в двух написаниях их разводит.
- Схема данных, которые потом станут значением ввода (вариант выбора в блоке формы), проверяет их по тем же правилам, что и сервер при приёме: если сервер значение никогда не примет, редактор и MCP не должны суметь его сохранить.
- Флажок из HTML-формы принимается только значением, которое шлёт отмеченный флажок (`CHECKED_VALUE`); не прислан или пусто — не отмечен, прочее — ошибка, а не догадка. Согласие на обработку персональных данных — только так: запись «согласие дано» должна быть правдой.
- Списки форматов и типов (как `ImageFormat`, `imageMimeTypes`) берём из `@averra/schema` и выводим из них обратные справочники, а не пишем рядом свою копию.

## Блоки

- Поля блока описываются через `z.strictObject`: лишнее поле — ошибка, а не тихо выброшенные данные.
- `.meta({ title })` ставим последним в цепочке. Из него берутся подписи в админке и подсказки для MCP.
- Картинка в блоке — поле `Image` из `@averra/schema` (`{ mediaId, alt }`, alt обязателен). Пометка `x-widget` в `.meta()` ставит в админке свой виджет вместо обычных полей. Справочник картинок (`media`) блок получает пропсом, а выводит через `Picture` из `packages/blocks/src/ui`: сам `<img>` в блоках не пишем, иначе потеряются форматы, `srcset` и размеры.
- Стили пишем только на CSS Modules и переменных темы (`var(--color-accent)`). Конкретных цветов в блоках нет.
- Новый блок:
  1. схема в `packages/schema/src/blocks/<имя>.ts` и строчки в каталоге и союзе в `blocks/index.ts`;
  2. компонент в `packages/blocks/src/<имя>/` и `case` в `Page.tsx`. Без него проект не скомпилируется.
- Поля формы описывает одна таблица `fieldRules` в `packages/schema/src/forms.ts`. Из неё и HTML-атрибуты в браузере (`formFieldInput`), и проверка заявки на сервере (`leadValuesSchema`). Атрибуты проверки в компоненте руками не пишем. Новый тип поля — строка в `formFieldTypes` и `fieldRules` и ветка в обеих функциях. Образцы значений в `forms.test.ts` прогоняются через обе стороны. `pattern` пишем так, чтобы он компилировался с флагом `v`, как в браузере (`patternRegExp`): знаки внутри класса экранированы.
- Блоки на сайте работают без JavaScript. Форма — обычная HTML-форма, её адрес приёма блок получает пропсом `formAction` (без него, в предпросмотре, форма не отправляется). Состояние «отправлено» показывает CSS по `:target`, а не скрипт.
- Варианты выбора с подписями для людей — пометка `x-enum-titles` в `.meta()` (`{ значение: подпись }`). Да/нет — `z.boolean()`: админка рисует флажок.

## API

- Все маршруты лежат под `/api`.
- Зависимости приходят явно через `createApp(deps)`, глобальных синглтонов нет.
- `app.ts` и модули маршрутов не импортируют Node API (`fs`, `process` и т.п.). Админка читает типы API, и Node-импорты сломают ей проверку типов. Всё платформенное живёт в `index.ts` или за интерфейсами (например, хранилище файлов).
- Конфиг читается только в `config.ts` и проверяется Zod-схемой. В других местах `process.env` не трогаем.
- Ошибку сервера в лог пишем через `errorForLog` (`src/log-error.ts`): у ошибки запроса к базе в тексте и стеке — параметры запроса, а у её причины в `detail` — строка целиком, и там бывают секреты (зашифрованный пароль SMTP) и персональные данные. В лог идут запрос с плейсхолдерами, сообщение и код ошибки базы, места в коде. Логгер, который пишет чужие сообщения (Better Auth, `logger.log` в `auth/auth.ts`), не верит типам: Better Auth передаёт первым аргументом и саму ошибку, а логгер, который на ней падает, прячет исходный сбой.
- Ошибки отдаём в едином формате и по-русски, включая 404 неизвестного маршрута и 500: `{ "error": { "code": "...", "message": "..." } }`. Если ошибку можно привязать к полю (400 проверки, 409 «адрес занят»), в `issues` идёт путь до поля: админка покажет сообщение прямо у него.
- Коды: 400 — вход не прошёл схему, 404 — нет сайта или страницы, 409 — запрос правильный, но спорит с тем, что в базе (`conflict` из `src/errors.ts`), 410 — ссылка из письма была, но больше не действует (приглашение принято, отозвано или истекло; `invitationError`). Создание отвечает 201 с созданным, удаление — 204 без тела.
- Файлы и картинки — только через интерфейсы `MediaStorage` (`src/media/storage.ts`) и `ImageProcessor` (`src/media/processor.ts`). Реализации на диске и на sharp подключают `index.ts` и `testing.ts`, маршруты их не импортируют.
- Путь к файлу строит только сервер — `mediaKey(siteId, mediaId, имя)` из id и имени, которое составил сам. Пользовательский ввод (имя файла, расширение, `Content-Type`) в путь не попадает, а тип файла определяется по содержимому.
- Ссылки на картинки в страницах проверяет API: при сохранении и возврате версии каждый `mediaId` должен быть в медиатеке этого сайта, а картинку, которая стоит в черновике или на сайте, удалить нельзя.
- Выгрузка, которая растёт вместе с данными (CSV заявок), отдаётся потоком (`stream` из `hono/streaming`) порциями с курсором по ключу сортировки, а не собирается строкой в памяти. Курсор — значения последней строки порции: время текстом (`created_at::text`) и id, в SQL `(created_at, id) < ($1::timestamptz, $2::uuid)`. Не время, прошедшее через `Date` (микросекунды Postgres в `Date` теряются), и не подзапрос по id строки (удалили её во время выгрузки — подзапрос даст NULL, и выгрузка молча оборвётся).
- Предел, который считается по накопленным данным (дневной объём заявок), не должен закрывать сервис для честных пользователей: он касается только того, что его выбирает (крупных заявок), а маленькие проходят под обычными лимитами частоты. Размер, по которому считается предел, хранится в своей колонке (`leads.data_bytes`), а не пересчитывается из jsonb на каждом запросе.
- Сборка сайта на сервере приходит в маршруты интерфейсом `SitePublisher` (`src/publish/queue.ts`) через `createApp(deps)`. Процесс Astro, папки релизов и файлы — в `src/publish/` и подключаются в `index.ts`. Новый путь, который меняет опубликованное (публикация, удаление опубликованной страницы, потом — публикация по расписанию), после записи в базу зовёт `publisher.request(siteId)`. Сбой постановки в очередь публикацию не отменяет, он пишется в лог.
- Чужой процесс, которому не нужны секреты API (сборщик сайта), получает окружение по списку (`PASSED_ENV` в `src/publish/renderer.ts`), а не `process.env` целиком: его вывод попадает в журнал и в админку.
- Пути от `import.meta.url` в коде API считаются с глубины `src/<папка>/` — на той же глубине лежит сборка `dist/server/`, и куски бандла кладутся рядом с точками входа. Новый такой путь — проверка в `scripts/build.ts`.
- Модуль — это папка `src/modules/<имя>/`: в `routes.ts` HTTP и проверка входа, в `repo.ts` запросы к базе. `service.ts` появляется, когда логика перерастает один запрос.
- Вход проверяем через `validate(target, schema)` из `src/validate.ts`: ошибка приходит как 400 с путём до каждого кривого поля.

## Доступ

- Всё под `/api` закрыто по умолчанию: общий `authenticate` (`src/auth/middleware.ts`) пускает без входа только короткий список (`/api/health*`, `GET …/snapshot`, `GET /api/media/:id/:file`, `GET /api/password-reset`, `POST /api/invitations/lookup|register`, `POST /api/forms/:siteId/:slug/:blockId`, `/api/auth/*`). Открыть новый маршрут — значит осознанно вписать его туда. Открытый изменяющий маршрут пускает только по секрету из письма, его проверяет сам маршрут. Исключение — приём заявок с сайта: он открыт для всех, поэтому стоит под антиспамом (ловушка, лимиты по IP и по сайту, размер тела) и принимает только то, что есть в опубликованной версии страницы.
- Действия с персональными данными посетителей (`personalData` в `src/auth/access.ts`: `leads.*`) токену API запрещены в `requireSite` отдельной проверкой (403), что бы ни стояло в таблице ролей. Новое такое действие — строка и в таблице, и в `personalData`.
- Ответ посетителю сайта (не админке) — HTML-страница: сайт без JS, и JSON в браузере человеку ничего не скажет. Страницы собирает `messagePage` (`modules/leads/pages.ts`) через `html`…`` с экранированием и отдаёт с `PAGE_HEADERS` (CSP без скриптов). JSON (`ApiError`) — только если клиент просит его явно (`Accept` без `text/html`). Перенаправлять посетителя можно только на источник, который сам прислал форму (`Origin`, иначе `Referer`; `returnUrl`): других адресов из запроса не берём, открытого редиректа нет. Путь возврата — из маршрута (страница известна), а не из `Referer`: в чужой источник браузер по умолчанию шлёт `Referer` без пути.
- Ключи из запроса (поля формы, параметры) складываются в `Object.create(null)` и проверяются `Object.hasOwn`, а не `in` или `obj[key] ??`: иначе ключ `constructor` найдётся у `Object.prototype`.
- Лимит, ключ которого общий для многих (сайт), тратят только запросы, которые дошли до дела (сохранённая заявка). Иначе мусор с многих IP выбивает лимит у настоящих людей. Лимит по IP — на всё.
- IP посетителя — только ключ счётчика в памяти (`createRateLimiter`). В базу и в лог его не пишем (152-ФЗ).
- Открытый маршрут, который пишет в базу (приём заявок), ограничен не только частотой, но и объёмом записанного за сутки на сайт, и этот предел считается в базе: частотные лимиты в памяти забываются при перезапуске, а база растёт насовсем.
- Права сайта маршрут не проверяет сам, а объявляет действие: `requireSite(db, 'page.publish')`. Что какой роли можно, решает одна таблица в `src/auth/access.ts`; новое действие — новая строка в ней. Сайты создаёт только владелец (`requireOwner`).
- Коды: 401 — не вошёл или токен недействителен; 403 — роль на сайте есть, но действие ей не разрешено; 404 — сайта нет **или он чужой** (снаружи это неразличимо). Все — в формате `ApiError`, ответы Better Auth тоже переводятся в него.
- Учебный секрет (`DEV_AUTH_SECRET`), демо-сайт и владелец для разработки — только в учебном режиме: явный флаг `--dev` (его ставят только скрипт `dev` у API и e2e), `NODE_ENV` не `production`, а `ADMIN_URL` и `API_URL` на этом компьютере (`isLocalDev` в `config.ts`). Учебный режим не бывает режимом по умолчанию: ни забытая переменная, ни их полное отсутствие не должны его открывать. На учебном секрете API ещё и отвечает только соединениям с loopback и с `Host` на localhost (`src/client-ip.ts`), но это добавочная защита: прокси на том же сервере, который шлёт свой `Host` (nginx по умолчанию), её обходит. Всё, что опасно без своих секретов, включается по правилу `isLocalDev`, а не по одному `NODE_ENV`. Учебный секрет узнаётся не точным совпадением, а `isDevAuthSecret` (после нормализации ищутся его узнаваемые части): вариант с пробелами, кавычками или в другом регистре — тот же публичный секрет.
- Что делать с запросом до приложения, зная адрес сокета (`X-Forwarded-For`, loopback), — `prepareRequest` в `src/client-ip.ts`, без побочных эффектов и с тестом. `index.ts` только подключает его.
- Изменяющий запрос с cookie принимаем только с `Origin` админки. Запросы с токеном (`Authorization: Bearer`) Origin не проверяют: браузер сам токен не подставит.
- Токены API: в базе только SHA-256, сам токен показывается один раз; строка ищется по id из токена, хеш сравнивается за постоянное время. Права токена — редактор на одном сайте.
- Пароли и токены не печатаем и не логируем. Пароль в команды — скрытым вводом или переменной окружения, не аргументом.
- Действие, через которое можно перехватить доступ (сейчас — настройки почты: через неё уходят ссылки сброса пароля), — только владелец и только с повторным вводом своего пароля: `passwords.confirm` из `src/auth/confirm-password.ts` (`verifyPassword` Better Auth по cookie запроса). Неудачи считаются на пользователя: попытка учитывается до проверки, а удачная возвращается (`refund` у `createRateLimiter`). Неверный пароль — 403 `invalid_password` с путём до поля, а не 401: 401 админка понимает как «сессия кончилась». Сначала — проверка, можно ли действие вообще (409), потом пароль.
- Счётчик неудач своего пароля один на все пути, которыми вошедший проверяет пароль по HTTP. Его создаёт `createApp` (`createPasswordConfirmation`) и отдаёт и подтверждению, и обёртке смены пароля (`passwords.attempt`). Иначе лимит одного пути обходится другим. Эндпоинт Better Auth, который проверяет пароль, либо идёт через этот счётчик (обёрткой, как `/change-password`), либо закрыт: `CLOSED_AUTH_PATHS` в `src/auth/auth.ts` (`disabledPaths` Better Auth, сейчас `/verify-password`). Пометка `scope: 'server'` у эндпоинта Better Auth доступа по HTTP не закрывает. Вход — отдельный путь со своим лимитом по IP: его счётчик на аккаунт заблокировал бы владельцу вход по чужой воле.
- Ссылка с токеном в письме (сброс пароля, приглашение) ведёт на экран админки, токен — во фрагменте: `ADMIN_URL/<экран>#token=…`. Фрагмент не уходит на сервер, поэтому токен не попадает в логи и `Referer`; экран читает его один раз (`useLinkToken`) и убирает из адреса. В API токен приходит в теле запроса, а не в пути: путь пишется в лог.
- Токены из писем в базе — только хешем. Свои (приглашения) — как токены API: `<префикс>_<id строки>_<секрет>`, строка по id, `constantTimeEqual` по SHA-256. Токены Better Auth (сброс) хеширует `verification.storeIdentifier` (`hashVerificationIdentifier`). С хешером Better Auth ищет запись ещё и по идентификатору, собранному из присланного, как есть, и сохранённая строка не должна с ним совпасть. Поэтому в базе на месте разделителя всегда `#` (`<имя>#<хеш>` или `#<хеш>`), а идентификаторы Better Auth начинаются с постоянной приставки без `#` (`reset-password:`, `delete-account-`), с которой сохранённая строка не начинается. Плагин или эндпоинт, где идентификатор целиком задаёт клиент (номер телефона в `phone-number`, адрес в `siwe`), это нарушает — перед включением перепроверить. Токен Better Auth из запроса проверяем по формату до него (`ResetPasswordToken`), а варианты путей его эндпоинтов, которые мы оборачиваем, и закрытые пути в любом написании сквозной маршрут `/api/auth/*` не пропускает (404). Одноразовость — одним условным `UPDATE … WHERE ещё не использовано RETURNING` или атомарным погашением Better Auth, а не «прочитать, потом записать».
- Ответ на запрос, по которому можно узнать, есть ли пользователь («Забыли пароль?»), одинаков для любого адреса и по телу, и по времени (порог ответа), а лимит по адресу считает и несуществующие адреса.
- Свои лимиты — `createRateLimiter` (`src/rate-limit.ts`): число ключей в памяти ограничено, очистка не обходит всю таблицу на каждом запросе. Ключ, который выбирает клиент без входа (адрес почты), учитывается только после лимита по IP: иначе один клиент, перебирая ключи, раздувает память. Действие, которое шлёт письмо на любой адрес (приглашение), тоже под лимитом — и на адрес, и на того, кто шлёт.
- Записи с персональными данными, которые больше не нужны, удаляются по сроку обработчиком очереди (`cleanupAlso`), а не живут бессрочно. Закрытые приглашения — по `MAIL_RETENTION_DAYS` (`run(before)`), заявки — по сроку своего сайта (`lead_retention_days`, `run(before, now)`).
- Встроенная база (PGlite) не выполняет запрос мимо открытой транзакции — он ждёт её конца, и выходит взаимная блокировка. Внутри `db.transaction` все запросы — через `tx`; что нужно спросить у базы после отката, спрашиваем после транзакции.
- Админка прячет то, что роли нельзя, но правило живёт в API: скрытая кнопка — удобство, а не защита.

## Почта

- Письма уходят только через очередь: `enqueueMail(dbOrTx, { template, data, to })` из `src/mail/outbox.ts` тем же объектом базы или транзакции, что и действие. Прямо из запроса письмо не шлём: упал SMTP — действие не должно откатиться, а письмо — потеряться. Мимо очереди шлёт только `pnpm mail:test`.
- Провайдер — только через интерфейс `Mailer` (`src/mail/mailer.ts`). Реализации (`smtp-mailer.ts` на nodemailer, `file-mailer.ts`, `memory-mailer.ts`) подключают `index.ts`, `testing.ts` и команды; маршруты получают только состояние почты без секретов (`MailDeps`).
- From ставит провайдер из конфига, а не данные письма. Всё, что идёт в заголовки (адреса, тема, имя отправителя, Reply-To), проверяется схемами `MailAddress`, `MailSubject`, `MailSenderName` из `@averra/schema`: перевод строки — ошибка, а не тихая чистка. Строки данных шаблона, которые могут попасть в тему, — `MailLine()`, ссылки — `MailUrl` (только http и https). Адрес почты — шаблон `MAIL_ADDRESS_PATTERN`, один для `MailAddress` и для `pattern` в форме сайта; `z.email()` для адресов писем не берём (он не пускает IDN и punycode-зоны).
- Письмо о конкретной записи с персональными данными (заявке) ссылается на неё (`lead_id`, `ON DELETE CASCADE`): удалили запись — удалились и письма с её копией.
- Кто-то, кроме владельца, может направить письма с персональными данными на свои адреса (адреса уведомлений о заявках) — об этом в той же транзакции письмо владельцам и прежним адресам.
- Шаблон — файл в `src/mail/templates/` (`defineMailTemplate`: схема данных, пример для предпросмотра, `render`) и строка в `templates/index.ts`. HTML пишется только тегом `html` из `src/mail/html.ts`: подстановки экранируются, сырого HTML из данных нет. Оформление — инлайн-стилями через помощники `src/mail/layout.ts`, без `<style>` и внешних ресурсов. У каждого письма есть текстовая версия.
- SMTP — только шифрование (`secure` или `requireTLS`) и `rejectUnauthorized: true` явным параметром. Параметров, которые снимают проверку сертификата или шифрование (`ignoreTLS`, `opportunisticTLS`, `rejectUnauthorized: false`), в коде нет, а схема настроек из админки строгая: лишнее поле — 400. Своему CA доверяют только тесты (параметр `ca`) и API e2e (стандартный `NODE_EXTRA_CA_CERTS`: добавляет корневой сертификат, проверку не снимает).
- Колбэк `connect` у `SMTPConnection` nodemailer зовёт и тогда, когда сервер закрыл сокет сразу после TCP. Поэтому проверка по шагам (`diagnoseSmtp`) считает TLS пройденным только при живом и зашифрованном соединении (`destroyed`, `secure`). Сбой после открытого TCP объясняется с `FailureContext.connected` — без подсказки про файрвол. Подсказка «адрес должен принадлежать ящику» — только на 5xx на `MAIL FROM`; 4xx — временный лимит, настройки не трогать.
- Порт SMTP из админки — только 465 (TLS) или 587 (STARTTLS): схема (`smtpModes` в `@averra/schema`) и CHECK в базе. Проверки подключения — под лимитом на владельца. `connectPort` у `SmtpOptions` (подключиться к другому порту) — только для тестов, как `ca`: из API его не задать, а из окружения — только в учебном режиме (`DEV_SMTP_CONNECT_PORT` у API e2e, вне учебного режима конфиг не стартует).
- Пароль SMTP — в окружении или в базе только зашифрованным (`SecretBox`, ниже). Наружу его нет никогда, даже зашифрованным: ответ API отдаёт состояние («задан» или «не читается»), в лог идут названия полей, а не значения. Любой текст ошибки SMTP проходит `maskSecrets` (пароль и его base64), прежде чем попасть в очередь, лог, ответ проверки или вывод команды. В ответы API провайдер идёт без пароля (`MailerInfo`).
- Сохранённый пароль SMTP уходит только на сохранённый сервер: пустое поле пароля оставляет прежний, только если сервер тот же (`effectivePassword`). Иначе уведённая сессия направила бы «Проверить подключение» на свой сервер и получила бы пароль в `AUTH`.
- Действие без пароля владельца, которое пользуется сохранённым секретом (сейчас — «Проверить подключение» с сохранённым паролем SMTP), разрешено только на сохранённых данных целиком: сохранённые настройки и адрес самого владельца (`checkPasswordOf`). Иначе уведённая сессия слала бы через ящик студии (SPF и DKIM проходят) свои письма кому угодно.
- Секрет, который приходится хранить в базе, — только через `SecretBox` (`src/crypto/secret-box.ts`, реализация — AES-256-GCM в `aes-gcm.ts`): свой случайный IV на каждое шифрование, тег 16 байт с явной длиной, контекст (AAD) — к чему секрет относится, версия ключа в записи. Формат записи держит CHECK в базе. Ключ — своя переменная (`MAIL_ENCRYPTION_KEY`), не производная от `AUTH_SECRET`; учебный ключ — по правилам учебного секрета (`isDevMailKey`). Не расшифровалось — состояние с причиной («введите заново»), а не 500.
- Почта решается так: окружение (`SMTP_HOST` или явный `MAIL_TRANSPORT`) → настройки из админки (`mail_settings`) → по умолчанию. Её держит `MailRuntime` (`src/mail/runtime.ts`): маршруты спрашивают нынешнее состояние (`mail.runtime.status()`), а не значение, взятое при старте, обработчик берёт провайдера перед каждым письмом (`mailer()`), а смена настроек идёт через `exclusive` (транзакция с письмами, потом пересборка провайдера). Так письмо, легшее в очередь вместе с новыми настройками, уходит уже по ним. Сбой пересборки после коммита наружу не бросается: смена уже в базе, и запись в журнал и пробуждение обработчика должны случиться. Почта тогда на паузе (не на прежнем провайдере), а `mailer()` перечитывает настройки снова.
- Команда, которая кладёт письмо в очередь (`pnpm member:invite`), решает «почта есть» так же, как API: SMTP из админки — только если его пароль расшифровывается ключом из окружения (`readStoredPassword` из `src/mail/runtime.ts`), и причина отказа та же. Ссылки из писем ведут на `ADMIN_URL`: localhost при почте по SMTP — команда отказывает, API предупреждает в логе и на странице «Почта» (`localLinkWarning`, `src/mail/link-warning.ts`).
- Данные письма из очереди перед отправкой снова проверяются нынешней схемой шаблона. Список писем в API — без `data`: там персональные данные.
- Письмо на адрес, который ввёл посетитель сайта (подтверждение заявки), — только фиксированный текст: в схеме шаблона нет ни одного поля с его вводом (`lead-received` — только название сайта). Иначе форма становится рассылкой чужого текста с нашего домена. Такое письмо — только после антиспама и под лимитом на адрес. Лимит «на адрес» считается по ящику, а не по строке адреса: `mailboxKey` (`src/mail/mailbox-key.ts`, колонка `mail_outbox.recipient_key`) сводит `vasya+1@…`, регистр, точки Gmail и домены Яндекса к одному ящику. Письмо уходит на адрес как его ввели.
- Письмо, которое ставится вместе с действием посетителя (заявка), пишется в той же транзакции, что и запись о действии: не легло письмо — нет и записи, а посетитель видит ошибку. Свой подвал у шаблона — `footer` в `MailContent`, если общий («отвечать не нужно») неправда, как у письма с `Reply-To`.
- Данные письма живут в очереди только до отправки: `markSent` стирает `data`, база держит это проверкой `mail_outbox_data_lifetime`. Шаблон, в данных которого секрет (одноразовая ссылка с токеном), объявляет `secret: { lifetimeMs }`: его данные стираются и после окончательной неудачи, а письмо, которое не ушло за срок ссылки, не отправляется (`expires_at`). Такое письмо не повторяют — человек запрашивает новую ссылку. В базе остаётся только хеш токена (`verifications` у сброса пароля, `user_invitations` у приглашений), а не ссылка из письма.
- Аренда письма в очереди — на одно письмо: обработчик продлевает её (`renewLease`) перед отправкой каждого письма пачки и пропускает письмо, если его уже взял другой. Сбой записи «отправлено» — не неудачная попытка: письмо остаётся в `sending` до конца аренды. Ошибка сервера (DNS, соединение, TLS, вход) прерывает проход и ставит обработчик на паузу, а не тратит попытки всех писем пачки. Отказ на `MAIL FROM` — ошибка настроек (адрес отправителя не того ящика, под которым вход), а не письма: проход прерывается с паузой, а попытки не тратятся ни у одного письма, в том числе у того, на котором сломалось (`rejectedSender` у `MailSendError`). Окончательный отказ конкретного письма — только 5xx на `RCPT TO` и `DATA`. Время попытки (`last_attempt_at`) пишет `renewLease` перед настоящей отправкой, а не забор пачки: у отпущенного без попытки письма его нет.
- Время в очереди — параметр (`now`), а не `now()` базы: тесты двигают часы. Тесты SMTP — с настоящим `smtp-server` на свободном порту и сертификатом от тестового CA (`src/mail/testing/smtp.ts`, сертификаты — `testing/certs.ts`), без писем наружу. SMTP из админки в тестах API ходит туда же: `createTestApi({ smtp: { ca, connectPort } })`.

## Админка

- Маршруты — TanStack Router, описаны в коде в `apps/admin/src/router.tsx`. Экран берёт параметры через `getRouteApi`, а не импортом маршрута: так нет циклических импортов.
- Данные — TanStack Query. Опции запросов (`queryOptions`) — в `src/queries.ts`, ими пользуются и загрузчики маршрутов, и экраны. Ключи от общего к частному (`['sites', id, 'pages', slug]`): после мутации сбрасываем префикс, и всё зависимое перезагрузится само.
- Экран, который берёт данные в своё состояние один раз (редактор), грузит их через `fetchQuery`, а не из кеша: иначе сохранение устаревшего черновика затрёт чужие правки.
- Всё, что закрытый экран показывает сразу, грузит загрузчик маршрута (в том числе разделы только для владельца — по роли из `meQuery`), а не `useQuery` после отрисовки: запрос, ушедший после показа экрана, при истёкшей сессии уводит на вход посреди работы. Второстепенное (раздел «Участники» на экране сайта) загрузчик ждёт через `Promise.allSettled`: его сбой не прячет весь экран за экраном ошибки, а показывается внутри раздела (`useQuery` с `retryOnMount: false` и кнопкой «Повторить»).
- Экраны без входа (`/login`, `/forgot-password`, `/reset-password`, `/invite`) перечислены в `PUBLIC_PATHS` в `router.tsx`.
- Ошибка поля связана с ним через `aria-describedby` и `aria-invalid`, после неудачной отправки фокус уходит на первое поле с ошибкой. Общая ошибка формы — в `role="alert"`.
- Свой виджет поля (выбор картинки) приходит в `SchemaForm` явно, через `widgets`: форма общая и не знает ни про сайт, ни про медиатеку.
- Файл из API (CSV) админка скачивает запросом через клиент API и `Blob`, а не ссылкой на API: админка и API бывают на разных адресах, а запрос идёт с той же cookie и тем же разбором ошибок.
- У каждого экрана свой заголовок вкладки — `usePageTitle(...)` из `src/ui/use-page-title.ts`, и свой `<main>`.
- Параметры адреса (id сайта, адрес страницы) маршрут проверяет теми же схемами, что API, и на кривые отвечает `notFound({ data: 'Сайт не найден' })`, а не запросом в API.
- Экран, который живёт на параметре адреса и держит своё состояние (формы, сообщения), рисуется с `key` по этому параметру: переход «Назад» между сайтами не должен переносить состояние.
- Если действие убирает элемент с фокусом (удаление, возврат версии), фокус переводим на понятное место — заголовок списка (`tabIndex={-1}`), соседнюю кнопку, — а не оставляем на `body`.
- Запросы в API — через клиент из `src/api.ts` или `apiFetch`: сетевой сбой становится `NetworkError` («API не отвечает»), а любой другой `TypeError` (ошибка в коде) так не называется.
- Окно поверх экрана — нативный `<dialog>` через `showModal()`: фокус остаётся внутри, Esc закрывает, своей разметки для этого не нужно.
- Подтверждение опасных действий (удаление, уход с несохранёнными правками, «Сохранить без проверки») — `window.confirm`: работает с клавиатуры и экранным диктором без своей разметки.
- Секрет (пароль SMTP) в форму не приходит никогда: поле пустое, рядом — состояние («задан», «не читается»), пустое поле при сохранении — оставить прежний. После сохранения форма собирается заново (`key`), и поля паролей пустые. Что проверяли («Проверить подключение»), мутация получает явной переменной: пока идёт проверка, поля могут поправить. Так же явно сохранение получает, с чем сохранять — итог проверки или «без проверки» (`SaveProof`): мутация не превращает одно в другое молча.
- Список, который переставляют, — `SortableList` и `useSortableItem` из `src/ui/SortableList.tsx` (dnd-kit), а не свои обработчики мыши. Тащат за ручку `DragHandle` с подписью, где есть имя пункта («Перетащить блок «…»»), стрелки ↑↓ рядом остаются и подключаются через `useMoveButtons` (фокус не теряется на краю списка). Тексты для диктора — из `src/ui/sortable.ts`, по-русски и с именами пунктов; английских текстов dnd-kit по умолчанию быть не должно. Сама перестановка — `moveItem` оттуда же.
- Пунктам без своего id (пункты списков в формах) нужны постоянные ключи — `useItemKeys`: ключ по индексу после перестановки указывает на соседа. В данные ключи не попадают.

## База

- Drizzle. Локально работает PGlite (настоящий Postgres, собранный в WASM, данные лежат в `apps/api/.data`), в проде — PostgreSQL по `DATABASE_URL` через node-postgres. Базу выбирает `dbTargetOf`, открывает `createDb(target)` (`src/db/client.ts`). Тип `Db` один на оба драйвера. Сырой запрос (`db.execute`) читает результат как `{ rows }` — так отдают и PGlite, и node-postgres. Драйвер, который отдаёт иначе (postgres.js), не подключаем.
- Замок базы (`src/db/lock.ts`) — только у PGlite. С PostgreSQL команды терминала работают при запущенном API.
- Встроенная база — один процесс. API и команды терминала (`pnpm user:create`, `token:*`) открывают её через замок (`src/db/lock.ts`); новая команда, которой нужна база, берёт его через `openDb()` из `src/cli/common.ts`. Отказ из-за замка показывает `DbLockedError.hint` — путь к файлу замка: pid упавшего процесса мог достаться постороннему.
- Таблицы Better Auth (`users`, `sessions`, `accounts`, `verifications`) описаны в нашей `schema.ts` и меняются нашими миграциями; набор их полей задаёт Better Auth.
- Схема базы меняется только миграциями: правим `apps/api/src/db/schema.ts`, запускаем `pnpm db:generate` и коммитим SQL из `apps/api/drizzle` вместе с кодом. API применяет миграции сам при старте.
- В коде поля в camelCase, в базе колонки в snake_case.
- `site_id` есть в каждой таблице с контентом.
- Опубликованную версию страницы меняет только `sitesRepo.publish`, и в той же транзакции он пишет снимок в `page_revisions`. Новый путь публикации (по расписанию, из MCP) идёт через него же, иначе история разойдётся с сайтом.
- История не переписывается: возврат версии меняет только черновик. Данные из истории, которые снова идут в работу, проверяем нынешними схемами: снимок в базе старый, а схемы в коде меняются.
- Миграция, которая вводит производные данные (как история), заполняет их и для того, что уже лежит в базе: в базе пользователя есть контент, созданный до неё.

## Тесты

- Vitest. API тестируем через `app.request()` без запуска сервера, с PGlite в памяти. Медиатека в тестах — своя временная папка у каждого `createTestApi()`, её удаляет `close()`. Картинки для тестов рисует sharp прямо в тесте, бинарных файлов в репозитории нет.
- Тесты ходят в API так же, как настоящие клиенты: `createTestApi()` даёт `loginAs('owner' | 'editor' | 'client')` (заголовки сессии с `Origin` админки) и `createToken(siteId)`. Права в обход проверок не отключаем.
- Лимит попыток входа общий на процесс. Тест, который входит через HTTP, ставит себе свой `X-Forwarded-For`; помощники входят серверным вызовом Better Auth и лимит не тратят.
- Тест пишем вместе с кодом, а не «потом».
- Тесты не делят объекты с состоянием: каждый тест создаёт свой экземпляр (фабрикой или в `beforeEach`). Проверка — `vitest run --sequence.shuffle` и запуск одного теста через `-t`.
- То, чем драйверы базы расходятся (сырые запросы, типы, транзакции, пул), проверяет `src/db/postgres.test.ts` на настоящем драйвере node-postgres: сервер протокола Postgres поверх PGlite (`@electric-sql/pglite-socket`) на порту 0. Закрывать по порядку: API (пул), дождаться, пока сервер разберёт закрытые соединения, сервер, потом PGlite — иначе его обработчик упадёт после тестов.
- Скрипт для сервера (`deploy/install.sh`) тестируется в `deploy/tests` настоящим bash (на Windows — Git Bash) с подделками внешних команд (docker, ss, getent, hostname) первыми в PATH: они пишут, с чем их позвали. Подделки ставятся в PATH внутри bash, а не через окружение Node: Git Bash ставит `/usr/bin` впереди унаследованного PATH. Права `.env` проверяются на всех системах по вызову `chmod 600` (подделка `chmod` пишет вызов и зовёт настоящий), а на Linux — ещё и по режиму файла. `pnpm check` на Linux идёт в CI на каждый push и pull request (`.github/workflows/ci.yml`).
- Сквозные сценарии (админка → API → рендерер) — Playwright в `e2e/`. Запуск — `pnpm e2e`, в `pnpm check` они не входят.
- e2e ищут элементы по ролям и подписям (`getByRole`, `getByLabel`), как их видит человек с экранным диктором, а не по CSS-классам. Нет подписи — сначала чиним доступность.
- В редакторе несколько живых областей `role="status"`: у каждого списка с перетаскиванием своя (dnd-kit). Статус редактора e2e ищут внутри области «Страница», объявления — внутри своего списка. Перетаскивание мышью — `dragWithMouse` (по шагам, как человек), первую стрелку после подъёма с клавиатуры — `firstArrow`: dnd-kit начинает слушать стрелки через тик после подъёма, и слишком быстрое нажатие теряется.
- e2e не зависят друг от друга и от порядка: каждый стартует с известного состояния (фикстура в `e2e/tests/fixtures.ts` возвращает демо-сайт к исходному: главная — демо, других страниц нет) или создаёт свои данные. Свои сайты тест называет уникально: они копятся до следующего прогона. Проверка — `pnpm e2e --shuffle`.
- e2e стартуют уже вошедшими владельцем (cookie от проекта `setup`). Тест, которому нужен вход как таковой или другой пользователь, берёт пустой `storageState` и свой `X-Forwarded-For`. Общую сессию из файла тесты не завершают: «Выйти» жмут только в своей.
- Посетитель опубликованного сайта в e2e — свой контекст браузера: без входа (`storageState` пустой), с выключенным JavaScript (`javaScriptEnabled: false`), если проверяем сайт без JS, и со своим `X-Forwarded-For`, чтобы лимиты по IP не делились между тестами.
- Что админка прячет от роли, e2e проверяет подменой роли в ответах API (`page.route`, `tests/client.spec.ts`), а права — тесты API. Настоящего участника e2e заводят приглашением (`tests/invitations.spec.ts`, `createMember` в `tests/password-reset.spec.ts`): команды не открывают базу, пока запущен API e2e. Письма e2e читают из своего файлового ящика (`tests/mailbox.ts`).
- e2e, который меняет настройки почты (SMTP в админке), возвращает их в `finally` — удаляет настройки через API: остальные e2e читают файловый ящик. Его тестовый SMTP-сервер слушает свой порт (`smtpTest.port` в `e2e/urls.ts`, не ниже 1024: такой порт на Linux без root не занять), в форме — 587, а API e2e подключается к серверу через `DEV_SMTP_CONNECT_PORT`. CA создаёт `scripts/smtp-certs.ts` до старта API, а API e2e доверяет ему через `NODE_EXTRA_CA_CERTS`.
- API e2e запущен с `PUBLISH_DIR` (`e2e/.data/sites`): каждая публикация в e2e собирает демо-сайт настоящим Astro в фоне. На экране сайта две живые области (`role="status"`): у списка страниц и у раздела «Сайт на сервере», поэтому статус ищем внутри своего раздела.
- Порты e2e (API 4100, админка 5273, рендерер 4421), база и картинки в `e2e/.data` — свои, чтобы не задеть `pnpm dev` и его базу. Любой сервер, который e2e поднимает рядом с `pnpm dev`, не должен делить с ним базу и файлы-замки, которые запрещают второй запуск. Поэтому рендерер в e2e идёт с `astro dev --ignore-lock`.

## Установка и публикация на сервере

- Установка на VPS — `deploy/`: `Dockerfile` (цели `api` и `web`), `compose.yaml`, `Caddyfile`, `install.sh`. Секретов в образах нет (`.dockerignore`), они приходят из `.env` установки. API в образе — только prod-зависимости и собранный JS (запускается не через tsx; tsx и esbuild приезжают транзитивно с vite и astro для сборщика сайта), от пользователя `node`, без флага `--dev` и с `NODE_ENV=production`. Ни один контейнер не работает от root: Caddy (`web`) — от `caddy`. Прав контейнеру — минимум: `api` без capabilities и с `no-new-privileges`, `caddy` — только `NET_BIND_SERVICE`. У `api` `init: true`: он запускает сборщик с потомками. `TRUST_PROXY` включает `compose.yaml` рядом с Caddy, а не образ. Это держит тест установщика.
- Установщик повторяем: уже записанный секрет не меняется никогда, созданное (владелец, сайт) второй раз не создаётся, `.env` читается как текст (не `source`) и пишется с правами 600 до того, как встанет на место. Значения, которые попадают в Caddyfile и `.env` (домены, почта, тег образа), проверяются шаблоном: ни пробелов, ни переводов строк. Секрет в команду в контейнере — переменной окружения (`-e VAR` без значения), а не аргументом. Секрет установщику (пароль владельца, токен GHCR) — скрытым вопросом или переменной окружения, никогда флагом. Проверки окружения — функции через `problem`: обычный прогон на первой останавливается, `--dry-run` показывает все.
- Сайт на сервере — статика из `PUBLISH_DIR/<сайт>/current`. Сборки — только через очередь (`createPublishQueue`): по одной на установку, журнал в `site_builds`. Новая версия — новая папка, `current` меняется переименованием новой ссылки поверх старой. Папку, на которую смотрит `current`, не правим и не удаляем.
- Рендерер для публикации собирает сайт с `CMS_LINKS=relative`: картинки — `/media/<id>/<файл>` из папки версии, формы — `/api/forms/…` на свой же домен (Caddy передаёт этот путь в API). В версию попадают только файлы, на которые ссылаются страницы: картинки по ссылкам из HTML (`copyReferencedMedia`), `_astro` — по ссылкам из HTML, CSS и JS (`pruneUnusedAssets`).
- Кеш в Caddy: `Cache-Control` ставится на ветку `handle`, а не матчером по пути файла — `header` выполняется раньше `try_files` и видит исходный путь. Неизменяемое (`immutable`) — только то, у чего в имени хеш или uuid: `/assets/*` админки (своя ветка без `try_files`, нет файла — 404), `/_astro/*` и `/media/<uuid>/…` сайта. Страница сайта может называться как служебная папка (`media`), поэтому матчеры сайта точные.
- Сборки при старте API: `markInterrupted` до `serve()`, `resume` — после (сборщик ходит в этот же API). Сборки, которые уже идут в этом процессе, прерванными не считаются.
- Сторонние actions в `.github/workflows` закреплены по SHA коммита с версией в комментарии, Node — `actions/setup-node` с версией из `devEngines.runtime`.
- Caddy на домене сайта открывает в API только `/api/forms/*`. Новый открытый путь сайта в API — осознанно, строкой в `Caddyfile`.
