# План: Averra CMS — своя CMS для лендингов

> v0.9 от 16 октября 2026: этапы 0–2 готовы, на этапе 3 сделаны почта (шаг 3.1), сброс пароля и приглашения участников (шаг 3.2), настройки SMTP в админке (шаг 3.3), формы и заявки (шаг 3.4) и мелочи формы после приёмки (шаг 3.5). Решено: у каждого клиента своя установка на его VPS (модуль 9), поэтому установка и обновления идут следующим крупным шагом. Живой документ, правим по ходу.

Averra CMS — внутренняя система студии Averra для быстрых, лёгких и аккуратно сделанных лендингов. Всё, ради чего в WordPress ставят плагины (ACF, Yoast, Smush, Contact Form 7…), есть в ядре. Контент хранится как JSON по схемам, сайт собирается в статический HTML, нейронки работают с теми же схемами через MCP.

**Как разворачивается.** Как WordPress, а не как Тильда: у каждого клиента своя установка Averra на его VPS. Студия её ставит, обновляет и обслуживает, клиент работает в своей админке. Данные клиента (страницы, заявки, медиа) живут на его сервере, а не у студии. Несколько сайтов в одной установке тоже можно — пригодится клиенту с двумя лендингами, — но это не главный сценарий.

## Принципы

1. **Одна схема — много потребителей.** Блок описывается один раз: Zod-схема + компонент. Из схемы автоматически получаются валидация в API, TS-типы, формы в админке и JSON Schema для MCP.
2. **Контент — это данные, а не HTML.** Страница — это JSON со списком блоков и их полей. HTML в базе не храним.
3. **В git лежат код и схемы, в базе — то, что меняет человек.** Блоки, типы контента и пресеты тем живут в коде. Контент, медиа и настройки конкретного сайта хранятся в базе.
4. **Явное вместо глобального.** Никаких глобальных хуков по строковым именам и никакого глобального состояния. Хуки вешаются на конкретный тип (`beforeSave`, `afterPublish`), данные передаются в компоненты явно.
5. **На выходе статика.** HTML и CSS, а JavaScript только там, где без него никак (форма, слайдер). Сайт быстрый, хостинг почти бесплатный, взламывать почти нечего.
6. **Стили только через токены.** Блок не знает конкретных цветов и шрифтов, только роли из темы («акцент», «фон»). Поменял фирменный цвет, и поменялся весь сайт.
7. **Нейронка — такой же клиент API, как админка.** Те же схемы, те же права, правки только в черновик. Публикует человек.
8. **Клиент не заложник.** Любой сайт выгружается статическим архивом, который откроет любой разработчик.

## Модули

Твои пункты 1–7 плюс два, без которых лендинга не бывает: формы (8) и публикация (9).

### 1. Авторизация и пользователи
*Заменяет: штатных пользователей WP, Wordfence / Two Factor, Ultimate Member для личных кабинетов.*

- Два раздельных пула пользователей: **админка** (ты, редакторы, клиенты) и **посетители сайта**. Разные таблицы и разные сессии, поэтому посетитель в принципе не может оказаться в админке.
- Криптографию сами не пишем, берём проверенную библиотеку (например, Better Auth): хеширование паролей, сессии в httpOnly-cookie, сброс пароля, лимит попыток входа.
- Роли в установке клиента: **владелец** — студия (почта, пользователи, обновления; при желании владельцем можно сделать и клиента — сервер его), **редактор** — подрядчик или контент-менеджер сайта, **клиент** — заказчик для повседневной работы: тексты, заявки, откат версий. Участник видит только свои сайты.
- API-токены с правами на конкретный сайт, они понадобятся для MCP.
- ✓ Сброс пароля по ссылке из письма и приглашение участников на сайт письмом ([шаг 3.2](docs/steps/3.2-password-reset-invitations.md)). Приглашает и отзывает только владелец; дать это редактору — одна строка `members.invite` в `apps/api/src/auth/access.ts`, если понадобится.
- **MVP:** вход в админку, сессии, сброс пароля, роли — готово.
- **Потом:** 2FA, вход по ссылке из письма. Посетители сайта — когда появится проект, где реально нужен личный кабинет.

### 2. Контент и вывод
*Заменяет: ACF, Custom Post Type UI.*

- Страница хранится как JSON: `{ blocks: [{ type: "hero", variant: "split", props: { … } }] }`. Каждый блок проверяется своей схемой.
- Черновик → публикация. Предпросмотр черновика по закрытой ссылке.
- Ревизии — снимки JSON при публикации, откат в один клик (с JSON это почти бесплатно).
- Общие данные сайта (шапка, подвал, контакты, соцсети) задаются один раз и доступны всем блокам.
- Вывод: рендерер берёт JSON сайта и собирает статику (Astro рендерит те же React-компоненты блоков).
- **Потом:** коллекции (отзывы, услуги, блог), когда понадобится больше одной страницы.

### 3. Медиа
*Заменяет: Smush, ShortPixel, Imagify.*

- Загрузка → проверка типа и размера → удаление EXIF (там бывают GPS-координаты) → оригинал в хранилище.
- Ресайз под набор ширин и конвертация в WebP/AVIF (sharp). На выходе `srcset`, `sizes` и `loading="lazy"` проставляются сами.
- Точка фокуса для кадрирования. Alt обязателен, нейронка может его предлагать.
- SVG принимаем только после очистки: через SVG легко протащить XSS.
- Хранилище спрятано за интерфейсом: в разработке локальный диск, в проде S3-совместимое.
- Минификацию CSS и JS делает сборщик, получаем её бесплатно.

### 4. SEO и настройки сайта
*Заменяет: Yoast / Rank Math, Redirection, Site Kit.*

- На странице: title, description, OG-картинка (по умолчанию генерируется из заголовка), canonical, noindex.
- На сайте: sitemap.xml и robots.txt генерируются сами, набор favicon из одной картинки, JSON-LD (организация, FAQ), 301-редиректы, страница 404.
- Аналитика и верификация — просто поля в настройках: Метрика, Вебмастер, GA, Search Console.
- Цель в Метрике на отправку формы (из модуля 8). Сайт без JavaScript сам цель на отправку не поставит. Варианты: цель на открытие страницы с якорем `#…-sent` (на него API возвращает посетителя после заявки) или серверная отправка цели из API при приёме заявки (Measurement Protocol / офлайн-конверсии Метрики). Решить вместе со счётчиком Метрики в этом шаге.
- Проверки «как у Yoast», но по делу: длина title и description, один h1, alt у всех картинок. Многое решается самой конструкцией: блоки сами правильно расставляют заголовки.
- Технические настройки: домен, язык, часовой пояс, реквизиты для подвала.

### 5. Конструктор блоков
*Заменяет: Elementor, Gutenberg с наборами блоков.*

Главное решение: **секции, а не свободный холст.** Как стандартные блоки в Тильде, а не Zero Block: выбрал секцию и вариант оформления, заполнил поля. Адаптивность гарантирует код блока, а не ручная расстановка под каждый экран. Свободный холст — отдельный продукт размером со всю остальную систему.

- Блок = компонент + схема + варианты + картинка для каталога.
- Редактор: добавить, удалить, переставить или скрыть блок. Поля генерируются из схемы. Живой предпросмотр в iframe на тех же компонентах, что и в проде, с переключателем десктоп / планшет / телефон.
- Адаптивные настройки в разумных пределах: скрыть на телефоне, число колонок, порядок элементов.
- **MVP:** 3 блока. **К первому клиенту:** 12–15.

### 6. Нейронки и MCP

- MCP-сервер — тонкая обёртка над тем же API: `list_blocks` (со схемами), `get_page`, `create_draft`, `update_draft`, `upload_image`, `request_publish`.
- Прототип уже есть: `list_blocks`, `list_sites`, `get_page`, `save_draft` и `publish_page`, пока только локально. Ходит в API по токену с правами редактора на одном сайте (`pnpm token:create`).
- Схемы инструментов генерируются из тех же Zod-схем. Невалидную страницу API просто не примет, так что сломать вёрстку нейронка не может.
- Доступ по токену с правами на конкретный сайт, правки только в черновик.
- Сценарии: черновик лендинга по брифу, «перепиши тексты под другую аудиторию», alt-тексты и мета-теги.
- **Потом:** Telegram-бот для клиента: «поменяй цену на 5000» → черновик → превью → «Опубликовать?».

### 7. Цвета и стилизация
*Заменяет: Customizer, theme.json.*

- Дизайн-токены → CSS-переменные: цвета по ролям (фон, текст, акцент, состояния), шрифты, шкала размеров, отступы, скругления, тени.
- Тема сайта — набор значений токенов: несколько готовых пресетов плюс свои.
- Проверка контраста по WCAG прямо при выборе цветов: серый текст на сером фоне не пройдёт.
- Шрифты раздаём со своего сервера, а не с Google Fonts: так быстрее и без лишних внешних запросов.

### 8. Формы и заявки
*Заменяет: Contact Form 7 / WPForms, Flamingo, плагины капчи.*

- ✓ Блок «Форма заявки» со схемой полей ([шаг 3.4](docs/steps/3.4-forms-leads.md)): имя, телефон, почта, строка, многострочный текст, выбор из списка, флажок. Валидация в браузере (HTML-атрибуты) и на сервере идёт по одной схеме. Сайт остаётся без JavaScript: обычная HTML-форма в API, после приёма — 303 на страницу с якорем, «Спасибо» показывает CSS (`:target`).
- ✓ Заявки сохраняются в базе (`leads`, проверка по опубликованной версии страницы) и дублируются письмом владельцу или менеджеру в той же транзакции. В админке раздел «Заявки»: список, карточка, «обработана», удаление, CSV с защитой от CSV-инъекции, счётчик новых. Видят владелец и клиент сайта, токен MCP — никогда.
- ✓ Антиспам: скрытое поле-ловушка (honeypot), лимит частоты по IP и по сайту, предел размера тела, дневной предел объёма заявок на сайт (10 МБ за сутки для заявок крупнее 8 КБ, маленькие проходят и сверх него; считается в базе — [шаг 3.5](docs/steps/3.5-forms-cleanup.md)). Минимальное время заполнения на статике честно не сделать — не делаем. Капча — только если реально спамят.
- ✓ Согласие на обработку персональных данных обязательно и явное: засчитывается только значение отмеченного флажка, прочее — отказ ([шаг 3.5](docs/steps/3.5-forms-cleanup.md)). Ссылка на политику — обязательное поле блока. В заявке записано, на что и когда согласились. IP не храним, заявки удаляются по сроку сайта (по умолчанию 180 дней). Для клиентов из РФ заявки хранятся на сервере в РФ (152-ФЗ) — это про выбор хостинга (модуль 9).
- Массовое удаление заявок (выбрать флажками в списке и удалить) — когда понадобится. Пока рост базы держит дневной предел объёма, а заявки удаляются по сроку сайта; «удалить за период» не годится — вместе со спамом ушли бы настоящие заявки (шаг 3.5).
- Уведомления о заявках в Telegram и вебхук в CRM — отдельным шагом. Встают на тот же outbox: заявка и задача уведомления — одной транзакцией, отправка с повторами. Токен бота и адрес вебхука — секреты сайта, хранить как пароль SMTP (`SecretBox`).
- Цель в Метрике на отправку формы — в модуле 4 (SEO и аналитика): без JavaScript её не поставить, варианты записаны там.

### 9. Установка, публикация и обновления
*Заменяет: установку WordPress на хостинг, кеш-плагины (WP Super Cache, W3 Total Cache), UpdraftPlus, ManageWP.*

Одна установка на клиента, на его VPS. Клиентов много, а студия одна, поэтому главное здесь — чтобы ставить, обновлять и чинить N установок было скучно и безопасно.

- **Установка одной командой** на чистый VPS (Ubuntu): Docker Compose — API с админкой, PostgreSQL, Caddy. Домен сайта и поддомен админки, SSL Caddy выпускает и продлевает сам. Мастер первого запуска: секреты генерируются, владелец создаётся, учебный режим на сервере невозможен (это уже держит `config.ts`).
- **Лёгкость:** всё работает на дешёвом VPS с 1–2 ГБ памяти. Самое тяжёлое — сборка Astro при публикации, её меряем.
- **«Опубликовать»** → сборка статики прямо на этом VPS → атомарная подмена папки, которую отдаёт Caddy. В выкладку попадают только файлы, на которые ссылается страница: Astro кладёт в `dist` бандл React для интерактивных островов, даже когда страница его не загружает.
- **Обновления:** версии выходят релизами (образы с номером версии). Обновление: бэкап → новая версия → миграции → проверка `/api/health/ready` → при сбое откат на прежний образ и бэкап. Миграции только совместимые вперёд. Обновить все установки студии — одной командой по списку серверов.
- **Бэкапы** базы и медиа по расписанию, хранение N копий; по желанию — во внешнее хранилище (например, Yandex Object Storage). Восстановление проверяется, а не только запись.
- **Состояние установок:** версия, живы ли API и база, когда был последний бэкап и последняя публикация, работает ли почта — чтобы студия видела всех клиентов сразу.
- **Клиент не заложник:** экспорт сайта статическим архивом и полный экспорт данных.
- Для 152-ФЗ VPS клиента из РФ стоит в России — тогда заявки и так хранятся там.

### 10. Почта
*Заменяет: WP Mail SMTP, Post SMTP, Email Templates.*

**Какие письма.**
- ✓ Новая заявка с формы — владельцу или менеджеру сайта (адреса — настройка сайта, по умолчанию владельцы). Адрес посетителя ставим в Reply-To, чтобы ответить можно было прямо из почты ([шаг 3.4](docs/steps/3.4-forms-leads.md)).
- ✓ Подтверждение посетителю, что заявка получена (можно выключить на сайте). Только фиксированный текст сайта, без того, что посетитель ввёл в форму, — см. «Безопасность».
- ✓ Сброс пароля админки по ссылке из письма.
- ✓ Приглашение участника на сайт: клиент получает ссылку и сам задаёт пароль, без передачи пароля руками.
- Позже: вход по ссылке из письма, уведомление о входе с нового устройства, сбой публикации.

**Отправка.**
- ✓ Интерфейс `Mailer` в коде, как `Storage` у медиа: провайдер меняется, код писем — нет.
- ✓ Провайдеры: SMTP (nodemailer) в проде; в разработке письма кладутся в папку `.data/mail` и не уходят наружу — их удобно смотреть руками и читать в e2e; в тестах — в память.
- ✓ Письма не отправляются прямо из запроса, а пишутся в таблицу `mail_outbox` в той же транзакции, что и заявка (паттерн outbox). Отдельный обработчик шлёт их с повторами и растущей паузой, хранит статус и последнюю ошибку. Упал SMTP — заявка не теряется, письмо уйдёт позже. Ошибка настроек (неверный вход, адрес отправителя не того ящика) очередь не сжигает: обработчик выжидает, а письма ждут исправления.
- ✓ Отправленные письма с персональными данными чистятся из `mail_outbox` через N дней (152-ФЗ: храним не дольше, чем нужно).

**Шаблоны.**
- ✓ Шаблон — компонент со схемой данных (Zod). Данные проверяются схемой перед отправкой, поэтому письмо не уйдёт с пустым полем или чужим типом.
- ✓ Из одного шаблона собираются HTML с инлайн-стилями (почтовые клиенты не понимают нормальный CSS) и текстовая версия.
- ✓ Всё, что пришло от пользователя, только экранируется, как в React; сырого HTML в письмах нет.
- Оформление берётся из темы сайта (цвета, логотип), письма системы — в стиле студии.
- ✓ Тексты по-русски. В админке — предпросмотр каждого шаблона на примерных данных, как блоки в редакторе.

**Подключение SMTP.**
- ✓ Настройки SMTP в админке ([шаг 3.3](docs/steps/3.3-smtp-settings.md)): на странице «Почта», одни на всю установку. Менять может только владелец и только с повторным вводом своего пароля. «Проверить подключение» по ещё не сохранённым настройкам проходит те же шаги, что `pnpm mail:test`. Сохранить можно после успешной проверки или явно «без проверки», и всем владельцам уходит письмо «Настройки почты изменены». Сменить пароль или провайдера можно без доступа к серверу, перезапуск не нужен.
- ✓ Переменные окружения необязательны, проверяются в `config.ts`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`. Если заданы, они главнее админки, и она показывает их только для чтения. SMTP не задан нигде — почта выключена, и админка честно говорит, что сброс пароля и уведомления о заявках не работают.
- ✓ Команда `pnpm mail:test --to …` отправляет пробное письмо и показывает, на каком шаге сломалось: соединение, TLS, вход, отправка.
- Провайдер — российский (SMTP Яндекс 360, Unisender Go и т.п.): в письмах о заявках есть персональные данные (152-ФЗ).
- Потом, вместе с формами: свой SMTP у сайта, чтобы письма клиента уходили с его домена. Модель к этому готова: строка `mail_settings` с `site_id`, пароль шифруется так же, но со своим контекстом.

**Безопасность.**
- ✓ Только шифрованное соединение: TLS на 465 или STARTTLS на 587 с обязательным шифрованием. Сертификат сервера проверяется всегда — отключать проверку нельзя даже в настройках.
- ✓ Пароль SMTP хранится в переменной окружения или в базе, и в базе только зашифрованным: AES-256-GCM, отдельный ключ `MAIL_ENCRYPTION_KEY` (не из `AUTH_SECRET`), свой IV на каждое шифрование, версия ключа в записи. Его нет в git, логах и ответах API, в том числе в зашифрованном виде. В текстах ошибок он маскируется. Нет ключа — SMTP в админке только для чтения. Ключ не тот — почта выключена с понятной причиной «введите пароль SMTP заново».
- ✓ Украденная сессия не перенаправит письма сброса пароля на свой сервер: для смены SMTP нужен пароль владельца. Неудач — до 5 за 15 минут, и счётчик общий у всех путей, которыми вошедший проверяет свой пароль (настройки почты и смена пароля). Проверка пароля Better Auth по HTTP закрыта, так что через сессию пароль не подобрать быстрее, чем входом. Сохранённый пароль SMTP уходит только на сохранённый сервер, а в проверке подключения (она пароля владельца не просит) работает только с сохранёнными настройками и на почту владельца: через ящик студии не разослать своих писем. Проверка подключения ходит только на порты 465 и 587 и под лимитом, так что сканером портов сервер не станет.
- ✓ Адреса, тема и имя отправителя проверяются схемой: переводы строк запрещены, иначе через них подставляют свои заголовки письма (header injection).
- ✓ Форма не должна стать рассылкой спама. Письмо посетителю содержит только фиксированный текст, а не то, что он ввёл (в схеме шаблона только название сайта). Подтверждение — не чаще раза в сутки на ящик с сайта (адрес сводится к ящику: без метки «+», регистра, точек Gmail — шаг 3.5), заявки — под лимитом по IP и по сайту, и подтверждение уходит только после проверки антиспама формы (шаг 3.4).
- ✓ Заявки нельзя молча перенаправить: адреса уведомлений меняют владелец и клиент сайта, и о каждой смене письмом узнают все владельцы и прежние адреса (шаг 3.4). Решено (16 октября): смена адресов остаётся у клиента — это его установка и его заявки (решение 6).
- ✓ Ссылки сброса пароля и приглашения одноразовые: в базе лежит только хеш токена, и сам он ссылкой не работает (строка в базе не похожа на идентификатор Better Auth, формат токена проверяется до него), срок жизни ограничен (сброс — 1 час, приглашение — 7 дней), после использования или нового запроса токен сгорает. На «забыл пароль» ответ всегда одинаковый, чтобы нельзя было проверить, есть ли такой адрес. Лимит запросов сброса: сначала по IP, потом по адресу, счётчики в памяти ограничены по размеру. Лимит приглашений на адрес и на владельца.
- From — всегда на своём домене. У домена студии и доменов клиентов настроены SPF, DKIM и DMARC: без них письма уходят в спам, а домен легко подделать. Что и как прописать в DNS — инструкция в README.

## Модель данных (первый набросок)

`site_id` есть везде с первого дня, даже пока сайт один. Прикручивать поддержку нескольких сайтов потом очень больно.

- `sites` — домен, настройки и тема (JSON)
- `users` (роль `owner` | `member`), `site_members` (роль участника на сайте: `editor` | `client`); `sessions`, `accounts`, `verifications` — таблицы Better Auth
- `pages` — `site_id`, `slug`, `draft` (JSON) и `title` черновика, `published` (JSON) и `published_title` опубликованной версии (заполнены вместе, это проверяет база), статус
- `page_revisions` — снимок при каждой публикации: страница, номер версии, заголовок и блоки (JSON), кто опубликовал (пользователь или токен) и когда
- `media` — картинки сайта: исходное имя, тип, размеры, вес, варианты (JSON), кто (пользователь или токен) и когда загрузил. Файлы — в хранилище по ключу из id
- `leads` — заявки с форм: сайт, страница (ссылка и адрес), блок, заголовок формы, данные — снимок полей с подписями, согласие (текст, политика, версия страницы, время), статус `new` / `processed`, когда создана. IP не храним. Удаляются через `lead_retention_days` сайта; там же в `sites` — адреса уведомлений и подтверждение посетителю
- `mail_outbox` — письма к отправке: сайт и заявка, о которой письмо (`lead_id`: удалили заявку — удалились и её письма), шаблон, данные (только до отправки; у писем со ссылкой-токеном — и до неудачи или срока ссылки), кому и ключ ящика получателя (для лимита подтверждений), статус, попытки, следующая попытка, аренда обработчика на одно письмо, срок ссылки, последняя ошибка, когда отправлено; чистятся через `MAIL_RETENTION_DAYS`
- `mail_settings` — настройки SMTP из админки: сервер, порт и шифрование (только 465 TLS или 587 STARTTLS — CHECK), логин, пароль только зашифрованным (формат записи — CHECK), отправитель, когда прошла проверка подключения, кто и когда сохранил. Строка с `site_id` NULL — на всю установку, она одна. Строки сайтов появятся с формами
- `user_invitations` — приглашения участников: хеш токена, почта, сайт, роль, кто пригласил и кто принял, срок (7 дней), когда принято или отозвано; у адреса на сайте одно открытое приглашение. Закрытые удаляются через `MAIL_RETENTION_DAYS` после закрытия (в них адрес человека)
- `api_tokens` — SHA-256 токена, сайт, кто выпустил, когда пользовались, отзыв
- `redirects`

## Порядок работы

Делаем не модуль за модулем, а вертикальными срезами: сначала один лендинг проходит весь путь от JSON до HTML, потом этот путь обрастает возможностями. Начинаем с того, где больше всего неизвестного (схемы, рендер, предпросмотр). Понятные вещи вроде авторизации делаем, когда они понадобятся.

Сроки грубые: работа вечерами и с нейронками.

### Этап 0. Фундамент — готово ✓
- Монорепозиторий (pnpm workspaces + catalog), строгий TypeScript, Biome, Vitest.
- Node 24 LTS закреплена в проекте (`devEngines.runtime`): pnpm скачивает её сам, глобальная версия не важна.
- База локально — PGlite (Docker на машине нет): подключение и проверка через `/api/health/ready`. Миграции появятся вместе с первыми таблицами на этапе 1.
- Типизированный клиент API в админке (Hono RPC) — с первого дня.
- Соглашения записаны в [CONVENTIONS.md](CONVENTIONS.md).
- **Готово, когда:** `pnpm -r --parallel dev` поднимает api, admin и renderer, а `pnpm -r typecheck`, `pnpm -r test` и `pnpm lint` проходят.

### Этап 1. Скелет: один лендинг от JSON до HTML — готово ✓
- ✓ Схемы блоков, страницы и темы (`packages/schema`).
- ✓ Токены v0 (модуль 7): палитра, шрифты, отступы → CSS-переменные.
- ✓ 3 блока (модуль 5): первый экран, преимущества, призыв к действию.
- ✓ Рендерер собирает лендинг в статический HTML без JavaScript (модуль 2).
- ✓ Страница лежит в базе как JSON, API читает и сохраняет её с проверкой по схемам, рендерер берёт сайт из API (модуль 2).
- ✓ Цикл «правка через API → публикация → пересборка» проверен вживую.
- Lighthouse пока не замерян. Производительность и доступность должны быть около 100; в SEO не хватает meta description — её даст модуль 4.

### Этап 2. Админка (~4–6 недель) — готово ✓
Порядок поменяли: первым сделали редактор, потому что в нём больше всего неизвестного. Вход нужен до выкладки в интернет и идёт следующим.
- ✓ Редактор страницы v1 (модуль 5): блоки можно добавлять, переставлять и удалять; формы полей строятся по JSON Schema блоков; живой предпросмотр в iframe с переключением телефон / планшет / десктоп; проверка при вводе той же схемой, что в API.
- ✓ Черновик и публикация из редактора (модуль 2).
- ✓ Сквозные тесты на Playwright (`pnpm e2e`): редактор, предпросмотр, сохранение, публикация и опубликованный сайт. Заголовок страницы теперь тоже публикуется, а не меняет сайт сразу при сохранении.
- ✓ Навигация по сайтам и страницам: список сайтов → страницы сайта → редактор, у каждого экрана свой адрес. Создание сайта и страницы, удаление страницы (кроме главной), в списке видно, что опубликовано и где есть неопубликованные правки. Уйти из редактора с несохранёнными правками можно только после вопроса.
- ✓ Вход, сессии, роли (модуль 1) и токены для MCP: вход по почте и паролю (Better Auth, httpOnly-cookie, лимит попыток), регистрации нет, владельца создаёт `pnpm user:create`. Роли: владелец, редактор и клиент сайта; чужой сайт участнику не виден. API закрыт по умолчанию, открыт только снимок опубликованного. MCP ходит по токену `pnpm token:create`. Сброс пароля по почте — когда появится отправка писем.
- ✓ История версий (модуль 2): каждая публикация пишет снимок страницы (заголовок, блоки, кто и когда) в той же транзакции. В редакторе — панель «История»: версию можно посмотреть в предпросмотре и вернуть в черновик, сайт при этом не меняется до публикации. Возвращать может и клиент.
- ✓ Медиа (модуль 3): медиатека сайта, загрузка JPEG/PNG/WebP/AVIF (тип по содержимому, SVG не принимаем), поворот по EXIF и удаление метаданных, варианты 480–1920 в AVIF, WebP и исходном формате (sharp). Хранилище за интерфейсом (пока папка на диске). Поле «картинка» с обязательным alt, первый экран в варианте split, на сайте `<picture>` с `srcset`, `sizes` и размерами. Используемую картинку удалить нельзя. Админка сверяет размер файла с лимитом до отправки, обработка идёт в очереди (две картинки одновременно).
- ✓ Перетаскивание (модуль 5): блоки в списке редактора и пункты списков в формах блоков (например, «Пункты» у «Преимуществ») переставляются мышью или пальцем за ручку и с клавиатуры (пробел, стрелки, пробел; Escape отменяет). Диктор слышит по-русски, какой блок поднят и на какой он позиции. Стрелки ↑↓ остались.
- ✓ Хвосты этапа 2 ([шаг 2.6](docs/steps/2.6-cleanup.md)): разобраны все 49 замечаний проверяющих. Главное — API больше не работает с учебным секретом вне явного учебного режима: его включает только флаг `--dev` у `pnpm dev` и e2e, и только на localhost. Ни забытый на сервере `NODE_ENV=production`, ни запуск вовсе без переменных его не открывают, демо-сайт и владелец для разработки — тоже только в нём. Ещё: русские сообщения схем в API, командах и MCP; высокие картинки; страницы со старыми адресами; рендерер в `pnpm dev` без `CMS_SITE_ID`; фокус, заголовки вкладок и подписи ручек в админке.

Всё это покрыто тестами API на PGlite в памяти и сквозными тестами в браузере (`pnpm e2e`, 48 тестов, проходят и в случайном порядке).

- Комментарии, форумы, поиск по сайту.

## Сквозные правила: «нормально, а не криво-косо»
- Всё, что приходит снаружи (через API, формы, MCP), проверяется схемой.
- Тесты на схемы блоков и e2e на сценарий «собрал → опубликовал» (Playwright).
- Lighthouse 95+ — обязательная проверка перед публикацией, а не пожелание.
- Доступность: семантичная вёрстка, alt, контраст, управление с клавиатуры.
- Секреты хранятся в переменных окружения, а не в git. На вход и формы стоят лимиты, ошибки логируются.

## Стек (предложение)

| Слой | Выбор | Почему |
|---|---|---|
| Рантайм | Node.js 24 LTS, закреплена в проекте | поддержка до апреля 2028; 25-я уже снята с поддержки |
| Пакеты | pnpm 12 (workspaces + catalog) | строгий, быстрый, одна версия зависимостей на весь репозиторий |
| Язык | TypeScript 6 везде | одна схема на API, админку, блоки и MCP; 7-ю пока не поддерживает astro check |
| API | Hono | лёгкий, типизированный клиент для админки из коробки |
| База | PostgreSQL + Drizzle, локально PGlite | JSONB для страниц, нормальные миграции; для разработки не нужен Docker |
| Установка | Docker Compose + Caddy на VPS клиента | одна команда на чистом сервере, SSL сам, обновление сменой образа |
| Схемы | Zod | валидация, TS-типы и JSON Schema из одного места |
| Админка | React + Vite | блоки и так на React, предпросмотр работает на тех же компонентах |
| Сборка сайтов | Astro | статика из React-компонентов, ноль JS по умолчанию |
| Картинки | sharp | ресайз, WebP/AVIF |
| Авторизация | Better Auth | чтобы не писать криптографию самому |
| Перетаскивание | dnd-kit (`core` + `sortable`) | клавиатура и объявления для экранного диктора из коробки, тексты свои |
| MCP | официальный TypeScript SDK | эталонная реализация протокола |
| Линт и формат | Biome | один инструмент вместо ESLint + Prettier |
| Тесты | Vitest, Playwright | юнит-тесты и e2e |

## Структура репозитория

```
averra-cms/
├─ packages/
│  ├─ schema/     # Zod-схемы: блоки, страница, настройки
│  ├─ blocks/     # React-компоненты блоков
│  └─ tokens/     # дизайн-токены → CSS-переменные
├─ apps/
│  ├─ api/        # Hono + Drizzle + Postgres
│  ├─ admin/      # React SPA
│  ├─ renderer/   # Astro: JSON сайта → статический HTML
│  └─ mcp/        # MCP-сервер поверх api
├─ e2e/           # сквозные тесты на Playwright
└─ PLAN.md
```

## Принятые решения
1. **Стек — TypeScript + Hono + проверенные библиотеки.** Не PHP: Node в стеке нужна в любом случае (блоки на React, сборка на Astro), а схемы пришлось бы дублировать на двух языках. Не NestJS: его валидация построена на DTO-классах, это второй источник схем рядом с Zod, плюс много обвязки для проекта одного человека. И не «голый»: всё сложное берём из библиотек, сами пишем только то, что и есть CMS.
2. **`site_id` с первого дня:** поддержка нескольких сайтов заложена в модель данных сразу.
3. **Конструктор — секции, а не свободный холст.**
4. **Посетители сайта — потом**, когда появится проект с личным кабинетом.
5. **Node 24 LTS закреплена в проекте**, pnpm скачивает её сам. 25-ю не берём: она снята с поддержки в июне 2026, и vitest 5 её не поддерживает.
6. **Своя установка у каждого клиента**, как WordPress, а не одна установка студии на всех. Данные клиента на его сервере, клиент не заложник студии, а сбой одной установки не задевает остальных. Цена — обслуживать много установок, поэтому установка, обновления с откатом, бэкапы и обзор состояния — часть продукта, а не ручная работа (модуль 9). Внутри своей установки настройки сайта — дело клиента: например, адреса уведомлений о заявках он меняет сам, а владельцам и прежним адресатам уходит письмо о смене.
