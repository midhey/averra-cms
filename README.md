# Averra CMS

Внутренняя система студии Averra для быстрых и аккуратных лендингов. Что и зачем — в [PLAN.md](PLAN.md), правила кода — в [CONVENTIONS.md](CONVENTIONS.md).

## Запуск

Нужен pnpm 12. Ставить Node под проект не нужно: версия закреплена в `package.json` (`devEngines.runtime`, Node 24 LTS). pnpm скачает её при установке и запускает все скрипты на ней, какая бы Node ни стояла глобально и что бы ни было в PATH. Чтобы запустить сам pnpm, подойдёт любая Node ≥ 18 с corepack: `corepack pnpm …`.

```bash
pnpm install
pnpm dev
```

| Что | Адрес |
|---|---|
| API | http://localhost:4000/api/health |
| Админка | http://localhost:5173 |
| Рендерер | http://localhost:4321 |

### Первый запуск: владелец и сайт для рендерера

Админка и API закрыты входом, регистрации нет. Перед первым входом нужен владелец — выбери один способ:

- **Для разработки:** скопируй `apps/api/.env.example` в `apps/api/.env`. Если в базе ещё нет пользователей, API при старте создаст владельца из `DEV_OWNER_EMAIL` / `DEV_OWNER_PASSWORD` (в примере — учебные значения, только для разработки: работает лишь в учебном режиме `pnpm dev` при `NODE_ENV=development` и адресах админки и API на localhost). Там же, в пустой базе, API заводит демо-сайт.
- **Командой** (так же и в проде): `pnpm user:create --email anna@example.ru --name "Анна"`. Пароль команда спросит скрыто, дважды, или возьмёт из переменной `CMS_USER_PASSWORD`. Он не печатается и не попадает в аргументы и логи.

Рендерер собирает один сайт — тот, что в `CMS_SITE_ID` (`apps/renderer/.env`, шаблон — `.env.example`; id виден в адресе админки `/sites/<id>`). В `pnpm dev` без него рендерер показывает демо-сайт свежей базы (`d0000000-0000-4000-8000-000000000001`) и пишет об этом в лог, так что сразу после клонирования всё работает. Если твоя база старше и у демо-сайта другой id или нужен другой сайт — впиши его. `pnpm build` без `CMS_SITE_ID` не соберётся: сборка должна явно знать, какой сайт собирает. Первый сайт из API рендерер не берёт: список сайтов виден только после входа, а снимок сайта открыт и берётся по id.

### Учебный секрет и прод

Без своего `AUTH_SECRET` API подписывает cookie учебным секретом, а он лежит в репозитории. Поэтому так API запускается только в учебном режиме, и его надо попросить явно: флаг `--dev` ставит скрипт `pnpm dev` (и e2e), а `pnpm --filter @averra/api start` его не ставит. Вдобавок `NODE_ENV` не `production`, а `ADMIN_URL` и `API_URL` (если заданы) указывают на этот компьютер (`localhost`, `*.localhost`, `127.x.x.x`, `[::1]`). Только в учебном режиме API заводит в пустой базе демо-сайт и владельца из `DEV_OWNER_*`. Без флага, даже вовсе без переменных, API без `AUTH_SECRET` не стартует и объясняет почему, а учебный секрет, вписанный руками, не примет вне учебного режима — как и его варианты (с пробелами по краям, в кавычках, в другом регистре или только его часть). Флаг пишется ровно `--dev`: опечатка или лишний аргумент — ошибка с подсказкой, и API не стартует. Команды терминала (`pnpm user:create` и другие) сеть не слушают и на свежем клоне работают и без `AUTH_SECRET`.

Добавочная защита: на учебном секрете API отвечает только на запросы к `localhost` с этого компьютера (403 остальным), смотрит на адрес соединения и на имя в `Host`. Прямой запрос из сети и прокси, который передаёт настоящий `Host` (Caddy по умолчанию), получат 403. Но у проверки есть предел: nginx по умолчанию шлёт API свой `Host` апстрима (`127.0.0.1:4000`), а прокси «для всех имён» передаёт `Host` клиента как есть, и тот может написать `localhost`. Через такие прокси запрос пройдёт, поэтому `pnpm dev` на сервере не запускай — для сервера есть `start` со своими переменными. На сервере задай `NODE_ENV=production`, `AUTH_SECRET` (`openssl rand -base64 32`), `ADMIN_URL` и `API_URL`: в проде все три обязательны, а cookie ставятся только по HTTPS (`Secure`; так же, если `API_URL` начинается с `https://`). Чтобы задавать SMTP в админке, нужен ещё `MAIL_ENCRYPTION_KEY` (`openssl rand -base64 32`, см. «SMTP в админке»). Без него API стартует, но настройки SMTP на странице «Почта» будут только для чтения.

| `pnpm check` | линтер, типы и тесты — всё, что нужно перед коммитом |
| `pnpm e2e` | сквозные тесты в браузере (Playwright), см. ниже |
| `pnpm build` | собирает админку и рендерер |
| `pnpm typecheck` | проверяет типы во всех пакетах |
| `pnpm test` | запускает тесты во всех пакетах |
| `pnpm lint` | проверяет линтером и форматтером |
| `pnpm format` | то же, но сразу исправляет |
| `pnpm db:generate` | создаёт миграцию по изменениям в `apps/api/src/db/schema.ts` |
| `pnpm user:create --email … --name … [--role owner\|member]` | создаёт пользователя админки (по умолчанию владельца); пароль — скрытым вводом или из `CMS_USER_PASSWORD` |
| `pnpm user:password --email …` | задаёт пользователю новый пароль (скрытым вводом или из `CMS_USER_PASSWORD`), завершает все его входы и сжигает ссылки сброса. Путь восстановления доступа без почты |
| `pnpm member:add --email … --site <id> --role editor\|client` | даёт участнику доступ к сайту (повторный вызов меняет роль) |
| `pnpm member:invite --email … --site <id> --role editor\|client [--by <почта владельца>]` | приглашает участника письмом, как «Пригласить» в админке: письмо ложится в очередь и уходит, когда запустится API. Ссылку не печатает, но говорит, на какой адрес админки (`ADMIN_URL`) она ведёт; ссылку на localhost при почте через SMTP не ставит вовсе. SMTP из админки, пароль которого API не расшифрует (нет `MAIL_ENCRYPTION_KEY` или он не тот), почтой не считает и отказывает с той же причиной, что показывает API. Без `--by` приглашает единственный владелец, при нескольких `--by` обязателен |
| `pnpm token:create --site <id> --name … [--by <почта>]` | выпускает токен API для MCP и показывает его один раз |
| `pnpm token:list` | токены: сайт, кто выпустил, когда пользовались, отозван ли (без самих токенов) |
| `pnpm token:revoke --id <id>` | отзывает токен |
| `pnpm mail:test --to <адрес>` | шлёт проверочное письмо напрямую и по шагам показывает, где сломалось (см. «Почта»). Проверяет почту из окружения; SMTP, заданный в админке, проверяет кнопка «Проверить подключение» |

Команды — это скрипты корневого `package.json`, он работает вместо Makefile. pnpm заодно стоит в проекте как dev-зависимость, чтобы скрипты могли вызывать его сами, даже если глобально pnpm не установлен.

Команды пользователей и токенов открывают базу напрямую. Встроенная база (PGlite) не выдерживает два процесса сразу, поэтому, пока запущен `pnpm dev`, они откажутся работать и попросят его остановить: API и команды берут файл-замок рядом с базой (`apps/api/.data/pglite.lock`). Замок от упавшего процесса снимается сам. На Windows pid быстро переиспользуются, и замок упавшего API может достаться постороннему живому процессу: тогда сообщение покажет путь к файлу замка — если `pnpm dev` не запущен, удали этот файл.

## Вход и права

Вход — по почте и паролю (Better Auth), сессия живёт в httpOnly-cookie (`SameSite=Lax`, в проде ещё и `Secure`). Попыток входа — не больше трёх за 10 секунд с одного IP, дальше 429 «Слишком много попыток».

| Роль | Что может |
|---|---|
| владелец (`owner`) | всё: все сайты, создание сайтов, приглашение участников |
| редактор (`editor`) на сайте | читать, править, публиковать, создавать и удалять страницы своих сайтов; загружать и удалять картинки |
| клиент (`client`) на сайте | читать и править черновики существующих страниц своего сайта, загружать картинки; публиковать, создавать и удалять — нет |
| токен API | как редактор, но на одном сайте |

Глобальная роль пользователя — `owner` или `member`; участника на сайт приглашает владелец письмом (экран сайта или `pnpm member:invite`), а `pnpm member:add` даёт доступ уже заведённому пользователю. Чужой сайт для участника выглядит как несуществующий (404), а не «запрещено» (403): так не видно, что он вообще есть.

### Сброс пароля

«Забыли пароль?» на экране входа → почта → письмо «Сброс пароля» со ссылкой `ADMIN_URL/reset-password#token=…` → новый пароль дважды → вход. Сброс сделан на Better Auth (`sendResetPassword`), письмо идёт через очередь почты. Правила:

- ссылка одноразовая и живёт час; новый запрос сжигает прежнюю ссылку; после смены пароля все входы пользователя завершаются;
- в базе (`verifications`) лежит только SHA-256 токена (`reset-password#<хеш>`), а сам токен — только в письме. Разделитель `#`, а не двоеточие, выбран не случайно: Better Auth, не найдя запись по хешу, ищет её ещё и по строке `reset-password:<присланный токен>` как есть, и с двоеточием хеш из базы сам работал бы как токен. Вдобавок API пускает к Better Auth только токен его формата (24 буквы и цифры). Токен во фрагменте ссылки (`#token=`): браузер не шлёт фрагмент на сервер, поэтому токен не попадает в логи и `Referer`, а экран сразу убирает его из адресной строки;
- ответ на запрос один и тот же, есть такой адрес или нет, и не раньше чем через 300 мс: ни по тексту, ни по времени не узнать, есть ли пользователь. Письмо уходит только существующему;
- лимиты: 5 запросов за 15 минут с одного IP и 3 запроса за 15 минут на один адрес (считаются любые адреса, поэтому и 429 ничего не выдаёт). Оба счётчика свои, в обёртке; правило Better Auth на этот путь только запасное (10 за 15 минут), а варианты пути (`/request-password-reset/`, другой регистр и т. п.) отвечают 404 и лимит не тратят; попыток задать пароль по ссылке — 10 в минуту с IP. IP проверяется первым: запрос, отбитый по IP, в счётчик адресов не попадает — и тогда, когда его отбил запасной лимит Better Auth (попытка адреса возвращается). Счётчики живут в памяти процесса API и помнят не больше 10 000 ключей (при нехватке места вытесняется самый давний);
- почта не настроена — экран «Забыли пароль?» сразу говорит, что сброс недоступен и как вернуть доступ: попросить владельца или на сервере остановить API и выполнить `pnpm user:password --email …`.

### Приглашения

Владелец на экране сайта (раздел «Участники») вводит почту и роль — редактор или клиент — и жмёт «Пригласить» (или выполняет `pnpm member:invite`). Человек получает письмо со ссылкой `ADMIN_URL/invite#token=…` и по ней сам задаёт имя и пароль, а если вход у этого адреса уже есть — входит своим паролем и принимает приглашение. После этого он видит только этот сайт со своей ролью. Правила:

- ссылка одноразовая и действует 7 дней; в базе (`user_invitations`) только SHA-256 токена; повторное приглашение того же адреса на тот же сайт отзывает прежнее;
- лимиты: одному адресу на один сайт — не больше 3 приглашений в час, от одного владельца — не больше 50 в час (429 `rate_limited`);
- закрытые приглашения (принятые, отозванные, истёкшие) удаляются через `MAIL_RETENTION_DAYS` дней после закрытия, вместе с чисткой очереди писем: в них адрес человека;
- принятое, отозванное и истёкшее приглашение отвечает понятной ошибкой (410), неизвестная ссылка — 404;
- владельца админки и того, кто уже участник сайта, пригласить нельзя (409). Сменить роль — `pnpm member:add`. Если роль выдали командой уже после приглашения, принятие её не меняет;
- приглашают и отзывают только владельцы: редактору и клиенту — 403, чужой сайт — 404. Без почты приглашение не отправить (503), и экран сайта говорит об этом заранее.

Переменные API для медиатеки — `MEDIA_DIR` и `MEDIA_MAX_BYTES` (см. «Картинки»). Переменные API для входа (`apps/api/.env`, все описаны в `.env.example`): `NODE_ENV` (на сервере — `production`), `AUTH_SECRET` (подпись cookie, от 32 символов; без него — только учебный режим, см. «Учебный секрет и прод»), `ADMIN_URL` (адрес админки: только с него принимаются запросы с cookie, и на него ведут ссылки в письмах; в проде обязателен), `API_URL` (адрес API снаружи; в проде обязателен), `TRUST_PROXY=true` — если перед API стоит прокси, который сам ставит `X-Forwarded-For`. По этому заголовку считаются лимиты попыток входа и запросов сброса пароля; без прокси API перезаписывает его адресом соединения, чтобы клиент не мог его подделать.

## API

| Запрос | Что делает |
|---|---|
| `POST /api/auth/sign-in/email` | вход: `{ "email", "password" }`, ставит cookie сессии. Остальные эндпоинты Better Auth — тоже под `/api/auth/*` (`sign-out`, `get-session`…). Проверка пароля Better Auth `POST /api/auth/verify-password` закрыта (404): через неё уведённая сессия подбирала бы пароль мимо лимита |
| `POST /api/auth/change-password` | сменить свой пароль: `{ "currentPassword", "newPassword" }` → `200 { status: "changed", message }` и новая cookie сессии; остальные входы пользователя завершаются. Неверный текущий пароль — 403 `invalid_password` у поля `currentPassword`. Неудач — не больше 5 за 15 минут на пользователя, счётчик общий с паролем владельца у настроек SMTP, дальше 429. Без входа — 401, не из админки — 403 |
| `GET /api/password-reset` | работает ли сброс пароля по почте: `{ available }`. **Открыт без входа**: его спрашивает экран «Забыли пароль?» |
| `POST /api/auth/request-password-reset` | «Забыли пароль?»: `{ "email" }`. Ответ всегда `200 { status: "sent", message }`, есть адрес или нет; письмо — только существующему. Почта выключена — 503 `mail_disabled`, лимит — 429 `rate_limited` |
| `POST /api/auth/reset-password` | новый пароль по ссылке: `{ "token", "newPassword" }`. Ссылка использована, устарела, заменена новой или токен не того формата (не 24 буквы и цифры) — 400 `invalid_token`. Все сессии пользователя завершаются. `GET /api/auth/reset-password/:token` Better Auth закрыт (404): токен в пути попал бы в лог |
| `GET /api/me` | кто вошёл: `{ kind: "user", user: { id, name, email, role } }` (для токена — `{ kind: "token", token: { id, siteId } }`) |
| `GET /api/sites` | сайты, доступные вошедшему (владельцу — все, токену — его сайт) |
| `POST /api/sites` | создать сайт (только владелец): `{ "name": "…" }`. Тема — по умолчанию, главная страница создаётся сразу (черновик) |
| `GET /api/sites/:siteId` | сайт: название, тема и роль вошедшего на нём (`access`) |
| `GET /api/sites/:siteId/snapshot` | тема, опубликованные страницы и справочник `media` с вариантами их картинок — всё, что нужно рендереру. **Открыт без входа** |
| `GET /api/sites/:siteId/pages` | страницы сайта: заголовок, адрес, когда опубликована, есть ли неопубликованные изменения |
| `POST /api/sites/:siteId/pages` | создать страницу: `{ "slug": "o-nas", "title": "…", "template": "hero" }`, шаблон `hero` (первый экран из каталога) или `empty` (по умолчанию). Занятый адрес — 409 |
| `GET /api/sites/:siteId/pages/:slug` | страница с черновиком и опубликованной версией. Страницы со старыми адресами (до шага 2.1 пускались и `a-`, `--a`) открываются, сохраняются, публикуются и удаляются как обычные, но новую страницу с таким адресом не создать |
| `PUT /api/sites/:siteId/pages/:slug` | сохранить черновик: `{ "title": "…", "content": { "blocks": […] } }`. Если страницы нет, создаёт её (клиенту — 404). Картинка не из медиатеки этого сайта — 409 с путём до поля |
| `POST /api/sites/:siteId/pages/:slug/publish` | опубликовать черновик вместе с заголовком. Каждая публикация пишет версию в историю |
| `DELETE /api/sites/:siteId/pages/:slug` | удалить страницу вместе с её историей. Главную (`index`) удалить нельзя — 409 |
| `GET /api/sites/:siteId/pages/:slug/revisions` | история публикаций, новые сверху (последние 100): `id`, `version` (1, 2, 3…), `title`, `publishedAt`, `author` (`{ kind: "user" \| "token", name }` или `null`, если автор неизвестен) |
| `GET /api/sites/:siteId/pages/:slug/revisions/:revisionId` | версия целиком: то же плюс `content` с блоками |
| `POST /api/sites/:siteId/pages/:slug/revisions/:revisionId/restore` | вернуть версию в черновик (заголовок и блоки). Опубликованная версия и история не меняются. Отвечает страницей, как `GET …/pages/:slug`. Версия, которую не пропускают нынешние схемы блоков или в которой есть удалённая из медиатеки картинка, — 409 |
| `GET /api/sites/:siteId/media` | медиатека сайта: `{ items, maxBytes }`. `items` — картинки, новые сверху: `id`, `originalName`, `mimeType`, `width`, `height`, `size` (байт), `createdAt`, `author` и `variants` (`format`, `width`, `height`, `size`, `url`). `maxBytes` — предельный размер файла (`MEDIA_MAX_BYTES`): админка проверяет файл до отправки |
| `POST /api/sites/:siteId/media` | загрузить картинку: multipart, поле `file`. JPEG, PNG, WebP или AVIF (тип — по содержимому файла, а не по расширению), не больше `MEDIA_MAX_BYTES` и 50 Мп. Отвечает 201 с картинкой. SVG, GIF и прочее — 415, слишком большой файл — 413. Тело больше лимита отклоняется, не дочитанным, и соединение обрывается, поэтому клиенту лучше сверить размер с `maxBytes` заранее. Одновременно обрабатываются две картинки, остальные ждут очереди |
| `DELETE /api/sites/:siteId/media/:mediaId` | удалить картинку вместе с файлами. Если она стоит в черновике или опубликованной версии какой-нибудь страницы — 409 со списком страниц |
| `GET /api/media/:mediaId/:file` | файл варианта (`480.avif`, `960.webp`…). **Открыт без входа**: на него ссылается сайт. Кешируется навсегда (`immutable`), с `X-Content-Type-Options: nosniff` |
| `GET /api/sites/:siteId/invitations` | приглашения сайта (только владелец), новые сверху, последние 100: `id`, `email`, `role`, `status` (`pending`, `accepted`, `revoked`, `expired`), `invitedBy` (имя), `createdAt`, `expiresAt`, `acceptedAt`, `revokedAt`. Токена нет |
| `POST /api/sites/:siteId/invitations` | пригласить: `{ "email", "role": "editor" \| "client" }` → 201 с приглашением, письмо — в очередь. Владелец или уже участник — 409 у поля `email`, почта выключена — 503, лимит — 429 `rate_limited` |
| `DELETE /api/sites/:siteId/invitations/:invitationId` | отозвать: 204 (и повторно), принятое — 409, чужое — 404 |
| `POST /api/invitations/lookup` | что за приглашение по токену из ссылки: `email`, `role`, `siteName`, `inviterName`, `expiresAt`, `userExists`. **Открыт без входа**. Ошибки ссылки: 404 `invitation_not_found`, 410 `invitation_used` / `invitation_revoked` / `invitation_expired` |
| `POST /api/invitations/register` | принять новым пользователем: `{ "token", "name", "password" }` → 201 `{ siteId, email }`. **Открыт без входа**. У адреса уже есть вход — 409 `user_exists` |
| `POST /api/invitations/accept` | принять тем, под кем вошли: `{ "token" }` → `{ siteId }`. Уже участник сайта — роль остаётся прежней. Другой адрес — 403 с подсказкой, токен API — 403 |
| `GET /api/mail` | почта (только владелец): `status` — `{ enabled: true, provider }` (провайдер без пароля: `kind`: `smtp`, `file` или `memory`, сервер, режим, вход, отправитель) или `{ enabled: false, reason }`. Состояние нынешнее: после смены SMTP в админке оно меняется без перезапуска. `settings` — `maxAttempts`, `retentionDays`; `linkWarning` — предупреждение, если письма уходят по SMTP, а ссылки в них ведут на localhost (`ADMIN_URL`), иначе `null`; `templates` — `id`, `title`, `description` |
| `GET /api/mail/smtp` | настройки SMTP без пароля: `source` (`env` — окружение, `database` — админка, `none`), `editable`, `lock` (почему нельзя менять: `{ reason: "env" \| "no_key", message }` или `null`), `key` (`env`, `dev` или `null`), `settings` — `host`, `port`, `security`, `user`, `fromAddress`, `fromName`, `password` (`set` или `unreadable`), `passwordProblem` (почему не читается: `no_key`, `wrong_key`, `corrupted`, `format`; читается — `null`), `verifiedAt`, `updatedAt`, `updatedBy` — или `null` |
| `POST /api/mail/smtp/check` | проверить подключение по ещё не сохранённым настройкам: `{ host, port, security, user, password?, fromAddress, fromName, to }`. Пустой `password` — сохранённый, но только с сохранёнными настройками целиком и только на почту самого владельца: иначе 400 у поля `password` или `to`. Ответ `{ ok, steps: [{ step, ok, message }], checkToken }`, токен — только при успехе. Порт не 465/587, лишнее поле, перевод строки — 400; правка недоступна — 409 `mail_settings_locked`; больше 10 проверок за 15 минут — 429 |
| `PUT /api/mail/smtp` | сохранить: те же поля, плюс `currentPassword` и `checkToken` успешной проверки или `skipCheck: true`. Пустой `password` — сохранённый, только для того же сервера. Ответ `{ smtp, changed, notified }`. Без пароля владельца или без проверки и «без проверки» — 400; неверный пароль — 403 `invalid_password`, после пятой неудачи за 15 минут — 429 (счётчик общий со сменой пароля); проверка была для других настроек или устарела — 409 `check_stale`; SMTP в окружении или нет ключа — 409 `mail_settings_locked` |
| `DELETE /api/mail/smtp` | удалить настройки из админки: `{ currentPassword }` → `{ smtp, notified }`; настроек нет — 404 |
| `GET /api/mail/outbox` | последние 100 писем очереди, новые сверху: `recipient`, `template`, `status` (`pending`, `sending`, `sent` или `failed`), `attempts`, `nextAttemptAt`, `lastError`, `lastAttemptAt` (когда письмо последний раз пробовали отправить; у взятых в пачку и отпущенных без попытки его нет), `sentAt`, `expiresAt` (срок одноразовой ссылки в письме), `createdAt` и `canRetry` — можно ли повторить письмо. Данные письма не отдаются: в них персональные данные |
| `POST /api/mail/outbox/:id/retry` | вернуть ждущее или неотправленное письмо в очередь сейчас, попытки с нуля. Отправленное или отправляющееся — 409. Письмо с одноразовой ссылкой (сброс пароля, приглашение), которое не ушло или у которого истёк срок ссылки, — тоже 409: ссылка из него стёрта, нужна новая |
| `GET /api/mail/templates/:template/preview` | шаблон письма на примерных данных: `subject`, `html`, `text` |

Без входа открыты только `/api/health`, `/api/health/ready`, `GET /api/sites/:siteId/snapshot`, `GET /api/media/:mediaId/:file`, `GET /api/password-reset`, `POST /api/invitations/lookup`, `POST /api/invitations/register` и `/api/auth/*`; остальное отвечает 401. Вход — cookie сессии или заголовок `Authorization: Bearer <токен>`. Изменяющие запросы с cookie принимаются только с `Origin` админки (`ADMIN_URL`). Действие, которое роли не разрешено, — 403, чужой или несуществующий сайт — 404.

При первом запуске API кладёт в пустую базу демо-сайт. Главная страница сайта имеет slug `index`. Адрес страницы — латиница в нижнем регистре и цифры, дефис только между ними (`o-nas`, `price-2026`). Ошибки приходят в одном формате и по-русски — и у проверки схемами (`setupZodMessages` из `@averra/schema` включён в API, админке, командах терминала и MCP), и у неизвестных кодов Better Auth (общее сообщение по статусу, код как есть): `{ "error": { "code", "message", "issues"? } }` — и у наших маршрутов, и у эндпоинтов Better Auth (`unauthorized`, `forbidden`, `invalid_email_or_password`, `rate_limited`…); у 400 и у 409 «адрес занят» в `issues` есть путь до поля.

Заголовок страницы, как и блоки, попадает на сайт только после публикации: сохранённый черновик сайт не меняет.

История версий: каждая публикация в той же транзакции сохраняет снимок — заголовок, блоки, кто (пользователь или токен) и когда. Верхняя версия в истории — то, что сейчас на сайте. Смотреть историю может любой, кто видит сайт, а возвращать версию в черновик — любой, кто правит черновики, включая клиента: возврат сайт не меняет. Страницы, опубликованные до появления истории, получили версию 1 без автора.

## Картинки

Картинки живут в медиатеке сайта. При загрузке API определяет тип по содержимому (sharp), поворачивает снимок по EXIF и удаляет все метаданные: EXIF с местом съёмки, XMP, IPTC, ICC-профиль (цвета переводятся в sRGB). Потом режет его на ширины 480, 960, 1440 и 1920 (не шире исходника; если исходник уже 1920, добавляется и его собственная ширина; очень высокий вариант — длинная инфографика, скриншот страницы — ужимается ещё и до 16383 px по высоте: больше не умеют WebP и AVIF) и каждую кодирует в AVIF, WebP и, для JPEG и PNG, в исходный формат как запасной. Рядом хранится чистый оригинал в полном размере, чтобы потом можно было нарезать новые варианты, но наружу он не отдаётся.

Файлы лежат в хранилище за интерфейсом (`apps/api/src/media/storage.ts`). Сейчас это папка `MEDIA_DIR`, по умолчанию `apps/api/.data/media`, потом будет S3. Путь к файлу сервер строит только из id сайта, id картинки и имени варианта, которое составил сам. Имя загруженного файла хранится только для показа в админке. Предельный размер файла задаёт `MEDIA_MAX_BYTES` (по умолчанию 10 МБ).

В блоке картинка — это поле `{ mediaId, alt }` (схема `Image` в `@averra/schema`), alt обязателен, до 200 символов. Пока картинка есть у первого экрана в варианте `split` (текст слева, картинка справа): в этом варианте она обязательна, в других её быть не должно (там её не видно, а удалить из медиатеки такую «используемую» картинку было бы нельзя). Id в адресах и в ссылках на картинки принимаются в любом регистре и приводятся к строчным. API не даст сохранить ссылку на картинку чужого сайта или несуществующую и не даст удалить картинку, которая стоит в черновике или на сайте. Рендерер выводит `<picture>` с источниками AVIF и WebP, `srcset`, `sizes` и размерами исходника, поэтому вёрстка не прыгает. Картинки грузятся лениво, кроме картинки первого блока страницы: у неё `loading="eager"` и `fetchpriority="high"`. Пока файлы картинок на опубликованном сайте берутся из API (`CMS_API_URL`), выкладку вместе со статикой даст модуль публикации.

Рендерер берёт данные из API, поэтому для `pnpm build` API должен быть запущен. При сборке страницы сайта статические, а в `pnpm dev` рендерер собирает страницу на каждый запрос: новая страница видна по своему адресу сразу после публикации, без перезапуска. Сайт выбирается переменной `CMS_SITE_ID` (`apps/renderer/.env`); без неё `pnpm dev` показывает демо-сайт, а сборка падает с подсказкой. Главная открывается только по корню, `/index` — 404, как на собранном сайте. В dev Astro пишет в лог «getStaticPaths() ignored in dynamic page…»: так и задумано, маршрут статический только при сборке. Адрес API задаёт `CMS_API_URL`, по умолчанию `http://localhost:4000`. Админка в dev-режиме ходит в API через прокси Vite по тому же `CMS_API_URL`, а её порт задаёт `ADMIN_PORT` (по умолчанию 5173).

## Почта

Письма системы (сброс пароля, приглашения, потом — уведомления о заявках) уходят не прямо из запроса, а через очередь `mail_outbox`: письмо пишется в базу в той же транзакции, что и действие, а обработчик в процессе API отправляет его с повторами. Упал SMTP — действие не откатывается, письмо уйдёт позже. Провайдер спрятан за интерфейсом `Mailer` (`apps/api/src/mail/mailer.ts`): SMTP в проде, файловый ящик в разработке, память в тестах.

SMTP задают одним из двух способов: на странице «Почта» в админке (см. «SMTP в админке» ниже) или переменными окружения. Приоритет такой: окружение (`SMTP_HOST` или явный `MAIL_TRANSPORT`) → настройки из админки → по умолчанию (файловый ящик в `pnpm dev`, иначе почта выключена). Если SMTP задан в окружении, он главнее: админка показывает его только для чтения, без пароля, с пометкой «задано на сервере».

### Настройка

Переменные API (`apps/api/.env`, все описаны в `.env.example`):

| Переменная | Что задаёт |
|---|---|
| `MAIL_TRANSPORT` | `smtp`, `file` или `off`. Не задано: есть `SMTP_HOST` — `smtp`; есть SMTP в админке — он; учебный режим (`pnpm dev`) — `file`; иначе почта выключена. `file` в проде не принимается. Заданный явно, он главнее админки |
| `SMTP_HOST`, `SMTP_PORT` | сервер SMTP провайдера, порт по умолчанию 465 |
| `SMTP_SECURITY` | `tls` (TLS сразу, порт 465) или `starttls` (обязательный STARTTLS, порт 587). Для 465, 587 и 25 берётся из порта, для другого порта — обязательно. Режима без шифрования нет |
| `SMTP_USER`, `SMTP_PASSWORD` | вход на SMTP. Пароль из окружения в базу, логи, ответы API и вывод команд не попадает, в текстах ошибок маскируется (`***`) |
| `MAIL_FROM`, `MAIL_FROM_NAME` | отправитель: адрес на своём домене (обязателен для SMTP) и имя, по умолчанию «Averra CMS». Адрес должен принадлежать ящику, под которым идёт вход (`SMTP_USER`): у Яндекс 360 — совпадать с логином или быть его алиасом, иначе сервер отвечает на `MAIL FROM` отказом «553 Sender address rejected: not owned by auth user» |
| `MAIL_DIR` | папка файлового ящика, по умолчанию `.data/mail` (в `apps/api`) |
| `MAIL_MAX_ATTEMPTS` | сколько раз пробовать отправить письмо, по умолчанию 8. Пауза растёт: 1, 3, 9, 27… минут, не больше 6 часов — около 12 часов на всё |
| `MAIL_RETENTION_DAYS` | через сколько дней удалять письма из очереди, по умолчанию 30: отправленные — от отправки, неотправленные — от последней попытки, так и не ушедшие (почта была выключена) — от постановки. В них персональные данные (152-ФЗ). Тот же срок — у закрытых приглашений (`user_invitations`) |
| `MAIL_ENCRYPTION_KEY` | ключ, которым шифруется пароль SMTP из админки: 32 случайных байта в base64. Без него SMTP в админке только для чтения. В `pnpm dev` без него берётся учебный ключ из репозитория. См. «SMTP в админке» |
| `DEV_SMTP_CONNECT_PORT` | только для разработки и e2e: SMTP из админки подключается к этому порту того же сервера вместо 465 и 587 (тестовый SMTP на свободном порту). Вне учебного режима — ошибка конфига |

Соединение с SMTP только шифрованное, а сертификат сервера проверяется всегда: настройки, которая это выключает, нет, и `NODE_TLS_REJECT_UNAUTHORIZED=0` в окружении на почту не действует. На 587 сервер без STARTTLS — ошибка, а не письмо открытым текстом. Адреса, тема и имя отправителя проверяются схемами: перевод строки в них — ошибка, а не новый заголовок письма.

Данные письма (кому что подставить в шаблон) лежат в очереди только до отправки: у отправленного письма их уже нет, остаются кому, когда и статус. Письма со ссылкой-токеном (сброс пароля, приглашение) теряют данные и после неудачи, а не ушедшие за срок ссылки не отправляются вовсе. Если SMTP не пускает (неверный пароль, TLS, сервер недоступен) или не принимает адрес отправителя, обработчик не пробует каждое письмо, а выжидает с растущей паузой до 30 минут; «Повторить» в админке и сохранение настроек SMTP будят его сразу. Отказ адресу отправителя — ошибка настроек, а не письма: попытки писем на нём не тратятся, письма со ссылками не стираются и уйдут, когда настройки поправят (причина видна в очереди у первого письма). Окончательно не отправляется только письмо, которому сервер отказал в адресе получателя или в самом письме (5xx на `RCPT TO` или `DATA`). При остановке API (Ctrl+C) дожидается письма, которое уже отправляет; второй Ctrl+C — выход сразу.

Без SMTP (ни в окружении, ни в админке) почта выключена явно: API работает, на экране «Почта» в админке видно, что не так, а действия, которым нужна почта (сброс пароля, приглашения), отвечают 503 `mail_disabled` с объяснением, и экраны админки говорят об этом заранее.

Ссылки в письмах ведут на `ADMIN_URL`. Если это адрес этого компьютера (localhost), а письма уходят по SMTP, адресат ссылку не откроет: почти наверняка на сервере забыли `ADMIN_URL`. API в этом случае предупреждает — строкой в логе при старте и на странице «Почта», — но письма шлёт: в `pnpm dev` SMTP бывает настроен нарочно, чтобы проверить настоящую доставку себе. `pnpm member:invite` строже и отказывает до записи в базу: её запускают ради одного письма, и ссылку на localhost по SMTP отправлять незачем.

**Файловый ящик** (`pnpm dev` без SMTP): письма не уходят наружу, а ложатся в `apps/api/.data/mail` парой файлов — `<время>-<id>.eml` (открывается почтовым клиентом) и `.json` с темой, адресами, текстом и HTML. e2e пишут свой ящик в `e2e/.data/mail`.

### SMTP в админке

Сменить пароль SMTP или провайдера можно без доступа к серверу. На странице «Почта», в разделе «Настройки SMTP», владелец задаёт сервер, порт и шифрование (только «465 — TLS сразу» или «587 — STARTTLS»), логин, пароль, адрес и имя отправителя. Настройки одни на всю установку и лежат в таблице `mail_settings`. Свой SMTP у сайта появится вместе с формами, модель к нему готова.

- **Пароль — только на запись.** В базе он лежит только зашифрованным: AES-256-GCM, свой случайный IV на каждое шифрование, тег проверяется, в записи — версия ключа. Наружу он не отдаётся никогда, даже зашифрованным: ни в ответах API, ни в логе, ни в ошибках, ни на странице. Админка показывает только «задан» или «не читается». Пустое поле при сохранении — оставить прежний пароль, но только для того же сервера. Сменили сервер — пароль нужно ввести заново: сохранённый пароль уходит только на сохранённый сервер.
- **Менять — только владелец и только со своим паролем.** Через SMTP уходят письма сброса пароля. С одной украденной сессией без этого можно было бы поставить свой сервер, сбросить пароль любому и забрать аккаунт. Пароль проверяет Better Auth. Неверный пароль — 403 `invalid_password`. Неудачных попыток — не больше 5 за 15 минут на пользователя, удачные не считаются. Счётчик общий у всех путей, которыми вошедший проверяет свой пароль: у настроек почты и у смены пароля (`/api/auth/change-password`). Проверка пароля самого Better Auth (`/api/auth/verify-password`) по HTTP закрыта. Поэтому с уведённой сессией пароль не подобрать быстрее, чем без неё: остаётся только вход, а у него свой лимит — 3 попытки за 10 секунд с одного IP.
- **«Проверить подключение»** проходит те же шаги, что `pnpm mail:test` (DNS, соединение, TLS, вход, отправка проверочного письма на указанный адрес), по ещё не сохранённым настройкам и показывает каждый шаг. Сертификат сервера проверяется всегда, выключить проверку нечем: схема настроек строгая, лишнее поле вроде `rejectUnauthorized` — 400. Порты только 465 и 587, проверок — не больше 10 за 15 минут на владельца: сервер не станет сканером портов. Пароля владельца проверка не просит, поэтому сохранённый пароль SMTP (пустое поле) в ней работает только с сохранёнными настройками целиком и только на почту самого владельца. Иначе уведённая сессия слала бы через ящик студии письма со своим именем отправителя кому угодно. Поменяли поле или адрес для проверки — введите пароль SMTP или сохраните без проверки.
- **Сохранить** можно после успешной проверки этих же настроек (её итог живёт 15 минут) или явной кнопкой «Сохранить без проверки». В логе API остаётся запись: кто, когда и какие поля поменял, без значений и без пароля. Каждому владельцу уходит письмо «Настройки почты изменены» — через очередь и уже по новым настройкам. Обработчик очереди подхватывает новые настройки без перезапуска API. Если сразу после сохранения API не смог их перечитать (сбой базы), запись в логе всё равно остаётся, а почта встаёт на паузу — не продолжает идти через прежние настройки — и перечитывается перед следующим проходом очереди.
- **«Удалить настройки»** (тоже с паролем владельца) возвращает почту к окружению или к варианту по умолчанию.

**Ключ `MAIL_ENCRYPTION_KEY`.** Это 32 случайных байта в base64, отдельные от `AUTH_SECRET`: утечка одного не даёт другого. Сгенерировать:

```bash
openssl rand -base64 32
# или, без openssl (Windows):
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Впишите ключ в окружение API (`apps/api/.env` или переменные сервера) и перезапустите API. Без ключа API работает, но SMTP в админке только для чтения, и страница объясняет, как получить ключ. В `pnpm dev` без ключа берётся учебный ключ из репозитория. Страница предупреждает, что пароль под ним защищён только для вида, поэтому настоящий пароль от почты в разработке не вводите. Учебный ключ и его варианты (пробелы, кавычки, регистр, base64url, его часть) вне учебного режима — ошибка конфига, как с учебным `AUTH_SECRET`.

Храните ключ отдельно от бэкапов базы: украденный бэкап без ключа не раскрывает пароль SMTP. **Если ключ потерян или сменился**, пароль SMTP в базе не расшифровать. API при этом работает, а почта выключается с причиной «введите пароль SMTP заново». Сброс пароля и приглашения честно говорят, что почта не работает. Достаточно ввести пароль SMTP на странице «Почта» и сохранить, и он зашифруется новым ключом. Других данных ключ не шифрует, так что больше ничего не теряется.

### Проверка: `pnpm mail:test`

```bash
pnpm mail:test --to anna@example.ru
```

Отправляет письмо «Проверка почты» напрямую, мимо очереди и базы, поэтому работает и при запущенном `pnpm dev`. Команда проверяет почту из окружения. SMTP, заданный в админке, она не видит (базу не открывает) и подсказывает проверить его кнопкой «Проверить подключение» на странице «Почта»: шаги там те же. Для SMTP команда идёт по шагам и печатает каждый: DNS (имя сервера находится), соединение (порт открыт), TLS (шифрование и сертификат), вход, отправка. Сломанный шаг отмечен «✗» с объяснением, что поправить, и ответом сервера; пароль не печатается. Например, отказ на `MAIL FROM` объясняется так: адрес отправителя должен принадлежать ящику, под которым идёт вход (у Яндекс 360 — совпадать с логином или быть его алиасом). А если порт ждёт TLS сразу, а задан `starttls` (465 вместо 587), сломается шаг TLS с подсказкой `SMTP_SECURITY=tls`, а не «соединение». С файловым ящиком команда пишет, куда легло письмо. Почта выключена — объясняет, что задать, и выходит с кодом 1.

### Провайдер

Берём российского провайдера: в письмах о заявках есть персональные данные посетителей, а по 152-ФЗ их обработка должна идти на серверах в РФ. Для писем студии и небольших сайтов хватает **Яндекс 360 для бизнеса** (SMTP `smtp.yandex.ru`, порт 465, вход — адрес ящика и пароль приложения, а не пароль от аккаунта; `MAIL_FROM` — тот же адрес или его алиас). Если писем много или нужна статистика доставки — транзакционный сервис вроде **Unisender Go** (SMTP с логином и ключом из кабинета). Подойдёт любой провайдер с SMTP по TLS — главное, чтобы адрес `MAIL_FROM` был на домене, который этот провайдер подтвердил.

### SPF, DKIM и DMARC

Без этих трёх записей в DNS письма с домена уходят в спам, а сам домен легко подделать. Настраиваются один раз на домен отправителя (`example.ru` из `MAIL_FROM`), у домена студии и у доменов клиентов. Все три — TXT-записи у регистратора или в DNS-хостинге.

1. **SPF** — какие серверы вправе слать письма от домена. Одна TXT-запись на самом домене (`@`), строку даёт провайдер. Для Яндекс 360: `v=spf1 redirect=_spf.yandex.net`. Если писем шлют несколько сервисов, их `include:` собираются в **одну** запись: `v=spf1 include:<первый> include:<второй> ~all`. Вторая запись `v=spf1` ломает обе.
2. **DKIM** — подпись писем ключом домена. Ключ генерирует провайдер (в Яндекс 360 — «Почта → DKIM-подпись»), а в DNS кладётся открытая часть: TXT-запись `<селектор>._domainkey` (у Яндекса — `mail._domainkey`) со значением `v=DKIM1; k=rsa; p=…`. Длинное значение копируй целиком, как дал провайдер.
3. **DMARC** — что делать с письмами, которые не прошли SPF и DKIM, и куда слать отчёты. TXT-запись `_dmarc`: начни с наблюдения `v=DMARC1; p=none; rua=mailto:dmarc@example.ru`, через пару недель без чужих отправителей в отчётах ужесточи до `p=quarantine`, потом `p=reject`.

Как проверить:

- записи видны в DNS: `nslookup -type=TXT example.ru`, `nslookup -type=TXT mail._domainkey.example.ru`, `nslookup -type=TXT _dmarc.example.ru` (или `dig TXT … +short`). Новые записи расходятся от нескольких минут до суток;
- отправь себе `pnpm mail:test --to <твой ящик на Gmail или Яндексе>` и открой исходный текст письма («Показать оригинал» / «Свойства письма»): в заголовке `Authentication-Results` должно быть `spf=pass`, `dkim=pass` и `dmarc=pass`, а домен в `dkim` (`header.d=`) — тот же, что в `From`.

| Адрес | Экран |

| `/login` | вход. Сюда ведёт любой экран без входа, а после входа — обратно, туда, где был. Ссылка «Забыли пароль?» |
| `/forgot-password` | «Забыли пароль?»: почта → письмо со ссылкой. Почта выключена — как вернуть доступ иначе. Открыт без входа |

| `/invite#token=…` | приглашение по ссылке из письма: сайт, роль, кто пригласил; новому — имя и пароль, существующему — вход паролем или «Принять приглашение». Открыт без входа |
| `/` | список доступных сайтов и «Новый сайт» (только владельцу) |
| `/sites/:siteId` | страницы сайта: состояние публикации, «Новая страница», удаление (клиенту — только список). У владельца — «Участники»: пригласить по почте и список приглашений с «Отозвать» |
| `/sites/:siteId/media` | медиатека: загрузка (с прогрессом; файл больше лимита отклоняется сразу, без отправки), превью, размеры и вес, удаление (кроме клиента; картинку, которая стоит на странице, API удалить не даст и скажет, где она) |
| `/sites/:siteId/pages/:slug` | редактор страницы: блоки и пункты списков переставляются стрелками и перетаскиванием (см. ниже). Кнопка «История» показывает публикации: выбранная версия открывается в предпросмотре, «Вернуть в черновик» делает её черновиком (с вопросом, если есть несохранённые правки) |
| `/mail` | почта (только владелец, ссылка «Почта» в шапке): включена ли и через что; «Настройки SMTP» — форма с «Проверить подключение» (шаги ✓/✗), «Сохранить» с паролем владельца, «Сохранить без проверки» и «Удалить настройки» (или только чтение, если SMTP задан на сервере или нет ключа); очередь писем с ошибками и кнопкой «Повторить», предпросмотр каждого шаблона — HTML в iframe без скриптов и текстовая версия |

В шапке — имя вошедшего и «Выйти». Если сессия кончилась посреди работы (любой ответ 401), админка ведёт на вход и потом возвращает на тот же экран; несохранённые правки редактора защищает обычный вопрос перед уходом. То, что роли нельзя (публикацию, создание и удаление страниц для клиента), админка не показывает, но решает всё равно API.

У каждого экрана свой адрес и свой заголовок вкладки («Сайты — Averra CMS», «<сайт> — страницы — Averra CMS», «<страница> — редактор — Averra CMS»), поэтому обновление вкладки оставляет на месте, а ссылку можно сохранить. Кривой id сайта или адрес страницы в ссылке — экран «Сайт не найден» / «Страница не найдена». Назад ведут хлебные крошки вверху экрана. Уйти из редактора с несохранёнными правками (по ссылке, кнопкой «Назад» браузера или закрыв вкладку) можно только после подтверждения.

Блоки в списке слева и пункты списков в форме блока (например, «Пункты» у «Преимуществ») переставляются стрелками ↑↓ или перетаскиванием за ручку ⠿ — мышью, пальцем или с клавиатуры: Tab до ручки, пробел или Enter поднимает, стрелки ↑↓ двигают, пробел, Enter или Tab ставит, Escape отменяет. Ручка подписана именем блока или пункта («Перетащить блок «Почему выбирают нас»»), а стрелка, которая на краю списка стала недоступной, передаёт фокус соседней. Экранный диктор по-русски говорит, что поднято и на какой оно позиции. Порядок меняется в черновике, когда блок поставлен, и сразу виден в предпросмотре; на сайт он попадает после сохранения и публикации, как любая правка. Перетаскивание сделано на dnd-kit (`@dnd-kit/core` и `@dnd-kit/sortable`), обёртка — `apps/admin/src/ui/SortableList.tsx`.

Поле «картинка» в форме блока открывает медиатеку в модальном окне: там картинку выбирают или сразу загружают новую. Рядом — поле «Описание картинки (alt)» и кнопки «Заменить картинку» и «Убрать картинку». Предпросмотр показывает выбранную картинку теми же компонентами, что и сайт.

Маршруты — TanStack Router (`apps/admin/src/router.tsx`), загрузка и кеш данных — TanStack Query (`apps/admin/src/queries.ts`).

## Сквозные тесты (e2e)

Пакет `e2e/` гоняет сценарии админки в настоящем браузере: сайты и страницы → правка в форме → предпросмотр → сохранение → публикация → опубликованный сайт. Один раз поставь браузер (только Chromium, около 120 МБ в общий кеш Playwright):

```bash
pnpm --filter @averra/e2e exec playwright install chromium
```

Запуск:

```bash
pnpm e2e                        # все тесты
pnpm e2e --shuffle              # в случайном порядке: тесты не должны зависеть друг от друга
pnpm e2e tests/editor.spec.ts   # один файл
pnpm e2e --headed               # с видимым окном браузера
```

Playwright сам поднимает свои копии API, админки и рендерера и гасит их в конце. Порты свои, чтобы не мешать `pnpm dev`:

| Что | Адрес в e2e |
|---|---|
| API | http://localhost:4100 |
| Админка | http://localhost:5273 |
| Рендерер | http://localhost:4421 |
| Тестовый SMTP | 127.0.0.1:2587 (только на время `tests/smtp-settings.spec.ts`) |

Запущенный рядом `pnpm dev` не мешает, и наоборот: рендерер e2e стартует с `astro dev --ignore-lock` и не берёт файл-замок Astro (`apps/renderer/.astro/dev.json`; брошенный замок от упавшего сервера он может удалить), по которому Astro не даёт поднять второй dev-сервер в том же проекте. Если какой-то из этих портов занят, прогон сразу падает: тесты не пойдут по чужому серверу. База, картинки и файловый ящик почты e2e лежат в `e2e/.data` и стираются перед каждым прогоном, база разработки в `apps/api/.data` не трогается. Перед каждым тестом демо-сайт возвращается в исходное состояние через API: главная — демо, страницы, созданные другими тестами, удаляются. Сайты, которые создают тесты, остаются до следующего прогона, поэтому у каждого своё название.

Админка e2e закрыта входом, как и настоящая. API e2e при старте создаёт владельца с учебными данными из `e2e/urls.ts` (`e2eOwner`). Проект `setup` входит им один раз и сохраняет cookie в `e2e/.data/owner.json`: остальные тесты стартуют уже вошедшими, а фикстура ходит в API с той же cookie. Вход, выход и лимит попыток проверяет `tests/auth.spec.ts` в браузере без сохранённой сессии. Письма тесты читают из файлового ящика e2e (`tests/mailbox.ts`): так приглашение и сброс пароля проходят целиком, а участника заводит приглашение, а не команда. Рендерер e2e собирает демо-сайт по его постоянному id.

Настройки SMTP в админке (`tests/smtp-settings.spec.ts`) проверяются с настоящим тестовым SMTP-сервером. Настройки пускают только порты 465 и 587, а порт ниже 1024 на Linux без root не занять. Поэтому сервер слушает свой порт `127.0.0.1:2587`, в форме стоит 587, а API e2e подключается к тестовому серверу через `DEV_SMTP_CONNECT_PORT`. Эту переменную API принимает только в учебном режиме, вне его конфиг не стартует. Сертификат у сервера — от своего CA. Его создаёт `scripts/smtp-certs.ts` перед стартом API, а API e2e доверяет ему через стандартную переменную Node `NODE_EXTRA_CA_CERTS`: она добавляет корневой сертификат, проверку не снимает. В конце тест удаляет настройки SMTP, и остальные тесты снова пишут в файловый ящик.

Упавший тест оставляет трассу в `e2e/test-results`, а сводный отчёт лежит в `e2e/playwright-report` (`pnpm --filter @averra/e2e exec playwright show-report`). В конце прогона в логе бывает строка `[API] … Command failed`: это Playwright гасит сервер API, на Windows иначе не умеет.

`pnpm check` e2e не запускает: он должен оставаться быстрым. Перед коммитом, который меняет админку, API или рендерер, гоняй и `pnpm e2e`.

## MCP

`apps/mcp` — MCP-сервер, через который нейронка собирает лендинги. Инструменты: `list_blocks`, `list_sites`, `get_page`, `save_draft` и `publish_page`. Входные схемы инструментов — те же Zod-схемы, что проверяют страницы в API, поэтому кривой блок не пройдёт ни там, ни там.

Сервер описан в `.mcp.json` и запускается на закреплённой в проекте Node (`node_modules/.bin/node.exe`, путь под Windows). MCP — обычный клиент API и входит токеном с правами редактора на одном сайте. Настройка:

1. Останови `pnpm dev` (команде нужна база) и выпусти токен: `pnpm token:create --site <id сайта> --name mcp`. Токен показывается один раз.
2. Скопируй `apps/mcp/.env.example` в `apps/mcp/.env` (он в `.gitignore`) и вставь строку `CMS_API_TOKEN=…` из вывода команды.
3. Запусти `pnpm dev`, открой новую сессию Claude Code в папке проекта и разреши сервер `averra`. Если сервер уже был запущен, перезапусти его: токен читается при старте.

Без токена сервер всё равно стартует: `list_blocks` работает, а остальные инструменты отвечают, как получить токен. `list_sites` показывает только сайт токена. Отозвать токен — `pnpm token:revoke --id <id>`; после этого MCP получит понятную ошибку «API не принял токен».

Astro по умолчанию отправляет анонимную телеметрию. Отключить её: `pnpm --filter @averra/renderer exec astro telemetry disable`.
