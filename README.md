# CMS для лендингов

Своя система для быстрых и аккуратных лендингов. Что и зачем — в [PLAN.md](PLAN.md), правила кода — в [CONVENTIONS.md](CONVENTIONS.md).

## Запуск

Нужен pnpm 12. Ставить Node под проект не нужно: версия закреплена в `package.json` (`devEngines.runtime`, Node 24 LTS). pnpm скачает её при установке и запускает все скрипты на ней, какая бы Node ни стояла глобально и что бы ни было в PATH. Чтобы запустить сам pnpm, подойдёт любая Node ≥ 18 с corepack: `corepack pnpm …`.

```bash
pnpm install
pnpm dev
```

| Что | Адрес |
|---|---|
| API | http://localhost:4000/api/health |
| Админка | http://localhost:5173 |
| Рендерер | http://localhost:4321 |

## Команды

| Команда | Что делает |
|---|---|
| `pnpm dev` | поднимает API, админку и рендерер |
| `pnpm check` | линтер, типы и тесты — всё, что нужно перед коммитом |
| `pnpm e2e` | сквозные тесты в браузере (Playwright), см. ниже |
| `pnpm build` | собирает админку и рендерер |
| `pnpm typecheck` | проверяет типы во всех пакетах |
| `pnpm test` | запускает тесты во всех пакетах |
| `pnpm lint` | проверяет линтером и форматтером |
| `pnpm format` | то же, но сразу исправляет |
| `pnpm db:generate` | создаёт миграцию по изменениям в `apps/api/src/db/schema.ts` |

Команды — это скрипты корневого `package.json`, он работает вместо Makefile. pnpm заодно стоит в проекте как dev-зависимость, чтобы скрипты могли вызывать его сами, даже если глобально pnpm не установлен.

## API

| Запрос | Что делает |
|---|---|
| `GET /api/sites` | список сайтов |
| `POST /api/sites` | создать сайт: `{ "name": "…" }`. Тема — по умолчанию, главная страница создаётся сразу (черновик) |
| `GET /api/sites/:siteId/snapshot` | тема и опубликованные страницы — всё, что нужно рендереру |
| `GET /api/sites/:siteId/pages` | страницы сайта: заголовок, адрес, когда опубликована, есть ли неопубликованные изменения |
| `POST /api/sites/:siteId/pages` | создать страницу: `{ "slug": "o-nas", "title": "…", "template": "hero" }`, шаблон `hero` (первый экран из каталога) или `empty` (по умолчанию). Занятый адрес — 409 |
| `GET /api/sites/:siteId/pages/:slug` | страница с черновиком и опубликованной версией |
| `PUT /api/sites/:siteId/pages/:slug` | сохранить черновик: `{ "title": "…", "content": { "blocks": […] } }` |
| `POST /api/sites/:siteId/pages/:slug/publish` | опубликовать черновик вместе с заголовком |
| `DELETE /api/sites/:siteId/pages/:slug` | удалить страницу. Главную (`index`) удалить нельзя — 409 |

При первом запуске API кладёт в пустую базу демо-сайт. Главная страница сайта имеет slug `index`. Адрес страницы — латиница в нижнем регистре и цифры, дефис только между ними (`o-nas`, `price-2026`). Ошибки приходят в одном формате: `{ "error": { "code", "message", "issues"? } }`; у 400 и у 409 «адрес занят» в `issues` есть путь до поля.

Заголовок страницы, как и блоки, попадает на сайт только после публикации: сохранённый черновик сайт не меняет.

Рендерер берёт данные из API, поэтому для `pnpm build` API должен быть запущен. При сборке страницы сайта статические, а в `pnpm dev` рендерер собирает страницу на каждый запрос: новая страница видна по своему адресу сразу после публикации, без перезапуска. Сайт выбирается переменной `CMS_SITE_ID`, без неё берётся первый. Адрес API задаёт `CMS_API_URL`, по умолчанию `http://localhost:4000`. Админка в dev-режиме ходит в API через прокси Vite по тому же `CMS_API_URL`, а её порт задаёт `ADMIN_PORT` (по умолчанию 5173).

## Админка

| Адрес | Экран |
|---|---|
| `/` | список сайтов и «Новый сайт» |
| `/sites/:siteId` | страницы сайта: состояние публикации, «Новая страница», удаление |
| `/sites/:siteId/pages/:slug` | редактор страницы |

У каждого экрана свой адрес, поэтому обновление вкладки оставляет на месте, а ссылку можно сохранить. Назад ведут хлебные крошки вверху экрана. Уйти из редактора с несохранёнными правками (по ссылке, кнопкой «Назад» браузера или закрыв вкладку) можно только после подтверждения.

Маршруты — TanStack Router (`apps/admin/src/router.tsx`), загрузка и кеш данных — TanStack Query (`apps/admin/src/queries.ts`).

## Сквозные тесты (e2e)

Пакет `e2e/` гоняет сценарии админки в настоящем браузере: сайты и страницы → правка в форме → предпросмотр → сохранение → публикация → опубликованный сайт. Один раз поставь браузер (только Chromium, около 120 МБ в общий кеш Playwright):

```bash
pnpm --filter @cms/e2e exec playwright install chromium
```

Запуск:

```bash
pnpm e2e                        # все тесты
pnpm e2e --shuffle              # в случайном порядке: тесты не должны зависеть друг от друга
pnpm e2e tests/editor.spec.ts   # один файл
pnpm e2e --headed               # с видимым окном браузера
```

Playwright сам поднимает свои копии API, админки и рендерера и гасит их в конце. Порты свои, чтобы не мешать `pnpm dev`:

| Что | Адрес в e2e |
|---|---|
| API | http://localhost:4100 |
| Админка | http://localhost:5273 |
| Рендерер | http://localhost:4421 |

Запущенный рядом `pnpm dev` не мешает, и наоборот: рендерер e2e стартует с `astro dev --ignore-lock` и не трогает файл-замок Astro (`apps/renderer/.astro/dev.json`), по которому Astro не даёт поднять второй dev-сервер в том же проекте. Если какой-то из этих портов занят, прогон сразу падает: тесты не пойдут по чужому серверу. База e2e лежит в `e2e/.data` и стирается перед каждым прогоном, база разработки в `apps/api/.data` не трогается. Перед каждым тестом демо-сайт возвращается в исходное состояние через API: главная — демо, страницы, созданные другими тестами, удаляются. Сайты, которые создают тесты, остаются до следующего прогона, поэтому у каждого своё название.

Упавший тест оставляет трассу в `e2e/test-results`, а сводный отчёт лежит в `e2e/playwright-report` (`pnpm --filter @cms/e2e exec playwright show-report`). В конце прогона в логе бывает строка `[API] … Command failed`: это Playwright гасит сервер API, на Windows иначе не умеет.

`pnpm check` e2e не запускает: он должен оставаться быстрым. Перед коммитом, который меняет админку, API или рендерер, гоняй и `pnpm e2e`.

## MCP

`apps/mcp` — MCP-сервер, через который нейронка собирает лендинги. Инструменты: `list_blocks`, `list_sites`, `get_page`, `save_draft` и `publish_page`. Входные схемы инструментов — те же Zod-схемы, что проверяют страницы в API, поэтому кривой блок не пройдёт ни там, ни там.

Сервер описан в `.mcp.json` и запускается на закреплённой в проекте Node (`node_modules/.bin/node.exe`, путь под Windows). Чтобы подключить его к Claude Code, открой новую сессию в папке проекта и разреши сервер `cms`. MCP работает через API, так что сначала запусти `pnpm dev`.

Astro по умолчанию отправляет анонимную телеметрию. Отключить её: `pnpm --filter @cms/renderer exec astro telemetry disable`.

## Структура

```
apps/
  api/        # Hono + Drizzle, локально база — PGlite
  admin/      # React + Vite: сайты, страницы и редактор с живым предпросмотром
  renderer/   # Astro: JSON сайта → статический HTML
  mcp/        # MCP-сервер для нейронок поверх API
e2e/          # сквозные тесты на Playwright
packages/
  schema/     # Zod-схемы: блоки, страница, тема
  tokens/     # тема → CSS-переменные
  blocks/     # React-компоненты блоков
```
