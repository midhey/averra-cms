# Averra CMS

Внутренняя система студии Averra для быстрых и аккуратных лендингов. Что и зачем — в [PLAN.md](PLAN.md), правила кода — в [CONVENTIONS.md](CONVENTIONS.md).

## Запуск

Нужен pnpm 12. Ставить Node под проект не нужно: версия закреплена в `package.json` (`devEngines.runtime`, Node 24 LTS). pnpm скачает её при установке и запускает все скрипты на ней, какая бы Node ни стояла глобально и что бы ни было в PATH. Чтобы запустить сам pnpm, подойдёт любая Node ≥ 18 с corepack: `corepack pnpm …`.

```bash
pnpm install
pnpm dev
```

| Что | Адрес |
|---|---|
| API | http://localhost:4000/api/health |
| Админка | http://localhost:5173 |
| Рендерер | http://localhost:4321 |

### Первый запуск: владелец и сайт для рендерера

Админка и API закрыты входом, регистрации нет. Перед первым входом нужен владелец — выбери один способ:

- **Для разработки:** скопируй `apps/api/.env.example` в `apps/api/.env`. Если в базе ещё нет пользователей, API при старте создаст владельца из `DEV_OWNER_EMAIL` / `DEV_OWNER_PASSWORD` (в примере — учебные значения, только для разработки: работает лишь в учебном режиме `pnpm dev` при `NODE_ENV=development` и адресах админки и API на localhost). Там же, в пустой базе, API заводит демо-сайт.
- **Командой** (так же и в проде): `pnpm user:create --email anna@example.ru --name "Анна"`. Пароль команда спросит скрыто, дважды, или возьмёт из переменной `CMS_USER_PASSWORD`. Он не печатается и не попадает в аргументы и логи.

Рендерер собирает один сайт — тот, что в `CMS_SITE_ID` (`apps/renderer/.env`, шаблон — `.env.example`; id виден в адресе админки `/sites/<id>`). В `pnpm dev` без него рендерер показывает демо-сайт свежей базы (`d0000000-0000-4000-8000-000000000001`) и пишет об этом в лог, так что сразу после клонирования всё работает. Если твоя база старше и у демо-сайта другой id или нужен другой сайт — впиши его. `pnpm build` без `CMS_SITE_ID` не соберётся: сборка должна явно знать, какой сайт собирает. Первый сайт из API рендерер не берёт: список сайтов виден только после входа, а снимок сайта открыт и берётся по id.

### Учебный секрет и прод

Без своего `AUTH_SECRET` API подписывает cookie учебным секретом, а он лежит в репозитории. Поэтому так API запускается только в учебном режиме, и его надо попросить явно: флаг `--dev` ставит скрипт `pnpm dev` (и e2e), а `pnpm --filter @averra/api start` его не ставит. Вдобавок `NODE_ENV` не `production`, а `ADMIN_URL` и `API_URL` (если заданы) указывают на этот компьютер (`localhost`, `*.localhost`, `127.x.x.x`, `[::1]`). Только в учебном режиме API заводит в пустой базе демо-сайт и владельца из `DEV_OWNER_*`. Без флага, даже вовсе без переменных, API без `AUTH_SECRET` не стартует и объясняет почему, а учебный секрет, вписанный руками, не примет вне учебного режима — как и его варианты (с пробелами по краям, в кавычках, в другом регистре или только его часть). Флаг пишется ровно `--dev`: опечатка или лишний аргумент — ошибка с подсказкой, и API не стартует. Команды терминала (`pnpm user:create` и другие) сеть не слушают и на свежем клоне работают и без `AUTH_SECRET`.

Добавочная защита: на учебном секрете API отвечает только на запросы к `localhost` с этого компьютера (403 остальным), смотрит на адрес соединения и на имя в `Host`. Прямой запрос из сети и прокси, который передаёт настоящий `Host` (Caddy по умолчанию), получат 403. Но у проверки есть предел: nginx по умолчанию шлёт API свой `Host` апстрима (`127.0.0.1:4000`), а прокси «для всех имён» передаёт `Host` клиента как есть, и тот может написать `localhost`. Через такие прокси запрос пройдёт, поэтому `pnpm dev` на сервере не запускай — для сервера есть `start` со своими переменными. На сервере задай `NODE_ENV=production`, `AUTH_SECRET` (`openssl rand -base64 32`), `ADMIN_URL` и `API_URL`: в проде все три обязательны, а cookie ставятся только по HTTPS (`Secure`; так же, если `API_URL` начинается с `https://`). Чтобы задавать SMTP в админке, нужен ещё `MAIL_ENCRYPTION_KEY` (`openssl rand -base64 32`, см. «SMTP в админке»). Без него API стартует, но настройки SMTP на странице «Почта» будут только для чтения.

| `pnpm format` | то же, но сразу исправляет |

| `pnpm site:create --name … [--print-id]` | создаёт сайт, как «Новый сайт» в админке; `--print-id` печатает только id (так его берёт установщик) |
| `pnpm user:password --email …` | задаёт пользователю новый пароль (скрытым вводом или из `CMS_USER_PASSWORD`), завершает все его входы и сжигает ссылки сброса. Путь восстановления доступа без почты |

Ссылку не печатает, но говорит, на какой адрес админки (`ADMIN_URL`) она ведёт; ссылку на localhost при почте через SMTP не ставит вовсе. SMTP из админки, пароль которого API не расшифрует (нет `MAIL_ENCRYPTION_KEY` или он не тот), почтой не считает и отказывает с той же причиной, что показывает API. Без `--by` приглашает единственный владелец, при нескольких `--by` обязателен |
| `pnpm token:create --site <id> --name … [--by <почта>]` | выпускает токен API для MCP и показывает его один раз |
| `pnpm token:list` | токены: сайт, кто выпустил, когда пользовались, отозван ли (без самих токенов) |

| `pnpm mail:test --to <адрес>` | шлёт проверочное письмо напрямую и по шагам показывает, где сломалось (см. «Почта»). Проверяет почту из окружения; SMTP, заданный в админке, проверяет кнопка «Проверить подключение» |
| `pnpm --filter @averra/api status [--json]` | состояние установки: версия, база, бэкапы, обновление, сборки, почта, диск и проблемы. Базу только читает. На сервере — `node dist/server/status.js`, его зовёт `averra.sh status` |
| `pnpm fleet status` / `pnpm fleet update --version X [--only имя,…]` | все установки студии по списку серверов: состояние и обновление по очереди с остановкой на первой ошибке (см. «Несколько установок») |

Команды — это скрипты корневого `package.json`, он работает вместо Makefile. pnpm заодно стоит в проекте как dev-зависимость, чтобы скрипты могли вызывать его сами, даже если глобально pnpm не установлен.

Команды пользователей и токенов открывают базу напрямую. С PostgreSQL (`DATABASE_URL`, сервер) они работают и при запущенном API. Встроенная база (PGlite) не выдерживает два процесса сразу, поэтому, пока запущен `pnpm dev`, они откажутся работать и попросят его остановить: API и команды берут файл-замок рядом с базой (`apps/api/.data/pglite.lock`). Замок от упавшего процесса снимается сам. На Windows pid быстро переиспользуются, и замок упавшего API может достаться постороннему живому процессу: тогда сообщение покажет путь к файлу замка — если `pnpm dev` не запущен, удали этот файл.

## Вход и права

Вход — по почте и паролю (Better Auth), сессия живёт в httpOnly-cookie (`SameSite=Lax`, в проде ещё и `Secure`). Попыток входа — не больше трёх за 10 секунд с одного IP, дальше 429 «Слишком много попыток».

| Роль | Что может |
|---|---|
| владелец (`owner`) | всё: все сайты, создание сайтов, приглашение участников, заявки с форм |
| редактор (`editor`) на сайте | читать, править, публиковать, создавать и удалять страницы своих сайтов; загружать и удалять картинки. Заявок не видит: персональные данные посетителей ему не нужны |
| клиент (`client`) на сайте | читать и править черновики существующих страниц своего сайта, загружать картинки; публиковать, создавать и удалять — нет. Заявки своего сайта видит, обрабатывает, удаляет и настраивает: это его заявки |
| токен API | как редактор, но на одном сайте. Заявок не видит никогда (403), как бы ни менялись права ролей |

Глобальная роль пользователя — `owner` или `member`; участника на сайт приглашает владелец письмом («Настройки сайта» или `pnpm member:invite`), а `pnpm member:add` даёт доступ уже заведённому пользователю. Чужой сайт для участника выглядит как несуществующий (404), а не «запрещено» (403): так не видно, что он вообще есть.

### Сброс пароля

«Забыли пароль?» на экране входа → почта → письмо «Сброс пароля» со ссылкой `ADMIN_URL/reset-password#token=…` → новый пароль дважды → вход. Сброс сделан на Better Auth (`sendResetPassword`), письмо идёт через очередь почты. Правила:

- ссылка одноразовая и живёт час; новый запрос сжигает прежнюю ссылку; после смены пароля все входы пользователя завершаются;
- в базе (`verifications`) лежит только SHA-256 токена (`reset-password#<хеш>`), а сам токен — только в письме. Разделитель `#`, а не двоеточие, выбран не случайно: Better Auth, не найдя запись по хешу, ищет её ещё и по строке `reset-password:<присланный токен>` как есть, и с двоеточием хеш из базы сам работал бы как токен. Вдобавок API пускает к Better Auth только токен его формата (24 буквы и цифры). Токен во фрагменте ссылки (`#token=`): браузер не шлёт фрагмент на сервер, поэтому токен не попадает в логи и `Referer`, а экран сразу убирает его из адресной строки;
- ответ на запрос один и тот же, есть такой адрес или нет, и не раньше чем через 300 мс: ни по тексту, ни по времени не узнать, есть ли пользователь. Письмо уходит только существующему;
- лимиты: 5 запросов за 15 минут с одного IP и 3 запроса за 15 минут на один адрес (считаются любые адреса, поэтому и 429 ничего не выдаёт). Оба счётчика свои, в обёртке; правило Better Auth на этот путь только запасное (10 за 15 минут), а варианты пути (`/request-password-reset/`, другой регистр и т. п.) отвечают 404 и лимит не тратят; попыток задать пароль по ссылке — 10 в минуту с IP. IP проверяется первым: запрос, отбитый по IP, в счётчик адресов не попадает — и тогда, когда его отбил запасной лимит Better Auth (попытка адреса возвращается). Счётчики живут в памяти процесса API и помнят не больше 10 000 ключей (при нехватке места вытесняется самый давний);
- почта не настроена — экран «Забыли пароль?» сразу говорит, что сброс недоступен и как вернуть доступ: попросить владельца или на сервере остановить API и выполнить `pnpm user:password --email …`.

### Приглашения

Владелец в «Настройках сайта» (раздел «Участники») вводит почту и роль — редактор или клиент — и жмёт «Пригласить» (или выполняет `pnpm member:invite`). Человек получает письмо со ссылкой `ADMIN_URL/invite#token=…` и по ней сам задаёт имя и пароль, а если вход у этого адреса уже есть — входит своим паролем и принимает приглашение. После этого он видит только этот сайт со своей ролью. Правила:

- ссылка одноразовая и действует 7 дней; в базе (`user_invitations`) только SHA-256 токена; повторное приглашение того же адреса на тот же сайт отзывает прежнее;
- лимиты: одному адресу на один сайт — не больше 3 приглашений в час, от одного владельца — не больше 50 в час (429 `rate_limited`);
- закрытые приглашения (принятые, отозванные, истёкшие) удаляются через `MAIL_RETENTION_DAYS` дней после закрытия, вместе с чисткой очереди писем: в них адрес человека;
- принятое, отозванное и истёкшее приглашение отвечает понятной ошибкой (410), неизвестная ссылка — 404;
- владельца админки и того, кто уже участник сайта, пригласить нельзя (409). Сменить роль — `pnpm member:add`. Если роль выдали командой уже после приглашения, принятие её не меняет;
- приглашают и отзывают только владельцы: редактору и клиенту — 403, чужой сайт — 404. Без почты приглашение не отправить (503), и раздел «Участники» говорит об этом заранее.

Переменные API для медиатеки — `MEDIA_DIR` и `MEDIA_MAX_BYTES` (см. «Картинки»). Переменные API для входа (`apps/api/.env`, все описаны в `.env.example`): `NODE_ENV` (на сервере — `production`), `AUTH_SECRET` (подпись cookie, от 32 символов; без него — только учебный режим, см. «Учебный секрет и прод»), `ADMIN_URL` (адрес админки: только с него принимаются запросы с cookie, и на него ведут ссылки в письмах; в проде обязателен), `API_URL` (адрес API снаружи; в проде обязателен), `TRUST_PROXY=true` — если перед API стоит прокси, который сам ставит `X-Forwarded-For`. По этому заголовку считаются лимиты попыток входа и запросов сброса пароля; без прокси API перезаписывает его адресом соединения, чтобы клиент не мог его подделать.

## API

| Запрос | Что делает |
|---|---|
| `POST /api/auth/sign-in/email` | вход: `{ "email", "password" }`, ставит cookie сессии. Остальные эндпоинты Better Auth — тоже под `/api/auth/*` (`sign-out`, `get-session`…). Проверка пароля Better Auth `POST /api/auth/verify-password` закрыта (404): через неё уведённая сессия подбирала бы пароль мимо лимита |
| `POST /api/auth/change-password` | сменить свой пароль: `{ "currentPassword", "newPassword" }` → `200 { status: "changed", message }` и новая cookie сессии; остальные входы пользователя завершаются. Неверный текущий пароль — 403 `invalid_password` у поля `currentPassword`. Неудач — не больше 5 за 15 минут на пользователя, счётчик общий с паролем владельца у настроек SMTP, дальше 429. Без входа — 401, не из админки — 403 |
| `GET /api/password-reset` | работает ли сброс пароля по почте: `{ available }`. **Открыт без входа**: его спрашивает экран «Забыли пароль?» |
| `POST /api/auth/request-password-reset` | «Забыли пароль?»: `{ "email" }`. Ответ всегда `200 { status: "sent", message }`, есть адрес или нет; письмо — только существующему. Почта выключена — 503 `mail_disabled`, лимит — 429 `rate_limited` |
| `POST /api/auth/reset-password` | новый пароль по ссылке: `{ "token", "newPassword" }`. Ссылка использована, устарела, заменена новой или токен не того формата (не 24 буквы и цифры) — 400 `invalid_token`. Все сессии пользователя завершаются. `GET /api/auth/reset-password/:token` Better Auth закрыт (404): токен в пути попал бы в лог |
| `GET /api/me` | кто вошёл: `{ kind: "user", user: { id, name, email, role } }` (для токена — `{ kind: "token", token: { id, siteId } }`) |
| `GET /api/sites` | сайты, доступные вошедшему (владельцу — все, токену — его сайт) |
| `POST /api/sites` | создать сайт (только владелец): `{ "name": "…" }`. Тема — по умолчанию, главная страница создаётся сразу (черновик) |
| `GET /api/sites/:siteId` | сайт: название, тема, роль вошедшего на нём (`access`) и `newLeads` — сколько новых заявок (`null`, если роли заявки не видны: редактор, токен) |
| `GET /api/sites/:siteId/snapshot` | тема, опубликованные страницы и справочник `media` с вариантами их картинок — всё, что нужно рендереру. **Открыт без входа** |
| `GET /api/sites/:siteId/pages` | страницы сайта: заголовок, адрес, когда опубликована, есть ли неопубликованные изменения |
| `POST /api/sites/:siteId/pages` | создать страницу: `{ "slug": "o-nas", "title": "…", "template": "hero" }`, шаблон `hero` (первый экран из каталога) или `empty` (по умолчанию). Занятый адрес — 409 |
| `GET /api/sites/:siteId/pages/:slug` | страница с черновиком и опубликованной версией. Страницы со старыми адресами (до шага 2.1 пускались и `a-`, `--a`) открываются, сохраняются, публикуются и удаляются как обычные, но новую страницу с таким адресом не создать |
| `PUT /api/sites/:siteId/pages/:slug` | сохранить черновик: `{ "title": "…", "content": { "blocks": […] } }`. Если страницы нет, создаёт её (клиенту — 404). Картинка не из медиатеки этого сайта — 409 с путём до поля |
| `POST /api/sites/:siteId/pages/:slug/publish` | опубликовать черновик вместе с заголовком. Каждая публикация пишет версию в историю |
| `DELETE /api/sites/:siteId/pages/:slug` | удалить страницу вместе с её историей. Главную (`index`) удалить нельзя — 409 |
| `GET /api/sites/:siteId/pages/:slug/revisions` | история публикаций, новые сверху (последние 100): `id`, `version` (1, 2, 3…), `title`, `publishedAt`, `author` (`{ kind: "user" \| "token", name }` или `null`, если автор неизвестен) |

Действие, которое роли не разрешено, — 403, чужой или несуществующий сайт — 404.

При первом запуске API кладёт в пустую базу демо-сайт. Главная страница сайта имеет slug `index`. Адрес страницы — латиница в нижнем регистре и цифры, дефис только между ними (`o-nas`, `price-2026`). Ошибки приходят в одном формате и по-русски — и у проверки схемами (`setupZodMessages` из `@averra/schema` включён в API, админке, командах терминала и MCP), и у неизвестных кодов Better Auth (общее сообщение по статусу, код как есть): `{ "error": { "code", "message", "issues"? } }` — и у наших маршрутов, и у эндпоинтов Better Auth (`unauthorized`, `forbidden`, `invalid_email_or_password`, `rate_limited`…); у 400 и у 409 «адрес занят» в `issues` есть путь до поля.

Заголовок страницы, как и блоки, попадает на сайт только после публикации: сохранённый черновик сайт не меняет.

История версий: каждая публикация в той же транзакции сохраняет снимок — заголовок, блоки, кто (пользователь или токен) и когда. Верхняя версия в истории — то, что сейчас на сайте. Смотреть историю может любой, кто видит сайт, а возвращать версию в черновик — любой, кто правит черновики, включая клиента: возврат сайт не меняет. Страницы, опубликованные до появления истории, получили версию 1 без автора.

## Картинки

Картинки живут в медиатеке сайта. При загрузке API определяет тип по содержимому (sharp), поворачивает снимок по EXIF и удаляет все метаданные: EXIF с местом съёмки, XMP, IPTC, ICC-профиль (цвета переводятся в sRGB). Потом режет его на ширины 480, 960, 1440 и 1920 (не шире исходника; если исходник уже 1920, добавляется и его собственная ширина; очень высокий вариант — длинная инфографика, скриншот страницы — ужимается ещё и до 16383 px по высоте: больше не умеют WebP и AVIF) и каждую кодирует в AVIF, WebP и, для JPEG и PNG, в исходный формат как запасной. Рядом хранится чистый оригинал в полном размере, чтобы потом можно было нарезать новые варианты, но наружу он не отдаётся.

Файлы лежат в хранилище за интерфейсом (`apps/api/src/media/storage.ts`). Сейчас это папка `MEDIA_DIR`, по умолчанию `apps/api/.data/media`, потом будет S3. Путь к файлу сервер строит только из id сайта, id картинки и имени варианта, которое составил сам. Имя загруженного файла хранится только для показа в админке. Предельный размер файла задаёт `MEDIA_MAX_BYTES` (по умолчанию 10 МБ).

В блоке картинка — это поле `{ mediaId, alt }` (схема `Image` в `@averra/schema`), alt обязателен, до 200 символов. Пока картинка есть у первого экрана в варианте `split` (текст слева, картинка справа): в этом варианте она обязательна, в других её быть не должно (там её не видно, а удалить из медиатеки такую «используемую» картинку было бы нельзя). Id в адресах и в ссылках на картинки принимаются в любом регистре и приводятся к строчным. API не даст сохранить ссылку на картинку чужого сайта или несуществующую и не даст удалить картинку, которая стоит в черновике или на сайте. Рендерер выводит `<picture>` с источниками AVIF и WebP, `srcset`, `sizes` и размерами исходника, поэтому вёрстка не прыгает. Картинки грузятся лениво, кроме картинки первого блока страницы: у неё `loading="eager"` и `fetchpriority="high"`. В `pnpm dev` файлы картинок на сайте берутся из API (`CMS_API_URL`). При публикации на сервере (`PUBLISH_DIR`) нужные странице варианты лежат в папке версии сайта (`/media/<id>/<файл>`) и отдаются Caddy как статика, см. «Установка на сервер».

Рендерер берёт данные из API, поэтому для `pnpm build` API должен быть запущен. При сборке страницы сайта статические, а в `pnpm dev` рендерер собирает страницу на каждый запрос: новая страница видна по своему адресу сразу после публикации, без перезапуска. Сайт выбирается переменной `CMS_SITE_ID` (`apps/renderer/.env`); без неё `pnpm dev` показывает демо-сайт, а сборка падает с подсказкой. Главная открывается только по корню, `/index` — 404, как на собранном сайте. В dev Astro пишет в лог «getStaticPaths() ignored in dynamic page…»: так и задумано, маршрут статический только при сборке. Адрес API задаёт `CMS_API_URL`, по умолчанию `http://localhost:4000`. Админка в dev-режиме ходит в API через прокси Vite по тому же `CMS_API_URL`, а её порт задаёт `ADMIN_PORT` (по умолчанию 5173).

## Формы и заявки

Блок «Форма заявки» (`form`) ставится на страницу, как любой другой. У него есть заголовок и текст, поля, текст кнопки, текст после отправки, текст согласия и ссылка на политику конфиденциальности. Ссылка обязательна: без неё форму с персональными данными не сохранить и не опубликовать. Поле формы — это ключ (латиница: `name`, `phone`, `comment`; `website` и `consent` заняты), тип, подпись, «обязательное» и подсказка. Типы такие: имя, телефон, почта, строка текста, многострочный текст, выбор из списка (с вариантами) и флажок. Пределы и шаблоны по типам записаны в одном месте (`packages/schema/src/forms.ts`). Из них получаются HTML-атрибуты проверки в браузере (`required`, `type`, `maxlength`, `pattern`, `autocomplete`) и проверка заявки на сервере. Тест следит, чтобы браузер и сервер принимали одно и то же.

**Как работает без JavaScript.** На сайте обычная форма `<form method="post">`, а её `action` — открытый адрес API `CMS_API_URL/api/forms/<сайт>/<страница>/<блок>`, тот же API, откуда сайт берёт картинки. Посетитель жмёт кнопку, и API проверяет заявку по **опубликованной** версии блока (черновик на приём не влияет), сохраняет её и отвечает 303 обратно на страницу с якорем `#<id блока>-sent`. CSS (`:target`) показывает текст успеха и прячет форму. Страница возврата — источник из `Origin` (браузер шлёт его с каждой межсайтовой POST-формой) и путь страницы из адреса приёма: страница и так известна. Путь из `Referer` не годится: по умолчанию (`strict-origin-when-cross-origin`) браузер шлёт в чужой источник только `https://сайт/`, без пути, и посетитель неглавной страницы попал бы на главную. `Referer` берётся, только если указывает на эту же страницу (тогда сохраняется её точный вид: `/o-nas/` или `/o-nas.html`). Других адресов API не знает и на них не перенаправляет. Если браузер не прислал ни `Origin`, ни `Referer`, API показывает свою страницу «Заявка отправлена». Ошибки — понятная страница от API: что не так (подписями полей), совет нажать «Назад» (браузер сохранит введённое) и ссылка на форму. Почти всё проверяет ещё браузер по атрибутам, так что до этой страницы доходит редко. В предпросмотре админки форма не отправляется.

**Неизвестные поля** отбрасываются: в заявку и письма попадает только то, что объявила форма. Тело разбирается в объект без прототипа, так что ключ поля вроде `constructor` работает как любой другой. **Переводы строк** в однострочных полях (имя, телефон, почта, строка, выбор) — ошибка, а не тихая чистка: эти значения идут в письмо, почта — ещё и в `Reply-To`. В многострочном поле можно перевод строки и табуляцию, другие управляющие символы (в том числе NUL) — 400. **Почта** проверяется одним шаблоном `MAIL_ADDRESS_PATTERN` и в браузере (`pattern`), и на сервере (`MailAddress`): домен может быть кириллическим (`anna@пример.рф`) или в punycode, как его отправляет Chrome. У обязательных однострочных полей без своего шаблона есть `pattern` «не одни пробелы». Расхождение осталось одно: обязательное многострочное поле из одних пробелов браузер пропустит (у `textarea` нет `pattern`), а сервер ответит страницей ошибки. **Флажки** принимаются только значением `yes` — его шлёт отмеченный флажок формы; не прислан или пусто — не отмечен, любое другое значение (`no`, `0`, `false`) — 400. **Варианты выбора** — одна строка: вариант с переводом строки или управляющим символом не проходит схему блока, и форму с ним не сохранить и не опубликовать (сервер такой выбор всё равно не принял бы).

**Антиспам без капчи.**
- Скрытое поле-ловушка `website`: за краем экрана, скрыто от диктора и не в порядке Tab. Если оно заполнено, ответ тот же «успех», но заявки и писем нет.
- Лимиты в памяти процесса: с одного IP — 5 отправок за 10 минут (считаются все, и ловушка, и неверные), на сайт — 100 сохранённых заявок за час. Ловушка и неверные формы лимит сайта не тратят: иначе бот с многих IP выбрал бы его, и настоящие посетители получали бы 429. Сверх лимита — 429 со страницей «Слишком много заявок, попробуйте через N минут».
- Дневной предел объёма: сайт принимает не больше 10 МБ данных заявок за последние сутки (`LEAD_LIMITS.perSiteDailyBytes`), но касается он только **крупных** заявок — с данными больше 8 КБ (`LEAD_LIMITS.smallLeadBytes`). Размер заявки пишется в колонку `leads.data_bytes`, сумма считается в базе по индексу сайта и времени, поэтому переживает перезапуск API и не распаковывает jsonb. Честная заявка — 0,5–2 КБ (с одним многострочным полем, заполненным до предела, — около 4,5 КБ), она проходит и сверх предела, под обычными лимитами частоты: спамер, набивший предел крупными заявками, не закрывает форму для всех. Крупная заявка сверх предела получает 429 со страницей «Форма сейчас не принимает заявки… сократите текст в полях» и `Retry-After: 3600`, а в лог API пишется строка (без данных посетителя), чтобы студия заметила атаку. Худший рост базы в сутки на сайт — 10 МБ крупных заявок плюс 8 КБ × 2400 маленьких (лимит сайта 100 в час), около 30 МБ, а не ~240 МБ без предела.
- Тело — не больше `LEAD_BODY_LIMIT` (~227 КБ), иначе 413. Предел посчитан из схемы: 12 многострочных полей по 2000 символов, каждый в urlencoded — до 9 байт, плюс запас. Честная форма до `maxlength` в него всегда влезает.
- Минимального времени заполнения нет. Метка, поставленная при сборке, — время сборки; получить метку при открытии страницы без JS можно только формой, которую отдаёт сам API (iframe), а это ломает вид и высоту блока. Подробно — в [шаге 3.4](docs/steps/3.4-forms-leads.md).

**152-ФЗ.** Согласие на обработку персональных данных обязательно и явное: засчитывается только значение отмеченного флажка (`consent=yes`). Без него, пустое или любое другое значение (`no`, `0`, `false`) — 400 «Нужно согласие на обработку персональных данных», и записи о согласии нет. В заявку пишется, на что согласился посетитель: текст у флажка, ссылка на политику, номер опубликованной версии страницы и время. IP посетителя не хранится: для лимитов он живёт только в памяти процесса. Заявки удаляются через срок, заданный у сайта (по умолчанию 180 дней, от 7 до 1825), — обработчиком очереди писем раз в час. Письма о заявке связаны с ней (`mail_outbox.lead_id`, `ON DELETE CASCADE`): удалили заявку руками или по сроку — удалились и её письма, в том числе неотправленные с копией полей и подтверждение с почтой посетителя. До удаления заявки письма о ней живут по обычным правилам очереди (`MAIL_RETENTION_DAYS`). Заявки видят владелец и клиент сайта. Редактор их не видит, токен API (MCP) — тоже, никогда.

**Письма** ставятся в очередь в той же транзакции, что и заявка. Не записалось письмо — нет и заявки, а посетитель видит «Заявка не сохранена».
- **«Новая заявка»** — на адреса уведомлений сайта (пусто — всем владельцам админки). В письме все поля подписями (всё экранировано) и ссылка на заявку в админке. Тема — «Новая заявка с сайта «<название сайта>»», без ввода посетителя. Если посетитель указал почту, она стоит в `Reply-To`, и «Ответить» в почте напишет ему.
- **«Заявка получена»** — посетителю, если он указал почту и на сайте включено подтверждение. Текст постоянный: в письме только название сайта, без имени и других полей посетителя, иначе форму превратили бы в рассылку. Не чаще раза в сутки в один ящик с одного сайта и только после ловушки и лимитов. Ящик — это адрес, сведённый `mailboxKey` (`apps/api/src/mail/mailbox-key.ts`): нижний регистр, без метки после `+` (`vasya+1@…` и `vasya+2@…` — один ящик), домен в punycode, у Gmail (`gmail.com`, `googlemail.com`) ещё без точек в имени, у Яндекса (`yandex.ru`, `ya.ru`, `yandex.com` и др.) — один домен и точка как дефис. Ключ хранится в `mail_outbox.recipient_key`; само письмо уходит на адрес, который ввёл посетитель.
- **Почта выключена** — заявки сохраняются, писем нет, и раздел «Заявки» говорит, что уведомления не уходят и почему.

**В админке** в боковой панели сайта — пункт «Заявки» со счётчиком новых. Там вкладки «Новые» / «Обработанные» / «Все», список (новые сверху) и рядом карточка заявки с согласием, «Отметить обработанной» / «Вернуть в новые», «Ответить письмом» (если посетитель оставил почту), «Удалить» и «Скачать CSV». CSV отдаётся потоком: API читает заявки порциями по 500 и сразу пишет их в ответ, в памяти лежит одна порция, а не все заявки за срок хранения. Колонки — подписи полей всех заявок: каждая берёт место из самой свежей заявки, где она есть, подписи свежих заявок слева. Переставили поля в форме — колонки идут как в новой форме. Курсор порции — время и id последней строки значениями, поэтому удаление заявки во время выгрузки её не обрывает. Файл разделён `;`, в UTF-8 с BOM — так его сразу открывает Excel с русской локалью. Значения, которые начинаются с `=`, `+`, `-`, `@`, табуляции или возврата каретки, получают впереди `'` (защита от CSV-инъекции). Настройки заявок — адреса уведомлений, срок хранения, подтверждение посетителю — в «Настройках сайта», раздел «Заявки». Адреса меняют владелец и клиент сайта; о смене письмом узнают все владельцы и прежние адреса, чтобы заявки нельзя было молча перенаправить.

## Почта

Письма системы (сброс пароля, приглашения, уведомления о заявках) уходят не прямо из запроса, а через очередь `mail_outbox`: письмо пишется в базу в той же транзакции, что и действие, а обработчик в процессе API отправляет его с повторами. Упал SMTP — действие не откатывается, письмо уйдёт позже. Провайдер спрятан за интерфейсом `Mailer` (`apps/api/src/mail/mailer.ts`): SMTP в проде, файловый ящик в разработке, память в тестах.

SMTP задают одним из двух способов: на странице «Почта» в админке (см. «SMTP в админке» ниже) или переменными окружения. Приоритет такой: окружение (`SMTP_HOST` или явный `MAIL_TRANSPORT`) → настройки из админки → по умолчанию (файловый ящик в `pnpm dev`, иначе почта выключена). Если SMTP задан в окружении, он главнее: админка показывает его только для чтения, без пароля, с пометкой «задано на сервере».

### Настройка

Переменные API (`apps/api/.env`, все описаны в `.env.example`):

| Переменная | Что задаёт |
|---|---|
| `MAIL_TRANSPORT` | `smtp`, `file` или `off`. Не задано: есть `SMTP_HOST` — `smtp`; есть SMTP в админке — он; учебный режим (`pnpm dev`) — `file`; иначе почта выключена. `file` в проде не принимается. Заданный явно, он главнее админки |
| `SMTP_HOST`, `SMTP_PORT` | сервер SMTP провайдера, порт по умолчанию 465 |
| `SMTP_SECURITY` | `tls` (TLS сразу, порт 465) или `starttls` (обязательный STARTTLS, порт 587). Для 465, 587 и 25 берётся из порта, для другого порта — обязательно. Режима без шифрования нет |
| `SMTP_USER`, `SMTP_PASSWORD` | вход на SMTP. Пароль из окружения в базу, логи, ответы API и вывод команд не попадает, в текстах ошибок маскируется (`***`) |
| `MAIL_FROM`, `MAIL_FROM_NAME` | отправитель: адрес на своём домене (обязателен для SMTP) и имя, по умолчанию «Averra CMS». Адрес должен принадлежать ящику, под которым идёт вход (`SMTP_USER`): у Яндекс 360 — совпадать с логином или быть его алиасом, иначе сервер отвечает на `MAIL FROM` отказом «553 Sender address rejected: not owned by auth user» |
| `MAIL_DIR` | папка файлового ящика, по умолчанию `.data/mail` (в `apps/api`) |
| `MAIL_MAX_ATTEMPTS` | сколько раз пробовать отправить письмо, по умолчанию 8. Пауза растёт: 1, 3, 9, 27… минут, не больше 6 часов — около 12 часов на всё |
| `MAIL_RETENTION_DAYS` | через сколько дней удалять письма из очереди, по умолчанию 30: отправленные — от отправки, неотправленные — от последней попытки, так и не ушедшие (почта была выключена) — от постановки. В них персональные данные (152-ФЗ). Тот же срок — у закрытых приглашений (`user_invitations`) |
| `MAIL_ENCRYPTION_KEY` | ключ, которым шифруется пароль SMTP из админки: 32 случайных байта в base64. Без него SMTP в админке только для чтения. В `pnpm dev` без него берётся учебный ключ из репозитория. См. «SMTP в админке» |
| `DEV_SMTP_CONNECT_PORT` | только для разработки и e2e: SMTP из админки подключается к этому порту того же сервера вместо 465 и 587 (тестовый SMTP на свободном порту). Вне учебного режима — ошибка конфига |

Соединение с SMTP только шифрованное, а сертификат сервера проверяется всегда: настройки, которая это выключает, нет, и `NODE_TLS_REJECT_UNAUTHORIZED=0` в окружении на почту не действует. На 587 сервер без STARTTLS — ошибка, а не письмо открытым текстом. Адреса, тема и имя отправителя проверяются схемами: перевод строки в них — ошибка, а не новый заголовок письма.

Данные письма (кому что подставить в шаблон) лежат в очереди только до отправки: у отправленного письма их уже нет, остаются кому, когда и статус. Письма со ссылкой-токеном (сброс пароля, приглашение) теряют данные и после неудачи, а не ушедшие за срок ссылки не отправляются вовсе. Если SMTP не пускает (неверный пароль, TLS, сервер недоступен) или не принимает адрес отправителя, обработчик не пробует каждое письмо, а выжидает с растущей паузой до 30 минут; «Повторить» в админке и сохранение настроек SMTP будят его сразу. Отказ адресу отправителя — ошибка настроек, а не письма: попытки писем на нём не тратятся, письма со ссылками не стираются и уйдут, когда настройки поправят (причина видна в очереди у первого письма). Окончательно не отправляется только письмо, которому сервер отказал в адресе получателя или в самом письме (5xx на `RCPT TO` или `DATA`). При остановке API (Ctrl+C) дожидается письма, которое уже отправляет; второй Ctrl+C — выход сразу.

Без SMTP (ни в окружении, ни в админке) почта выключена явно: API работает, на экране «Почта» в админке видно, что не так, а действия, которым нужна почта (сброс пароля, приглашения), отвечают 503 `mail_disabled` с объяснением, и экраны админки говорят об этом заранее.

Ссылки в письмах ведут на `ADMIN_URL`. Если это адрес этого компьютера (localhost), а письма уходят по SMTP, адресат ссылку не откроет: почти наверняка на сервере забыли `ADMIN_URL`. API в этом случае предупреждает — строкой в логе при старте и на странице «Почта», — но письма шлёт: в `pnpm dev` SMTP бывает настроен нарочно, чтобы проверить настоящую доставку себе. `pnpm member:invite` строже и отказывает до записи в базу: её запускают ради одного письма, и ссылку на localhost по SMTP отправлять незачем.

**Файловый ящик** (`pnpm dev` без SMTP): письма не уходят наружу, а ложатся в `apps/api/.data/mail` парой файлов — `<время>-<id>.eml` (открывается почтовым клиентом) и `.json` с темой, адресами, текстом и HTML. e2e пишут свой ящик в `e2e/.data/mail`.

### SMTP в админке

Сменить пароль SMTP или провайдера можно без доступа к серверу. На странице «Почта», в разделе «Настройки SMTP», владелец задаёт сервер, порт и шифрование (только «465 — TLS сразу» или «587 — STARTTLS»), логин, пароль, адрес и имя отправителя. Настройки одни на всю установку и лежат в таблице `mail_settings`. Свой SMTP у сайта появится вместе с формами, модель к нему готова.

- **Пароль — только на запись.** В базе он лежит только зашифрованным: AES-256-GCM, свой случайный IV на каждое шифрование, тег проверяется, в записи — версия ключа. Наружу он не отдаётся никогда, даже зашифрованным: ни в ответах API, ни в логе, ни в ошибках, ни на странице. Админка показывает только «задан» или «не читается». Пустое поле при сохранении — оставить прежний пароль, но только для того же сервера. Сменили сервер — пароль нужно ввести заново: сохранённый пароль уходит только на сохранённый сервер.
- **Менять — только владелец и только со своим паролем.** Через SMTP уходят письма сброса пароля. С одной украденной сессией без этого можно было бы поставить свой сервер, сбросить пароль любому и забрать аккаунт. Пароль проверяет Better Auth. Неверный пароль — 403 `invalid_password`. Неудачных попыток — не больше 5 за 15 минут на пользователя, удачные не считаются. Счётчик общий у всех путей, которыми вошедший проверяет свой пароль: у настроек почты и у смены пароля (`/api/auth/change-password`). Проверка пароля самого Better Auth (`/api/auth/verify-password`) по HTTP закрыта. Поэтому с уведённой сессией пароль не подобрать быстрее, чем без неё: остаётся только вход, а у него свой лимит — 3 попытки за 10 секунд с одного IP.
- **«Проверить подключение»** проходит те же шаги, что `pnpm mail:test` (DNS, соединение, TLS, вход, отправка проверочного письма на указанный адрес), по ещё не сохранённым настройкам и показывает каждый шаг. Сертификат сервера проверяется всегда, выключить проверку нечем: схема настроек строгая, лишнее поле вроде `rejectUnauthorized` — 400. Порты только 465 и 587, проверок — не больше 10 за 15 минут на владельца: сервер не станет сканером портов. Пароля владельца проверка не просит, поэтому сохранённый пароль SMTP (пустое поле) в ней работает только с сохранёнными настройками целиком и только на почту самого владельца. Иначе уведённая сессия слала бы через ящик студии письма со своим именем отправителя кому угодно. Поменяли поле или адрес для проверки — введите пароль SMTP или сохраните без проверки.
- **Сохранить** можно после успешной проверки этих же настроек (её итог живёт 15 минут) или явной кнопкой «Сохранить без проверки». В логе API остаётся запись: кто, когда и какие поля поменял, без значений и без пароля. Каждому владельцу уходит письмо «Настройки почты изменены» — через очередь и уже по новым настройкам. Обработчик очереди подхватывает новые настройки без перезапуска API. Если сразу после сохранения API не смог их перечитать (сбой базы), запись в логе всё равно остаётся, а почта встаёт на паузу — не продолжает идти через прежние настройки — и перечитывается перед следующим проходом очереди.
- **«Удалить настройки»** (тоже с паролем владельца) возвращает почту к окружению или к варианту по умолчанию.

**Ключ `MAIL_ENCRYPTION_KEY`.** Это 32 случайных байта в base64, отдельные от `AUTH_SECRET`: утечка одного не даёт другого. Сгенерировать:

```bash
openssl rand -base64 32
# или, без openssl (Windows):
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Впишите ключ в окружение API (`apps/api/.env` или переменные сервера) и перезапустите API. Без ключа API работает, но SMTP в админке только для чтения, и страница объясняет, как получить ключ. В `pnpm dev` без ключа берётся учебный ключ из репозитория. Страница предупреждает, что пароль под ним защищён только для вида, поэтому настоящий пароль от почты в разработке не вводите. Учебный ключ и его варианты (пробелы, кавычки, регистр, base64url, его часть) вне учебного режима — ошибка конфига, как с учебным `AUTH_SECRET`.

Храните ключ отдельно от бэкапов базы: украденный бэкап без ключа не раскрывает пароль SMTP. **Если ключ потерян или сменился**, пароль SMTP в базе не расшифровать. API при этом работает, а почта выключается с причиной «введите пароль SMTP заново». Сброс пароля и приглашения честно говорят, что почта не работает. Достаточно ввести пароль SMTP на странице «Почта» и сохранить, и он зашифруется новым ключом. Других данных ключ не шифрует, так что больше ничего не теряется.

### Проверка: `pnpm mail:test`

```bash
pnpm mail:test --to anna@example.ru
```

Отправляет письмо «Проверка почты» напрямую, мимо очереди и базы, поэтому работает и при запущенном `pnpm dev`. Команда проверяет почту из окружения. SMTP, заданный в админке, она не видит (базу не открывает) и подсказывает проверить его кнопкой «Проверить подключение» на странице «Почта»: шаги там те же. Для SMTP команда идёт по шагам и печатает каждый: DNS (имя сервера находится), соединение (порт открыт), TLS (шифрование и сертификат), вход, отправка. Сломанный шаг отмечен «✗» с объяснением, что поправить, и ответом сервера; пароль не печатается. Например, отказ 5xx на `MAIL FROM` объясняется так: адрес отправителя должен принадлежать ящику, под которым идёт вход (у Яндекс 360 — совпадать с логином или быть его алиасом). Временный отказ 4xx (обычно лимит писем отправителя) — иначе: настройки менять не нужно, письма подождут в очереди. Если сервер принял соединение и сразу его закрыл или ответил не по SMTP, сломан шаг TLS с подсказкой проверить порт и шифрование, а не «файрвол». А если порт ждёт TLS сразу, а задан `starttls` (465 вместо 587), сломается шаг TLS с подсказкой `SMTP_SECURITY=tls`, а не «соединение». С файловым ящиком команда пишет, куда легло письмо. Почта выключена — объясняет, что задать, и выходит с кодом 1.

### Провайдер

Берём российского провайдера: в письмах о заявках есть персональные данные посетителей, а по 152-ФЗ их обработка должна идти на серверах в РФ. Для писем студии и небольших сайтов хватает **Яндекс 360 для бизнеса** (SMTP `smtp.yandex.ru`, порт 465, вход — адрес ящика и пароль приложения, а не пароль от аккаунта; `MAIL_FROM` — тот же адрес или его алиас). Если писем много или нужна статистика доставки — транзакционный сервис вроде **Unisender Go** (SMTP с логином и ключом из кабинета). Подойдёт любой провайдер с SMTP по TLS — главное, чтобы адрес `MAIL_FROM` был на домене, который этот провайдер подтвердил.

### SPF, DKIM и DMARC

Без этих трёх записей в DNS письма с домена уходят в спам, а сам домен легко подделать. Настраиваются один раз на домен отправителя (`example.ru` из `MAIL_FROM`), у домена студии и у доменов клиентов. Все три — TXT-записи у регистратора или в DNS-хостинге.

1. **SPF** — какие серверы вправе слать письма от домена. Одна TXT-запись на самом домене (`@`), строку даёт провайдер. Для Яндекс 360: `v=spf1 redirect=_spf.yandex.net`. Если писем шлют несколько сервисов, их `include:` собираются в **одну** запись: `v=spf1 include:<первый> include:<второй> ~all`. Вторая запись `v=spf1` ломает обе.
2. **DKIM** — подпись писем ключом домена. Ключ генерирует провайдер (в Яндекс 360 — «Почта → DKIM-подпись»), а в DNS кладётся открытая часть: TXT-запись `<селектор>._domainkey` (у Яндекса — `mail._domainkey`) со значением `v=DKIM1; k=rsa; p=…`. Длинное значение копируй целиком, как дал провайдер.
3. **DMARC** — что делать с письмами, которые не прошли SPF и DKIM, и куда слать отчёты. TXT-запись `_dmarc`: начни с наблюдения `v=DMARC1; p=none; rua=mailto:dmarc@example.ru`, через пару недель без чужих отправителей в отчётах ужесточи до `p=quarantine`, потом `p=reject`.

Как проверить:

- записи видны в DNS: `nslookup -type=TXT example.ru`, `nslookup -type=TXT mail._domainkey.example.ru`, `nslookup -type=TXT _dmarc.example.ru` (или `dig TXT … +short`). Новые записи расходятся от нескольких минут до суток;
- отправь себе `pnpm mail:test --to <твой ящик на Gmail или Яндексе>` и открой исходный текст письма («Показать оригинал» / «Свойства письма»): в заголовке `Authentication-Results` должно быть `spf=pass`, `dkim=pass` и `dmarc=pass`, а домен в `dkim` (`header.d=`) — тот же, что в `From`.

Все экраны, кроме входа и редактора, — в оболочке с боковой панелью (шаг 3.9): переключатель сайта, разделы сайта (Обзор, Страницы, Медиатека, Заявки со счётчиком новых, Настройки сайта), у владельца — блок «Установка» (Почта с состоянием, Состояние с версией), внизу — кто вошёл, его роль и «Выйти». Пунктов, которых роль не видит, нет. На телефоне панель — меню под верхней полосой (кнопка «Меню», Esc закрывает). Если сессия кончилась посреди работы (любой ответ 401), админка ведёт на вход и потом возвращает на тот же экран; несохранённые правки редактора защищает обычный вопрос перед уходом. То, что роли нельзя (публикацию, создание и удаление страниц для клиента), админка не показывает, но решает всё равно API.

У каждого экрана свой адрес и свой заголовок вкладки («Сайты — Averra CMS», «<сайт> — обзор — Averra CMS», «<сайт> — страницы — Averra CMS», «<страница> — редактор — Averra CMS»), поэтому обновление вкладки оставляет на месте, а ссылку можно сохранить. Кривой id сайта или адрес страницы в ссылке — экран «Сайт не найден» / «Страница не найдена». Из редактора назад ведёт «Назад к сайту» в его полосе (на обзор сайта), по остальным — боковая панель. Уйти из редактора с несохранёнными правками (по ссылке, кнопкой «Назад» браузера или закрыв вкладку) можно только после подтверждения.

**Редактор** — своя полноэкранная раскладка без боковой панели. В полосе сверху — название сайта, заголовок страницы (поле прямо в полосе) и плашка состояния: «Есть несохранённые правки», «Черновик сохранён · не опубликован», «Сохранено · правки не опубликованы» или «Опубликовано» — по тому, что отдаёт API. Слева — блоки страницы со счётчиком «3 из 50»: тип, подсказка содержимого (заголовок, число пунктов или полей формы), у выбранного — стрелки и «Удалить блок» (на узком экране — у каждого блока). «Добавить блок» открывает окно с каталогом: у каждого блока название, описание и пример, блок встаёт после выбранного. В центре — живой предпросмотр в рамке выбранной ширины (телефон 375, планшет 768, десктоп 1280 px, широкий ужимается масштабом); выбранный блок подсвечен рамкой, щелчок по блоку в предпросмотре выбирает его. Подсветка и выбор — только в iframe админки: на сайт ничего не попадает. Справа — поля блока: подпись, подсказка, ошибка, счётчик символов; варианты оформления — карточки с миниатюрами, короткий выбор — сегменты, длинный — список, ссылки — моноширинным, пункты списков — карточки. На экране уже 64rem колонки становятся вкладками «Блоки / Предпросмотр / Поля» (третья — «История», пока она открыта); выбор блока в списке открывает «Поля», а стрелки и «Удалить блок» на вкладке «Блоки» её не переключают. Полоса там компактнее: состояние — точкой и текстом вместо плашки, «История» — иконкой с подписью для диктора, кнопки меньше, переключатель ширины — над предпросмотром; на телефоне (уже 40rem) ещё и название сайта спрятано (рядом «Назад к сайту»), а заголовок сжимается с многоточием.

Блоки в списке слева и пункты списков в форме блока (например, «Пункты» у «Преимуществ») переставляются стрелками ↑↓ (у блока — когда он выбран) или перетаскиванием за ручку (значок перетаскивания `drag` из набора иконок) — мышью, пальцем или с клавиатуры: Tab до ручки, пробел или Enter поднимает, стрелки ↑↓ двигают, пробел, Enter или Tab ставит, Escape отменяет. Ручка подписана именем блока или пункта («Перетащить блок «Почему выбирают нас»»), а стрелка, которая на краю списка стала недоступной, передаёт фокус соседней. Экранный диктор по-русски говорит, что поднято и на какой оно позиции. Порядок меняется в черновике, когда блок поставлен, и сразу виден в предпросмотре; на сайт он попадает после сохранения и публикации, как любая правка. Перетаскивание сделано на dnd-kit (`@dnd-kit/core` и `@dnd-kit/sortable`), обёртка — `apps/admin/src/ui/SortableList.tsx`.

Поле «картинка» в форме блока — карточка: превью, имя файла, размеры и форматы («1600 × 1000 · AVIF, WebP, JPEG») и «Заменить» («Выбрать картинку», пока не выбрана). Она открывает медиатеку в модальном окне: там картинку выбирают или сразу загружают новую. Ниже — обязательное «Описание картинки (alt)» со счётчиком и «Убрать картинку». Предпросмотр показывает выбранную картинку теми же компонентами, что и сайт.

Маршруты — TanStack Router (`apps/admin/src/router.tsx`), загрузка и кеш данных — TanStack Query (`apps/admin/src/queries.ts`).

- **Проверки** в `pnpm check`: stylelint по `*.scss` (конфиг кита, `stylelint.config.mjs`), граница токенов (сырой цвет — HEX, функция цвета, именованный цвет, — `--palette-*` или примитив радиуса, тени, шкалы текста вне `packages/ui/src/foundation/tokens` и `packages/ui/src/themes` — ошибка; системные цвета (`Highlight`, `CanvasText`, устаревшие `WindowText`…) — только внутри `@media (forced-colors: active)`, иначе нарушение вида `system`; в админке нет ни одного `.css`, проверка идёт по всем стилям без исключений), компиляция всех `.scss`, объявлена ли каждая `var(--…)`, контраст темы (текст 4,5:1, границы полей и кольцо фокуса 3:1).

## Установка на сервер

У каждого клиента своя установка на его VPS (PLAN, решение 6): PostgreSQL, API и Caddy в Docker Compose. Caddy выпускает сертификаты сам, а «Опубликовать» собирает сайт прямо на сервере. Подробно, с решениями и чек-листом живой проверки, — [шаг 3.6](docs/steps/3.6-vps-install.md).

| `https://admin.<домен сайта>` | админка (статика) и API под `/api` на одном источнике: cookie без CORS |
| `deploy/Dockerfile` | образы `api` (API, обработчик очереди писем, сборщик сайта Astro; prod-зависимости, API — собранный JS без tsx, пользователь `node`) и `web` (Caddy + статика админки, пользователь `caddy`) |
| `deploy/compose.yaml` | `postgres` (том `postgres`), `api` (тома `sites` и `media`, наружу не открыт; `init`, без capabilities, `no-new-privileges`), `caddy` (80/443, из прав только `NET_BIND_SERVICE`, том `sites` только на чтение) |
| `deploy/install.sh` | установщик: проверки, `.env` с секретами, запуск, владелец и сайт, таймер бэкапов |
| `deploy/averra.sh` → `/opt/averra/averra.sh` | бэкапы, восстановление, обновление с откатом, состояние (см. ниже) |
| `deploy/src/fleet.ts` (`pnpm fleet`) | все установки студии по списку серверов: состояние и обновление |
| `/opt/averra/.env` | настройки и секреты установки (права 600). Ведёт установщик |

**Публикация на сервере.** «Опубликовать» (и удаление опубликованной страницы) ставит сборку сайта в очередь. Сборки идут по одной на всю установку. API запускает Astro отдельным процессом: `apps/renderer/scripts/build-release.mjs`, с ограничением памяти и таймаутом, без секретов API в окружении. Сборка идёт в новую папку `PUBLISH_DIR/<сайт>/releases/<версия>`. В неё же ложатся файлы картинок опубликованных страниц — тех, что выбраны в блоках, а не встретились путём `/media/…` в тексте (из прежней версии — жёсткой ссылкой), а неиспользуемые файлы Astro (`_astro/*.js` островов) убираются. Потом ссылка `current` атомарно переключается на новую папку, и Caddy со следующего запроса отдаёт новую версию, без простоя и перезапуска. Хранятся 5 последних версий. Упала сборка — на сайте прежняя версия, обзор сайта в админке говорит об этом, а «Настройки сайта» показывают причину и «Собрать заново». Журнал сборок — таблица `site_builds`. После перезапуска API прерванные сборки и опубликованные сайты без собранной версии собираются заново.

Переменные API для сервера (все в `apps/api/.env.example`; в установке их задаёт `compose.yaml`):

| Переменная | Что задаёт |
|---|---|
| `DATABASE_URL` | PostgreSQL: `postgres://пользователь:пароль@хост:5432/база` (драйвер node-postgres, пул 5 соединений). Не задан — встроенный PGlite в `PGLITE_DIR` |
| `PUBLISH_DIR` | папка собранных сайтов. Задана — публикация собирает сайт на сервере; не задана (`pnpm dev`) — только меняет базу |
| `PUBLISH_KEEP_RELEASES` | сколько версий сайта хранить, по умолчанию 5 (текущая не удаляется) |
| `PUBLISH_TIMEOUT_SECONDS` | сколько ждать сборку, по умолчанию 300 |
| `PUBLISH_MAX_MEMORY_MB` | предел кучи процесса сборки, по умолчанию 768. Замер демо-сайта — около 300–350 МБ RSS |
| `RENDERER_DIR` | папка пакета рендерера, по умолчанию `apps/renderer` рядом с API |
| `AVERRA_VERSION` | версия установки; в образ её кладёт сборка релиза (`ARG AVERRA_VERSION`), без неё — `dev` |
| `STATE_DIR` | папка состояния установки (итоги бэкапов и обновлений от `averra.sh`), в контейнере — `/data/state` только на чтение. Не задана — бэкапов нет (разработка) |

### Установка

На сервере нужны Ubuntu (22.04 или 24.04), root (`sudo`) и два DNS-имени: A-записи домена сайта и `admin.<домен>` на IP сервера, а AAAA — только на IPv6 сервера или никаких (их проверяет установщик). Порты 80 и 443 должны быть свободны.

```bash
# с машины студии: только установщик и конфигурация (не всю папку deploy)
ssh root@vps mkdir -p /root/averra-deploy
scp deploy/install.sh deploy/averra.sh deploy/compose.yaml root@vps:/root/averra-deploy/
# на сервере
cd /root/averra-deploy
sudo bash install.sh --site-domain remont.ru --email studio@averra.ru --version 0.6.0 \
  --ghcr-user <логин GitHub>
```

- Токен GHCR (только `read:packages`) установщик спросит скрыто, как и пароль владельца: в историю команд и в список процессов он не попадает. Без терминала — переменной окружения, не набирая значение в командной строке: `read -rs GHCR_TOKEN; export GHCR_TOKEN; sudo -E bash install.sh … --ghcr-user <логин>`.
- Пароль владельца установщик спросит скрыто. Без терминала его можно передать переменной `AVERRA_OWNER_PASSWORD`, но не аргументом.
- Нет Docker — `--install-docker` поставит пакеты Ubuntu `docker.io` и `docker-compose-v2`.
- Сервер за NAT (публичного IP нет на интерфейсе) — `--public-ip <IP>`. DNS ещё не разошёлся — `--skip-dns-check`, но тогда Caddy не получит сертификат, пока DNS не заработает.
- `--dry-run` показывает план и проходит проверки только на чтение (права на папку, Docker, порты, DNS): выводит все проблемы сразу и выходит с кодом 1, если они есть. Ничего не меняет. Без прав на `/opt/averra` установщик сразу просит запустить его через `sudo`. `--env-only` только пишет `/opt/averra/.env` и `compose.yaml`. Все флаги — `bash install.sh --help`.
- На сервер копируются только эти три файла — всё, что берёт установщик. Папка `deploy/` на машине студии — пакет рабочей области: в ней `node_modules` со ссылками на typescript, vitest и Node машины разработчика (`scp -r` идёт по ссылкам — около 120 МБ инструментов разработки), тесты, а бывает и список серверов студии, если его положили туда вопреки «Несколько установок». У клиента на сервере root.
- У домена не должно быть A- или AAAA-записей на чужие адреса: Let's Encrypt проверяет каждый адрес, IPv6 — первым, и лишняя AAAA-запись от панели регистратора сорвёт выпуск сертификата. Установщик требует, чтобы все записи вели на сервер (у сервера с IPv4 и IPv6 за NAT — `--public-ip` на каждый адрес).
- Повторный запуск безопасен: секреты (`AUTH_SECRET`, `MAIL_ENCRYPTION_KEY`, пароль Postgres, `BACKUP_PASSPHRASE` — пароль шифрования копий бэкапов) не перегенерируются, владелец и сайт второй раз не создаются. Новые домены, почта или версия из флагов записываются в `.env` и применяются.
- После установки задайте SMTP на странице «Почта» в админке. Пароль SMTP шифруется `MAIL_ENCRYPTION_KEY` из `.env`, храните `.env` отдельно от бэкапов базы. Если SMTP нужен из окружения, его задаёт `compose.override.yaml` рядом с `compose.yaml` (`services.api.environment: SMTP_HOST…`): compose подхватит его сам.

Учебного режима на сервере нет: API в образе запускается без `--dev` и с `NODE_ENV=production`.

Управление — из `/opt/averra`: `docker compose ps`, `docker compose logs -f api`, `docker compose exec api node dist/server/user-password.js --email …`. Команды терминала на сервере запускаются как `node dist/server/<команда>.js`.

### Образы и версии

Образы собирает GitHub Actions (`.github/workflows/release.yml`, сторонние actions закреплены по SHA) для версии `vX.Y.Z`: сначала `pnpm check`, потом `ghcr.io/midhey/averra-api:X.Y.Z` и `ghcr.io/midhey/averra-web:X.Y.Z` под amd64 и arm64. Пакет GHCR по умолчанию закрыт, даже у открытого репозитория, поэтому на сервере нужен токен GitHub только с `read:packages`. Docker хранит его в `/root/.docker/config.json` (base64, это не шифр), поэтому токен — только на чтение пакетов. Почему GHCR, а не сборка на месте, — в шаге 3.6. Собрать образы руками:

```bash
docker build -f deploy/Dockerfile --target api -t ghcr.io/midhey/averra-api:0.6.0 .
docker build -f deploy/Dockerfile --target web -t ghcr.io/midhey/averra-web:0.6.0 .
```

`pnpm check` на Linux идёт и на каждый push в master и pull request (`.github/workflows/ci.yml`).

**Как выходит версия.** Версию и `CHANGELOG.md` ведёт release-please (`.github/workflows/release-please.yml`) по сообщениям коммитов: после каждого пуша в master он открывает или обновляет pull request «chore: release X.Y.Z» со списком изменений. Пока версия ниже 1.0: `fix` — патч, `feat` и ломающие изменения (`feat!`, `BREAKING CHANGE`) — минорная. `docs`, `test`, `chore` и `refactor` версию не поднимают и в список не попадают. Влили этот pull request — release-please ставит тег `vX.Y.Z`, делает релиз на GitHub и в том же запуске вызывает `release.yml`: проверки и образы. Первая версия — 0.1.0; другую задаёт строка `Release-As: X.Y.Z` в теле коммита. Теги руками не ставим. Пересобрать образы уже выпущенной версии (например, если сборка упала) — Actions → release → Run workflow с её тегом.

Release-please работает со встроенным `GITHUB_TOKEN`, поэтому:

- один раз в настройках репозитория: Settings → Actions → General → «Allow GitHub Actions to create and approve pull requests»;
- на pull request релиза `ci.yml` сам не запускается (GitHub не запускает workflow на события от `GITHUB_TOKEN`). Проверки всё равно идут: `pnpm check` — в `release.yml` перед образами, и `ci.yml` — после вливания в master;
- `release.yml` не ждёт пуша тега: тег от `GITHUB_TOKEN` его бы и не запустил. Его вызывает `release-please.yml` напрямую (`workflow_call`), личный токен (PAT) не нужен.

Кеш в Caddy: страницы сайта и `index.html` админки (вместе с её экранами `/sites/…`) — `no-cache`. Файлы с хешем в имени (`/_astro/*` сайта, `/assets/*` админки) и картинки `/media/<uuid>/…` кешируются на год (`immutable`). Нет файла `/assets/…` админки — 404, а не `index.html`.

Прод-сборка API без Docker: `pnpm --filter @averra/api build`, запуск — `node --enable-source-maps apps/api/dist/server/index.js` (или `pnpm --filter @averra/api start:prod`).

Версия установки — в образе API (`AVERRA_VERSION`, её передаёт `release.yml` из тега версии). Её видно владельцу в боковой панели и на экране «Состояние установки» и в `averra.sh status`. В открытых маршрутах (`/api/health*`) версии нет.

### Управление установкой: `averra.sh`

Установщик кладёт рядом с `.env` скрипт `/opt/averra/averra.sh` (только root) и папки `backups` (700) и `state` (её читает API, только на чтение). Подробно, с решениями и чек-листом живой проверки, — [шаг 3.7](docs/steps/3.7-updates-backups.md).

| Команда (от root) | Что делает |
|---|---|
| `averra.sh backup` | бэкап базы и медиа с проверкой восстановлением |
| `averra.sh backups` | список бэкапов |
| `averra.sh verify <бэкап>` | проверить бэкап ещё раз: контрольные суммы, восстановление дампа во временную базу |
| `averra.sh restore <бэкап> [--yes]` | восстановить; `--from-s3` — из внешнего хранилища |
| `averra.sh update --version X [--yes]` | обновить с бэкапом и откатом |
| `averra.sh status [--json]` | состояние установки (то же, что блок в админке) |

Бэкап, восстановление и обновление не идут одновременно: у них общий замок (`flock`).

### Обновление

```bash
sudo /opt/averra/averra.sh update --version 0.7.0
```

**Обрыв SSH не страшен.** Обновление идёт отдельным процессом на сервере (служба systemd `averra-update-<время>`, без systemd — `setsid`), а команда только показывает его лог (`/opt/averra/update.log`; лог дописывается, прошлые запуски — выше черты `==== …`, больше мегабайта — в `update.log.1`). Пока идёт бэкап или восстановление, `update` сразу отказывает и ничего не трогает. Обрыв связи, закрытый терминал или Ctrl+C прерывают показ, а не обновление: оно доходит до «Готово» или до отката. Посмотреть, чем кончилось: `tail /opt/averra/update.log`, `averra.sh status` или «Состояние установки». Повтор той же команды, пока обновление идёт, показывает его лог. Если процесс всё же оборвался (перезагрузка сервера), повторите `averra.sh update --version <та же>`: он не ответит «уже версия», а **доведёт прерванное** — проверит новую версию и закончит обновление или откатит (с восстановлением базы, если миграции прошли). Пока обновление не закончено, в «Состоянии» итог «идёт»; дольше часа — проблема «похоже, оборвалось». Код выхода 3 — процесс оборвался без итога.

**Установка шага 3.6 (до `averra.sh`).** В ней нет `averra.sh`, папок `backups` и `state` и таймера бэкапов, поэтому первый переход — повторным запуском установщика новой версии: скопируйте `install.sh`, `averra.sh` и `compose.yaml` из новой версии репозитория (как в «Установке») и запустите `install.sh` с теми же флагами и `--version <новая>`. Повторный запуск безопасен (секреты, владелец и сайт сохраняются), он доставит `averra.sh`, папки, `BACKUP_PASSPHRASE` и таймер и поднимет новую версию. Бэкапа перед этим переходом скрипт не делает — снимите его руками (`docker compose exec -T postgres pg_dump -U averra -d averra -Fc > /root/averra-before.dump`). Дальше — `averra.sh update`.

1. Скачивает образы новой версии, пока всё работает. Не скачались — выход, ничего не менялось.
2. Берёт из образа API `compose.yaml` и `averra.sh` этой версии: конфигурация установки обновляется вместе с версией.
3. Останавливает API и делает бэкап с проверкой (`…-pre-update`). С этой минуты заявки и правки не принимаются (сайт открыт), поэтому бэкап — последнее состояние базы. Не удался — прежний API снова запускается, выход, ничего не менялось. Копия во внешнее хранилище выгружается в конце, когда сервис снова работает.
4. Записывает `AVERRA_VERSION` в `.env` (прежняя — `AVERRA_PREVIOUS_VERSION`, прежний `compose.yaml` — `compose.yaml.prev`) и поднимает новый API: миграции он применяет сам при старте.
5. Ждёт `/api/health/ready` (до 180 с; больше — переменной окружения процесса, не `.env`: `sudo AVERRA_READY_TIMEOUT=300 /opt/averra/averra.sh update …`). Готов — поднимает Caddy с новой админкой и проверяет, что API и Caddy держатся в `running` (`docker compose ps`, дважды с паузой: Caddy с ошибкой в конфигурации перезапускается по кругу). Всё работает — ставит новый `averra.sh`, итог «обновлено».
6. Не готово — откат: сначала останавливается новый API (чтобы он не применил миграции после подсчёта), прежние `.env` и `compose.yaml`; если миграции успели примениться (число строк в `drizzle.__drizzle_migrations` выросло), база восстанавливается из бэкапа шага 3. **Рабочая база при этом не удаляется**, а переименовывается в `averra_rolled_back_<время UTC>`: в ней то, что новая версия успела принять (заявки). Скрипт пишет её имя, оно же — в `state/update-last.json` и в «Состоянии установки». Посмотреть: `docker compose exec postgres psql -U averra -d averra_rolled_back_…`; удаляется сама вместе со старыми бэкапами через `BACKUP_KEEP` дней. Прежний API поднимается и проверяется. Код выхода 1 — «откатились», 2 — «откат не удался, нужен человек» (подсказка, какой бэкап восстанавливать), 3 — процесс обновления оборвался (повторите команду).

Итог пишется в `state/update-last.json` и виден в «Состоянии установки». Сайт посетители видят всё время (его отдаёт Caddy), админка и приём заявок недоступны от остановки API перед бэкапом до готовности нового (бэкап лендинга с проверкой — секунды, плюс старт API). Миграции только совместимые вперёд (CONVENTIONS, «База»): прежний образ работает на базе после миграций новой версии — это нужно, если при откате база не восстановилась или прежний образ поднимают руками. Проверяет тест `apps/api/src/db/migrations-compat.test.ts` (удаления, переименования, смена типа, `NOT NULL`, новые ограничения, удаление индексов и ограничений).

### Бэкапы и восстановление

**Что и где.** Бэкап — папка `/opt/averra/backups/<время UTC>-<вид>/`: `db.dump` (`pg_dump -Fc`), `media.tar.gz` (медиатека; снимается отдельным контейнером с томом, поэтому бэкап идёт и при лежащем API), `SHA256SUMS` и `manifest.json`. Опубликованные сайты не бэкапятся: API собирает их заново из базы и медиатеки. Служебные папки восстановления в томе медиатеки (`media/.averra-*`) в архив не попадают. Папка — только root, файлы — 600. `.env` в бэкап не входит: храните его (или хотя бы `BACKUP_PASSPHRASE`) отдельно.

**Расписание.** Таймер systemd `averra-backup.timer` — каждый день около 03:30, пропущенный (сервер был выключен) делается при старте. Журнал: `journalctl -u averra-backup`. Руками — `averra.sh backup`.

**Проверка.** Каждый бэкап восстанавливается во временную базу `averra_verify` (`pg_restore --exit-on-error`), число миграций и таблиц сверяется с рабочей базой, архив медиа читается целиком. Не прошёл — бэкап считается неудачным, файлы удаляются, «Состояние установки» показывает причину.

**Сколько хранить.** `BACKUP_KEEP` в `.env` (по умолчанию 7, от 1 до 365): столько последних удачных бэкапов и **не старше стольких дней** — локально и во внешнем хранилище. Чистка идёт после каждого бэкапа, удачного и неудачного: если бэкапы падают, старые копии всё равно уходят по сроку (и через 48 часов без удачного бэкапа «Состояние» тревожит). Кривой `BACKUP_KEEP` — бэкап не делается, причина сразу видна в «Состоянии установки». Не удалось почистить внешнее хранилище (нет права на удаление, хранилище не ответило) — «Состояние» говорит, что срок хранения там нарушается.

**Внешнее хранилище** (по желанию) — S3-совместимое, например Yandex Object Storage. Строки в `/opt/averra/.env`:

```bash
BACKUP_S3_BUCKET=studio-backups
BACKUP_S3_ACCESS_KEY_ID=…            # сервисный аккаунт с правом записи только в этот бакет
BACKUP_S3_SECRET_ACCESS_KEY=…
# необязательно:
BACKUP_S3_ENDPOINT=https://storage.yandexcloud.net   # по умолчанию
BACKUP_S3_REGION=ru-central1                         # по умолчанию
BACKUP_S3_PREFIX=averra/remont.ru                    # по умолчанию averra/<домен сайта>
BACKUP_KEEP=7
```

Копия выгружается образом `rclone/rclone:1.75.2` и **шифруется** (crypt rclone: XSalsa20 + Poly1305, имена файлов тоже) паролем `BACKUP_PASSPHRASE` — его создаёт установщик. Ключи и пароль уходят в контейнер переменными окружения, не аргументами. **Сохраните `BACKUP_PASSPHRASE` в менеджере паролей студии**: без него копию не расшифровать, если сервер пропадёт вместе с `.env`. Ключу нужны права на запись, список и удаление (`storage.editor` в Yandex Object Storage): без удаления не соблюсти срок хранения. Второй страховкой поставьте в бакете правило жизненного цикла «удалять объекты старше `BACKUP_KEEP` + 2 дней». Не выгрузилось — локальный бэкап всё равно удачный, а «Состояние установки» пишет, что копии нет.

**Восстановление.**

```bash
sudo /opt/averra/averra.sh backups                       # что есть
sudo /opt/averra/averra.sh restore 20261016-033512-scheduled
sudo /opt/averra/averra.sh restore --from-s3 20261016-033512-scheduled   # сервер новый
```

Сверяются контрольные суммы, дамп восстанавливается сначала в отдельную базу `averra_restore` — не встал, рабочая база не тронута. Медиатека из бэкапа сначала распаковывается во временную папку на своём томе — рабочая пока не тронута. Потом API останавливается, базы меняются именами (прежняя — `averra_before_restore`; если такая база — или папка `.averra-before-restore` в томе медиатеки — уже есть от прошлого неразобранного восстановления, скрипт откажет и ничего не удалит; не встала восстановленная — прежняя возвращается на место). Пока API стоит, медиатека подменяется распакованной (прежняя отходит в папку `.averra-before-restore` на том же томе — переименованием, без копирования) и очищается том сайтов. Только потом API поднимается: при старте он сам собирает опубликованные сайты заново — уже из восстановленных базы **и** медиатеки (на новом сервере медиатека до подмены пуста, и сборка без картинок упала бы). Поднялся — прежние медиатека и база (`averra_before_restore`) удаляются. Медиатека не подменилась или API не поднялся — прежние база, медиатека и `SITE_ID` возвращаются на место, а неподнявшаяся база остаётся как `averra_failed_restore_<время UTC>` (в ней данные бэкапа: её видно в «Состоянии установки», удаляется сама через `BACKUP_KEEP` дней). Всё, что изменилось после бэкапа, пропадает, поэтому скрипт спрашивает подтверждение (`--yes` — без вопроса). На новом сервере: `install.sh`, потом в `.env` впишите прежние `BACKUP_PASSPHRASE` (без него копию не расшифровать) и `BACKUP_S3_*`, потом `restore --from-s3`. Остальные секреты могут быть новыми, но с оговорками: новый `AUTH_SECRET` просто выкинет всех из админки (войти заново), а с новым **`MAIL_ENCRYPTION_KEY`** сохранённый в базе пароль SMTP не расшифруется — почта выключится с причиной «введите пароль SMTP заново». Либо перенесите прежний `MAIL_ENCRYPTION_KEY` в `.env` до восстановления (поэтому `.env` стоит хранить у студии целиком, отдельно от бэкапов), либо введите пароль SMTP на странице «Почта» после. `SITE_ID` (какой сайт Caddy отдаёт на домене) скрипт берёт из манифеста бэкапа сам.

**Персональные данные (152-ФЗ).** В дампе заявки посетителей и адреса пользователей админки. Бэкапы живут конечный срок — не дольше `BACKUP_KEEP` дней (чистка по возрасту после каждого бэкапа по таймеру, удачного или нет), — поэтому удалённая в базе заявка (руками или по сроку сайта) исчезает и из бэкапов не позже чем через `BACKUP_KEEP` дней, плюс сутки до следующего запуска таймера. То же — у служебных баз `averra_rolled_back_…` (откат обновления) и `averra_failed_restore_…` (восстановление, на котором не поднялся API); пока они лежат, их показывает «Состояние установки». `averra_before_restore` (прежняя рабочая база, которую восстановление не смогло вернуть на место) по сроку не удаляется — это рабочие данные, «Состояние» просит разобрать её руками. Условия: таймер работает (сервер включён), внешнее хранилище даёт удалять, обновление не брошено оборванным — его бэкап `pre-update` и отложенная база хранятся, пока `averra.sh update` его не доведёт (видно как `update_interrupted`), и база `averra` на месте — если откат обновления кончился неудачей и рабочие данные лежат под служебным именем, служебные базы по сроку не удаляются, пока рабочую не вернут. Всё это видно в «Состоянии установки». В политике обработки персональных данных клиента срок хранения заявок указывайте как «срок сайта + `BACKUP_KEEP` дней» (по умолчанию 180 + 7). Внешнее хранилище для клиентов из РФ — в РФ (Yandex Object Storage), копия зашифрована ключом, которого у хранилища нет.

### Несколько установок

Студия обслуживает установки по списку серверов с машины разработчика (нужен SSH-ключ, у которого есть root или `sudo` без пароля на `/opt/averra/averra.sh`):

```bash
mkdir -p ~/.config/averra
cp deploy/servers.example.txt ~/.config/averra/servers.txt   # вне репозитория
pnpm fleet status                                   # таблица: версия, база, бэкап, почта, проблемы
pnpm fleet update --version 0.7.0                   # по очереди, первая ошибка — стоп
pnpm fleet update --version 0.7.0 --only remont     # только эти серверы
```

Список — `~/.config/averra/servers.txt` (другой — `--file <путь>`, относительный от папки, где запущен `pnpm`, или переменная `AVERRA_SERVERS`). **Не кладите его в `deploy/`**: файлы оттуда уезжают на серверы клиентов, а список раскрыл бы клиенту адреса остальных установок. На случай ошибки `servers.txt` есть в `.gitignore` и `.dockerignore`. Строка списка: `<имя> <пользователь@хост> [port=<порт>] [dir=<папка установки>]`. SSH только по ключам (`BatchMode=yes`): пароль не спрашивается, неизвестный ключ хоста — отказ. Поэтому первый вход на новый сервер — руками (`ssh root@…`), со сверкой отпечатка. `status` выходит с кодом 1, если где-то проблема или сервер не ответил; `update` пишет, что обновлено, где сломалось и что не трогали. Обрыв SSH или Ctrl+C посреди `pnpm fleet update` не бросает сервер на полпути: обновление на нём идёт отдельно от SSH и доработает само; итог — `pnpm fleet status`, повтор `pnpm fleet update` покажет ход идущего обновления или доведёт оборвавшееся. Состояние студия получает по SSH (`averra.sh status --json`), а не токеном по HTTPS: в интернет ничего нового не открыто, и работает, даже когда API лежит.

### Выгрузка: клиент не заложник

В «Настройках сайта», раздел «Выгрузка»: «Скачать сайт архивом» — ZIP готового сайта (HTML, CSS, картинки), который отдаст любой веб-сервер; «Выгрузить все данные» (владелец и клиент) — ZIP с `site.json` (страницы с историей, тема, медиатека, заявки), оригиналами картинок и описанием формата. В данных — персональные данные посетителей: обращаться с выгрузкой как с заявками.

## Сквозные тесты (e2e)

Пакет `e2e/` гоняет сценарии админки в настоящем браузере: сайты и страницы → правка в форме → предпросмотр → сохранение → публикация → опубликованный сайт. Один раз поставь браузер (только Chromium, около 120 МБ в общий кеш Playwright):

```bash
pnpm --filter @averra/e2e exec playwright install chromium
```

Запуск:

```bash
pnpm e2e                        # все тесты
pnpm e2e --shuffle              # в случайном порядке: тесты не должны зависеть друг от друга
pnpm e2e tests/editor.spec.ts   # один файл
pnpm e2e --headed               # с видимым окном браузера
```

Playwright сам поднимает свои копии API, админки и рендерера и гасит их в конце. Порты свои, чтобы не мешать `pnpm dev`:

| Что | Адрес в e2e |
|---|---|
| API | http://localhost:4100 |
| Админка | http://localhost:5273 |
| Рендерер | http://localhost:4421 |
| Тестовый SMTP | 127.0.0.1:2587 (только на время `tests/smtp-settings.spec.ts`) |

Запущенный рядом `pnpm dev` не мешает, и наоборот: рендерер e2e стартует с `astro dev --ignore-lock` и не берёт файл-замок Astro (`apps/renderer/.astro/dev.json`; брошенный замок от упавшего сервера он может удалить), по которому Astro не даёт поднять второй dev-сервер в том же проекте. Если какой-то из этих портов занят, прогон сразу падает: тесты не пойдут по чужому серверу. База, картинки и файловый ящик почты e2e лежат в `e2e/.data` и стираются перед каждым прогоном, база разработки в `apps/api/.data` не трогается. Перед каждым тестом демо-сайт возвращается в исходное состояние через API: главная — демо, страницы, созданные другими тестами, удаляются. Сайты, которые создают тесты, остаются до следующего прогона, поэтому у каждого своё название.

Админка e2e закрыта входом, как и настоящая. API e2e при старте создаёт владельца с учебными данными из `e2e/urls.ts` (`e2eOwner`). Проект `setup` входит им один раз и сохраняет cookie в `e2e/.data/owner.json`: остальные тесты стартуют уже вошедшими, а фикстура ходит в API с той же cookie. Вход, выход и лимит попыток проверяет `tests/auth.spec.ts` в браузере без сохранённой сессии. Письма тесты читают из файлового ящика e2e (`tests/mailbox.ts`): так приглашение и сброс пароля проходят целиком, а участника заводит приглашение, а не команда. Рендерер e2e собирает демо-сайт по его постоянному id.

API e2e запущен с `PUBLISH_DIR=e2e/.data/sites`, как на сервере: публикация собирает демо-сайт настоящим Astro в папку версии (`tests/server-build.spec.ts`). Рендерер e2e по-прежнему `astro dev` и показывает сайт из API.

Форма заявки (`tests/forms.spec.ts`) проверяется как у посетителя: свой контекст браузера с выключенным JavaScript (`javaScriptEnabled: false`) и без входа отправляет форму на сайте рендерера. Тест видит «Спасибо» по якорю, заявку в админке и письма в файловом ящике, а кнопка «Скачать CSV» скачивает файл с заявкой из потокового ответа API. У каждого такого посетителя свой `X-Forwarded-For`, поэтому лимит заявок с одного IP тесты между собой не делят.

Настройки SMTP в админке (`tests/smtp-settings.spec.ts`) проверяются с настоящим тестовым SMTP-сервером. Настройки пускают только порты 465 и 587, а порт ниже 1024 на Linux без root не занять. Поэтому сервер слушает свой порт `127.0.0.1:2587`, в форме стоит 587, а API e2e подключается к тестовому серверу через `DEV_SMTP_CONNECT_PORT`. Эту переменную API принимает только в учебном режиме, вне его конфиг не стартует. Сертификат у сервера — от своего CA. Его создаёт `scripts/smtp-certs.ts` перед стартом API, а API e2e доверяет ему через стандартную переменную Node `NODE_EXTRA_CA_CERTS`: она добавляет корневой сертификат, проверку не снимает. В конце тест удаляет настройки SMTP, и остальные тесты снова пишут в файловый ящик.

Упавший тест оставляет трассу в `e2e/test-results`, а сводный отчёт лежит в `e2e/playwright-report` (`pnpm --filter @averra/e2e exec playwright show-report`). В конце прогона в логе бывает строка `[API] … Command failed`: это Playwright гасит сервер API, на Windows иначе не умеет.

`pnpm check` e2e не запускает: он должен оставаться быстрым. Перед коммитом, который меняет админку, API или рендерер, гоняй и `pnpm e2e`.

## MCP

`apps/mcp` — MCP-сервер, через который нейронка собирает лендинги. Инструменты: `list_blocks`, `list_sites`, `get_page`, `save_draft` и `publish_page`. Входные схемы инструментов — те же Zod-схемы, что проверяют страницы в API, поэтому кривой блок не пройдёт ни там, ни там. Форму заявки нейронка ставит, как любой блок (`list_blocks` отдаёт её схему и пример), а заявки с неё через MCP не прочитать: в них персональные данные, и токену API они закрыты.

Сервер описан в `.mcp.json` и запускается на закреплённой в проекте Node (`node_modules/.bin/node.exe`, путь под Windows). MCP — обычный клиент API и входит токеном с правами редактора на одном сайте. Настройка:

1. Останови `pnpm dev` (команде нужна база) и выпусти токен: `pnpm token:create --site <id сайта> --name mcp`. Токен показывается один раз.
2. Скопируй `apps/mcp/.env.example` в `apps/mcp/.env` (он в `.gitignore`) и вставь строку `CMS_API_TOKEN=…` из вывода команды.
3. Запусти `pnpm dev`, открой новую сессию Claude Code в папке проекта и разреши сервер `averra`. Если сервер уже был запущен, перезапусти его: токен читается при старте.

Без токена сервер всё равно стартует: `list_blocks` работает, а остальные инструменты отвечают, как получить токен. `list_sites` показывает только сайт токена. Отозвать токен — `pnpm token:revoke --id <id>`; после этого MCP получит понятную ошибку «API не принял токен».

Astro по умолчанию отправляет анонимную телеметрию. Отключить её: `pnpm --filter @averra/renderer exec astro telemetry disable`.

## Документация

Сайт документации — `apps/docs` на Astro Starlight, выкладывается на https://midhey.github.io/averra-cms/. Страницы — Markdown в `apps/docs/src/content/docs`, язык по умолчанию русский. Поиск работает только в собранном сайте: `pnpm docs:build`, потом `pnpm --filter @averra/docs preview`.

- Ссылки между страницами пишем от корня сайта вместе с `/averra-cms/` (`[Установка](/averra-cms/install/)`). Битая ссылка или якорь роняет сборку. Сборка входит в `pnpm check`: битую документацию не пускает в master локальный `pnpm check` перед коммитом (пушим прямо в master, CI проверяет уже после пуша).
- Выкладка — `.github/workflows/docs.yml`: при пуше в master с изменениями в `apps/docs` и вручную (Actions → docs → Run workflow). Workflow собирает сайт сам, с той же проверкой ссылок, поэтому битый сайт на Pages не уедет, даже если попал в master. Один раз в настройках репозитория: Settings → Pages → Source — GitHub Actions.
- Английский добавится папкой `src/content/docs/en` и строкой в `locales` в `astro.config.mjs`: русские страницы и их адреса не меняются.
