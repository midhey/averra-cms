# CMS для лендингов

Своя система для быстрых и аккуратных лендингов. Что и зачем — в [PLAN.md](PLAN.md), правила кода — в [CONVENTIONS.md](CONVENTIONS.md).

## Запуск

Нужен pnpm 12. Ставить Node под проект не нужно: версия закреплена в `package.json` (`devEngines.runtime`, Node 24 LTS). pnpm скачает её при установке и запускает все скрипты на ней, какая бы Node ни стояла глобально и что бы ни было в PATH. Чтобы запустить сам pnpm, подойдёт любая Node ≥ 18 с corepack: `corepack pnpm …`.

```bash
pnpm install
pnpm dev
```

| Что | Адрес |
|---|---|
| API | http://localhost:4000/api/health |
| Админка | http://localhost:5173 |
| Рендерер | http://localhost:4321 |

### Первый запуск: владелец и сайт для рендерера

Админка и API закрыты входом, регистрации нет. Перед первым входом нужен владелец — выбери один способ:

- **Для разработки:** скопируй `apps/api/.env.example` в `apps/api/.env`. Если в базе ещё нет пользователей, API при старте создаст владельца из `DEV_OWNER_EMAIL` / `DEV_OWNER_PASSWORD` (в примере — учебные значения, только для разработки; вне `NODE_ENV=development` это не работает).
- **Командой** (так же и в проде): `pnpm user:create --email anna@example.ru --name "Анна"`. Пароль команда спросит скрыто, дважды, или возьмёт из переменной `CMS_USER_PASSWORD`. Он не печатается и не попадает в аргументы и логи.

Рендерер собирает один сайт, и его id надо задать: скопируй `apps/renderer/.env.example` в `apps/renderer/.env` и впиши `CMS_SITE_ID` (id виден в адресе админки `/sites/<id>`; у демо-сайта свежей базы он всегда `d0000000-0000-4000-8000-000000000001`). Раньше рендерер брал первый сайт из API, но список сайтов теперь виден только после входа, а снимок сайта открыт и берётся по id.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm dev` | поднимает API, админку и рендерер |
| `pnpm check` | линтер, типы и тесты — всё, что нужно перед коммитом |
| `pnpm e2e` | сквозные тесты в браузере (Playwright), см. ниже |
| `pnpm build` | собирает админку и рендерер |
| `pnpm typecheck` | проверяет типы во всех пакетах |
| `pnpm test` | запускает тесты во всех пакетах |
| `pnpm lint` | проверяет линтером и форматтером |
| `pnpm format` | то же, но сразу исправляет |
| `pnpm db:generate` | создаёт миграцию по изменениям в `apps/api/src/db/schema.ts` |
| `pnpm user:create --email … --name … [--role owner\|member]` | создаёт пользователя админки (по умолчанию владельца); пароль — скрытым вводом или из `CMS_USER_PASSWORD` |
| `pnpm member:add --email … --site <id> --role editor\|client` | даёт участнику доступ к сайту (повторный вызов меняет роль) |
| `pnpm token:create --site <id> --name … [--by <почта>]` | выпускает токен API для MCP и показывает его один раз |
| `pnpm token:list` | токены: сайт, кто выпустил, когда пользовались, отозван ли (без самих токенов) |
| `pnpm token:revoke --id <id>` | отзывает токен |

Команды — это скрипты корневого `package.json`, он работает вместо Makefile. pnpm заодно стоит в проекте как dev-зависимость, чтобы скрипты могли вызывать его сами, даже если глобально pnpm не установлен.

Команды пользователей и токенов открывают базу напрямую. Встроенная база (PGlite) не выдерживает два процесса сразу, поэтому, пока запущен `pnpm dev`, они откажутся работать и попросят его остановить: API и команды берут файл-замок рядом с базой (`apps/api/.data/pglite.lock`). Замок от упавшего процесса снимается сам.

## Вход и права

Вход — по почте и паролю (Better Auth), сессия живёт в httpOnly-cookie (`SameSite=Lax`, в проде ещё и `Secure`). Попыток входа — не больше трёх за 10 секунд с одного IP, дальше 429 «Слишком много попыток».

| Роль | Что может |
|---|---|
| владелец (`owner`) | всё: все сайты, создание сайтов |
| редактор (`editor`) на сайте | читать, править, публиковать, создавать и удалять страницы своих сайтов |
| клиент (`client`) на сайте | читать и править черновики существующих страниц своего сайта; публиковать, создавать и удалять — нет |
| токен API | как редактор, но на одном сайте |

Глобальная роль пользователя — `owner` или `member`; участнику доступ к сайту даёт `pnpm member:add`. Чужой сайт для участника выглядит как несуществующий (404), а не «запрещено» (403): так не видно, что он вообще есть.

Переменные API для входа (`apps/api/.env`, все описаны в `.env.example`): `AUTH_SECRET` (подпись cookie; в проде обязателен, от 32 символов), `ADMIN_URL` (адрес админки: только с него принимаются запросы с cookie; в проде обязателен), `API_URL` (адрес API снаружи; в проде обязателен), `TRUST_PROXY=true` — если перед API стоит прокси, который сам ставит `X-Forwarded-For`. По этому заголовку считается лимит попыток входа; без прокси API перезаписывает его адресом соединения, чтобы клиент не мог его подделать.

## API

| Запрос | Что делает |
|---|---|
| `POST /api/auth/sign-in/email` | вход: `{ "email", "password" }`, ставит cookie сессии. Остальные эндпоинты Better Auth — тоже под `/api/auth/*` (`sign-out`, `get-session`…) |
| `GET /api/me` | кто вошёл: `{ kind: "user", user: { id, name, email, role } }` (для токена — `{ kind: "token", token: { id, siteId } }`) |
| `GET /api/sites` | сайты, доступные вошедшему (владельцу — все, токену — его сайт) |
| `POST /api/sites` | создать сайт (только владелец): `{ "name": "…" }`. Тема — по умолчанию, главная страница создаётся сразу (черновик) |
| `GET /api/sites/:siteId` | сайт: название, тема и роль вошедшего на нём (`access`) |
| `GET /api/sites/:siteId/snapshot` | тема и опубликованные страницы — всё, что нужно рендереру. **Открыт без входа** |
| `GET /api/sites/:siteId/pages` | страницы сайта: заголовок, адрес, когда опубликована, есть ли неопубликованные изменения |
| `POST /api/sites/:siteId/pages` | создать страницу: `{ "slug": "o-nas", "title": "…", "template": "hero" }`, шаблон `hero` (первый экран из каталога) или `empty` (по умолчанию). Занятый адрес — 409 |
| `GET /api/sites/:siteId/pages/:slug` | страница с черновиком и опубликованной версией |
| `PUT /api/sites/:siteId/pages/:slug` | сохранить черновик: `{ "title": "…", "content": { "blocks": […] } }`. Если страницы нет, создаёт её (клиенту — 404) |
| `POST /api/sites/:siteId/pages/:slug/publish` | опубликовать черновик вместе с заголовком. Каждая публикация пишет версию в историю |
| `DELETE /api/sites/:siteId/pages/:slug` | удалить страницу вместе с её историей. Главную (`index`) удалить нельзя — 409 |
| `GET /api/sites/:siteId/pages/:slug/revisions` | история публикаций, новые сверху (последние 100): `id`, `version` (1, 2, 3…), `title`, `publishedAt`, `author` (`{ kind: "user" \| "token", name }` или `null`, если автор неизвестен) |
| `GET /api/sites/:siteId/pages/:slug/revisions/:revisionId` | версия целиком: то же плюс `content` с блоками |
| `POST /api/sites/:siteId/pages/:slug/revisions/:revisionId/restore` | вернуть версию в черновик (заголовок и блоки). Опубликованная версия и история не меняются. Отвечает страницей, как `GET …/pages/:slug`. Версия, которую не пропускают нынешние схемы блоков, — 409 |

Без входа открыты только `/api/health`, `/api/health/ready`, `GET /api/sites/:siteId/snapshot` и `/api/auth/*`; остальное отвечает 401. Вход — cookie сессии или заголовок `Authorization: Bearer <токен>`. Изменяющие запросы с cookie принимаются только с `Origin` админки (`ADMIN_URL`). Действие, которое роли не разрешено, — 403, чужой или несуществующий сайт — 404.

При первом запуске API кладёт в пустую базу демо-сайт. Главная страница сайта имеет slug `index`. Адрес страницы — латиница в нижнем регистре и цифры, дефис только между ними (`o-nas`, `price-2026`). Ошибки приходят в одном формате: `{ "error": { "code", "message", "issues"? } }` — и у наших маршрутов, и у эндпоинтов Better Auth (`unauthorized`, `forbidden`, `invalid_email_or_password`, `rate_limited`…); у 400 и у 409 «адрес занят» в `issues` есть путь до поля.

Заголовок страницы, как и блоки, попадает на сайт только после публикации: сохранённый черновик сайт не меняет.

История версий: каждая публикация в той же транзакции сохраняет снимок — заголовок, блоки, кто (пользователь или токен) и когда. Верхняя версия в истории — то, что сейчас на сайте. Смотреть историю может любой, кто видит сайт, а возвращать версию в черновик — любой, кто правит черновики, включая клиента: возврат сайт не меняет. Страницы, опубликованные до появления истории, получили версию 1 без автора.

Рендерер берёт данные из API, поэтому для `pnpm build` API должен быть запущен. При сборке страницы сайта статические, а в `pnpm dev` рендерер собирает страницу на каждый запрос: новая страница видна по своему адресу сразу после публикации, без перезапуска. Сайт выбирается переменной `CMS_SITE_ID` (`apps/renderer/.env`), без неё рендерер отвечает ошибкой с подсказкой. Адрес API задаёт `CMS_API_URL`, по умолчанию `http://localhost:4000`. Админка в dev-режиме ходит в API через прокси Vite по тому же `CMS_API_URL`, а её порт задаёт `ADMIN_PORT` (по умолчанию 5173).

## Админка

| Адрес | Экран |
|---|---|
| `/login` | вход. Сюда ведёт любой экран без входа, а после входа — обратно, туда, где был |
| `/` | список доступных сайтов и «Новый сайт» (только владельцу) |
| `/sites/:siteId` | страницы сайта: состояние публикации, «Новая страница», удаление (клиенту — только список) |
| `/sites/:siteId/pages/:slug` | редактор страницы. Кнопка «История» показывает публикации: выбранная версия открывается в предпросмотре, «Вернуть в черновик» делает её черновиком (с вопросом, если есть несохранённые правки) |

В шапке — имя вошедшего и «Выйти». Если сессия кончилась посреди работы (любой ответ 401), админка ведёт на вход и потом возвращает на тот же экран; несохранённые правки редактора защищает обычный вопрос перед уходом. То, что роли нельзя (публикацию, создание и удаление страниц для клиента), админка не показывает, но решает всё равно API.

У каждого экрана свой адрес, поэтому обновление вкладки оставляет на месте, а ссылку можно сохранить. Назад ведут хлебные крошки вверху экрана. Уйти из редактора с несохранёнными правками (по ссылке, кнопкой «Назад» браузера или закрыв вкладку) можно только после подтверждения.

Маршруты — TanStack Router (`apps/admin/src/router.tsx`), загрузка и кеш данных — TanStack Query (`apps/admin/src/queries.ts`).

## Сквозные тесты (e2e)

Пакет `e2e/` гоняет сценарии админки в настоящем браузере: сайты и страницы → правка в форме → предпросмотр → сохранение → публикация → опубликованный сайт. Один раз поставь браузер (только Chromium, около 120 МБ в общий кеш Playwright):

```bash
pnpm --filter @cms/e2e exec playwright install chromium
```

Запуск:

```bash
pnpm e2e                        # все тесты
pnpm e2e --shuffle              # в случайном порядке: тесты не должны зависеть друг от друга
pnpm e2e tests/editor.spec.ts   # один файл
pnpm e2e --headed               # с видимым окном браузера
```

Playwright сам поднимает свои копии API, админки и рендерера и гасит их в конце. Порты свои, чтобы не мешать `pnpm dev`:

| Что | Адрес в e2e |
|---|---|
| API | http://localhost:4100 |
| Админка | http://localhost:5273 |
| Рендерер | http://localhost:4421 |

Запущенный рядом `pnpm dev` не мешает, и наоборот: рендерер e2e стартует с `astro dev --ignore-lock` и не трогает файл-замок Astro (`apps/renderer/.astro/dev.json`), по которому Astro не даёт поднять второй dev-сервер в том же проекте. Если какой-то из этих портов занят, прогон сразу падает: тесты не пойдут по чужому серверу. База e2e лежит в `e2e/.data` и стирается перед каждым прогоном, база разработки в `apps/api/.data` не трогается. Перед каждым тестом демо-сайт возвращается в исходное состояние через API: главная — демо, страницы, созданные другими тестами, удаляются. Сайты, которые создают тесты, остаются до следующего прогона, поэтому у каждого своё название.

Админка e2e закрыта входом, как и настоящая. API e2e при старте создаёт владельца с учебными данными из `e2e/urls.ts` (`e2eOwner`). Проект `setup` входит им один раз и сохраняет cookie в `e2e/.data/owner.json`: остальные тесты стартуют уже вошедшими, а фикстура ходит в API с той же cookie. Вход, выход и лимит попыток проверяет `tests/auth.spec.ts` в браузере без сохранённой сессии. Рендерер e2e собирает демо-сайт по его постоянному id.

Упавший тест оставляет трассу в `e2e/test-results`, а сводный отчёт лежит в `e2e/playwright-report` (`pnpm --filter @cms/e2e exec playwright show-report`). В конце прогона в логе бывает строка `[API] … Command failed`: это Playwright гасит сервер API, на Windows иначе не умеет.

`pnpm check` e2e не запускает: он должен оставаться быстрым. Перед коммитом, который меняет админку, API или рендерер, гоняй и `pnpm e2e`.

## MCP

`apps/mcp` — MCP-сервер, через который нейронка собирает лендинги. Инструменты: `list_blocks`, `list_sites`, `get_page`, `save_draft` и `publish_page`. Входные схемы инструментов — те же Zod-схемы, что проверяют страницы в API, поэтому кривой блок не пройдёт ни там, ни там.

Сервер описан в `.mcp.json` и запускается на закреплённой в проекте Node (`node_modules/.bin/node.exe`, путь под Windows). MCP — обычный клиент API и входит токеном с правами редактора на одном сайте. Настройка:

1. Останови `pnpm dev` (команде нужна база) и выпусти токен: `pnpm token:create --site <id сайта> --name mcp`. Токен показывается один раз.
2. Скопируй `apps/mcp/.env.example` в `apps/mcp/.env` (он в `.gitignore`) и вставь строку `CMS_API_TOKEN=…` из вывода команды.
3. Запусти `pnpm dev`, открой новую сессию Claude Code в папке проекта и разреши сервер `cms`. Если сервер уже был запущен, перезапусти его: токен читается при старте.

Без токена сервер всё равно стартует: `list_blocks` работает, а остальные инструменты отвечают, как получить токен. `list_sites` показывает только сайт токена. Отозвать токен — `pnpm token:revoke --id <id>`; после этого MCP получит понятную ошибку «API не принял токен».

Astro по умолчанию отправляет анонимную телеметрию. Отключить её: `pnpm --filter @cms/renderer exec astro telemetry disable`.

## Структура

```
apps/
  api/        # Hono + Drizzle, локально база — PGlite
  admin/      # React + Vite: сайты, страницы и редактор с живым предпросмотром
  renderer/   # Astro: JSON сайта → статический HTML
  mcp/        # MCP-сервер для нейронок поверх API
e2e/          # сквозные тесты на Playwright
packages/
  schema/     # Zod-схемы: блоки, страница, тема
  tokens/     # тема → CSS-переменные
  blocks/     # React-компоненты блоков
```
