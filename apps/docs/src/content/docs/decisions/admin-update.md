Для студии и разработчика: как кнопка «Обновить» в админке обновляет установку и почему API для
этого не получил ни Docker, ни команд сервера.

## Решение

Владелец нажимает «Обновить до X» в «Состоянии установки». API **только кладёт файл-заявку** в
отдельную папку `/opt/averra/requests` — единственное, что он пишет на сервере. Хост видит заявку
(path-юнит systemd), сам разбирает её строго и запускает тот же `averra.sh update`, что и по SSH:
бэкап, новая версия, миграции, проверка, откат при сбое. Доступную версию хост узнаёт сам
(`averra.sh check-update`), и заявка проходит, только если просит ровно её.

Кнопка — только у владельца установки. Редактору и клиенту её нет, токену API (MCP) — никогда:
действие `installation.update` в `apps/api/src/auth/access.ts` и `tokenDenied`.

## Почему хост, а не контейнер

- **Сокет Docker — это root на сервере.** API открыт в интернет; дай ему Docker — любая уязвимость
  в нём или в зависимости стала бы полным захватом сервера клиента. Обновление делает только
  `averra.sh` от root, как раньше по SSH.
- **Заявка — данные, а не команда.** В ней версия, время и id владельца. Хост берёт из неё одну
  версию `X.Y.Z`, сверяет с той, что нашёл сам, и с установленной; кривая заявка — отказ в журнале
  и в «Состоянии», без обновления. Даже захваченный API может только попросить обновиться до уже
  вышедшей версии из настроенного источника — то, что студия и так сделала бы.
- **Один путь обновления.** Бэкап, откат, доведение прерванного и лог — те же, что у
  `averra.sh update` по SSH и `pnpm fleet update`: второй копии логики нет.
- **API переживает своё же обновление.** Посреди обновления API останавливается — делать
  обновление он не может по определению. Хост ведёт его до конца, админка ждёт и показывает итог.
- **Path-юнит, а не опрос раз в минуту.** Заявку видно сразу, без записи в журнал systemd каждую
  минуту. Служба удаляет заявку первым делом, а `ExecStopPost` — в любом случае: иначе `PathExists`
  запускал бы её по кругу. Само обновление уходит в свою службу (`systemd-run`), служба заявки
  кончается за секунды.
- **Службы и папки ставит сам `averra.sh`** (`install-units`, `ensure-dirs`): `install.sh` зовёт
  его, а при обновлении прежний скрипт зовёт у **нового** `ensure-dirs` до запуска новой версии и
  `install-units` после её проверки — папки и службы новой версии доезжают без ручного шага.
- **Кнопка не обещает того, чего хост не сделает.** Нет systemd или path-юнит выключен или упал —
  кнопки нет (`requestsWatched`). Версия без образов в реестре не считается найденной. Заявку,
  которую хост не забрал за 10 минут, админка называет потерявшейся, и новая её заменяет.
  Ломающий релиз (BREAKING CHANGES: шаг на сервере) — в том числе пропущенный между установленной
  и последней версией — и установка после неудачного отката обновляются только по SSH, человеком,
  который видит сервер. Версию, обновление до которой уже откатилось, из админки не повторить:
  каждая попытка — минута-две без админки и ещё одна отложенная база с персональными данными.
- **Обрыв перезагрузкой доводит сервер сам.** На шаге бэкапа API остановлен, а у владельца нет
  SSH: служба `averra-update-resume` при старте сервера доводит прерванное (закончить или
  откатить), нового обновления не начинает.

## Почему только владелец

Обновление — решение о сервере, а не о сайте: оно останавливает админку и приём заявок на
минуту-две, меняет код всей установки и при сбое откатывает базу из бэкапа. За сервер отвечает
студия, которая ведёт установку, — она и есть владелец. Редактор делает контент, клиент
публикует свой бизнес — ни тому, ни другому не нужно решать, когда остановить сервер. Нейронка с
токеном API не видит, что сейчас идёт приём заявок или запуск рекламы, — это решение человека.
Студия узнаёт о каждой заявке служебным уведомлением «Запрошено обновление» (кто и до какой
версии).

## Чем платим

- На сервере больше частей: папка заявок с владельцем uid 1000, path-юнит и служба, файлы
  проверки версии в папке состояния.
- Проверка новой версии ходит в интернет (по умолчанию — API GitHub). Без сети — «не удалось
  проверить», кнопка остаётся на последней найденной версии. Ответ разбирается в образе
  установленной версии без сети и прав (`release-info.js`), чтобы не тащить на хост `jq` или
  Python.
- Новая версия видна раз в сутки (вместе с ночным бэкапом) или по `averra.sh check-update`, а не
  сразу после релиза.
- Обновление по ночам само (без кнопки) — следующим шагом, после этапа 4
  ([Дорожная карта](/averra-cms/roadmap/)).
