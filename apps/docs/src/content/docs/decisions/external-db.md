Для студии и разработчика: как Averra бэкапит, проверяет и восстанавливает управляемую PostgreSQL
у провайдера и почему не так, как свою базу.

## Решение

- Режим включается флагом `install.sh --external-db`, адрес — только переменной окружения
  `AVERRA_DATABASE_URL` или скрытым вводом. TLS обязателен: `sslmode=verify-full`, свой CA
  провайдера — `--db-ca-file`.
- Своей базы нет: отдельный `compose.external.yaml` без сервиса `postgres`, установщик кладёт его
  под именем `compose.yaml`, обновление берёт из образа нужный по `AVERRA_DB_MODE`.
- Клиент PostgreSQL для дампа — контейнер образа `postgres` **той же мажорной версии, что сервер**
  (её узнаёт установщик). Адрес разбирается в переменные libpq, пароль уходит в контейнер
  переменной окружения.
- **Проверка бэкапа** — во временном локальном контейнере `postgres` той же версии: без сети,
  удаляется в любом исходе вместе со своим анонимным томом данных (`docker rm -fv`).
- **Восстановление и откат** — в ту же базу, без новой базы и переименования: страховочный дамп
  текущей базы, потом одна транзакция «удалить схему `drizzle` и объекты `public` — загрузить
  дамп». Не поднялось — страховочный дамп той же транзакцией обратно.

## Почему

- **Прав нет.** У пользователя управляемой базы обычно владение одной базой и схемой `public`, но
  не `CREATEDB` и не суперпользователь. Своя база проверяет дамп во временной базе и
  восстанавливает через новую базу и переименование — на внешнем сервере это невозможно.
- **Временный контейнер лучше временной базы у провайдера:** он не просит прав, не нагружает
  сервер клиента и не оставляет на нём копий персональных данных. Та же мажорная версия — тот же
  `pg_restore`, что поднимет дамп в настоящей аварии.
- **Том контейнера — с ним же и удаляется.** Образ `postgres` объявляет `VOLUME` под данные, и
  Docker заводит анонимный том, куда восстанавливается полная копия рабочей базы. `--rm` удаляет
  его, только если контейнер остановился сам; наш `docker rm -f` в конце проверки приходит раньше
  и без `-v` оставил бы том навсегда — копия персональных данных вне срока хранения и лишние
  десятки мегабайт каждую ночь. Поэтому удаление всегда `rm -fv`, и брошенный обрывом контейнер
  следующая проверка убирает так же. Том в памяти (tmpfs) не выбран: на VPS с 1–2 ГБ копия
  базы в памяти рядом с API опаснее, чем на диске на минуту проверки.
- **Одна транзакция вместо переименования.** PostgreSQL выполняет DDL в транзакции: обрыв, сбой
  или перезагрузка посередине откатывают всё, и база остаётся прежней, а не пустой. Объекты
  удаляются явно, а не `pg_restore --clean`: тот удаляет только то, что есть в дампе, и таблицы
  новой версии пережили бы откат, а следующее обновление упало бы на их миграции.
- **Страховочный дамп** заменяет отложенную базу (`averra_rolled_back_…`): данные, принятые после
  бэкапа, не теряются молча, и есть путь назад — `averra.sh restore-dump`.
- **Итог восстановления — в файле состояния** (`restore-last.json`): API на время восстановления
  остановлен, и оборванное (`kill -9`, перезагрузка) иначе было бы видно только в терминале, где
  оно шло. Файл пишется до загрузки и после неё, поэтому `averra.sh status` без API скажет, на
  каком шаге оборвалось и какой дамп вернуть. Обрыв ровно между `COMMIT` и записью итога
  неотличим от обрыва до `COMMIT` — тогда сказано честно «либо, либо», а путь назад тот же.
- **Отдельный файл Compose, а не profiles.** Profiles потребовали бы новую строку
  `COMPOSE_PROFILES` в `.env` уже стоящих установок (иначе своя база не поднимется — ломающее
  изменение) или `!reset` и `depends_on.required` из Compose новее, чем в пакетах Ubuntu. Отдельный
  файл работает с любым Compose v2, а `compose.yaml` своей базы не меняется; расхождение файлов
  ловит тест.
- **`verify-full`, а не `require`.** `require` шифрует, но не сверяет имя сервера с сертификатом:
  подмену сервера он не заметит. И драйвер API (`pg`), и libpq проверяют при `verify-full` и
  цепочку, и имя сервера — но доверенные корни у них разные, об этом ниже.
- **Очистка перед загрузкой — по каталогу, а не по списку таблиц Averra.** Объекты `public`
  перечисляются из `pg_class`, `pg_type` и `pg_proc`; последовательности столбцов `serial` и
  `IDENTITY` не удаляются отдельно — они уходят с таблицей, а свой `DROP` у `IDENTITY` падает
  и откатил бы всю загрузку. SQL очистки проверяется тестом API на PGlite после всех миграций.

## Чем платим

- Восстановление держит API остановленным дольше: страховочный дамп снимается по сети.
- Проверка бэкапа поднимает на сервере установки второй PostgreSQL на время проверки: память и
  место под копию базы.
- Транзакция загрузки держит блокировки на всю базу, пока идёт: на это время база занята целиком —
  API и так остановлен.
- Страховочные дампы — копии персональных данных в папке бэкапов. Их видно в «Состоянии», и срок
  хранения бэкапов удаляет их через `BACKUP_KEEP` дней.
- Таблица образов клиента (16, 17, 18) ведётся руками: новая мажорная версия PostgreSQL у
  провайдера — новая строка в `install.sh` и `averra.sh`.
- Доверенные корни у API и у клиента бэкапов разные: API (Node) — встроенный в Node список
  корней, `pg_dump` в alpine — системные корни образа (`sslrootcert=system`). Для публичных
  центров сертификации это одно и то же, но не гарантированно: CA провайдера не из широко
  известных — всегда `--db-ca-file`, тогда оба проверяют по одному файлу.
- Восстановление, оборванное посередине, человек закрывает сам: вернуть страховочный дамп
  (`averra.sh restore-dump <дамп>`) или оставить как есть (`averra.sh restore-dump --dismiss`).
  Пока не решил, «Состояние» показывает проблему.
