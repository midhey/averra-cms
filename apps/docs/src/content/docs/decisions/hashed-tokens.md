Для разработчика: как хранятся токены API, ссылки сброса пароля и приглашений и почему так.

## Решение

- **Токены API и приглашений** — `<префикс>_<id строки>_<секрет>`. В базе только SHA-256. Строка
  ищется по id, хеш сравнивается за постоянное время. Сам токен показывается один раз (токен API) или
  есть только в письме (приглашение).
- **Ссылки сброса пароля** — Better Auth, но с хешером идентификатора: в базе
  `reset-password#<хеш>`. Разделитель — `#`, а не двоеточие, и формат токена проверяется до Better
  Auth.
- **Токен из письма — во фрагменте ссылки:** `ADMIN_URL/reset-password#token=…`. Экран читает его
  один раз и убирает из адреса. В API токен идёт в теле запроса, а не в пути.
- **Одноразовость** — одним условным `UPDATE … RETURNING` или атомарным погашением Better Auth.

## Почему

- **Утечка базы или бэкапа не даёт входа:** по хешу токен не восстановить.
- **Фрагмент не уходит на сервер:** токен не попадает в логи статики, прокси и в `Referer`.
- **`#` вместо двоеточия:** Better Auth, не найдя запись по хешу, ищет её ещё и по присланной строке
  как есть. С двоеточием хеш из базы сам работал бы как токен. Идентификаторы Better Auth
  начинаются с приставки без `#`, поэтому совпасть не может.
- **Постоянное время сравнения** и поиск по id — поиск в базе не превращается в подбор секрета.

## Чем платим

Потерянный токен не восстановить — только выпустить новый. Включая новый плагин Better Auth, где
идентификатор целиком задаёт клиент (номер телефона, адрес кошелька), это правило надо перепроверить.
