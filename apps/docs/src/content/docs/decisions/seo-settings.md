Для разработчика и студии: как устроен раздел «SEO» и почему именно так. Как им пользоваться —
[SEO](/averra-cms/admin/seo/).

## Решение

- **Один раздел на сайт целиком.** Настройки — колонка `sites.settings` (jsonb) по схеме
  `SiteSettings` из `@averra/schema`, название — `sites.name`. Админка сохраняет их карточками
  (`PATCH` присланных полей), сохранение пересобирает сайт.
- **Только владелец** (`site.settings`). SEO страницы — SEO-заголовок, описание, картинка,
  canonical и `noindex` — в её содержимом (`PageContent.seo`), его правит любой, кто правит
  страницу, и оно публикуется и хранится в истории вместе с блоками. Странице нужное от сайта
  (шаблон, описание и картинка по умолчанию, адрес) отдаёт `GET /api/sites/:siteId` (`seo`).
- **Новый сайт скрыт от поисковиков** (`noindex, nofollow` и `Disallow: /`), пока владелец не
  снимет флажок. Сайты, которые работали до этого раздела, открыты.
- **Редиректы и 404 отдаёт API.** Caddy отдаёт файлы версии сайта, а на адрес без файла спрашивает
  API (`handle_errors 404` → `GET /api/site/fallback/<путь>`): 301 по таблице из базы или 404 со
  страницей `404.html` текущей версии. В dev то же делает рендерер.
- **Страница 404 — обычная страница с адресом `404`.** Нет своей — сборка кладёт стандартную.
- **JS на сайте — только счётчики,** и только с заданным номером; номера проверяются строгими
  шаблонами и ещё раз при сборке. Цель «заявка» — адресом `?sent=<id формы>` после 303, без
  своего скрипта.
- **Иконки делает API** (sharp) из картинки медиатеки, рендерер кладёт их в корень сайта.
- **HTML `<head>`, robots.txt, sitemap.xml, манифест, JSON-LD** — чистые функции рендерера
  (`apps/renderer/src/lib/seo.ts`) с тестами.

## Почему

- **SEO — дело студии.** Одна ошибка (скрытый сайт, чужой домен в `canonical`, петля редиректов,
  чужой счётчик) выкидывает сайт из поиска. Клиенту хватает текстов и заявок, а описание своих
  страниц он правит в редакторе.
- **Скрытый по умолчанию.** Сайт делают на настоящем домене клиента до запуска: недоделанный сайт
  в индексе потом долго не выкурить. Забытый флажок виден — обзор напоминает о нём, а снять его —
  шаг запуска. Уже работающие сайты закрывать нельзя: они выпали бы из поиска.
- **Не Caddyfile.** Caddy читает конфиг при старте: сгенерированный файл в релизе потребовал бы
  перечитывать конфиг при каждой публикации, а давать API право перезагружать Caddy — лишняя
  власть. Таблица в базе действует сразу, подмена версии сайта остаётся атомарной, а логика
  проверяется тестами API без Caddy.
- **Страница главнее редиректа.** Caddy спрашивает API только про отсутствующие файлы — значит,
  существующая страница редирект перекрывает. API не даёт сохранить такой редирект, чтобы правило
  не было сюрпризом.
- **404 из версии сайта.** API берёт `404.html` той же версии, что и остальной сайт: оформление и
  стили совпадают, а архив сайта (`404.html` в корне) понимает любой статический хостинг.
- **Настройки с запасом на откат.** Чтение из базы отбрасывает незнакомые ключи, а поле верхнего
  уровня с непонятным значением (новый язык, таблица длиннее прежнего предела) читает значением по
  умолчанию и один раз пишет об этом в лог API. Админка, сборка и 404 после отката не падают.
  Сохранение пишет поверх того, что в базе, поэтому такое поле не затирается и снова заработает
  после обновления.

## Чем платим

- Адреса без файла на домене сайта идут в API (запрос к базе по первичному ключу). API не
  отвечает — на них 502, хотя страницы сайта отдаются.
- Редирект не сработает с адреса, где есть файл: страницу придётся удалить.
- Владелец должен не забыть открыть сайт поисковикам при запуске.
- Описание страницы и `noindex` уходят на сайт только с публикацией страницы, а настройки сайта —
  сразу после «Сохранить» (с пересборкой).
- Картинка страницы для соцсетей, проверки «как у Yoast» и `www.` из админки — позже ([дорожная
  карта](/averra-cms/roadmap/)).
