Для разработчика и агента, который пишет код в Averra. После страницы вы напишете код, который
пройдёт ревью с первого раза. Правила меняем осознанно и сразу записываем сюда.

Смежные правила — на своих страницах: [Схемы](/averra-cms/dev/schemas/),
[Свой блок](/averra-cms/dev/blocks/), [Стили](/averra-cms/dev/styles/),
[Тесты](/averra-cms/dev/testing/), [Доступ и секреты](/averra-cms/dev/security/),
[Сервер и установка](/averra-cms/dev/server/).

## Общее

- TypeScript в строгом режиме везде. `any` — только с комментарием, почему иначе нельзя.
- Форматирование и линт — Biome: 2 пробела, одинарные кавычки, без точек с запятой, строка до
  100 символов. Перед коммитом — `pnpm format` и `pnpm check`.
- Имена: типы и компоненты — `PascalCase`, функции и переменные — `camelCase`, файлы — `kebab-case`
  (кроме файлов компонентов: `App.tsx`).
- Комментарии — по-русски и только там, где неочевидно, **почему** сделано так. Что делает код,
  видно из кода.
- Тексты для людей (интерфейс, ошибки, письма) — по-русски, коротко и по делу.

## API

- Все маршруты — под `/api`.
- Зависимости приходят явно через `createApp(deps)`, глобальных синглтонов нет.
- `app.ts` и модули маршрутов **не импортируют Node API** (`fs`, `process` и т. п.): админка читает
  типы API, и Node-импорты сломают ей проверку типов. Платформенное — в `index.ts` или за
  интерфейсами.
- Конфиг читается только в `config.ts` и проверяется схемой. В других местах `process.env` не
  трогаем.
- Модуль — папка `src/modules/<имя>/`: `routes.ts` — HTTP и проверка входа, `repo.ts` — запросы к
  базе, `service.ts` — когда логика перерастает один запрос.
- Вход проверяем через `validate(target, schema)` из `src/validate.ts`: 400 с путём до каждого
  кривого поля.
- Ошибки — в едином формате `ApiError` и по-русски, включая 404 неизвестного маршрута и 500. Коды —
  [API](/averra-cms/dev/api/): 409 — `conflict` из `src/errors.ts`, 410 — `invitationError`.
- Ошибку сервера в лог пишем через `errorForLog` (`src/log-error.ts`): у ошибки запроса к базе в
  тексте — параметры, а в них бывают секреты и персональные данные. Логгер чужих сообщений (Better
  Auth) не верит типам: первым аргументом может прийти сама ошибка.
- Файлы и картинки — только через интерфейсы `MediaStorage` и `ImageProcessor`; реализации на диске
  и на sharp подключают `index.ts` и `testing.ts`.
- **Путь к файлу строит только сервер** — `mediaKey(siteId, mediaId, имя)` из id и имени, которое
  составил сам. Имя файла, расширение и `Content-Type` из запроса в путь не попадают, тип файла —
  по содержимому.
- Ссылки на картинки в страницах проверяет API при сохранении и возврате версии: каждый `mediaId` —
  из медиатеки этого сайта. Используемую картинку удалить нельзя.
- **Архив** (выгрузки) — ZIP потоком через `zipStream` (`src/modules/export/zip.ts`, fflate): файлы
  читаются по одному. Имена в архиве строит сервер, `..` и ведущий `/` не проходят. Без ZIP64 —
  предел 3,5 ГБ, проверяется до начала ответа.
- **Выгрузка, которая растёт с данными** (CSV заявок, заявки и история в `site.json`), — потоком,
  порциями с курсором по ключу сортировки. Курсор — значения последней строки: время текстом
  (`created_at::text`) и id, в SQL `(created_at, id) < ($1::timestamptz, $2::uuid)`. Не `Date`
  (теряет микросекунды) и не подзапрос по id (строку удалили — выгрузка молча оборвётся).
- **Предел по накопленным данным** (дневной объём заявок) не закрывает сервис честным людям: он
  касается только того, что его выбирает (крупных заявок). Размер для предела хранится в своей
  колонке, а не пересчитывается из jsonb.
- **Публикация** приходит в маршруты интерфейсом `SitePublisher` (`src/publish/queue.ts`). Новый
  путь, который меняет опубликованное, после записи в базу зовёт `publisher.request(siteId)`. Сбой
  постановки публикацию не отменяет — пишется в лог.
- Чужой процесс без нужды в секретах (сборщик сайта) получает окружение по списку (`PASSED_ENV` в
  `src/publish/renderer.ts`), а не `process.env` целиком: его вывод попадает в журнал и в админку.
- Пути от `import.meta.url` в API считаются с глубины `src/<папка>/` — на той же глубине лежит
  сборка `dist/server/`. Новый такой путь — проверка в `scripts/build.ts`.

## База

- Drizzle. Локально — PGlite (данные в `apps/api/.data`), в проде — PostgreSQL по `DATABASE_URL`
  через node-postgres. Базу выбирает `dbTargetOf`, открывает `createDb(target)`, тип `Db` один на
  оба драйвера. Сырой запрос (`db.execute`) читает результат как `{ rows }`; драйвер, который отдаёт
  иначе (postgres.js), не подключаем.
- Встроенная база — один процесс: API и команды открывают её через замок, новая команда — через
  `openDb()` из `src/cli/common.ts`. С PostgreSQL замка нет.
- **Внутри `db.transaction` все запросы — через `tx`.** PGlite не выполняет запрос мимо открытой
  транзакции — он ждёт её конца, и выходит взаимная блокировка.
- Схема меняется только миграциями: правим `apps/api/src/db/schema.ts`, `pnpm db:generate`,
  коммитим SQL из `apps/api/drizzle` вместе с кодом. Таблицы Better Auth (`users`, `sessions`,
  `accounts`, `verifications`) — тоже в нашей схеме и наших миграциях.
- В коде поля в camelCase, в базе колонки в snake_case. `site_id` — в каждой таблице с контентом.
- Опубликованную версию страницы меняет только `sitesRepo.publish`, и в той же транзакции пишет
  снимок в историю. Новый путь публикации — через него же.
- История не переписывается: возврат версии меняет только черновик.
- Миграция, которая вводит производные данные (как история), заполняет их и для того, что уже лежит
  в базе.

### Миграции только совместимые вперёд

Прежняя версия API должна работать на базе после миграций новой — это нужно для отката
([почему](/averra-cms/decisions/forward-migrations/)).

- **Можно:** новые таблицы, новые колонки с `DEFAULT` или без `NOT NULL`, индексы, снятие
  `NOT NULL`. Ограничения на таблицу или колонки, которые заводит эта же миграция.
- **Нельзя одним шагом:** удалить или переименовать таблицу или колонку, сменить тип, `SET NOT NULL`,
  новая `NOT NULL`-колонка без `DEFAULT`, `DROP DEFAULT`, новое ограничение (`UNIQUE`, `CHECK`,
  внешний ключ) или уникальный индекс на существующие колонки, `DROP`/`ALTER TYPE`, `DROP INDEX`
  (уникальные индексы — опора `ON CONFLICT` прежнего кода), `DROP CONSTRAINT`, удаление других
  объектов; любое другое `DROP`, кроме `DROP NOT NULL`.
- **Как делать:** в два релиза. Сначала новое рядом со старым (код пишет оба, читает новое), потом,
  когда старый код нигде не работает, — удаление старого с пометкой
  `-- averra:compat <почему безопасно>` прямо над этой инструкцией. Пометка разрешает одну
  инструкцию, а не всю миграцию.

Проверяет `src/db/migrations-compat.test.ts`; исключения до первого релиза — закрытым списком в нём.
Мажорную версию образа Postgres обычным обновлением не меняем.

## Админка

- **Маршруты** — TanStack Router, в коде в `src/router.tsx`. Экран берёт параметры через
  `getRouteApi`, а не импортом маршрута: так нет циклических импортов. Закрытые экраны, кроме
  редактора, — дети безпутевого маршрута `_app`, он рисует оболочку. Экраны без входа — в
  `PUBLIC_PATHS`.
- **Данные** — TanStack Query, опции запросов — в `src/queries.ts`. Ключи от общего к частному
  (`['sites', id, 'pages', slug]`): после мутации сбрасываем префикс.
- Экран, который берёт данные в своё состояние один раз (редактор), грузит их через `fetchQuery`, а
  не из кеша: иначе сохранение устаревшего черновика затрёт чужие правки.
- **Всё, что экран показывает сразу, грузит загрузчик маршрута**, а не `useQuery` после отрисовки:
  запрос после показа при истёкшей сессии уведёт на вход посреди работы. Второстепенное загрузчик
  ждёт через `Promise.allSettled`, а сбой показывается внутри раздела с кнопкой «Повторить».
- Параметры адреса маршрут проверяет теми же схемами, что API, и на кривые отвечает `notFound`, а
  не запросом.
- Экран, который живёт на параметре адреса и держит своё состояние, рисуется с `key` по этому
  параметру.
- Запросы — через клиент из `src/api.ts` или `apiFetch`: сетевой сбой становится `NetworkError`.
  Файл из API (CSV, архив) — запросом и `Blob`, а не ссылкой.
- Свой виджет поля (картинка) приходит в `SchemaForm` явно, через `widgets`: форма общая.
- **Доступность.** Ошибка поля связана через `aria-describedby` и `aria-invalid`, после неудачной
  отправки фокус — на первое поле с ошибкой; общая ошибка формы — `role="alert"`. Убрали элемент с
  фокусом — фокус на понятное место, а не на `body`. Недоступная, но только что нажатая кнопка —
  `aria-disabled`, а не `disabled`. У каждого экрана свой `<main>` и заголовок вкладки
  (`usePageTitle`).
- Окно — нативный `<dialog>` через `showModal()`; подтверждение опасного действия —
  `window.confirm`.
- Экран внутри оболочки — `Screen` и `PageHeader`, раздел — `Section`: ориентир region с именем по
  h2, по нему раздел находят диктор и e2e. Два ориентира с одним именем рядом не ставим, поэтому
  область прокрутки `DataTable` — `group`, а не `region`. Итог действия — `InlineAlert` с `live`, ошибка — `InlineAlert tone="danger"`, пусто — `EmptyState`.
  Время — `RelativeTime`, склонения — `pluralRu`.
- Список рядом с карточкой (заявки) — родительский маршрут со списком и ребёнок с карточкой.
- Перестановка — `SortableList` и `useSortableItem` (dnd-kit) с ручкой и стрелками рядом; тексты для
  диктора — по-русски из `src/ui/sortable.ts`. Пунктам без id — постоянные ключи `useItemKeys`.
- Редактор — вне оболочки (`src/editor/Editor.tsx`). Узкий экран меняет разметку через
  `useMediaQuery(NARROW_SCREEN)`, остальное — CSS. Невыбранная вкладка — `hidden`, а не
  размонтирована. Подсветка блока — только внутри iframe админки: в `@averra/blocks` и на сайт
  ничего для редактора не добавляем.
- Что панель показывает роли, решает `src/shell/sidebar-model.ts` (с тестом). Новый раздел сайта —
  строка там и ссылка в `src/shell/AdminLayout.tsx`. Админка прячет то, что роли нельзя, но правило
  живёт в API: скрытая кнопка — удобство, а не защита.
- **Секрет в форму не приходит никогда** (пароль SMTP): поле пустое, рядом — состояние («задан»,
  «не читается»), пустое поле при сохранении — оставить прежний. После сохранения форма собирается
  заново (`key`), поля паролей снова пустые.
- Мутация получает явной переменной, с чем работать. «Проверить подключение» — то, что проверяли:
  пока идёт проверка, поля могут поправить. Сохранение — итог проверки или «без проверки»
  (`SaveProof` в `src/mail/SmtpSettingsSection.tsx`); одно в другое мутация молча не превращает.

## Документация

- Сайт — `apps/docs` (Starlight), только штатные средства: страницы в Markdown, тема — переменными
  `--sl-*` в `src/styles/theme.css`, компоненты Starlight подменяем только при нужде.
- Ссылки между страницами — от корня с `/averra-cms/`, без относительных: так их проверяет
  `starlight-links-validator`, и битая ссылка роняет `pnpm check`.
- Каждая страница начинается с того, кому она и что он сможет после неё. Пишем для людей: коротко,
  по делу, без пересказа кода. Команды, переменные, маршруты и пути сверяем с кодом.
- Поменяли поведение, команду, переменную или маршрут — поправьте страницу в том же коммите.
- Рабочие планы шагов — в `.work/` (вне git), не в документации.
- Английский добавится папкой `src/content/docs/en` и строкой в `locales` в `astro.config.mjs`:
  русские страницы и адреса не меняются.

## Git

- Ветка — `master`, коммиты маленькие, в стиле Conventional Commits, по-английски. По ним
  release-please поднимает версию и пишет `CHANGELOG.md`, поэтому тип выбирают по тому, что
  заметят на установке. Какие типы поднимают версию — в [Релизах](/averra-cms/dev/releases/).
  Ломающее для установок (ручной шаг на сервере, новая строка `.env`) — `!` в заголовке и подвал
  `BREAKING CHANGE: <что сделать на сервере>` последней строкой: в заметки релиза идёт только он.
  Версию и теги руками не правим.
- Секреты — только в `.env` (он в `.gitignore`), шаблон — `.env.example`.
