Для разработчика, который добавляет канал (ВКонтакте, вебхук в CRM, SMS) или событие. После
страницы вы будете знать, куда что писать и что ядро сделает само.

Код — `apps/api/src/notifications`, маршруты — `apps/api/src/modules/notifications`, схемы входа —
`packages/schema/src/notifications.ts`. Почему так — [Уведомления: каналы и очередь](/averra-cms/decisions/notifications/).

## Как идёт уведомление

1. **Событие** (`events.ts`): id, аудитория (`leads` — получатели заявок сайта, `service` —
   служебные установки), схема данных, нейтральное сообщение `message(data)` — заголовок, абзацы,
   поля, ссылка — и, если нужно, своё письмо `mail(data)`.
2. **Ядро** (`notify.ts`): `notify(tx, deps, { event, data, siteId, leadId, now })` берёт
   подписанных получателей аудитории (`notification_recipients`) и ставит событие в каждый канал,
   который готов его везти. Всё — в транзакции действия: заявка и задача уведомить ложатся
   вместе. У «Новой заявки» без единого готового получателя — письмо владельцам.
   `notifyTargets` — то же для явного списка (владельцы, прежние получатели, проверка).
3. **Канал** ставит в свою очередь: почта — письмом в `mail_outbox` (`enqueueMail`), остальные —
   строкой в `notification_outbox` (`enqueueNotifications`).
4. **Обработчик** (`worker.ts`) в процессе API забирает строки готовых каналов и зовёт
   `channel.send()` по одной, с арендой, повторами (`retryDelayMs`) и паузой канала после сбоя.

## Интерфейс канала

`NotificationChannel` в `channel.ts`:

| Поле | Что это |
| --- | --- |
| `kind`, `title` | вид канала (строка `NotificationChannelKind` в `@averra/schema`) и название в админке |
| `address` | Zod-схема адреса получателя: почта, chat id. Её проходит каждый новый получатель (`addRecipient`) |
| `settings`, `secret` | Zod-схемы открытых настроек и секрета канала |
| `label(recipient)` | получатель словами: «manager@…», «Telegram «Отдел продаж»» — для письма о смене получателей и сводки «куда уходят заявки» |
| `describe(config, view)` | что канал рассказывает админке, без секретов: `owner` — владельцу в «Каналах», `site` — клиенту, чтобы привязать получателя |
| `defaultEnabled` | включён ли, пока владелец не трогал |
| `skips` | события, которые канал не возит (почта — «почта не работает») |
| `ready(config, context)` | можно ли ставить сейчас; нет — `reason` для админки |
| `check(config, context)` | «Проверить»: шаги `{ step, ok, message }`. Сразу (Telegram: `getMe` и сообщение в каждый чат) или через очередь — `context.queueTest(addresses)` (почта: письмо себе) |
| `enqueue(context, item, targets)` | поставить в очередь в транзакции действия |
| `send(config, address, message)` | отправить одно сообщение из `notification_outbox` |

Ядро знает каналы только через этот интерфейс: маршрутизация (`notify.ts`), очередь и обработчик,
вид каналов в админке (`channelsView`), «Проверить» (`POST /api/notifications/channels/:kind/check`),
сводка «куда уходят заявки» и письмо о смене получателей (`recipients.ts`). Почту по имени ядро
знает в одном месте — запасной путь «владельцам письмом», когда у заявки нет готовых получателей.

`config` — строка `notification_channels`: включён ли, открытые настройки (`settings`, JSON по
схеме адаптера) и секрет, уже расшифрованный (`secret.state`: `none`, `ok`, `unreadable`). Секрет
шифрует `SecretBox` с контекстом `notification_channels.<kind>:installation`.

Ошибки `send` — только `ChannelSendError` с видом:

- `retry` — повторить с растущей паузой (`retryAfterMs` — если канал сам сказал, когда);
- `permanent` — повторять бессмысленно: сообщение «не отправлено», данные стираются;
- `channel` — сломан канал целиком (сеть, токен): попытка не тратится, канал выжидает до 30 минут,
  остальные каналы работают.

Текст ошибки — по-русски и без секретов: он лежит в очереди и виден владельцу.

## Добавить канал

1. Вид канала — строкой в `NotificationChannelKind` (`packages/schema/src/notifications.ts`).
2. Адаптер — файл в `apps/api/src/notifications/channels/`, по образцу `telegram.ts`: схемы
   адреса, настроек и секрета, `label`, `describe`, `ready`, `check`, `enqueue: (ctx, item,
   targets) => enqueueNotifications(ctx, '<вид>', item, targets)` и `send`, который рисует
   `NotificationMessage` по-своему и экранирует всё из данных.
3. Строка в `createChannels` (`channels/index.ts`). Сеть (HTTP-клиент с Node API) — фабрикой из
   `index.ts`, как `botApi` у Telegram: файлы каналов видят маршруты, а их типы — админка.
4. Тесты: адаптер против локального фейкового сервера (как `testing/fake-telegram.ts`), реестр
   (`channels.test.ts` проверяет, что каждый вид из схемы — адаптер с полным интерфейсом, и что
   ядро называет получателей и показывает канал словами адаптера).

На этом канал работает: его получатели уходят в очередь и в письмо о смене получателей, в
«Каналах» админки — общая карточка (состояние, вкл/выкл, «Проверить»). Ядро, очередь, обработчик
и раздел «Уведомления» не меняются. Миграции не нужно: у `notification_channels.kind`,
`notification_recipients.channel` и `notification_outbox.channel` нет списка в CHECK.

Своё у канала — только то, чего у других нет: форма его секрета (только на запись и с паролем
владельца, как токен Telegram — `PUT /api/notifications/telegram`), способ добавить получателя
(у Telegram — привязка чата кодом, `telegram/binder.ts`) и, по желанию, своя карточка в админке
(`ChannelsSection.tsx`, слова для `describe`). Это его настройки, а не ядро.

## Добавить событие

1. Id — в `NotificationEventId` (`@averra/schema`), если на него подписывают, и подпись в
   `NOTIFICATION_EVENT_TITLES`.
2. Определение — в `notificationEvents` (`events.ts`): аудитория, схема данных, `message`.
3. Вызов `notify` там, где событие случается, в транзакции этого действия.

Служебное событие из состояния установки — сигнал в `serviceSignals` (`watch.ts`): ключ проблемы
(у дисков и сайтов — свой на каждый), событие и данные без персональных. Переходы и запись
состояния в `notification_watch` сделает `runServiceWatch`. Ключ, состояние которого в этом круге
не узнать (файл не читается) или о котором рано говорить «снова в порядке», отметьте в
`unknown(key, raisedAt)` — иначе он «пройдёт» по ошибке. `raisedAt` — когда проблему объявили:
`mail.down` снимается, только если письмо ушло позже него (`lastMailSentAt`), — пустая очередь
бывает и у сломанной почты, когда письма исчерпали попытки.

Разовое служебное событие, без «проблема — снова в порядке», — обычный `notify` в действии, как
`update.requested` (владелец нажал «Обновить», `modules/status/routes.ts`): в `watch.ts` его нет, в
схеме данных нет `state`.

## Telegram

- `telegram/bot-api.ts` — Bot API на `undici`: напрямую, через `ProxyAgent` (HTTP/HTTPS —
  туннелем CONNECT) или через `Socks5ProxyAgent` (SOCKS5: он сам раскодирует логин и пароль из
  адреса). `Socks5ProxyAgent` в undici 8 экспериментальный (в журнале — `ExperimentalWarning` при
  первом SOCKS): undici закреплён точной версией, а при обновлении обязаны пройти тесты с настоящим
  SOCKS5-рукопожатием в `telegram.test.ts`. Токен — в адресе запроса, из текстов ошибок он
  вычищается; адреса прокси в них нет вовсе — эти тексты видит и клиент.
- Адрес прокси разбирают двое: схема (`splitProxyUrl` в `@averra/schema`, без API среды —
  её читает и админка) и undici (через `URL`). `parseProxy` (`telegram/api.ts`) сверяет разборы;
  не совпали — 400 у поля `proxy`, а клиент Bot API отвечает ошибкой сети, не создавая агента.
  Спецсимволы в логине и пароле — только %-кодами.
- `telegram/format.ts` — текст с `parse_mode: HTML`: `& < >` экранируются, ссылка — текстом,
  значения полей делят то, что осталось от предела 4096 знаков после заголовка, подписей и ссылки.
- `telegram/binder.ts` — привязка чата одноразовым кодом: `getUpdates`, пока есть живые коды.
  `offset` живёт только в пределах сеанса привязки и одного бота: после недели без обновлений
  Telegram выбирает `update_id` случайно, и старый offset окажется выше хвоста очереди. На то,
  как сервер Bot API обработает такой offset, не полагаемся: tdlib читает очередь с головы, только
  если offset выше хвоста больше чем на 10, а при меньшем разрыве подтверждает (выбрасывает) всё
  ниже offset — и новое «Старт» тоже. Кончился сеанс — обработанное подтверждается и offset
  забывается; не подтвердилось — повторы отсеивает память последних `update_id`. Код, выданный,
  пока цикл подтверждал конец сеанса, не теряется: такой `wake()` поднимает флаг, и цикл
  запускается снова, как только кончится. Ответ бота в чат — тоже с экранированием: в нём
  название сайта. Опрос не удался (у бота webhook — 409, нет сети) — причина видна у ждущего кода
  в админке (`problem`).
- `TELEGRAM_API_URL` — свой адрес Bot API; e2e ходят в фейковый (`@averra/api/testing/telegram`).
