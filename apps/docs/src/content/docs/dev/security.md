Для разработчика, который трогает права, вход, открытые маршруты, почту или секреты. После страницы
вы будете знать, какие правила нельзя нарушать и почему, и не откроете дыру по забывчивости.

## Доступ

- **Всё под `/api` закрыто по умолчанию.** `authenticate` (`src/auth/middleware.ts`) пускает без
  входа только короткий список ([API](/averra-cms/dev/api/)). Открыть маршрут — значит осознанно
  вписать его туда. Открытый изменяющий маршрут пускает только по секрету из письма, его проверяет
  сам маршрут. Исключение — приём заявок: он открыт всем, поэтому стоит под антиспамом и принимает
  только то, что есть в опубликованной версии страницы.
- **Права сайта** маршрут не проверяет сам, а объявляет действие: `requireSite(db, 'page.publish')`.
  Что какой роли можно — одна таблица в `src/auth/access.ts`; новое действие — новая строка.
  Сайты создаёт только владелец (`requireOwner`).
- **Настройки SEO** (`site.settings`) — только владелец: индексация, адрес, редиректы и счётчики
  решает студия ([почему](/averra-cms/decisions/seo-settings/)). Шаблоны политики и согласия
  (`legal-pages`) — тоже: они читают реквизиты организации.
- **Скрипт cookie-уведомления** берёт номера счётчиков из `data-` атрибутов страницы и проверяет
  их тем же шаблоном, что схема, прежде чем вставить в адрес и вызов счётчика. Своих внешних
  загрузок у него нет, а в режиме согласия до согласия на странице нет ни одного скрипта счётчика.
- **Открытый снимок сайта** (`GET /api/site/snapshot`, `…/:siteId/snapshot`) отдаёт без входа
  только то, что и так видно снаружи: опубликованные страницы и настройки SEO. Коды проверки,
  номера счётчиков и таблица редиректов публичны с момента сохранения — коды и счётчики стоят в HTML,
  редиректы видны по ответу сервера, секретов в них нет. Организация (телефон, адрес, ИНН и ОГРН —
  у ИП это его личные данные) попадает только в разметку главной, поэтому в снимке её нет, пока
  главная не опубликована (`siteSnapshot`). Новое поле настроек, которого нет на сайте, в снимок не
  отдавайте.
- **Открытая карточка для соцсетей** (`GET /api/sites/:siteId/og/:slug`) рисуется только для
  опубликованной страницы и только по опубликованному заголовку: черновик наружу не виден, а набор
  карточек ограничен числом опубликованных страниц (кеш в памяти на 256 карточек, одна отрисовка
  за раз), и перебор адресов не заставляет рисовать заново. Предпросмотр с любым заголовком
  (`…/og-card`) — только тем, кто видит сайт, со своим кешем (не вытесняет карточки сайта) и
  очередью не длиннее четырёх: поток заголовков получает 429, а не очередь до бесконечности.
  В SVG карточки нет текста — только контуры букв и цвета темы `#RRGGBB`, проверенные схемой.
- **Canonical страницы на чужой домен** (`https://…`) может поставить любой, кто правит
  страницу, в том числе клиент и токен MCP. Такой canonical уводит страницу из выдачи в пользу
  того адреса — почти как редирект, который доступен только владельцу. Пока это не закрыто
  правами: в проверках SEO он виден советом «Основной адрес — другой» до публикации, страница
  пропадает из карты сайта, а публикация пишется в историю и откатывается. Ограничить его
  владельцем или доменами сайта — открытый вопрос (дорожная карта).
- **JS на опубликованном сайте — только счётчики аналитики**, и только с номером, заданным
  владельцем. Номер проходит строгий шаблон в схеме и ещё раз при сборке (`analyticsHead` в
  `apps/renderer/src/lib/seo.ts`): в скрипт попадают только цифры или `G-…`. Всё остальное из
  настроек уходит в HTML через экранирование, а в JSON-LD `<`, `>` и `&` записаны
  escape-последовательностями: строка не закроет `<script>` раньше времени.
- **Персональные данные посетителей** (`personalData` в `access.ts`: `leads.*` и `site.export`)
  токену API запрещены отдельной проверкой (403), что бы ни стояло в таблице. Новое такое действие —
  строка и в таблице, и в `personalData`.
- Коды: 401 — не вошёл или токен недействителен; 403 — роль есть, действие нельзя; 404 — сайта нет
  **или он чужой**.
- Изменяющий запрос с cookie — только с `Origin` админки. Запросы с токеном Origin не проверяют.
- **Ответ посетителю сайта** — HTML-страница (`messagePage` в `modules/leads/pages.ts`: тег `html` с
  экранированием, `PAGE_HEADERS` с CSP без скриптов). JSON — только по явному `Accept` без
  `text/html`. Перенаправлять посетителя — только на источник, который сам прислал форму (`Origin`,
  иначе `Referer`): открытого редиректа нет. Путь возврата — из маршрута, а не из `Referer`.
- **Редиректы сайта** (`GET /api/site/fallback/*`) ведут только туда, куда их направил владелец:
  внутренний путь или `https://`, без петель, — это проверяет схема при сохранении. Внутренний путь
  — с `/`, но не `//` и без `\` и управляющих символов: браузер читает `\` как `/`, и `/\evil.example`
  стал бы ссылкой на чужой домен. В `Location` не-ASCII кодируется (`redirectLocation`), одинаково в
  API и dev-рендерере.
- Ключи из запроса (поля формы) складываются в `Object.create(null)` и проверяются `Object.hasOwn`,
  а не `in`: иначе найдётся `constructor`.

## Учебный режим

Учебный секрет (`DEV_AUTH_SECRET`), демо-сайт и владелец для разработки — только в учебном режиме
(`isLocalDev` в `config.ts`): флаг `--dev` (его ставят только `dev` у API и e2e), `NODE_ENV` не
`production`, `ADMIN_URL` и `API_URL` на этом компьютере. Учебный режим не бывает режимом по
умолчанию: ни забытая переменная, ни их отсутствие его не открывают.

- Всё, что опасно без своих секретов, включается по `isLocalDev`, а не по одному `NODE_ENV`.
- Учебный секрет узнаётся `isDevAuthSecret` (после нормализации — по узнаваемым частям): с
  пробелами, в кавычках, в другом регистре — тот же публичный секрет. Учебный ключ почты — так же
  (`isDevMailKey`).
- На учебном секрете API отвечает только соединениям с loopback и с `Host` на localhost
  (`prepareRequest` в `src/client-ip.ts`) — это добавочная защита: прокси со своим `Host` её обходит.

Почему так — [Учебный режим только явно](/averra-cms/decisions/dev-mode/).

## Лимиты

- Свои лимиты — `createRateLimiter` (`src/rate-limit.ts`): число ключей в памяти ограничено.
- **Сначала IP, потом ключ, который выбирает клиент** (адрес почты): иначе перебор ключей раздувает
  память.
- **Лимит с общим ключом** (сайт) тратят только запросы, дошедшие до дела (сохранённая заявка):
  иначе мусор с многих IP выбивает лимит у настоящих людей. Лимит по IP — на всё.
- **IP — только ключ счётчика в памяти.** В базу и лог его не пишем (152-ФЗ).
- Открытый маршрут, который пишет в базу, ограничен и объёмом за сутки — в базе: частотные лимиты в
  памяти забываются при перезапуске, а база растёт насовсем.
- Действие, которое шлёт письмо на любой адрес (приглашение), — под лимитом и на адрес, и на того,
  кто шлёт.
- `X-Forwarded-For` доверяем только с `TRUST_PROXY=true`, иначе он перезаписывается адресом сокета.

## Пароли и токены

- Пароли и токены не печатаем и не логируем. В команды — скрытым вводом или переменной окружения,
  не аргументом.
- **Токены API** — в базе только SHA-256, сам токен показывается один раз. Формат
  `<префикс>_<id строки>_<секрет>`: строка ищется по id, хеш сравнивается за постоянное время
  (`constantTimeEqual`). Права токена — редактор на сайте, на который он выпущен (в установке
  сайт один).
- **Ссылки из писем** (сброс, приглашение) ведут на экран админки, токен — во фрагменте:
  `ADMIN_URL/<экран>#token=…`. Фрагмент не уходит на сервер, экран читает его один раз
  (`useLinkToken`) и убирает из адреса. В API токен приходит в теле, а не в пути.
- **Токены из писем в базе — только хешем.** Свои (приглашения) — как токены API. Токены сброса
  Better Auth хеширует `verification.storeIdentifier`; в базе на месте разделителя всегда `#`, а
  идентификаторы Better Auth начинаются с приставки без `#`, поэтому его запасной поиск по
  присланной строке «как есть» не совпадёт с сохранённой. Плагин, где идентификатор целиком задаёт
  клиент (`phone-number`, `siwe`), перед включением перепроверить. Токен сброса проверяем по формату
  до Better Auth; варианты путей обёрнутых эндпоинтов не пропускаем (404).
- Одноразовость — одним условным `UPDATE … WHERE ещё не использовано RETURNING` или атомарным
  погашением, а не «прочитать, потом записать».
- Ответ на «Забыли пароль?» одинаков для любого адреса — и по телу, и по времени, а лимит по адресу
  считает и несуществующие.
- **Действие, через которое можно перехватить доступ** (настройки почты), — только владелец и только
  с повторным вводом своего пароля: `passwords.confirm` (`src/auth/confirm-password.ts`). Неудачи
  считаются на пользователя, удачная возвращается (`refund`). Неверный пароль — 403
  `invalid_password` у поля, а не 401. Сначала проверка, можно ли действие (409), потом пароль.
- **Счётчик неудач своего пароля — один на все пути**, которыми вошедший проверяет пароль по HTTP
  (`createPasswordConfirmation` в `createApp`). Эндпоинт Better Auth, который проверяет пароль, либо
  идёт через него, либо закрыт (`CLOSED_AUTH_PATHS`, сейчас `/verify-password`). Пометка
  `scope: 'server'` доступа по HTTP не закрывает. Вход — отдельный путь со своим лимитом по IP:
  счётчик на аккаунт позволил бы кому угодно заблокировать владельцу вход.
- Записи с персональными данными удаляются по сроку обработчиком очереди (`cleanupAlso`): закрытые
  приглашения — по `MAIL_RETENTION_DAYS`, заявки — по сроку сайта.

## Почта

- **Письма — только через очередь:** `enqueueMail(dbOrTx, { template, data, to })` тем же объектом
  базы или транзакции, что и действие. Мимо очереди шлёт только `mail:test`.
- Провайдер — только через интерфейс `Mailer`; маршруты получают состояние почты без секретов.
- **From ставит провайдер из конфига.** Всё, что идёт в заголовки, проверяется схемами
  (`MailAddress`, `MailSubject`, `MailSenderName`, `MailLine()`), ссылки — `MailUrl`.
- Шаблон — файл в `src/mail/templates/` (`defineMailTemplate`: схема данных, пример, `render`) и
  строка в `templates/index.ts`. HTML — только тегом `html` из `src/mail/html.ts` (подстановки
  экранируются), оформление — инлайн-стилями из `src/mail/layout.ts`, без `<style>` и внешних
  ресурсов. У письма есть текстовая версия.
- Команда, которая кладёт письмо в очередь (`pnpm member:invite`), решает «почта есть» так же, как
  API (`readStoredPassword` из `src/mail/runtime.ts`). Ссылки из писем ведут на `ADMIN_URL`: если это
  localhost, а почта идёт по SMTP, команда отказывает, а API предупреждает в логе и на странице
  «Почта» (`src/mail/link-warning.ts`).
- Письмо посетителю на введённый им адрес — только фиксированный текст: в схеме шаблона нет полей с
  его вводом. Только после антиспама и под лимитом на ящик (`mailboxKey`).
- Письмо, которое ставится вместе с действием посетителя, — в той же транзакции. Письмо о записи с
  персональными данными ссылается на неё (`lead_id`, `ON DELETE CASCADE`).
- Кто-то, кроме владельца, может перенаправить письма с персональными данными — в той же транзакции
  письмо владельцам и прежним адресам.
- **Данные письма живут только до отправки** (`markSent` стирает, база держит проверкой). Шаблон с
  секретом объявляет `secret: { lifetimeMs }`: данные стираются и после неудачи, просроченное не
  отправляется и не повторяется.
- **SMTP — только шифрование** и `rejectUnauthorized: true` явно. Параметров, снимающих проверку,
  в коде нет, схема настроек из админки строгая. Своему CA доверяют только тесты (`ca`) и API e2e
  (`NODE_EXTRA_CA_CERTS`). Порт из админки — только 465 или 587; `connectPort` — только тесты.
- **Пароль SMTP** — в окружении или в базе только через `SecretBox` (`src/crypto/secret-box.ts`,
  AES-256-GCM: свой IV на каждое шифрование, тег 16 байт, AAD, версия ключа). Ключ —
  `MAIL_ENCRYPTION_KEY`, не производная от `AUTH_SECRET`. Наружу пароль не уходит никогда, даже
  зашифрованным; тексты ошибок проходят `maskSecrets`. Не расшифровалось — состояние с причиной, а
  не 500.
- Сохранённый пароль SMTP уходит только на сохранённый сервер (`effectivePassword`). Проверка
  подключения без пароля владельца работает с сохранённым паролем только на сохранённых настройках
  целиком и на почту самого владельца (`checkPasswordOf`).
- Почта решается так: окружение → настройки из админки → по умолчанию. Её держит `MailRuntime`
  (`src/mail/runtime.ts`): маршруты спрашивают нынешнее состояние, обработчик берёт провайдера перед
  каждым письмом, смена настроек — через `exclusive`.
- Аренда письма — на одно письмо (`renewLease`). Ошибка сервера (DNS, TLS, вход) ставит обработчик
  на паузу, а не тратит попытки; отказ на `MAIL FROM` — ошибка настроек, попытки не тратятся.
  Окончательный отказ письма — только 5xx на `RCPT TO` и `DATA`.
- **Проверка по шагам** (`diagnoseSmtp` в `src/mail/smtp-mailer.ts`). TLS считается пройденным
  только при живом зашифрованном соединении. Сбой после того, как TCP открылся, — не файрвол, и
  подсказки про него нет. Подсказка «адрес должен принадлежать ящику» — только на 5xx в ответ на
  `MAIL FROM`; 4xx — временный лимит, настройки не трогать. Как это проверяется в nodemailer — в
  комментариях у кода.
- Свой подвал у шаблона — `footer` в `MailContent` (`src/mail/templates/define.ts`), если общий
  («отвечать не нужно») неправда, как у письма с `Reply-To`.

Почему так — [Решения](/averra-cms/decisions/): outbox, пароль SMTP, токены хешем.
