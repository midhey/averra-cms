Для разработчика, который трогает `deploy/`, публикацию на сервере или состояние установки. После
страницы вы будете знать, какие правила держат установку безопасной и повторяемой.

Как этим пользуется студия — раздел [Установка и сопровождение](/averra-cms/install/).

## Образы и Compose

- `deploy/Dockerfile` — цели `api` и `web`; `compose.yaml`, `Caddyfile`, `install.sh`, `averra.sh`.
- **Секретов в образах нет** (`.dockerignore`): они приходят из `.env` установки.
- API в образе — только prod-зависимости и собранный JS, от пользователя `node`, без `--dev` и с
  `NODE_ENV=production`. Caddy — от `caddy`. Ни один контейнер не работает от root.
- Прав — минимум: `api` без capabilities и с `no-new-privileges`, `caddy` — только
  `NET_BIND_SERVICE`. У `api` `init: true`: он запускает сборщик с потомками.
- `TRUST_PROXY` включает `compose.yaml` рядом с Caddy, а не образ.
- Образ API — на той же Node, что в `devEngines.runtime`; версии базовых образов точные.
- Сторонние actions в `.github/workflows` — закреплены по SHA коммита с версией в комментарии; Node —
  `actions/setup-node` с версией из `devEngines.runtime`.

## Установщик

- **Повторяем:** записанный секрет не меняется никогда, созданное (владелец, сайт) второй раз не
  создаётся. `.env` читается как текст (не `source`) и пишется с правами 600 до того, как встанет на
  место.
- Значения, которые попадают в Caddyfile и `.env` (домены, почта, тег), проверяются шаблоном: ни
  пробелов, ни переводов строк.
- **Секреты** — скрытым вопросом или переменной окружения, никогда флагом. В команду в контейнере —
  переменной (`-e VAR` без значения), не аргументом.
- Проверки окружения — функции через `problem`: обычный прогон останавливается на первой,
  `--dry-run` показывает все.
- На сервер клиента копируются только `install.sh`, `averra.sh`, `compose.yaml` — это держит тест.

## Публикация на сервере

- Сайт — статика из `PUBLISH_DIR/<сайт>/current`. Сборки — только через очередь
  (`createPublishQueue`): по одной на установку, журнал в `site_builds`.
- Новая версия — новая папка; `current` меняется переименованием новой ссылки поверх старой. Папку,
  на которую смотрит `current`, не правим и не удаляем.
- Рендерер для публикации собирает сайт с `CMS_LINKS=relative`. В версию попадают только файлы, на
  которые ссылаются страницы: картинки (`copyReferencedMedia`) и `_astro` по ссылкам из HTML, CSS и
  JS (`pruneUnusedAssets`). Шрифты темы — папка `_fonts`: рендерер пишет в неё только начертания
  опубликованной темы, с хешем содержимого в имени (у темы на системных шрифтах папки нет).
- При старте API: `markInterrupted` до `serve()`, `resume` — после (сборщик ходит в этот же API).
- **Caddy на домене сайта открывает в API только `/api/forms/*`.** Новый открытый путь — осознанно,
  строкой в `Caddyfile`.
- Кеш в Caddy: `Cache-Control` ставится на ветку `handle`, а не матчером по пути файла — `header`
  выполняется раньше `try_files`. `immutable` — только то, у чего хеш или uuid в имени. Матчеры
  сайта точные: страница может называться `media`.

## `averra.sh`

- Всё, что делается с установкой снаружи контейнеров (бэкап, восстановление, обновление,
  состояние), — `deploy/averra.sh` на хосте. Конфигурация установки этой версии (`compose.yaml`,
  `averra.sh`) лежит в образе API (`/app/deploy`), обновление берёт её оттуда.
- Бэкап, восстановление и обновление держат один замок (`flock`).
- **Бэкап удачен только после проверки восстановлением.** Неудачный не хранится. Срок хранения —
  `BACKUP_KEEP` последних и не старше `BACKUP_KEEP` дней, по времени в имени, локально и во внешнем
  хранилище; чистка — после каждого бэкапа. Сбой чистки не глотается, он виден в состоянии.
  Собранные сайты не бэкапятся. Бэкап не зависит от API.
- **Восстановление базы — через новую базу и переименование.** Существующую служебную базу скрипт не
  удаляет, а отказывает. Откат обновления не удаляет рабочую базу никогда, а откладывает
  `averra_rolled_back_<время>`. Служебная база с временем в имени удаляется сроком бэкапов и видна в
  состоянии; без времени (`averra_before_restore`) — разбирает человек. Медиатека подменяется,
  пока API стоит.
- **Обновление останавливает API до бэкапа.** «Обновлено» — только когда API готов и API с Caddy
  держатся в `running`. Откат сначала останавливает новый API, потом считает миграции.
- **Долгая операция, которую нельзя бросить** (обновление), идёт процессом, отвязанным от SSH
  (`systemd-run`, без systemd — `setsid`), с выводом в файл. Ход — отметка по шагам
  (`.update-run`): повтор команды сначала доводит прерванное.
- **Файлы состояния** (`state/*.json`) пишет только `averra.sh`, атомарно (временный файл и `mv`);
  API их только читает (том `:ro`) и проверяет схемами (`BackupRun`, `UpdateRun`, `ReleaseCheck`,
  `ReleaseLatest`, `UpdateRequestDecision`): битый файл —
  «не читается», а не 500. Причина сбоя в них — фиксированная строка скрипта, не вывод команд.
- Секреты в чужой контейнер (rclone) — `-e VAR` без значения, пароль в `rclone obscure` — через
  stdin. Копия бэкапа вне сервера — только зашифрованная.

## Обновление из админки

Почему так — [Обновление из админки](/averra-cms/decisions/admin-update/).

- **У API нет Docker, сокета Docker, root и команд хоста — и не будет.** На хосте API пишет только
  в папку заявок `/opt/averra/requests` (в контейнере `/data/requests`, `REQUESTS_DIR`), владелец —
  `node` образа (uid 1000), права 700. Остальное с хоста — только чтение (`state`). Это держит тест
  `install.test.ts`.
- **Заявка** `requests/update.json` — одна строка ровно такого вида и порядка полей:
  `{"version":"X.Y.Z","requestedAt":"<ISO, Z>","requestedBy":"<uuid>"}`. API пишет её временным
  файлом и жёсткой ссылкой (`requestUpdate` в `src/status/host.ts`): целиком и только одну, вторая —
  409. Заявку, которую хост не забрал за 10 минут (`pendingStale`, `UPDATE_START_TIMEOUT_MS`),
  новая заменяет: служба заявок могла не работать, и кнопка не должна застревать навсегда. Схема — `UpdateRequestFile`, шаблон хоста — `REQUEST_RE` в `averra.sh`: меняются вместе.
- **Хост разбирает заявку без выполнения** (`averra.sh update-request`): `mv` в свою папку, не
  ссылка, обычный файл до 1 КБ, без нулевых байтов, вся строка — по `REQUEST_RE`, версия равна
  `release-latest.json` и новее `AVERRA_VERSION`, релиз не ломающий (`"breaking":true`), прошлое
  обновление не кончилось `rollback-failed` и не откатилось на этой же версии (`rolled-back` с
  `"to"` этой версии — так же решает `updateBlock` в схеме), замок свободен. Заявка удаляется до
  запуска, дальше — `start_worker`, тот же update (с `--request <время>`: не взял замок или так и
  не начал своё обновление — прерванное прошлое кончилось откатом — пишет отказ в
  `update-request.json`, а не молчит). `accepted` пишется до запуска (время заявки раньше начала
  её обновления), не запустился процесс — отказ поверх. Отказ — строка `---- … отклонена` в
  `update.log` и `state/update-request.json`, код 0: отказ — штатный итог, служба не помечается
  упавшей. Предел запусков у службы снят (`StartLimitIntervalSec=0`: systemd считает запуски, а
  не падения, и частые заявки остановили бы path-юнит); упавший path-юнит видно по `is-active`.
  Текст кривой заявки никуда не копируется.
- **Файлы проверки версии** (пишет только `averra.sh`): `release-check.json` — последняя попытка
  (`ReleaseCheck`: время, версия, ok, причина, `adminUpdate`, `requestsWatched` — включён и
  работает ли path-юнит заявок, `systemctl is-enabled` и `is-active`), `release-latest.json` —
  последний найденный релиз (`ReleaseLatest`, версия первым полем — по ней хост сверяет заявку;
  `breaking` — раздел BREAKING CHANGES у любого релиза новее установленной или промежуток виден
  не целиком, перед заметками; `releases` — сколько релизов в заметках; при сбое сети не
  стирается), `update-request.json` — решение по последней заявке (`UpdateRequestDecision`). В
  `update-last.json` — `step` (`UpdateStep`): шаг для показа хода, и `failedStep` — на каком шаге
  новая версия не прошла перед откатом (`FAILED_STEP` в `.update-run`); решения при обрыве
  по-прежнему принимает `PHASE` в `.update-run`.
- **Ответ источника релизов — чужие данные.** `check-update` качает его `curl` (только https,
  30 секунд, до 2 МБ) и разбирает `node dist/server/release-info.js --current <установленная>` в
  образе установленной версии (`--network none --read-only --cap-drop ALL`); на хост возвращается
  одна строка JSON, которую скрипт проверяет ещё раз. Источник — список релизов
  (`/releases?per_page=30`): заметки и `breaking` считаются за все версии новее установленной.
  Версия новее установленной записывается, только если её образы api и web есть в реестре
  (`docker manifest inspect`). Всё, что зависит от источника (формат, адрес, заголовки запроса), —
  в `release_source`, `check_update` общий; новый источник — ветка там и формат в
  `apps/api/src/release/release-info.ts`.
- **Службы systemd — в `averra.sh install-units`**, а не в `install.sh`: `averra-backup.service`
  (`ExecStartPre=-… check-update`) и `.timer`, `averra-update-request.path` (`PathExists`) и
  `.service` (`ExecStopPost` удаляет заявку), `averra-update-resume.service`
  (`ConditionPathExists=…/.update-run`, `Before=averra-backup.service`, включается без
  `--now`): при старте сервера `update-resume` доводит прерванное обновление (`update-worker
  --resume` — только `recover_update`, нового не начинает; замок ждёт до 30 минут, а не уходит
  сразу; откат — штатный итог, код 0). У прежнего скрипта с новым **два договора — команды
  не переименовывать**: `ensure-dirs` — перед запуском новой версии прежний скрипт копирует новый
  `averra.sh` из `.next` в папку установки (`.averra-next.sh`: папку установки скрипт берёт по
  своему месту) и зовёт его `ensure-dirs`, так папки для нового `compose.yaml` встают до
  `compose up`; новые папки добавлять в `ensure_dirs`. `install-units` — после удачного
  обновления, когда новый `averra.sh` уже на месте: службы systemd и проверка версии.
- Права — действие `installation.update` (только `owner`, токену — `tokenDenied`) через
  `requireInstallation`: в адресе нет сайта. Что сейчас с обновлением (409 на вторую заявку, опрос
  в админке) — одно правило `updateActivity` в схеме.

## Состояние установки

- Владельцу — `GET /api/status`, студии — `averra.sh status --json` по SSH (та же `collectStatus`).
  Нового токена и открытого маршрута для студии нет.
- В ответе — числа, времена и короткие причины: без адресов, путей, логинов и секретов. Версии нет
  в открытых маршрутах.
- Сведения с хоста (файлы состояния, `statfs`) приходят интерфейсом `HostStatus`
  (`src/status/host.ts`).
- Почта «работает», только если в очереди нет писем с ошибкой последней попытки; дольше 15 минут —
  проблема `mail_failing` (`mailStuck` из схемы, один порог для админки и `status.js`).
- Подписи итогов — общие в схеме (`UPDATE_RESULT_LABELS`, `SITE_BUILD_STATUS_LABELS`), кодов в
  тексте для человека нет.

## Студия

- Список серверов (`pnpm fleet`) — вне репозитория, `~/.config/averra/servers.txt`.
- Относительные пути в командах `pnpm` разрешаются от `INIT_CWD` (откуда запустили), а не от папки
  пакета.
