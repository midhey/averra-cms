Для студии. После страницы вы будете знать, что лежит в бэкапе, как подключить внешнее хранилище и
как восстановить установку — на месте или на новом сервере.

## Команды

| Команда (от root) | Что делает |
|---|---|
| `averra.sh backup` | бэкап базы и медиатеки с проверкой восстановлением |
| `averra.sh backups` | список бэкапов |
| `averra.sh verify <бэкап>` | проверить ещё раз: контрольные суммы и восстановление дампа во временную базу |
| `averra.sh restore <бэкап> [--yes]` | восстановить базу и медиатеку |
| `averra.sh restore --from-s3 <бэкап> [--yes]` | то же из внешнего хранилища |

Скрипт лежит в `/opt/averra/averra.sh`. Бэкап, восстановление и обновление не идут одновременно:
у них общий замок.

## Что в бэкапе

Папка `/opt/averra/backups/<время UTC>-<вид>/` (вид — `scheduled`, `manual` или `pre-update`):

- `db.dump` — дамп PostgreSQL;
- `media.tar.gz` — медиатека: оригиналы и варианты картинок;
- `SHA256SUMS` и `manifest.json` — контрольные суммы, версия, число миграций, итог проверки.

Права — только root: папка 700, файлы 600.

**Чего нет в бэкапе:**

- **собранных сайтов** — API собирает их заново из базы и медиатеки;
- **`.env`** — храните его у студии отдельно, хотя бы `BACKUP_PASSPHRASE` и
  `MAIL_ENCRYPTION_KEY`.

## Когда

- **Каждый день около 03:30** — таймер systemd `averra-backup.timer`. Пропущенный (сервер был
  выключен) делается при старте. Журнал — `journalctl -u averra-backup`.
- **Перед каждым обновлением** — `pre-update`.
- **Руками** — `averra.sh backup`.

Бэкап не зависит от API: медиатеку снимает отдельный контейнер с томом, поэтому бэкап идёт и при
лежащем API.

## Проверка

Каждый бэкап восстанавливается во временную базу, число миграций и таблиц сверяется с рабочей, а
архив медиатеки читается целиком. Не прошёл — бэкап неудачный, его файлы удаляются, а «Состояние
установки» показывает причину ([почему так](/averra-cms/decisions/verified-backups/)).

## Сколько хранится

`BACKUP_KEEP` в `/opt/averra/.env`, по умолчанию 7, от 1 до 365: столько последних удачных
бэкапов и **не старше стольких дней** — локально и во внешнем хранилище. Чистка — после каждого
бэкапа, удачного и неудачного. Кривое значение — бэкап не делается, причина видна в «Состоянии
установки» сразу.

## Внешнее хранилище

По желанию — S3-совместимое, например Yandex Object Storage. Строки в `/opt/averra/.env`:

```bash
BACKUP_S3_BUCKET=studio-backups
BACKUP_S3_ACCESS_KEY_ID=…            # сервисный аккаунт с доступом только к этому бакету
BACKUP_S3_SECRET_ACCESS_KEY=…
# необязательно:
BACKUP_S3_ENDPOINT=https://storage.yandexcloud.net   # по умолчанию
BACKUP_S3_REGION=ru-central1                         # по умолчанию
BACKUP_S3_PREFIX=averra/example.ru                    # по умолчанию averra/<домен сайта>
```

- Копия **шифруется** паролем `BACKUP_PASSPHRASE` (rclone crypt: XSalsa20 + Poly1305, имена
  файлов тоже). Пароль создаёт установщик. **Сохраните его в менеджере паролей студии**: без него
  копию не расшифровать, если сервер пропадёт вместе с `.env`.
- Ключу нужны права на запись, список и удаление (`storage.editor` в Yandex Object Storage): без
  удаления не соблюсти срок хранения. Второй страховкой поставьте в бакете правило жизненного цикла
  «удалять объекты старше `BACKUP_KEEP` + 2 дней».
- Ключи и пароль уходят в контейнер rclone переменными окружения, не аргументами.
- Не выгрузилось — локальный бэкап всё равно удачный, а «Состояние установки» пишет, что копии нет.
  Не удалились старые копии — тоже видно там.

## Восстановление на месте

```bash
sudo /opt/averra/averra.sh backups
sudo /opt/averra/averra.sh restore 20261016-033512-scheduled
```

Всё, что изменилось после бэкапа, пропадёт, поэтому скрипт спрашивает подтверждение (`--yes` — без
вопроса). Порядок:

1. Сверяются контрольные суммы. Медиатека распаковывается во временную папку, дамп встаёт в
   отдельную базу. Сбой здесь ничего не меняет.
2. API останавливается, базы меняются именами (прежняя — `averra_before_restore`), медиатека
   подменяется распакованной, том сайтов очищается.
3. API поднимается, ставит ссылку `main` на сайт установки из восстановленной базы и сам собирает
   опубликованный сайт — уже из восстановленных базы и медиатеки.
4. Поднялся — прежние база и медиатека удаляются. Нет — прежние база и медиатека возвращаются на
   место, а неподнявшаяся база остаётся как `averra_failed_restore_<время UTC>`
   (в ней данные бэкапа; удалится сама через `BACKUP_KEEP` дней).

Если от прошлого неразобранного восстановления уже есть база `averra_before_restore` или папка
`.averra-before-restore` в томе медиатеки, скрипт откажет и ничего не тронет. Разберите её руками
(«Состояние установки» её покажет).

## Восстановление на новом сервере

1. Поставьте Averra установщиком с тем же доменом и переключите DNS.
2. Впишите в новый `/opt/averra/.env` прежние `BACKUP_PASSPHRASE` и `BACKUP_S3_*`. Лучше и прежний
   `MAIL_ENCRYPTION_KEY` — тогда почта заработает сразу.
3. Восстановите:

   ```bash
   sudo /opt/averra/averra.sh restore --from-s3 20261016-033512-scheduled --yes
   ```

Какой сайт отдавать на домене, API узнаёт из восстановленной базы сам: `.env` для этого править не
нужно, даже если новый установщик успел завести свой сайт. Секреты могут быть новыми, с
оговорками:

- новый `AUTH_SECRET` — все выйдут из админки, войти заново прежними паролями;
- новый `MAIL_ENCRYPTION_KEY` — пароль SMTP из базы не расшифруется, почта выключится с причиной
  «введите пароль SMTP заново». Введите его на странице «Почта».
