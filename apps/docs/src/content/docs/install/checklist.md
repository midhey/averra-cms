Для студии перед первым клиентом и после крупных изменений в установке, обновлении или бэкапах.
Docker, Caddy, PostgreSQL и настоящий VPS на машине разработки не проверить — тесты подделывают
внешние команды. Пройдя этот список на тестовом сервере, вы убедитесь, что всё работает
по-настоящему.

**Нужно:** два тестовых VPS на Ubuntu 24.04 с 1–2 ГБ памяти, по два DNS-имени, бакет в Yandex
Object Storage и два релиза подряд (например, `0.2.0` и `0.2.1` с новой совместимой миграцией).
Итог и найденное запишите в задачу или заметки релиза.

## Образы

1. Релиз прошёл, в GHCR есть `averra-api` и `averra-web` нужной версии для amd64 и arm64. Образ API
   разумного размера (ориентир — меньше 600 МБ). Пакеты публичные: после `docker logout ghcr.io`
   команда `docker pull ghcr.io/midhey/averra-api:<версия>` проходит без входа.
2. В образе нет dev-зависимостей: `docker run --rm --entrypoint sh ghcr.io/midhey/averra-api:<версия>
   -c 'ls /app/node_modules/.pnpm | grep -E "^(vitest|drizzle-kit|typescript|@biomejs)@"'` — пусто.
   tsx и esbuild там есть: их приносят vite и astro для сборщика сайта.
3. Не root: `docker run --rm ghcr.io/midhey/averra-api:<версия> id` — `uid=1000(node)`;
   `docker run --rm --entrypoint id ghcr.io/midhey/averra-web:<версия>` — `uid=1000(caddy)`.
4. sharp на месте: `docker run --rm --entrypoint node ghcr.io/midhey/averra-api:<версия> -e
   "require('sharp')"` из `/app/apps/api` — без ошибок.

## Установка

5. `bash install.sh … --dry-run` без sudo — в списке проблем «нет прав… запустите через sudo».
6. Установка по [инструкции](/averra-cms/install/server/) без `--ghcr-user`: пароль спрашивается
   скрыто, в `history` его нет, в конце — адрес админки. `ls -l /opt/averra/.env` — `-rw-------` root.
7. Повторный запуск с теми же флагами — «секреты не менялись», владелец и сайт не созданы второй
   раз, вход в админку не слетел.
8. Без терминала: `read -rs AVERRA_OWNER_PASSWORD; export AVERRA_OWNER_PASSWORD; sudo -E bash
   install.sh … --yes </dev/null` на чистой папке — владелец создан, `ps aux` во время прогона
   пароля не показывает.
9. Прерванный прогон (Ctrl+C на записи `/opt/averra`) не оставляет файлов `.env.*`.
10. Проверки установщика: nginx на 80 — отказ «порты заняты»; домен не туда — отказ с адресами;
    AAAA-запись на чужой IPv6 при верной A — отказ с подсказкой про AAAA. `--dry-run` показывает
    все проблемы сразу.

## SSL, заголовки, процессы

11. Оба домена по https с сертификатом Let's Encrypt, http → https; `curl -I https://admin…` — HSTS
    и `X-Frame-Options`.
12. `docker compose exec caddy id` — `uid=1000(caddy)`. PID 1 в контейнере API — `docker-init`.
13. Кеш админки: `/` и `/pages` — `no-cache`, `/assets/<файл>` — `immutable`,
    `/assets/nope.js` — 404.
14. Учебного режима нет: `NODE_ENV` в контейнере API — `production`, в логе нет «Учебный режим»,
    демо-сайта нет. В логе первого запуска — «Создан сайт установки «<название>»», в
    `/data/sites` — ссылка `main` на папку этого сайта.

## Админка и публикация

15. Вход владельцем: cookie `Secure` и `HttpOnly`, без ошибок CORS. Сразу обзор сайта, без
    выбора сайта; в панели — название и домен сайта. Выход и вход снова.
16. Лендинг с картинкой и формой → «Опубликовать»: «Собирается…», потом «собран». Сайт по https,
    картинки с `/media/…` — `immutable`, HTML — `no-cache`.
17. Во время публикации `while true; do curl -s -o /dev/null -w '%{http_code}\n' https://сайт/;
    done` — только 200.
18. Сбой сборки не ломает сайт: `docker compose exec api sh -c 'chmod -w
    /data/sites/<id>/releases'`, «Опубликовать» — «Последняя сборка упала» с причиной, сайт
    прежний. Вернуть права, «Собрать заново» — новая версия.
19. Код рендерера только для чтения: `touch` в `/app/apps/renderer/src`, `scripts`, `node_modules`
    — «Permission denied»; `/app/apps/renderer/.astro` — ссылка в `/data/sites/.cache`.
20. Семь публикаций — в `releases` пять папок, `current` на последней.
21. «Опубликовать» и сразу `docker compose restart api` — после старта сборка прошла заново.
22. Пик памяти сборки (`docker stats`) на VPS 1 ГБ — без OOM, в логе API строка «собран за N с, пик
    памяти M МБ». Запишите цифру.

## Формы и почта

23. Заявка с сайта без JS — «Спасибо» на той же странице, заявка в админке. Шесть подряд с одного
    IP — 429 на шестой, с другого IP — проходит.
24. SMTP на странице «Почта», «Проверить подключение», заявка → письмо. Telegram на настоящем VPS:
    бот в «Уведомлениях» (с российского VPS — через прокси), «Проверить» — сообщение пришло,
    привязка чата ссылкой, заявка → сообщение в чат.
25. Неверный адрес отправителя («Сохранить без проверки») и 15 минут — в «Состоянии» «Письма не
    уходят», в `pnpm fleet status` — «с ошибкой 1». Исправить — проблема уходит.

## Бэкапы

26. `systemctl list-timers averra-backup.timer` — следующий запуск около 03:30;
    `systemctl start averra-backup.service` — бэкап прошёл.
27. `averra.sh backup` — в папке `db.dump`, `media.tar.gz`, `SHA256SUMS`, `manifest.json`, права
    600, папка 700; базы `averra_verify` после нет.
28. Испорченный дамп (`truncate -s 100 …/db.dump`) — `verify` отказывает. Остановленный Postgres —
    бэкап неудачный, в админке «Последний бэкап не удался». Остановленный API — бэкап удачный.
29. `BACKUP_KEEP=3` и пять бэкапов — осталось три. `BACKUP_KEEP=2` и папка с именем трёхдневной
    давности — после бэкапа её нет.
30. Внешнее хранилище: имена файлов в бакете зашифрованы, в `ps aux` во время выгрузки нет ключей.
    Неверный ключ — бэкап удачный, в админке «копия не выгрузилась». Ключ без права удаления —
    «старые копии не удалились».
31. Во время `restore` создать `/data/media/.averra-before-restore/x` — следующий бэкап её не берёт,
    а `restore` при ней отказывает.

## Восстановление

32. На месте: страница, заявка и картинка после бэкапа → `restore` — их нет, сайт пересобран
    («собран», а не «ошибка»), вход работает, `averra_before_restore` и `.averra-before-restore`
    после успеха нет, «Подменяю медиатеку» в выводе — до запуска API.
33. На новом сервере: установка с тем же доменом, прежние `BACKUP_PASSPHRASE` и `BACKUP_S3_*`,
    `restore --from-s3 … --yes`. Сайт, страницы, заявки и картинки прежние, первая сборка «собран»,
    `.env` не менялся, вход прежним паролем. С новым `MAIL_ENCRYPTION_KEY` — «введите пароль SMTP
    заново» и «введите токен бота заново» в «Уведомлениях»; с прежним — почта и Telegram работают
    сразу.
34. При существующей `averra_before_restore` — отказ, ни одна база не тронута.
35. Восстановление на образе, который не стартует, — «прежние база и медиатека на месте», в
    «Состоянии» `averra_failed_restore_…`, после `BACKUP_KEEP` дней её нет.

## Обновление и откат

36. `averra.sh update --version 0.2.1` под циклом `curl` — только 200. Версия новая,
    `compose.yaml.prev` рядом, бэкап `…-pre-update`, итог `updated`. Отдельно — обновление с
    версии, где ещё не было ссылки `main` (до «одна установка — один сайт»): сайт доступен сразу
    после обновления. Новый Caddy может ответить раньше, чем API поставит ссылку, — запишите,
    сколько секунд был 404, если он был.
37. Образ, у которого API не стартует, без миграций — код 1, «работает прежняя версия», база не
    восстанавливалась.
38. Образ с миграцией, который падает после неё — «восстанавливаю базу», миграций снова N,
    `averra_rolled_back_…` с N+1 миграцией в «Состоянии».
39. Образ `web` с ошибкой в Caddyfile — код 1, сайт отдаётся, итог `rolled-back`.
40. Форма в цикле во время обновления — 502 только пока идёт бэкап и старт; после отката с
    восстановлением заявки новой версии — в `averra_rolled_back_…`.
41. `averra.sh backup` во время `update` — отказ про замок; `update` во время бэкапа — отказ,
    `update.log` не обнулился.
42. Обрыв SSH через 10 секунд после старта обновления — служба `averra-update-*` идёт, лог доходит
    до «Готово», итог не `in-progress`. Повтор во время — показывает лог; после — «Уже версия».
43. `reboot` после «Запускаю 0.2.1» — `averra.sh status` «обновление оборвалось», повтор `update`
    доводит или откатывает.
44. Без systemd (Docker внутри контейнера) — обновление идёт через `setsid` и переживает закрытие
    SSH.

## Студия

45. `pnpm fleet status` с двумя серверами — таблица; выключенный сервер — строка «SSH: …», код 1;
    сервер не из `known_hosts` — отказ.
46. `pnpm fleet update --version 0.2.1` — по очереди; недоступный первый — стоп, второй не тронут.
47. Без `~/.config/averra/servers.txt` — отказ с полным путём; `--file ./my.txt` из корня
    репозитория находит файл.

## Выгрузка и прочее

48. «Скачать сайт архивом» открывается локально (`python -m http.server`) так же, как сайт;
    «Выгрузить все данные» — `site.json` с заявками и оригиналы картинок.
49. Место на диске в «Состоянии» близко к `df -h /var/lib/docker /opt/averra`.
50. `docker compose restart postgres` — API переживает, `/api/health/ready` снова 200. `reboot` —
    всё поднимается само. Версии нет в `curl -s https://admin…/api/health/ready`.

## SEO и адреса без страницы

51. Новая установка: `curl -s https://сайт/robots.txt` — `Disallow: /`, на главной
    `noindex, nofollow`, на обзоре админки — «Сайт скрыт от поисковиков». Снять флажок в «SEO» —
    после сборки `robots.txt` со строкой `Sitemap: https://сайт/sitemap.xml`, карта открывается.
52. `curl -I https://сайт/nope` — `404`, тело — страница 404 сайта в его оформлении (своя после
    публикации страницы `/404`). Сайт ещё не собран — «Страница не найдена» от API.
53. Редирект `/old → /` в «SEO»: `curl -I https://сайт/old` и `/old/` — `301`, `location: /`,
    без пересборки. Редирект с адреса существующей страницы админка не сохраняет. Метки не
    теряются: `curl -I "https://сайт/old?utm_source=ya"` — `location: /?utm_source=ya`.
    Закодированный `?` остаётся частью пути: `curl -I "https://сайт/old%3Fb?utm=1"` — `404`, а
    не `301` на `/?b`.
54. Иконка в «SEO» — после сборки `https://сайт/favicon.ico` и `/apple-touch-icon.png` отдаются,
    вкладка браузера с иконкой. Остановленный API — страницы сайта открываются, `/nope` — 502.
