Для студии. После страницы вы поставите Averra на подготовленный сервер, войдёте в админку
владельцем и будете знать, как безопасно перезапустить установщик.

Перед установкой — [требования к серверу](/averra-cms/install/requirements/).

## Запуск

На сервер копируются только четыре файла: установщик, `averra.sh`, `compose.yaml` и
`compose.external.yaml` (он нужен [внешней базе](#внешняя-база)). Папку `deploy/`
целиком не копируйте: в ней `node_modules` со ссылками на инструменты разработки (около 120 МБ)
и тесты, а бывает и список серверов студии — клиенту он ни к чему.

```bash
# с машины студии
ssh root@vps mkdir -p /root/averra-deploy
scp deploy/install.sh deploy/averra.sh deploy/compose.yaml deploy/compose.external.yaml root@vps:/root/averra-deploy/
# на сервере
cd /root/averra-deploy
sudo bash install.sh --site-domain example.ru --email studio@example.com --version 0.1.0
```

Установщик спросит скрыто пароль владельца. Секреты флагами не передаются: они
попали бы в историю команд и список процессов.

Что он делает:

1. Проверяет Docker, свободные порты 80 и 443 и DNS обоих доменов.
2. Пишет `/opt/averra/.env` с новыми секретами (`AUTH_SECRET`, `MAIL_ENCRYPTION_KEY`, пароль
   Postgres, `BACKUP_PASSPHRASE`) с правами 600 и кладёт рядом `compose.yaml` и `averra.sh`.
3. Скачивает образы (с `--ghcr-user` сначала входит в `ghcr.io`), поднимает PostgreSQL и API,
   ждёт готовности до трёх минут. Если скачивание упало, причину видно по ответу Docker:
   - `denied` или `unauthorized` — пакеты в GHCR ещё закрытые (их не переключили в Public после
     первого релиза, [Релизы](/averra-cms/dev/releases/)) или в `--api-image` / `--web-image`
     опечатка. Переключите пакеты или повторите установку с `--ghcr-user` и токеном
     `read:packages`;
   - `manifest unknown` — такой версии нет: проверьте `--version`.

   API при первом запуске сам создаёт сайт установки с названием из `--site-name`: одна
   установка — один сайт ([почему](/averra-cms/decisions/single-site/)).
4. Создаёт владельца.
5. Поднимает Caddy и ставит службы systemd — `averra.sh install-units`: ежедневный бэкап с
   проверкой новой версии (`averra-backup.timer`), заявки на обновление из админки
   (`averra-update-request.path`) и доведение обновления, прерванного перезагрузкой
   (`averra-update-resume.service`, запускается при старте сервера, только если обновление
   оборвалось). Папка заявок `/opt/averra/requests` (владелец — пользователь
   API, uid 1000, права 700) создаётся до запуска API: это единственное, что API пишет на сервере
   ([Обновления](/averra-cms/install/updates/#обновить-из-админки)).

В конце — адрес админки и что делать дальше.

## Флаги

| Флаг | Что задаёт |
|---|---|
| `--site-domain <домен>` | домен сайта. Обязателен при первой установке |
| `--email <почта>` | почта для Let's Encrypt и вход владельца. Обязателен при первой установке |
| `--version <версия>` | версия образов, например `0.1.0`. Обязателен при первой установке |
| `--admin-domain <домен>` | поддомен админки, по умолчанию `admin.<домен сайта>` |
| `--owner-name <имя>` | имя владельца, по умолчанию «Владелец» |
| `--site-name <название>` | название сайта при первом запуске (`SITE_NAME`), по умолчанию домен. Без кавычек и знаков `$ # \`; потом название живёт в базе |
| `--dir <папка>` | папка установки, по умолчанию `/opt/averra` |
| `--api-image`, `--web-image` | свои образы без тега (по умолчанию `ghcr.io/midhey/averra-api` и `averra-web`) |
| `--public-ip <IP>` | адрес сервера за NAT; у сервера с IPv4 и IPv6 — флаг на каждый адрес |
| `--ghcr-user <логин>` | вход в ghcr.io для закрытых образов (свой форк или пакет), токен спросят скрыто |
| `--skip-dns-check` | не проверять DNS. Сертификата не будет, пока DNS не заработает |
| `--skip-port-check` | не проверять порты 80 и 443 |
| `--install-docker` | поставить Docker из пакетов Ubuntu |
| `--external-db` | [внешняя PostgreSQL](#внешняя-база) вместо своей: адрес — переменной `AVERRA_DATABASE_URL` или скрытым вводом |
| `--db-ca-file <файл>` | корневой сертификат провайдера внешней базы (PEM), если он не из публичных |
| `--env-only` | только записать папку установки и `.env`, Docker не трогать |
| `--dry-run` | показать план и пройти проверки только на чтение, ничего не меняя |
| `--yes` | ничего не спрашивать |

`--dry-run` выводит все проблемы сразу и выходит с кодом 1, если они есть. Справка —
`bash install.sh --help`.

**Без терминала** секреты передаются переменными окружения, не набирая значение в командной
строке:

```bash
read -rs AVERRA_OWNER_PASSWORD; export AVERRA_OWNER_PASSWORD
sudo -E bash install.sh … --yes
```

Токен для закрытых образов передаётся так же: `read -rs GHCR_TOKEN; export GHCR_TOKEN` и флаг
`--ghcr-user <логин>`.

## Внешняя база

По умолчанию база — своя: контейнер `postgres` рядом с API. Если у клиента управляемая
PostgreSQL на другом сервере, установку ставят с флагом `--external-db`. Что нужно от базы и
провайдера — [Требования](/averra-cms/install/requirements/#внешняя-база).

Адрес — **не значением флага**: в нём пароль. Его передают переменной окружения или вводят
скрыто, когда установщик спросит:

```bash
read -rs AVERRA_DATABASE_URL; export AVERRA_DATABASE_URL
sudo -E bash install.sh --site-domain example.ru --email studio@example.com --version 0.1.0 \
  --external-db
```

Вид адреса — `postgres://пользователь:пароль@хост:6432/база`. Знаки `@ : / # ? %`, пробел и
кавычки в пароле записывают percent-encoded: `@` → `%40`, `:` → `%3A`, `/` → `%2F`, `#` → `%23`,
`?` → `%3F`, `%` → `%25`. Установщик разбирает адрес (пользователь, пароль, хост, порт, база) и
объясняет, что не так, не печатая сам адрес.

**TLS обязателен.** Нет `sslmode` — установщик допишет `sslmode=verify-full`: шифрование с
проверкой сертификата и имени хоста. `disable`, `allow` и `prefer` — отказ: пароль и заявки
шли бы по сети открыто. `require` и `verify-ca` — тоже отказ: они не сверяют имя сервера с
сертификатом. Сертификат провайдера выпущен не публичным центром — передайте его корневой
сертификат флагом `--db-ca-file /root/provider-ca.pem` (относительный путь — от текущей папки):
он ляжет в `/opt/averra/db-tls/ca.pem`, а в адрес допишется `sslrootcert`. `%00` в адресе —
отказ: нулевой байт клиент бэкапов и API поняли бы по-разному. Раскодированные пользователь и
пароль должны быть текстом UTF-8: `%FF` и другие одиночные байты — отказ (API такой адрес не
разберёт); знак не из латиницы кодируют всеми его байтами UTF-8 (`я` → `%D1%8F`). После разбора установщик убирает
`AVERRA_DATABASE_URL` из своего окружения: команды, которые он запускает, адрес не наследуют.

До записи `.env` установщик входит в базу клиентом PostgreSQL из образа `postgres` и проверяет:

- вход по TLS с проверкой сертификата. Не вошёл — причина словами: IP сервера не разрешён в
  `pg_hba.conf` или списке доступа провайдера, сертификат не сошёлся, пароль не тот, сервер не
  отвечает;
- версию сервера: 16, 17 или 18. По ней выбирается образ клиента той же версии —
  `AVERRA_PG_IMAGE` в `.env`: `pg_dump` не бывает старше сервера;
- право `CREATE` на базе (миграциям нужна схема `drizzle`) и на схеме `public`. Нет — установщик
  печатает готовый `GRANT` или `ALTER SCHEMA … OWNER` для владельца базы;
- что база пустая или уже база Averra: чужие таблицы в `public` — отказ. На повторном запуске
  (владелец уже создан) база должна быть базой Averra: адрес, который ведёт в базу без миграций
  (опечатка, другая база у провайдера), — отказ, иначе API поднялся бы на пустой базе без
  владельца.

Потом установщик скачивает образ клиента бэкапов (`AVERRA_PG_IMAGE`): не скачался — отказ сразу,
а не сбой первого ночного бэкапа.

В `.env` пишутся `AVERRA_DB_MODE=external`, `DATABASE_URL` в одинарных кавычках (Compose не
подставляет в них `$` из пароля) и `AVERRA_PG_IMAGE`. Своего контейнера `postgres` нет: в папку
установки ложится `compose.external.yaml` под именем `compose.yaml`, и API ждёт только внешнюю
базу. `--dry-run` показывает базу в плане и проходит те же проверки.

Режим — один на установку. Повторный запуск без флага остаётся на внешней базе, а адрес берёт
из `.env` или из новой `AVERRA_DATABASE_URL` (сменили пароль — запустите с ней). Перевести на
внешнюю базу установку, где уже есть владелец и данные в своей базе, установщик откажется: данные
остались бы в томе `postgres`. Если прошлая установка со своей базой оборвалась до создания
владельца, перевести можно: контейнер `postgres` установщик остановит и уберёт (том остаётся).
Переезд — бэкапом: новая установка с `--external-db` и
[`averra.sh restore`](/averra-cms/install/backups/#восстановление-на-новом-сервере).

Провайдер обновил сервер до новой мажорной версии — запустите установщик ещё раз: он узнает
версию и сменит образ клиента бэкапов.

## Первый вход

Откройте `https://admin.<домен>` и войдите почтой из `--email` и паролем, который ввели в
установщике. Сайт появится на домене после первой публикации.

Дальше:

- задайте SMTP на странице «Почта» — [Почта](/averra-cms/install/mail/);
- сохраните `.env` (или хотя бы `BACKUP_PASSPHRASE` и `MAIL_ENCRYPTION_KEY`) в менеджер паролей
  студии, отдельно от бэкапов;
- пригласите клиента — [Участники и приглашения](/averra-cms/admin/members/);
- заполните раздел [«SEO»](/averra-cms/admin/seo/): адрес, описание, иконку, счётчики. Сайт
  создаётся **скрытым от поисковиков**, пока его делают. Когда он готов к запуску, снимите
  «Скрыть сайт от поисковиков» в карточке «Индексация» — иначе его не найдут в поиске.

## Повторный запуск

Безопасен. Уже записанные секреты не меняются никогда, владелец и сайт второй раз не создаются.
Новые домены, почта или версия из флагов записываются в `.env` и применяются, ваши строки в
`.env` сохраняются. Так же — переход со старой установки без `averra.sh`: скопируйте четыре файла
новой версии и запустите установщик с прежними флагами и новой `--version`; бэкап перед этим
снимите руками (`docker compose exec -T postgres pg_dump -U averra -d averra -Fc >
/root/averra-before.dump`).

## Учебного режима на сервере нет

API в образе запускается с `NODE_ENV=production` и без флага `--dev`, поэтому учебного секрета,
демо-сайта и владельца для разработки на сервере не бывает. Подробно — [Учебный режим только
явно](/averra-cms/decisions/dev-mode/).

## Управление

Из `/opt/averra`:

```bash
docker compose ps                    # что запущено
docker compose logs -f api           # лог API
docker compose exec api node dist/server/user-password.js --email anna@example.ru
```

Команды терминала на сервере — `node dist/server/<команда>.js` в контейнере API: `user-create`,
`user-password`, `member-add`, `member-invite`, `token-create`, `token-list`,
`token-grant`, `token-revoke`, `mail-test`, `status`. С PostgreSQL они работают при запущенном API. Что делает каждая —
[Команды](/averra-cms/dev/commands/).

Бэкапы, восстановление, обновление и состояние — `averra.sh`:
[Обновления](/averra-cms/install/updates/), [Бэкапы](/averra-cms/install/backups/),
[Состояние](/averra-cms/install/status/).

## SMTP из окружения

Обычно SMTP задают в админке. Если он нужен из окружения, положите рядом с `compose.yaml` файл
`compose.override.yaml` — Compose подхватит его сам:

```yaml
services:
  api:
    environment:
      SMTP_HOST: smtp.yandex.ru
      SMTP_USER: noreply@example.ru
      SMTP_PASSWORD: ${SMTP_PASSWORD}
      MAIL_FROM: noreply@example.ru
```

Значение `SMTP_PASSWORD` — строкой в `/opt/averra/.env`. SMTP из окружения главнее админки: она
покажет его только для чтения.

## Если что-то пошло не так

| Что видно | Что делать |
|---|---|
| «нет прав на запись в /opt/averra» | запустить через `sudo` |
| «порты заняты» | остановить веб-сервер, который их держит (nginx, apache) |
| домен «не этого сервера» | поправить A/AAAA-записи или дождаться DNS; за NAT — `--public-ip` |
| API не стал готов за три минуты | `docker compose logs api`: обычно это образ не той версии или кривая строка в `.env` |
| «не удалось войти во внешнюю базу» | причина — в сообщении: доступ с IP сервера, сертификат (`--db-ca-file`), пароль, файрвол |
| Caddy не получил сертификат | DNS ещё не разошёлся или лишняя AAAA-запись; `docker compose logs caddy` |
