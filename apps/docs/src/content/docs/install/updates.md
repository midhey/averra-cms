Для студии. После страницы вы обновите установку до новой версии, поймёте, что значит каждый
исход, и будете знать, что делать, если связь оборвалась посреди обновления.

Как выходит новая версия и откуда берутся образы — [Релизы](/averra-cms/dev/releases/).

## Обновить

```bash
sudo /opt/averra/averra.sh update --version 0.2.0
```

В терминале скрипт спросит подтверждение («да»), `--yes` — без вопроса. Все установки студии сразу, по очереди — [`pnpm fleet update`](/averra-cms/install/fleet/).

Посетители видят сайт всё время: его отдаёт Caddy. Админка и приём заявок недоступны от остановки
API перед бэкапом до готовности новой версии — для лендинга это секунды на бэкап плюс старт API.
Форма в это окно получит 502.

## Что происходит по шагам

1. **Скачать образы** новой версии, пока всё работает. Не скачались — выход, ничего не менялось.
2. **Взять из образа** `compose.yaml` и `averra.sh` этой версии: конфигурация установки
   обновляется вместе с версией.
3. **Остановить API и сделать бэкап** с проверкой (`…-pre-update`). С этой минуты ничего не
   принимается, поэтому бэкап — последнее состояние базы. Не удался — прежний API снова
   запускается, выход.
4. **Переключить версию:** `AVERRA_VERSION` в `.env` (прежняя — в `AVERRA_PREVIOUS_VERSION`,
   прежний `compose.yaml` — в `compose.yaml.prev`), поднять новый API. Миграции он применяет сам
   при старте.
5. **Проверить:** дождаться `/api/health/ready` (до 180 секунд), поднять Caddy новой версии и
   убедиться, что API и Caddy держатся в `running`. Всё так — итог «обновлено».
6. **Иначе — откат** (ниже).

Внешняя копия бэкапа выгружается в самом конце, когда сервис уже работает.

Ждать готовности дольше — переменной окружения процесса, а не строкой `.env`:

```bash
sudo AVERRA_READY_TIMEOUT=300 /opt/averra/averra.sh update --version 0.2.0
```

## Откат

Если новая версия не стала готова:

1. Новый API останавливается — до подсчёта миграций, чтобы не успел применить их позже.
2. Возвращаются прежние `.env` и `compose.yaml`.
3. Если миграции успели пройти, база восстанавливается из бэкапа шага 3. **Рабочая база при этом не
   удаляется**, а откладывается как `averra_rolled_back_<время UTC>`: в ней то, что новая версия
   успела принять (заявки). Имя видно в выводе и в «Состоянии установки».
4. Поднимаются прежние API и Caddy.

Отложенную базу можно посмотреть:

```bash
cd /opt/averra
docker compose exec postgres psql -U averra -d averra_rolled_back_…
```

Перенесите из неё нужное. Удалится она сама вместе со старыми бэкапами через `BACKUP_KEEP` дней.

## Коды выхода

| Код | Что значит |
|---|---|
| 0 | обновлено |
| 1 | не начато (не скачались образы, не удался бэкап) или не прошло проверку — работает прежняя версия; что именно — в выводе и в «Состоянии» |
| 2 | откат не удался — нужен человек; скрипт подскажет, какой бэкап восстанавливать |
| 3 | процесс обновления оборвался без итога — повторите команду |

Итог пишется в `/opt/averra/state/update-last.json` и виден в «Состоянии установки».

## Обрыв связи не страшен

Обновление идёт отдельным процессом на сервере — службой systemd `averra-update-<время>`, без
systemd — через `setsid`. Команда только показывает его лог (`/opt/averra/update.log`). Обрыв SSH,
закрытый терминал или Ctrl+C прерывают показ, а не обновление: оно доходит до конца или до отката.

- Чем кончилось — `tail /opt/averra/update.log`, `averra.sh status` или «Состояние установки».
- Повтор той же команды, пока обновление идёт, показывает его лог.
- Процесс оборвался (перезагрузка сервера) — повторите `averra.sh update --version <та же>`. Она
  не ответит «уже эта версия», а **доведёт прерванное**: закончит обновление или откатит, с
  восстановлением базы, если миграции прошли.
- Обновление «идёт» дольше часа — в «Состоянии» проблема «похоже, оборвалось».

Пока идёт бэкап или восстановление, `update` сразу отказывает и ничего не трогает: у них общий замок.

## Почему откат безопасен

Миграции в Averra только совместимые вперёд: прежняя версия API работает на базе после миграций
новой. Это проверяет тест на каждый коммит. Поэтому прежний образ можно поднять и тогда, когда
база не восстановилась. Подробно — [Миграции только
вперёд](/averra-cms/decisions/forward-migrations/).

## Чего обновление не делает

**Не пересобирает сайт целиком.** Опубликованный сайт пересобирается сам, только если его версия
собрана до нынешнего формата релиза. Новое в обновлении, что видно на сайте только после сборки
(например, [карточки из заголовка](/averra-cms/admin/seo/#карточка-из-заголовка) у страниц без
своей картинки), появится после ближайшей публикации или сохранения настроек в разделе «SEO».
Так и с [cookie-уведомлением](/averra-cms/admin/cookies/): после обновления, где оно появилось,
счётчики сайта переходят на согласие посетителя с ближайшей сборкой — опубликуйте страницу или
нажмите «Собрать заново» в настройках сайта.

**Мажорную версию PostgreSQL** (`postgres:17…` в `compose.yaml`) обычное обновление не меняет:
новый мажор не читает файлы старого. Для этого нужна отдельная процедура (дамп и восстановление) —
её пока нет.

## Вернуть прежнюю версию руками

Если новая версия прошла проверку, но что-то не так уже в работе: обновите на прежнюю версию той же
командой (`averra.sh update --version <прежняя>`). Перед этим будет свой бэкап, а схема базы
прежней версии подходит — миграции совместимы вперёд. Данные, принятые новой версией, останутся.

Настройку раздела «SEO», которую прежняя версия не понимает (например, новый язык), она читает
значением по умолчанию и один раз пишет об этом в лог API. В базе настройка не меняется и снова
заработает после обновления. Ревизию страницы с полем, которого прежняя версия не знает,
восстановить в ней не получится — только в той версии, что её записала. Поля SEO страницы, которых
прежняя версия не знает (например, SEO-заголовок или картинку), её редактор не покажет, а
сохранение черновика в ней их сбросит; опубликованная версия страницы не меняется.
