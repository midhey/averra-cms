Для студии и владельца установки. После страницы вы обновите установку до новой версии — кнопкой
в админке или по SSH, — поймёте, что значит каждый исход, и будете знать, что делать, если связь
оборвалась посреди обновления.

Как выходит новая версия и откуда берутся образы — [Релизы](/averra-cms/dev/releases/).

## Обновить из админки

Владелец открывает «Состояние» → раздел «Обновление»: там «Установлена 0.1.0 · доступна 0.2.0»,
заметки к релизу и время последней проверки. Кнопка «Обновить до 0.2.0» спрашивает подтверждение
(что будет: бэкап, админка и приём заявок недоступны минуту-две, откат при сбое) и отправляет
заявку. Дальше экран сам показывает шаги — загрузка новой версии, бэкап, запуск и миграции,
проверка — и итог: «Обновлено» или «не прошло — работает прежняя версия» с тем, что делать. API
посреди обновления перезапускается: экран ждёт его и показывает итог сам, страницу можно не
закрывать. После обновления админка тоже новая — экран предложит обновить страницу.

Кнопка — только у владельца: редактор, клиент и токен API (MCP) обновлять не могут
([почему](/averra-cms/decisions/admin-update/)). Студия узнаёт, кто и до какой версии запросил
обновление, служебным уведомлением «Запрошено обновление»
([Уведомления](/averra-cms/admin/notifications/#служебные-события-владелец)) и строкой в журнале
API.

### Что делает сервер

У контейнера API нет ни Docker, ни root, ни команд хоста — обновляет только хост:

1. **Проверка новой версии.** `averra.sh check-update` спрашивает источник релизов (по умолчанию —
   релизы GitHub `midhey/averra-cms`) раз в сутки вместе с ночным бэкапом, сразу после установки и
   обновления и по команде. Берётся список последних 30 релизов: заметки и признак «ломающий» — за
   все версии новее установленной, а не только за последнюю. Новая версия считается найденной,
   только когда её образы api и web уже в реестре (`docker manifest inspect`): релиз на GitHub
   появляется на минуты раньше образов, а их сборка может упасть. Итог — в
   `/opt/averra/state/release-check.json` и `release-latest.json`. Нет сети или образов — «не
   удалось» с причиной, найденная раньше версия не стирается.
2. **Заявка.** API кладёт файл `/opt/averra/requests/update.json` (версия, когда, id владельца —
   ничего исполняемого). Одна заявка за раз: вторая, пока первая не забрана или обновление идёт, —
   отказ.
3. **Хост забирает заявку.** Служба `averra-update-request.path` видит файл сразу и запускает
   `averra.sh update-request`: заявка уходит из папки API, разбирается строго (обычный файл до
   1 КБ ровно одного вида, версия `X.Y.Z`, ровно та, что нашла проверка, и новее установленной) и
   удаляется **до** запуска. Не принимается и заявка на ломающий релиз (ниже), после неудачного
   отката прошлого обновления и на версию, обновление до которой уже откатилось. Не так — отказ
   строкой `---- … заявка из админки отклонена` в `update.log` и в «Состоянии», обновления нет.
   Отказ — штатный итог: служба заявок не помечается упавшей.
4. **Обновление** — тот же `averra.sh update` с бэкапом и откатом, что по SSH (ниже). Его ход по
   шагам — в `update-last.json`, экран читает его оттуда.

Если сервер не забрал заявку за 10 минут (служба заявок не работает), админка так и скажет и
вернёт кнопку: новая заявка заменит старую. Обновление по SSH удаляет незабранную заявку — решение
студии главнее.

### Когда кнопки нет

- **Ломающий релиз** — раздел «⚠ BREAKING CHANGES» (нужен шаг на сервере: новая строка `.env`,
  ручная команда; [Выпуск версий](/averra-cms/dev/releases/)) у новой версии **или у любой
  пропущенной** между установленной и новой: стоит 0.1.0, вышли 0.2.0 с шагом и 0.2.1 без него —
  кнопки нет. Так же, если установка отстала больше чем на 30 релизов и промежуток не виден
  целиком. Такое обновление ставит студия по SSH, сделав шаг.
- **Прошлое обновление кончилось неудачным откатом** — сначала установку чинит человек на сервере,
  дальше — обновление по SSH (оно запишет новый итог, и кнопка вернётся).
- **Обновление до этой версии уже откатилось** — повтор снова оставил бы админку без работы на
  минуту-две и отложил бы ещё одну базу. Кнопка вернётся со следующей версией; эту студия ставит по
  SSH, когда устранит причину.
- **Сервер без systemd** или служба заявок выключена или упала — заявки некому забирать.

Доступная версия и заметки к ней видны и без кнопки.

### Выключить кнопку

```bash
echo 'ADMIN_UPDATE=off' | sudo tee -a /opt/averra/.env
sudo /opt/averra/averra.sh install-units
```

Служба заявок выключается, лежащая заявка удаляется, новые не принимаются, а в админке вместо
кнопки — «выключено на сервере». Включить — убрать строку и снова `install-units`. Не проверять новые версии вовсе —
`UPDATE_SOURCE=off`; свой источник (форк) — `UPDATE_SOURCE=github:владелец/репозиторий`.

На сервере без `install.sh` (или в разработке) кнопки нет — вместо неё подсказка обновлять по
SSH.

## Обновить по SSH

```bash
sudo /opt/averra/averra.sh check-update            # есть ли новая версия
sudo /opt/averra/averra.sh update --version 0.2.0
```

В терминале скрипт спросит подтверждение («да»), `--yes` — без вопроса. Все установки студии сразу, по очереди — [`pnpm fleet update`](/averra-cms/install/fleet/).

Посетители видят сайт всё время: его отдаёт Caddy. Админка и приём заявок недоступны от остановки
API перед бэкапом до готовности новой версии — для лендинга это секунды на бэкап плюс старт API.
Форма в это окно получит 502.

## Что происходит по шагам

1. **Скачать образы** новой версии, пока всё работает. Не скачались — выход, ничего не менялось.
2. **Взять из образа** `compose.yaml` и `averra.sh` этой версии: конфигурация установки
   обновляется вместе с версией.
3. **Остановить API и сделать бэкап** с проверкой (`…-pre-update`). С этой минуты ничего не
   принимается, поэтому бэкап — последнее состояние базы. Не удался — прежний API снова
   запускается, выход.
4. **Переключить версию:** `AVERRA_VERSION` в `.env` (прежняя — в `AVERRA_PREVIOUS_VERSION`,
   прежний `compose.yaml` — в `compose.yaml.prev`), папки новой версии — её `averra.sh`
   (`ensure-dirs`), поднять новый API. Миграции он применяет сам
   при старте.
5. **Проверить:** дождаться `/api/health/ready` (до 180 секунд), поднять Caddy новой версии и
   убедиться, что API и Caddy держатся в `running`. Всё так — итог «обновлено».
6. **Иначе — откат** (ниже).

Внешняя копия бэкапа выгружается в самом конце, когда сервис уже работает. Последним новый
`averra.sh` ставит свои службы systemd и проверяет версию (`install-units`): службы новой версии
приезжают с обновлением, без ручного шага.

Ждать готовности дольше — переменной окружения процесса, а не строкой `.env`:

```bash
sudo AVERRA_READY_TIMEOUT=300 /opt/averra/averra.sh update --version 0.2.0
```

## Откат

Если новая версия не стала готова:

1. Новый API останавливается — до подсчёта миграций, чтобы не успел применить их позже.
2. Возвращаются прежние `.env` и `compose.yaml`.
3. Если миграции успели пройти, база восстанавливается из бэкапа шага 3. **Рабочая база при этом не
   удаляется**, а откладывается как `averra_rolled_back_<время UTC>`: в ней то, что новая версия
   успела принять (заявки). Имя видно в выводе и в «Состоянии установки».
4. Поднимаются прежние API и Caddy.

Отложенную базу можно посмотреть:

```bash
cd /opt/averra
docker compose exec postgres psql -U averra -d averra_rolled_back_…
```

Перенесите из неё нужное. Удалится она сама вместе со старыми бэкапами через `BACKUP_KEEP` дней.

## Коды выхода

| Код | Что значит |
|---|---|
| 0 | обновлено |
| 1 | не начато (не скачались образы, не удался бэкап) или не прошло проверку — работает прежняя версия; что именно — в выводе и в «Состоянии» |
| 2 | откат не удался — нужен человек; скрипт подскажет, какой бэкап восстанавливать |
| 3 | процесс обновления оборвался без итога — повторите команду |

Итог пишется в `/opt/averra/state/update-last.json` и виден в «Состоянии установки». Обновление
по заявке из админки идёт без терминала: итог — там же, лог — `update.log`, разбор заявки —
`journalctl -u averra-update-request`.

## Обрыв связи не страшен

Обновление идёт отдельным процессом на сервере — службой systemd `averra-update-<время>`, без
systemd — через `setsid`. Команда только показывает его лог (`/opt/averra/update.log`). Обрыв SSH,
закрытый терминал или Ctrl+C прерывают показ, а не обновление: оно доходит до конца или до отката.

- Чем кончилось — `tail /opt/averra/update.log`, `averra.sh status` или «Состояние установки».
- Повтор той же команды, пока обновление идёт, показывает его лог.
- Процесс оборвался (перезагрузка сервера) — прерванное **доводит служба
  `averra-update-resume`** при старте сервера: закончит обновление или откатит, с восстановлением
  базы, если миграции прошли. Нового обновления она не начинает; её вывод — в `update.log`
  (`==== … update-resume`). Без systemd — повторите `averra.sh update --version <та же>`: она не
  ответит «уже эта версия», а доведёт прерванное так же.
- Заявка из админки, пришедшая, когда прошлое обновление было прервано: сервер сначала доводит
  прерванное. Если оно кончилось откатом, заявка не выполняется, и «Состояние» говорит об этом.
- Обновление «идёт» дольше часа — в «Состоянии» проблема «похоже, оборвалось».

Пока идёт бэкап или восстановление, `update` сразу отказывает и ничего не трогает: у них общий замок.

## Почему откат безопасен

Миграции в Averra только совместимые вперёд: прежняя версия API работает на базе после миграций
новой. Это проверяет тест на каждый коммит. Поэтому прежний образ можно поднять и тогда, когда
база не восстановилась. Подробно — [Миграции только
вперёд](/averra-cms/decisions/forward-migrations/).

## Чего обновление не делает

**Не пересобирает сайт целиком.** Опубликованный сайт пересобирается сам, только если его версия
собрана до нынешнего формата релиза. Новое в обновлении, что видно на сайте только после сборки
(например, [карточки из заголовка](/averra-cms/admin/seo/#карточка-из-заголовка) у страниц без
своей картинки), появится после ближайшей публикации или сохранения настроек в разделе «SEO».
Так и с [cookie-уведомлением](/averra-cms/admin/cookies/): после обновления, где оно появилось,
счётчики сайта переходят на согласие посетителя с ближайшей сборкой — опубликуйте страницу или
нажмите «Собрать заново» в настройках сайта.

**Мажорную версию PostgreSQL** (`postgres:17…` в `compose.yaml`) обычное обновление не меняет:
новый мажор не читает файлы старого. Для этого нужна отдельная процедура (дамп и восстановление) —
её пока нет.

## Вернуть прежнюю версию руками

Если новая версия прошла проверку, но что-то не так уже в работе: обновите на прежнюю версию той же
командой (`averra.sh update --version <прежняя>`). Перед этим будет свой бэкап, а схема базы
прежней версии подходит — миграции совместимы вперёд. Данные, принятые новой версией, останутся.

Настройку раздела «SEO», которую прежняя версия не понимает (например, новый язык), она читает
значением по умолчанию и один раз пишет об этом в лог API. В базе настройка не меняется и снова
заработает после обновления. Ревизию страницы с полем, которого прежняя версия не знает,
восстановить в ней не получится — только в той версии, что её записала. Поля SEO страницы, которых
прежняя версия не знает (например, SEO-заголовок или картинку), её редактор не покажет, а
сохранение черновика в ней их сбросит; опубликованная версия страницы не меняется.
