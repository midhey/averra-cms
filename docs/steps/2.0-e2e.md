# Шаг 2.0. Сквозные тесты на Playwright

## Цель

Инфраструктура e2e-тестов, на которую опираются все следующие шаги этапа 2: одна команда `pnpm e2e` поднимает API, админку и рендерер на своих портах и своей базе, гоняет сценарии редактора в Chromium и всё за собой гасит. `pnpm check` остаётся быстрым и e2e не запускает.

## Решения и почему

1. **Отдельный пакет `@averra/e2e` в `e2e/`.** У Playwright свои зависимости и браузер; держать их в админке или в корне — смешивать роли. Пакет в workspace получает `devEngines.runtime` (Node 24) и `typecheck`, поэтому код тестов проверяется в `pnpm check`. Скрипта `test` у пакета нет: `pnpm -r test` его не трогает, e2e идут только через `pnpm e2e`.
2. **Порты e2e: API 4100, админка 5273, рендерер 4421.** На стандартных портах у пользователя может работать `pnpm dev`. `reuseExistingServer: false`: если порт занят, прогон падает сразу, а не гоняет тесты по чужой базе.
3. **Своя база в `e2e/.data/pglite`, очищается перед каждым прогоном.** Её стирает маленький скрипт `e2e/scripts/clean-data.ts` в команде запуска API. В `globalSetup` нельзя: Playwright запускает `webServer` раньше `globalSetup`. Скрипт удаляет саму `e2e/.data`, путь зашит в нём и снаружи не приходит, поэтому опечатка в команде не заденет `apps/api/.data` с контентом пользователя. На Windows Playwright гасит серверы жёстко (`gracefulShutdown` там не работает), так что PGlite может остаться в полусохранённом состоянии. Очистка перед прогоном делает это неважным.
4. **API для e2e запускается без watch** (`pnpm --filter @averra/api start` → `tsx src/index.ts`): перезапуск посреди прогона из-за правки файла сломал бы тесты. `NODE_ENV=development`, чтобы API положил демо-сайт в пустую базу.
5. **Админка: адрес API для прокси берётся из `CMS_API_URL`** (по умолчанию `http://localhost:4000`, как у рендерера), порт — из `ADMIN_PORT` (по умолчанию 5173). Для e2e ещё `--strictPort`: Vite не уезжает молча на соседний порт.
6. **Рендерер: `astro dev --port 4421` с `CMS_API_URL=http://localhost:4100`.** В dev-режиме страница грузит снимок из API на каждый запрос, поэтому опубликованная правка видна без пересборки.
7. **Изоляция тестов: перед каждым тестом демо-страница возвращается в исходное состояние через API** (сохранить демо-черновик и опубликовать). Создать свой сайт тест пока не может: в API нет такого маршрута, а редактор открывает первый сайт. Сайт один, поэтому тесты идут в один поток (`workers: 1`), а каждый стартует с одинакового известного состояния и от соседей не зависит. Независимость от порядка проверяем прогоном с `--shuffle`. Сброс идёт через типизированный клиент Hono (`hc<AppType>`): поменяется API — тесты перестанут компилироваться.
8. **Демо-данные из одного места.** Заголовок демо-страницы выносится в `@averra/schema` (`demoPageTitle`) рядом с `demoPage`: им пользуются и сид API, и сброс в e2e.
9. **Только Chromium**, `@playwright/test` 1.64.0 (вышел 7 октября 2026, старше суток). Браузер ставится отдельной командой `pnpm --filter @averra/e2e exec playwright install chromium`.
10. **Локаторы — по ролям и подписям** (`getByRole`, `getByLabel`), как их видит человек с экранным диктором. Тест заодно проверяет, что у полей есть подписи, а у кнопок — понятные имена.

- `pnpm-workspace.yaml`: `e2e` в `packages`.

- `.gitignore`: `e2e/.data`, отчёты Playwright (`playwright-report`, `test-results`).
- `e2e/` (новый пакет `@averra/e2e`): `package.json`, `tsconfig.json`, `playwright.config.ts`, `scripts/clean-data.ts`, `tests/fixtures.ts` (сброс демо-страницы и хелперы), `tests/editor.spec.ts`, `tests/publish.spec.ts`.
- `apps/api/package.json`: скрипт `start` (без watch).
- `apps/api` (добавлено по ходу, см. «Итог»): колонка `published_title`, миграция `0001_page_published_title`, публикация и снимок сайта работают с опубликованным заголовком.
- `apps/admin/vite.config.ts`: прокси на `CMS_API_URL`, порт из `ADMIN_PORT`.
- `packages/schema/src/demo.ts`: `demoPageTitle`; `apps/api/src/db/seed.ts` берёт его оттуда.
- Документация: README (запуск e2e, переменные админки), CONVENTIONS (правила e2e), PLAN (пункт этапа 2).

## Критерии готовности

1. `pnpm check` зелёный и не запускает Playwright.
2. `pnpm e2e` зелёный; после него на портах 4100, 5273, 4421 никто не слушает.
3. `pnpm e2e --shuffle` (или `--repeat-each`) тоже зелёный. Без `--`: pnpm 12 передаёт его Playwright как есть, и тот молча пропускает флаг после него — тесты не зависят от порядка.
4. Папка `e2e/.data` создаётся заново при каждом прогоне; `apps/api/.data` не меняется (время изменения файлов то же).
5. При занятом порту 4100 прогон падает с понятной ошибкой, а не идёт по чужой базе.
6. `pnpm dev` по-прежнему ходит в API на 4000 и открывает админку на 5173.
7. README описывает установку браузера, запуск, порты и где лежат отчёты.
8. `pnpm e2e` зелёный, пока рядом работает `pnpm dev` (или хотя бы его рендерер): e2e не трогает замок Astro и базу разработки.

## Тесты

### Юнит и интеграционные
Новых нет: поведение API и логики редактора не меняется. Существующие тесты сида и схем продолжают проходить с вынесенным `demoPageTitle`.

### e2e (`e2e/tests`)
`editor.spec.ts`:
- редактор открывается с демо-лендингом: заголовок страницы, три блока в списке в правильном порядке, первый экран в предпросмотре;
- правка заголовка первого экрана сразу видна в предпросмотре (iframe) без сохранения;
- пустой обязательный заголовок: сообщение «Поле не может быть пустым», пометка «ошибка» у блока, кнопки «Сохранить черновик» и «Опубликовать» выключены, предпросмотр показывает последнюю правильную версию; после исправления кнопки снова доступны;
- добавление блока: новый блок встаёт после выбранного, виден в списке и в предпросмотре, открывается в инспекторе;
- перестановка блоков стрелками меняет порядок в списке и в предпросмотре; крайние стрелки выключены; порядок сохраняется в черновике и переживает перезагрузку;
- удаление блока с подтверждением.

`publish.spec.ts`:
- сохранение черновика: статус «Черновик сохранён», правка переживает перезагрузку, но на сайте (рендерер 4421) ещё старый заголовок;
- публикация: статус «Опубликовано…», рендерер показывает новый заголовок;
- «Опубликовать» с несохранёнными правками сохраняет и публикует за один клик.

## Итог

Сделано всё из плана: пакет `@averra/e2e`, конфиг с тремя серверами на своих портах и своей базе, 11 e2e-тестов, команда `pnpm e2e`, документация. `pnpm check` зелёный и e2e не запускает (у пакета есть только `typecheck`). `pnpm e2e` зелёный (11 тестов, около 17 с вместе с запуском серверов), `pnpm e2e --shuffle --repeat-each 2` тоже зелёный.

Проверено руками:
- после прогона на 4100, 5273 и 4421 никто не слушает;
- файл-метка в `e2e/.data` исчезает при следующем прогоне, а время изменения файлов в `apps/api/.data` то же, что до работы;
- при занятом порте 4100 прогон сразу падает с «http://localhost:4100/api/health/ready is already used»;
- `pnpm --filter @averra/admin dev` без переменных по-прежнему открывается на 5173 и проксирует `/api` на 4000.

### Отклонения от плана

1. **e2e нашли настоящую ошибку, и она исправлена.** Заголовок страницы хранился в одной колонке `title`, поэтому «Сохранить черновик» сразу менял `<title>` опубликованного сайта, хотя блоки ждали публикации. Это противоречит правилу «на сайт попадает только опубликованная копия». Исправление:
   - в `pages` новая колонка `published_title` (миграция `apps/api/drizzle/0001_page_published_title.sql`); в ту же миграцию дописан перенос данных: у уже опубликованных страниц текущий заголовок считается опубликованным;
   - публикация копирует `title` в `published_title`, снимок сайта отдаёт опубликованный заголовок, сид кладёт его сразу;
   - тесты: в `apps/api/src/modules/sites/routes.test.ts` проверяется, что сохранённый черновик не меняет заголовок в снимке, а публикация меняет; новый `apps/api/src/db/migrate.test.ts` гоняет SQL миграции на базе со старыми данными и проверяет перенос; e2e «сохранённый черновик… на сайт не попадает» проверяет то же в браузере.
   Поэтому раздел «Юнит и интеграционные» уже не пустой.
2. **`fullyParallel: true` при `workers: 1`.** Без этого `--shuffle` перемешивает только файлы, а тесты внутри файла идут по порядку. Воркер всё равно один, так что одновременно тесты не идут.
3. **`@playwright/test` подключён как `^1.64.0`**, как остальные зависимости. Точную версию держит lockfile; при обновлении Playwright сам скажет переустановить браузер.
4. **Тестов больше, чем в задаче:** пустой заголовок страницы выключает сохранение; удаление блока с подтверждением и отменой; «Опубликовать» без предварительного сохранения; опубликованный порядок блоков совпадает с редактором; перестановка с клавиатуры (Enter на стрелке).
5. **Шум при остановке.** На Windows Playwright гасит серверы жёстко, и pnpm печатает `[API] … Command failed with exit code 1`. На результат это не влияет, в README сказано, что так и должно быть.

### Что осталось на потом

- Создавать свой сайт на тест пока нельзя: в API нет маршрута создания сайта, а админка открывает первый. Когда появится навигация по сайтам, тесты могут перейти на «каждый со своим сайтом» и идти в несколько воркеров.
- e2e пока не в CI: CI в проекте ещё нет. Конфиг уже учитывает `CI` (`forbidOnly`, один повтор).

## Исправления по проверке

1. **Рендерер e2e мешал `pnpm dev` (major).** Astro 7 держит файл-замок `apps/renderer/.astro/dev.json` и не запускает второй `astro dev` в том же проекте: при работающем `pnpm dev` прогон падал с «Another astro dev server is already running», а во время прогона не стартовал рендерер `pnpm dev`. Теперь в `e2e/playwright.config.ts` рендерер идёт с `astro dev --ignore-lock`: свой замок он не берёт и не пишет, разве что удаляет брошенный (от сервера, которого уже нет). Этот же флаг отключает уход Astro в фон, когда он считает, что его запустил агент (на macOS и Linux), так что процессом по-прежнему владеет `webServer`. Проверено: при работающем `astro dev --port 4521` (вместо `pnpm dev`) `pnpm e2e` зелёный, замок по-прежнему указывает на 4521, сервер на 4521 продолжает работать. К критериям готовности добавлен пункт 8. Правило «серверы e2e не делят с `pnpm dev` базу и замки» записано в CONVENTIONS, поведение описано в README.
2. **Снимок сайта мог молча потерять страницу.** Связь «`published` и `published_title` заполнены вместе» теперь держит база: CHECK `pages_published_with_title` в новой миграции `0002_page_published_with_title` (в `schema.ts` через `check()`). Отдельная миграция, а не правка `0001`: `0001` могла уже примениться к локальной базе. Перед проверкой миграция дозаполняет заголовок у опубликованных страниц, если он пуст, поэтому на старых данных она не падает. Тест в `apps/api/src/db/migrate.test.ts` применяет `0000`–`0002` к базе с такой строкой и проверяет перенос и что база отклоняет половинчатую публикацию в обе стороны.
3. **Пустой заголовок страницы показывал только красную рамку.** Схема заголовка вынесена в `@averra/schema` (`PageTitle`): ею пользуются и API (`SaveDraft`), и редактор. Под шапкой выводится «Заголовок страницы: Поле не может быть пустым» (или «Не больше 120 символов»), поле связано с текстом через `aria-describedby`. Тесты: e2e проверяет видимый текст, доступное описание поля, исчезновение ошибки после исправления и строку из одних пробелов; юнит-тест в `packages/schema/src/zod-messages.test.ts` (до шага 2.6 — в `apps/admin`) проверяет сообщения `PageTitle`.
4. **Проверки, которые проходили сами собой.** В тесте пустого поля блока строка из пробелов вводится после правильного значения, и проверяется сообщение об ошибке, а не только выключенные кнопки. В тесте удаления диалоги считаются: после отмены ровно один диалог с названием блока, после подтверждения — два.
5. **PLAN, «Модель данных»:** у `pages` указаны `title`/`published_title` и что они заполняются вместе.

Итог после исправлений: `pnpm check` зелёный; `pnpm e2e` зелёный (11 тестов), в том числе при работающем рядом рендерере; `pnpm e2e --shuffle --repeat-each 2` зелёный (22 теста). После прогонов порты 4100, 5273, 4421 и 4521 свободны.
