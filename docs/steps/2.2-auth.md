# Шаг 2.2. Вход, права и токены для MCP

## Цель

Админка и API закрыты: без входа видно только опубликованное (`GET /api/sites/:siteId/snapshot`) и `/api/health`. В админку входят по почте и паролю, регистрации с сайта нет: владельца создаёт команда в терминале. У пользователя есть роль, и он видит и правит только то, что ему положено. MCP продолжает работать, но уже по токену с правами на один сайт.

## Решения и почему

1. **Better Auth 1.7.7** (последняя стабильная, вышла 30.09.2026), адаптер Drizzle из коробки (`better-auth/adapters/drizzle`, `provider: 'pg'`). Криптографию, сессии, лимит попыток и проверку Origin берём из библиотеки, сами пишем только права и токены.
2. **Таблицы Better Auth — в нашей `schema.ts`**, миграция `auth` через `pnpm db:generate`. Имена во множественном числе, как у остальных (`users`, `sessions`, `accounts`, `verifications`; `usePlural: true`), колонки в snake_case. Id — `uuid` с генерацией в базе (`advanced.database.generateId: 'uuid'`), как у сайтов и страниц.
3. **Роль пользователя — колонка `users.role`: `owner` | `member`** (CHECK в базе). В Better Auth это `additionalFields.role` с `input: false`: поменять роль через эндпоинты Better Auth (`update-user`) нельзя. **Доступ участника к сайту — `site_members (site_id, user_id, role: editor | client)`**, первичный ключ `(site_id, user_id)`, CHECK на роль, каскадное удаление вместе с сайтом и пользователем.
4. **Права — одна таблица разрешений** в `src/auth/access.ts`:

   | Действие | owner | editor | client | токен |
   |---|---|---|---|---|
   | читать сайт и страницы | ✓ | ✓ | ✓ | ✓ (свой сайт) |
   | править черновик существующей страницы | ✓ | ✓ | ✓ | ✓ |
   | создать страницу (в том числе `PUT` на новый адрес) | ✓ | ✓ | — | ✓ |
   | опубликовать | ✓ | ✓ | — | ✓ |
   | удалить страницу | ✓ | ✓ | — | ✓ |
   | создать сайт | ✓ | — | — | — |

   Владелец видит все сайты. Токен = editor на одном сайте. Клиент правит только черновики уже существующих страниц: страницу, которую он не может удалить, ему и создавать незачем. Поэтому `PUT` на несуществующий адрес для клиента — 404 «Страница не найдена», а не тихое создание.
5. **Закрыто по умолчанию.** Общий middleware `authenticate` стоит на всём `/api` и пропускает без входа только явный список: `GET /api/health`, `GET /api/health/ready`, `GET /api/sites/:siteId/snapshot` и `/api/auth/*` (там Better Auth сам решает, что можно). Новый маршрут закрыт сам, пока его не внесут в список. Без входа — **401** `unauthorized` в формате `ApiError`.
6. **Доступ к сайту проверяет общий middleware `requireSite(permission)`**: ищет роль на сайте (владелец — если сайт есть; участник — по `site_members`; токен — если сайт его). Нет роли или нет сайта — **404 «Сайт не найден»**: чужой сайт для участника неотличим от несуществующего. Роль есть, но действие не разрешено — **403** `forbidden`. Маршруты сами права не проверяют, только объявляют, какое действие им нужно. Заодно из маршрутов уходят повторяющиеся `repo.find(siteId)`.
7. **Сессия — httpOnly-cookie Better Auth**, `SameSite=Lax`, `Secure` и префикс `__Secure-` в проде (`advanced.useSecureCookies` = `NODE_ENV === 'production'`). Регистрация выключена (`emailAndPassword.disableSignUp`). Пароль от 10 до 128 символов. Продление сессии (Better Auth обновляет её раз в сутки) доходит до браузера: middleware пробрасывает `Set-Cookie` от `getSession` в ответ.
8. **Лимит попыток входа включён всегда** (`rateLimit.enabled: true`, в памяти): встроенное правило Better Auth — 3 попытки входа за 10 секунд с одного IP, дальше 429. Better Auth берёт IP из `X-Forwarded-For`. Чтобы клиент не обходил лимит, подставляя заголовок, `index.ts` перезаписывает его адресом сокета; доверять заголовку от прокси (Caddy в проде) можно включить `TRUST_PROXY=true`. Это платформенный код, поэтому он в `index.ts`, а не в `app.ts`.
9. **CSRF.** Better Auth проверяет Origin на своих эндпоинтах. На наших изменяющих запросах (`POST`/`PUT`/`DELETE`) с cookie-сессией middleware требует `Origin` из доверенных (адрес админки и самого API); `SameSite=Lax` закрывает большую часть, а проверка Origin — ещё и соседние поддомены. Запросы с токеном не проверяются: у них нет «чужих» учётных данных, которые браузер подставил бы сам.
10. **Ответы Better Auth — в формате `ApiError`.** Обёртка над `auth.handler` переводит ошибки (`{ code, message }`) в `{ error: { code, message } }`, а самые частые сообщения — на русский: «Неверная почта или пароль», «Слишком много попыток входа. Подождите N с». Админка разбирает все ошибки одним кодом.
11. **Конфиг (`config.ts`, Zod):** `AUTH_SECRET` (от 32 символов; в проде обязателен, в разработке есть явно учебное значение по умолчанию), `ADMIN_URL` (адрес админки, он же `trustedOrigins`; в проде обязателен), `API_URL` (`baseURL` Better Auth, по умолчанию `http://localhost:<PORT>`), `TRUST_PROXY`, `DEV_OWNER_EMAIL` / `DEV_OWNER_PASSWORD` (только вместе).
12. **Первый владелец — `pnpm user:create --email … --name …`.** Пароль — скрытым вводом (дважды) или из `CMS_USER_PASSWORD`; не печатается и не логируется. Пользователь и его учётная запись (`accounts`, `provider_id = 'credential'`) пишутся в одной транзакции, пароль хеширует сам Better Auth (`ctx.password.hash`), так что вход его примет. `--role member` создаёт участника, `pnpm member:add --email … --site … --role editor|client` даёт ему доступ к сайту. Экрана управления пользователями в этом шаге нет (это «доступы для клиентов» из плана).
13. **Владелец для разработки.** Если `NODE_ENV=development` и в базе нет ни одного пользователя, API при старте создаёт владельца из `DEV_OWNER_EMAIL` / `DEV_OWNER_PASSWORD` (`apps/api/.env`; в `.env.example` — явно учебные значения с пометкой «только для разработки»). Не заданы — API пишет подсказку, как создать владельца. В проде такого сида нет.
14. **Токены для MCP — таблица `api_tokens`:** `id`, `site_id`, `name`, `token_hash` (SHA-256, hex), `created_by` (пользователь, `ON DELETE SET NULL`), `created_at`, `last_used_at`, `revoked_at`. Токен: `cms_<id>_<секрет>`, секрет — 32 случайных байта в base64url. По `id` ищем строку, хеш сравниваем за постоянное время (`constantTimeEqual` из `better-auth/crypto`): так поиск по базе не превращается в сравнение секрета. Хеш — Web Crypto (`crypto.subtle`), без Node API. Сам токен показывается один раз — в выводе `pnpm token:create --site <id> --name <имя>`; в базе его нет. `created_by` — `--by <почта>`, а если владелец один, то он. Отзыв — `pnpm token:revoke --id <id>`, список — `pnpm token:list`. Заголовок `Authorization: Bearer <токен>`; неверный, чужой формат или отозванный токен — 401, на cookie при этом не откатываемся.
15. **Команды терминала и встроенная база.** PGlite — однопроцессная база: если `pnpm dev` и `pnpm token:create` откроют одну папку одновременно, базу можно испортить. Поэтому API и команды берут файл-замок рядом с базой (`<PGLITE_DIR>.lock` с pid). Занят живым процессом — команда говорит «останови pnpm dev» и ничего не открывает; замок от упавшего процесса снимается сам. API при старте ждёт замок несколько секунд: `tsx watch` перезапускает его быстрее, чем старый процесс успевает выйти.
16. **MCP** читает `CMS_API_TOKEN` из `apps/mcp/.env` (путь от файла, а не от текущей папки: `.mcp.json` запускает сервер из корня) и шлёт `Authorization: Bearer`. Без токена сервер стартует, `list_blocks` работает, а инструменты с API отвечают: «Нужен токен API. Создай: pnpm token:create --site <id> --name mcp и положи его в apps/mcp/.env (CMS_API_TOKEN=…)». 401 от API — «Токен не принят (отозван или неверный)…». `list_sites` с токеном отдаёт его единственный сайт.
17. **Рендерер.** Снимок сайта публичный, а список сайтов — нет. Поэтому «первый сайт из API» больше не работает: `CMS_SITE_ID` обязателен (`apps/renderer/.env`, есть `.env.example`), без него — понятная ошибка, где взять id. Чтобы e2e знали id демо-сайта заранее, сид кладёт демо-сайт с постоянным id (`demoSiteId` в `@cms/schema`). У уже существующей базы демо-сайт остаётся со своим id.
18. **Админка.** Экран `/login` (почта, пароль, «Войти»). Корневой маршрут перед любым экраном, кроме входа, спрашивает `GET /api/me`; нет сессии — переход на `/login?redirect=<где был>`, после входа — обратно (только относительный адрес внутри админки, чтобы ссылка не уводила на чужой сайт). В шапке — имя пользователя и «Выйти». Любой 401 из запроса или мутации (сессия кончилась) — тоже на вход с возвратом; несохранённые правки редактора при этом защищает тот же вопрос перед уходом. Сайт отдаёт роль (`access`), и админка прячет то, что роли нельзя: «Новый сайт» — только владельцу, «Опубликовать», «Удалить» и «Новая страница» — не для клиента. Права всё равно проверяет API.
19. **`createTestApi`** отдаёт помощников: `loginAs(role, siteId?)` — заголовки сессии владельца, редактора или клиента (пользователь создаётся сразу, сессия — через `auth.api.signInEmail`, это серверный вызов и лимит попыток не тратит), `createToken(siteId)`, `revokeToken(id)`, `demoSiteId`. Тесты API и MCP переходят на них.
20. **e2e.** Учебные почта и пароль владельца e2e — в `e2e/urls.ts` (рядом с портами), API e2e получает их как `DEV_OWNER_*`. Проект `setup` входит один раз через API и сохраняет cookie в `e2e/.data/owner.json`; обычные тесты стартуют уже с ней, фикстура API ходит с той же cookie и `Origin` админки. Тесты входа ставят каждому свой `X-Forwarded-For` (API e2e идёт с `TRUST_PROXY=true`: перед ним прокси Vite), чтобы лимит попыток одного теста не задевал другой.

## Критерии готовности

1. `pnpm check` зелёный; `pnpm e2e` зелёный; `pnpm e2e --shuffle --repeat-each 2` зелёный.
2. Без входа любой маршрут API, кроме `/api/health*`, `GET …/snapshot` и `/api/auth/*`, отвечает 401 в формате `ApiError`; снимок отдаётся без входа.
3. Вход по почте и паролю ставит httpOnly-cookie `SameSite=Lax`; `Secure` — только в проде. Регистрация через `POST /api/auth/sign-up/email` не работает. Четвёртая попытка входа за 10 секунд — 429.
4. Права соответствуют таблице из решения 4: клиент получает 403 на публикацию и удаление, 404 на `PUT` новой страницы; участник получает 404 на чужой сайт и не видит его в списке; создавать сайты может только владелец.
5. Токен работает только для своего сайта (чужой — 404), отозванный и выдуманный — 401; в базе лежит только SHA-256 токена; `last_used_at` обновляется.
6. `pnpm user:create` создаёт владельца, пароль не попадает ни в вывод, ни в аргументы; повторная почта — понятная ошибка. `pnpm token:create` печатает токен один раз. При запущенном API команды отказываются открывать базу.
7. В разработке пустая база получает владельца из `DEV_OWNER_*`; в проде — нет.
8. MCP без токена стартует и отвечает понятной ошибкой с командой; с токеном проводит страницу от черновика до публикации.
9. Админка: без входа любой экран ведёт на вход и после входа возвращает туда же; в шапке имя; «Выйти» возвращает на вход, и админка снова закрыта; неверный пароль — сообщение у формы.
10. Документация описывает, как создать владельца, участника и токен и как настроить MCP и рендерер.

## Итог

Сделано всё из плана. Админка и API закрыты входом; снимок сайта и `/api/health*` открыты. Better Auth 1.7.7 с адаптером Drizzle, таблицы — миграция `0003_auth` (плюс `site_members` и `api_tokens`). Права — одна таблица разрешений и два middleware (`authenticate` на всём `/api`, `requireSite(permission)` на маршрутах сайта). Токены MCP — `pnpm token:create`, в базе только SHA-256, проверка за постоянное время. MCP читает токен из `apps/mcp/.env` и без него объясняет, как его получить. В админке есть экран входа, шапка с именем и «Выйти», переход на вход по любому 401 с возвратом на тот же экран. То, что роли нельзя, админка прячет.

Проверки: `pnpm check` зелёный (api — 115 тестов, admin — 44, mcp — 8, schema — 44). `pnpm e2e` зелёный (27 с проектом `setup`), `pnpm e2e --shuffle --repeat-each 2` тоже зелёный (53). Вживую на отдельной базе в scratchpad проверено: команды `user:create`, `member:add`, `token:create`, `token:list`; отказ команды при запущенном API; перехват замка упавшего процесса; лимит входа не обходится подменой `X-Forwarded-For`; экран входа; редактор с шапкой помещается в окно без прокрутки страницы. База разработки `apps/api/.data` не открывалась.

### Отклонения от плана и добавки

1. **Сверх задачи — команды `member:add`, `token:list`, `token:revoke`.** Без них роли editor/client и отзыв токена нельзя было бы применить, не правя базу руками. Экрана управления пользователями нет: это пункт «доступы для клиентов» из плана.
2. **Замок базы (`src/db/lock.ts`).** В задаче его не было. Но PGlite — однопроцессная база, и `pnpm token:create` при запущенном `pnpm dev` мог бы испортить базу с контентом. Теперь команда в этом случае отказывается работать и просит остановить `pnpm dev`. Цена: выпустить токен или пользователя на ходу нельзя, нужно остановить API.
3. **`X-Forwarded-For` перезаписывается адресом соединения** (если не задан `TRUST_PROXY=true`). Better Auth считает лимит входа по этому заголовку, и без перезаписи клиент мог бы обходить лимит. Проверено вживую: подмена заголовка не помогла, четвёртая попытка получила 429.
4. **Рендерер: `CMS_SITE_ID` обязателен, у демо-сайта постоянный id.** Это прямое следствие закрытого списка сайтов. У существующей базы разработки демо-сайт остаётся со старым id, поэтому `apps/renderer/.env` нужно заполнить один раз.
5. **`apps/api/vitest.config.ts` с `testTimeout: 30s`.** Тестовых файлов в API стало больше, а каждый поднимает свой PGlite. Под нагрузкой тест миграций один раз не уложился в 5 секунд по умолчанию.
6. **В `PUT` клиента** нужен свой путь (`updateDraft` без создания). Это видно в маршруте: `can(role, 'page.create')` решает, создавать ли страницу. Таблица разрешений при этом одна.
7. **Кеш админки при смене пользователя** очищается через `switchUser`, а не через `queryClient.clear()`. С `clear()` шапка оставалась подписана на удалённый запрос и после входа не появлялась; это поймал e2e.

### Что не проверено тестами напрямую и что осталось

- Продление сессии: `Set-Cookie` от `getSession` пробрасывается в ответ, но без сдвига времени это не проверить. Поведение — встроенное в Better Auth (`updateAge` — сутки).
- Скрытие кнопок для клиента в админке проверено юнит-тестом (`canPublish`, `canManagePages`) и тестами API, но не e2e. В e2e участника не завести: команды не открывают базу, пока API e2e запущен, а API для управления пользователями пока нет.
- Лимит попыток хранится в памяти процесса: после перезапуска API он сбрасывается, и у нескольких экземпляров API он у каждого свой. Для одного сервера этого достаточно. Если API станет несколько, перейти на `storage: 'database'`.
- Сброса пароля по почте нет: отправки писем ещё нет. Пока владелец может создать пользователя заново. Команду смены пароля стоит добавить вместе со сбросом.
- Права токена — как у редактора, то есть с публикацией (так требует задача). Принцип 7 из PLAN («публикует человек») это нарушает. Токен «только черновики» записан в этап 4.
- Чтобы перейти на эту версию, пользователю с существующей базой нужно один раз: создать владельца (`apps/api/.env` с `DEV_OWNER_*` или `pnpm user:create` при остановленном `pnpm dev`), выпустить токен MCP в `apps/mcp/.env` и задать `CMS_SITE_ID` в `apps/renderer/.env`.
