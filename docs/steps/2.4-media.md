# Шаг 2.4. Картинки

## Цель

На лендинг можно поставить свою картинку, не трогая JSON руками и не думая о форматах. Человек загружает файл в медиатеку сайта, выбирает его в поле «картинка» блока и пишет alt. Сервер сам чистит метаданные (EXIF с GPS), поворачивает снимок по EXIF, режет его под набор ширин и кодирует в AVIF и WebP. Рендерер и предпросмотр выводят `<picture>` с `srcset`, `sizes` и размерами, поэтому вёрстка не прыгает. Первый экран получил вариант `split`: текст слева, картинка справа.

## Решения и почему

1. **Хранилище — за интерфейсом `MediaStorage`** (`put`, `get`, `remove`). Сейчас это `diskStorage(root)`, папка на диске: по умолчанию `apps/api/.data/media`, её задаёт `MEDIA_DIR`. В тестах это временная папка, которая удаляется в `close()`, в e2e — `e2e/.data/media`. Потом здесь будет S3. Маршруты и `app.ts` получают хранилище через `createApp(deps)` и не импортируют `fs` (CONVENTIONS: админка читает типы `app.ts`).
2. **Пути строит только сервер.** Ключ файла — `<siteId>/<mediaId>/<имя варианта>`, где оба id — uuid из базы, а имя варианта сервер составил сам (`480.avif`, `original.jpg`). Имя загруженного файла идёт только в колонку `original_name` для показа в админке и в пути не попадает никогда. Локальное хранилище дополнительно проверяет ключ строгим шаблоном и то, что итоговый путь лежит внутри корня. Это вторая линия защиты от path traversal на случай ошибки выше.
3. **Обработка картинок (sharp) — тоже за интерфейсом `ImageProcessor`**: sharp — нативный модуль Node, и маршрутам его импортировать нельзя по той же причине, что `fs`. Реализация `sharpProcessor()` в `src/media/sharp-processor.ts` подключается в `index.ts` и `testing.ts`. Вместо исключений процессор возвращает результат с причиной отказа (`unsupported`, `too_many_pixels`, `broken`), а маршрут переводит её в HTTP-код.
4. **Тип определяется по содержимому.** `sharp(bytes).metadata().mediaType` должен быть одним из `image/jpeg`, `image/png`, `image/webp`, `image/avif`. Расширение имени и `Content-Type` части multipart не учитываются. SVG (через него легко протащить XSS, PLAN, модуль 3), GIF, HEIC, TIFF и не-картинки получают **415** `unsupported_media_type` с текстом «Можно загрузить JPEG, PNG, WebP или AVIF». Битый файл того же типа тоже получает 415, с текстом «Файл повреждён». У анимированных WebP и AVIF берётся первый кадр.
5. **Лимиты.** Размер файла — `MEDIA_MAX_BYTES`, по умолчанию 10 МБ, сверх него **413** `payload_too_large`. Тело запроса режет `bodyLimit` из Hono ещё до разбора multipart: лимит плюс 64 КиБ на заголовки частей, так что огромный файл не читается в память целиком. Число пикселей ограничено 50 Мп (`limitInputPixels`, тоже 413). Иначе маленький PNG-«бомба» на 10 МБ развернулся бы в гигабайты памяти.
6. **Метаданные удаляются.** Сначала снимок поворачивается по EXIF (`autoOrient: true` в конструкторе sharp), потом кодируется без `keepMetadata`/`withMetadata`. sharp по умолчанию не переносит в результат EXIF, XMP, IPTC и ICC и переводит цвета в sRGB. Это проверяет тест: JPEG с GPS, авторством, XMP и поворотом 6 → ни у одного варианта нет EXIF и XMP, а ширина и высота поменялись местами.
7. **Варианты.** Ширины 480, 960, 1440 и 1920 **не больше исходной**. Если исходник уже 1920 px, в набор добавляется и его собственная ширина: картинку 1000 px режем на 480, 960 и 1000, а не растягиваем до 1440. Каждая ширина кодируется в AVIF, WebP и исходный формат (JPEG или PNG — запасной для старых браузеров; если исходник уже WebP или AVIF, запасным будет он же). Отдельно хранится «чистый оригинал» в полном размере (`original.<ext>`): он нужен, чтобы потом перерезать картинку под новые ширины или точку фокуса без повторной загрузки. Наружу он не отдаётся.
8. **Таблица `media`**: `id`, `site_id` (каскад при удалении сайта), `original_name`, `mime_type` (CHECK: четыре разрешённых типа), `width`, `height` (CHECK > 0, уже после поворота), `size` (вес загруженного файла в байтах), `variants` jsonb (`format`, `width`, `height`, `size`, `file`), `original_file`, `uploaded_by` → users / `uploaded_by_token` → api_tokens (`ON DELETE SET NULL`, CHECK «не больше одного автора», как у истории), `created_at`. Миграция `0005_media`.
9. **API — модуль `media`.**
   - `GET /api/sites/:siteId/media` — медиатека сайта `{ items, maxBytes }` (лимит размера — см. «Исправления по проверке»), картинки новые сверху: `id`, `originalName`, `mimeType`, `width`, `height`, `size`, `createdAt`, `author`, `variants` (с `url`). Право — `site.read`.
   - `POST /api/sites/:siteId/media` — multipart, поле `file`. Ответ — 201 и запись в том же виде. Право — новое действие `media.upload`: владелец, редактор и клиент («права — как у страниц»: клиент правит свой сайт, значит, и картинки для него грузит).
   - `DELETE /api/sites/:siteId/media/:mediaId` — 204. Право — `media.delete`: владелец и редактор, как удаление страниц. Если картинка есть в черновике или опубликованной версии любой страницы сайта, ответ — 409 `conflict` со списком страниц в сообщении («используется на страницах: «Главная» (/) — черновик и сайт») и в `issues` (путь `pages.<slug>`). История версий использованием не считается: она не меняется, а вернуть версию без картинки не дадут (п. 11).
   - `GET /api/media/:mediaId/:file` — **публичный** файл варианта. Список открытых маршрутов в `auth/middleware.ts` пополняется этим путём. Файл должен быть в `variants` этой записи, иначе 404. Заголовки: `Content-Type` из нашего же списка форматов, `Cache-Control: public, max-age=31536000, immutable` (файл под данным id и именем никогда не меняется: новая картинка — новый id), `X-Content-Type-Options: nosniff`.
   - Чужой или несуществующий сайт — 404 (как везде), картинка другого сайта — 404 «Картинка не найдена».
10. **Схема: поле «картинка» в `@cms/schema`.** `Image = z.strictObject({ mediaId: uuid, alt: 1–200 символов })` с `meta({ 'x-widget': 'image' })`: по этой пометке конструктор форм ставит свой виджет вместо вложенной группы полей. Пометка доходит до JSON Schema (проверено, `z.toJSONSchema` переносит её и для `.optional().meta(...)`). Alt обязателен и проверяется той же схемой в API, админке и MCP. У `hero` появляются вариант `split` и поле `image`. В варианте `split` картинка обязательна: `superRefine` с путём `image` и сообщением «В варианте split нужна картинка: выберите её в медиатеке». Ошибка встаёт прямо у поля в редакторе, потому что путь тот же. В других вариантах картинки быть не должно (см. «Исправления по проверке», п. 6).
11. **Ссылки на картинки проверяет API.** Сохранение черновика (`PUT …/pages/:slug`) и возврат версии (`…/restore`) проверяют, что каждый `mediaId` в блоках есть в медиатеке **этого** сайта. Иначе 409 `conflict` с путём до поля (`content.blocks.0.props.image.mediaId`, «Картинки нет в медиатеке сайта»). Так нельзя сослаться на чужую картинку или на удалённую, а MCP с выдуманным id получит понятную ошибку. Id собирает `collectMediaRefs(content)` из `@cms/schema` обходом JSON: ключ `mediaId` бывает только у поля `Image` (лишние поля запрещены схемами).
12. **Снимок сайта знает варианты.** `GET …/snapshot` отдаёт `media` — справочник `{ [mediaId]: { width, height, variants[{ format, width, height, url }] } }` только по картинкам опубликованных страниц. `url` — путь `/api/media/<id>/<файл>`. Рендерер делает из него полный адрес через `CMS_API_URL`, админка оставляет относительным (ходит через прокси Vite, а `srcdoc` предпросмотра берёт базовый адрес у админки).
13. **Блоки получают справочник явно, пропсом** (принцип 4: явное вместо глобального): `Page({ content, media })` → `BlockComponentProps.media`. Компонент `Picture` в `packages/blocks/src/ui` выводит `<picture>`: `<source type="image/avif" srcset>`, `<source type="image/webp" srcset>`, `<img>` с `srcset` запасного формата, `sizes`, `width`/`height` исходника (браузер заранее знает пропорции, вёрстка не прыгает), `alt`, `decoding="async"`. По умолчанию `loading="lazy"`, а у первого блока страницы (это первый экран) `loading="eager"` и `fetchpriority="high"`. Картинки нет в справочнике (такого не должно быть, п. 11) — блок выводится без неё, а не падает.
14. **Админка.**
    - Экран `/sites/:siteId/media` «Медиатека», ссылка на него — на экране сайта. Там загрузка: поле файла с подписью «Загрузить картинку», прогресс `<progress>` (XHR, `upload.onprogress`: у fetch прогресса отправки нет) и статус в `role="status"`. Ошибки — в `role="alert"`, текстом API. Ниже сетка превью (самый маленький WebP), у каждой — имя, размеры, вес и «Удалить» (владельцу и редактору) с `window.confirm`. Если картинка используется, показывается ответ API со списком страниц.
    - Виджет поля «картинка» в `SchemaForm`: `fieldKind` → `'image'` по `x-widget`. Сама форма остаётся общей: виджет приходит в неё явно (`widgets.image`), как и справочник медиа. Виджет показывает превью выбранной картинки и кнопки «Выбрать картинку» / «Заменить» / «Убрать», а также текстовое поле «Описание картинки (alt)» со счётчиком и ошибкой у поля. Выбор открывает медиатеку в модальном `<dialog>`: фокус внутри, Esc закрывает, а загрузить новый файл можно прямо там.
    - Предпросмотр строит справочник из медиатеки сайта (`mediaQuery`), так что выбранная картинка сразу видна в iframe.
15. **MCP.** Загрузки через MCP пока нет (`upload_image` — этап 4). В правила каталога добавлена строка о том, что картинка — это `{ mediaId, alt }` из медиатеки сайта.

## Критерии готовности

1. `POST /api/sites/:siteId/media` принимает JPEG, PNG, WebP и AVIF (тип по содержимому) и отвечает 201 с вариантами. SVG, текст с расширением `.jpg` и GIF получают 415 с понятным сообщением. Файл больше лимита получает 413, а запрос без файла — 400.
2. Ни в одном варианте и в сохранённом оригинале нет EXIF и XMP. Снимок с ориентацией 6 повёрнут: ширина и высота поменялись местами.
3. Варианты не шире исходника: 3000 px → 480/960/1440/1920; 1000 px → 480/960/1000; 300 px → 300. У каждой ширины есть AVIF, WebP и запасной формат исходника.
4. `GET /api/media/:id/:file` без входа отдаёт файл с правильным `Content-Type`, `Cache-Control: … immutable` и `nosniff`. Неизвестный файл, оригинал и кривой id получают 404/400. Тело ответа совпадает с тем, что лежит в хранилище.
5. Права: клиент своего сайта видит медиатеку и загружает, но не удаляет (403). Участник чужого сайта получает 404, без входа — 401, токен своего сайта может всё, что редактор.
6. Удаление используемой картинки (в черновике или опубликованной версии) — 409 со списком страниц, файлы и запись на месте. Неиспользуемой — 204, после чего файлы из хранилища удалены и файл варианта отвечает 404.
7. Черновик со ссылкой на картинку чужого сайта или несуществующую — 409 с путём до поля. Возврат версии с удалённой картинкой — 409, черновик не тронут.
8. Снимок сайта отдаёт справочник `media` по картинкам опубликованных страниц (и только по ним).
9. Схема: `hero` с `variant: 'split'` без картинки не проходит, ошибка по пути `image`. Alt пустой или длиннее 200 — ошибка. JSON Schema поля несёт `x-widget: 'image'`.
10. Рендер: `<picture>` с `source` AVIF и WebP, `srcset`, `sizes`, у `img` `width`/`height` и `alt`. У первого блока `loading="eager"` и `fetchpriority="high"`, у остальных `loading="lazy"`.
11. Админка: медиатека с загрузкой (прогресс/состояние), сеткой и удалением. Виджет «картинка» в форме блока: выбрать, заменить, убрать, alt. Ошибки загрузки и удаления видны текстом. Всё работает с клавиатуры.
12. e2e: загрузить картинку → hero `split` → выбрать её → alt → опубликовать → на сайте `<picture>` с AVIF/WebP и alt. Удаление этой картинки из медиатеки отклонено с названием страницы.
13. `pnpm format` чистый, `pnpm check` и `pnpm e2e` (в том числе `--shuffle`) зелёные.

### e2e (`e2e/tests/media.spec.ts`)
- Сценарий задачи: загрузить картинку в медиатеке (видно состояние и превью) → своя страница → hero «split» → в поле видно ошибку «нужна картинка» → «Выбрать картинку» → выбрать в диалоге → alt → «Опубликовать» → на сайте `<picture>` с `source` `image/avif` и `image/webp`, у `img` alt, `width`/`height`, `fetchpriority="high"`; файл варианта открывается.
- Удаление используемой картинки из медиатеки отклонено с названием страницы, картинка остаётся.
- SVG при загрузке — понятная ошибка в `role="alert"`, в медиатеке ничего не появилось.

## Итог

Сделано по плану. Медиатека сайта принимает JPEG, PNG, WebP и AVIF: тип определяется по содержимому, SVG, GIF и подделки получают 415, слишком большой файл — 413. Снимок поворачивается по EXIF, метаданные удаляются, варианты 480–1920 (не шире исходника) кодируются в AVIF, WebP и исходный формат. Хранилище (папка на диске) и обработка (sharp) спрятаны за интерфейсами `MediaStorage` и `ImageProcessor`, пути строятся только из id. У `hero` появился вариант `split` с обязательной картинкой. Поле `Image` с обязательным alt и пометкой `x-widget` получает в админке свой виджет с выбором из медиатеки в `<dialog>`. Снимок сайта отдаёт справочник вариантов, на сайте выводится `<picture>` с AVIF/WebP, `srcset`, `sizes`, размерами, lazy/eager и `fetchpriority`. Используемую картинку удалить нельзя, ссылку на чужую или удалённую сохранить или вернуть из истории — тоже.

Проверки: `pnpm format` чистый, `pnpm check` зелёный (api 192 теста, schema 59, blocks 11, admin 59, mcp 8). `pnpm e2e` — 34 теста, из них 4 новых в `media.spec.ts`, `pnpm e2e --shuffle` и `pnpm e2e --shuffle --repeat-each 2` (67) тоже зелёные. Медиатеку, диалог выбора, поле с выбранной картинкой и сайт на десктопе и телефоне я посмотрел на скриншотах. Для этого был временный конфиг Playwright в scratchpad вне репозитория: он поднимал серверы e2e и потом их погасил.

### Отклонения от плана и добавки

1. **Тесты разложены иначе, чем в списке.** Проверки `hero`/`split` лежат в `packages/schema/src/media.test.ts` рядом с `Image`. Ссылки на картинки при сохранении, справочник в снимке и возврат версии с удалённой картинкой собраны в `apps/api/src/modules/media/refs.test.ts`, а не в `pages.test.ts`/`revisions.test.ts`. Добавились юнит-тесты `media/processor.test.ts` (ширины и форматы вариантов) и `media/disk-storage.test.ts` (ключи с `..`, абсолютный путь, обратный слеш, чужое расширение отклоняются).
2. **`Breadcrumbs`: проп `page` переименован в `current`.** Последний пункт теперь — адрес страницы или название раздела («Медиатека»).
3. **Неизвестное имя файла в `GET /api/media/:id/:file` — 404, а не 400:** имя сверяется со списком вариантов в базе, отдельной проверки шаблоном нет. Кривой id — 400 через `validate`.
4. **Хранилище называется `diskStorage`**, а не `localStorage`: в Node 24 есть глобальный `localStorage`, и одинаковое имя путало бы.
5. **Ширина исходника тоже идёт в набор**, если он уже 1920 (1000 → 480/960/1000). Это записано в решении 7 и проверено тестами.
6. **Превью в медиатеке — без alt** (`alt=""`): рядом подписано имя файла, а у кнопки выбора есть своё имя «Выбрать «файл»». Рамка ошибки у поля «картинка» ставится по `data-invalid`: `aria-invalid` у группы полей не предусмотрен, ошибку читает `aria-describedby`.

### Что не проверено тестами напрямую и что осталось

- **Файлы на опубликованном сайте берутся из API** (`CMS_API_URL/api/media/…`). Выкладку картинок вместе со статикой и экспорт архивом (принцип 8) даст модуль публикации (9). Тогда адреса в справочнике будут указывать туда.
- **Удаление сайта** (его пока нет) каскадом удалит строки `media`, а файлы останутся на диске. Когда появится удаление сайта, оно должно чистить хранилище.
- **Гонка «удалить ↔ сохранить»:** проверка использования и удаление — отдельные запросы. Если ровно между ними сохранить черновик с этой картинкой, ссылка повиснет (блок просто выведется без картинки). На одном процессе с PGlite это не воспроизвести.
- **Медиатека отдаётся целиком, без постраничной выдачи.** Её добавим, когда картинок станет много.
- Анимированные WebP и AVIF превращаются в первый кадр. «Чистый оригинал» хранится, но наружу не отдаётся. Точки фокуса и подсказки alt от нейронки (PLAN, модуль 3) — потом.
- MCP-инструмента загрузки (`upload_image`) нет, он запланирован на этап 4. В правила каталога добавлена строка о том, что картинка — это `{ mediaId, alt }` из медиатеки сайта.
- Для клиента, который сохраняет несуществующую страницу со ссылкой на чужую картинку, API ответит 409 (картинка) раньше, чем 404 (страница). Оба ответа — отказ, и порядок здесь не важен.

## Исправления по проверке

Проверяющий не принял шаг из-за двух серьёзных ошибок и нашёл пять мелких. Исправлено всё.

### Серьёзные

1. **Id заглавными буквами.** `z.uuid()` пропускает `3F25…`, Postgres сравнивает uuid без учёта регистра, а код сравнивал строки. Удаление используемой картинки с id заглавными проходило мимо проверки использования (`jsonb_path_exists` по строке), удаляло строку, а потом падало на `mediaKey` с 500 и оставляло файлы на диске. Публичный `GET /api/media/<ID>/…` и загрузка в сайт с id заглавными тоже давали 500.
   - В `@cms/schema` появился `Uuid()`, это `z.uuid().toLowerCase()`. Им проверяются все id в адресах API (медиатека, страницы, история) и в MCP, а через `MediaId` и ссылки на картинки в JSON страниц. Такие ссылки сохраняются строчными. JSON Schema у поля не меняется.
   - `requireSite` приводит сырой `:siteId` к строчным: иначе токен не узнавал свой сайт в адресе с заглавными буквами.
   - Ключи файлов при удалении и отдаче строятся из id, которые вернула база (`findFiles` отдаёт и `id`), а не из запроса.
   - Использование картинки ищется без учёта регистра (`jsonb_path_query(… '$.**.mediaId')` и `lower`). Промах здесь значил бы удаление картинки со страницы, поэтому от того, как id записан в JSON, проверка не зависит.
   - Правило записано в CONVENTIONS: id во входе — только `Uuid()`.
2. **Большой файл из админки.** На тело больше `MEDIA_MAX_BYTES` + 64 КиБ API отвечает 413, не дочитав его, и соединение рвётся. Через прокси Vite браузер видел «API не отвечает». Теперь:
   - `GET /api/sites/:siteId/media` отвечает `{ items, maxBytes }`: медиатека знает лимит.
   - Админка сверяет размер файла до отправки (`tooLargeMessage` в `media-format.ts`). Текст тот же, что у API: «Файл больше N МБ. Уменьшите картинку и загрузите снова». Сообщение собирает `fileTooLargeMessage` из `@cms/schema`, одно на обоих. Под полем загрузки написан лимит («не больше 10 МБ»).
   - Запасной вариант: если связь оборвалась посреди отправки (прогресс уже шёл, а тело ушло не всё), `uploadMedia` пишет «Связь оборвалась во время отправки файла. Если файл большой, уменьшите его…», а не «API не отвечает».

### Мелкие

3. **Тесты лимитов доказывают то, что заявляют.**
   - «Тело больше лимита» теперь шлёт маленький файл и раздутое поле рядом. Без `bodyLimit` такой запрос прошёл бы с 201, а тест проверяет 413 и что процессор не вызывался: у `createTestApi` появился параметр `images` для обёртки-счётчика.
   - Отдельный тест шлёт 50 МБ потоком с `Content-Length` и проверяет, что прочитано меньше 5 МБ.
   - Новый тест на `too_many_pixels`: PNG в сотню байт с IHDR 10000 × 6000 (размеры правятся руками, CRC пересчитывается через `zlib.crc32`) получает 413 с текстом про 50 Мп.
   - После каждого 413 проверяется, что в папке медиатеки ничего не добавилось: `createTestApi` отдаёт `mediaDir`.
   - `migrate.test.ts` проверяет `media_one_author`.
4. **Списки форматов из схемы.** `imageMimeTypes` стал `as const` с типом `ImageMimeType`, а обратный справочник `imageFormatOf` выводится из него. Ими пользуются маршруты, `sharp-processor.ts`, `StoredVariant.format` (`ImageFormat`), `media.mime_type` и `NewMedia.mimeType` (`ImageMimeType`). Текст про 50 мегапикселей собирается из `MAX_PIXELS`. SQL не поменялся: `db:generate` пишет «No schema changes».
5. **Комментарий в `storage.ts`** указывает на `disk-storage.ts`.
6. **Картинка в hero не в варианте split.** Раньше она оставалась в данных невидимой, но считалась используемой. Теперь схема `hero` отвечает ошибкой у поля `image`: «Картинка выводится только в варианте split: уберите её или выберите split». Данные совпадают с тем, что видно на странице, и «используется на странице» всегда правда. Описание поля говорит то же. Значит, при смене варианта человек увидит ошибку у поля и уберёт картинку одной кнопкой. Молча выбрасывать её схема не стала: это скрытая потеря данных, и JSON Schema для MCP не умеет выражать transform.
7. **Нагрузка от sharp.**
   - Обработка идёт через общую на процесс очередь `concurrencyLimit(PROCESSING_CONCURRENCY = 2)` из `processor.ts`, у неё есть свой юнит-тест.
   - Внутри одной картинки ширины режутся по очереди, по три формата сразу. Было до 13 конвейеров на загрузку, стало не больше трёх, и не больше двух загрузок одновременно.
   - Проверки по заголовку (тип, мегапиксели) идут до очереди, поэтому отказ приходит сразу.
   - Декодирование один раз в общий буфер не сделано. Сырой буфер высокой картинки шириной 1920 и в 50 Мп занял бы до 200 МБ. libvips и так читает исходник потоком, а для JPEG и WebP уменьшает его ещё при чтении, так что очереди хватает.

### Проверки

- `pnpm format` чистый, `pnpm check` зелёный: api 202 теста (было 192), schema 62 (было 59), blocks 11, tokens 2, admin 61 (было 59), mcp 8.
- `pnpm e2e` и `pnpm e2e --shuffle`: 35 тестов. Новый тест «файл больше лимита»: в e2e `MEDIA_MAX_BYTES` равен 2 МБ, файл 5 МБ. Тест ждёт текст причины в `role="alert"` и проверяет, что POST в медиатеку не ушёл.
- Новые API-тесты на id заглавными:
  - загрузка в сайт с id заглавными — 201, файлы лежат под строчными id;
  - токен с адресом в заглавных — 201;
  - файл варианта по id заглавными — 200;
  - удаление используемой картинки по id заглавными — 409, запись и все файлы на месте;

  - удаление неиспользуемой по id заглавными — 204, файлов нет.
- Схема: id заглавными в `Image` приводится к строчным, hero `centered` и `left` с картинкой не проходят.
