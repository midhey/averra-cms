# Шаг 2.6. Хвосты этапа 2

## Цель

Перед этапом 3 закрыть то, что нашли независимые проверяющие шагов 2.0–2.5: 49 замечаний, все minor. Каждое замечание сначала проверено на актуальность (часть закрыли следующие шаги), актуальное исправлено с тестом, если это поведение, неактуальное или спорное отклонено с причиной. Первым — безопасность: учебный секрет подписи cookie.

## Решение по секрету (замечание 25)

**Что было.** `NODE_ENV` по умолчанию — `development`. Если на сервере забыть `NODE_ENV=production`, API молча стартовал с `DEV_AUTH_SECRET`, который лежит в репозитории, ставил cookie без `Secure` и при заданных `DEV_OWNER_*` заводил владельца с учебным паролем.

Насколько это опасно сегодня. Better Auth 1.7 с выключенным кешем сессии в cookie сверяет токен сессии с базой, поэтому одного секрета мало, чтобы подделать вход: нужен ещё настоящий токен. Но всё, что Better Auth подписывает этим секретом (cookie «не запоминать меня», кеш сессии, если его когда-нибудь включат, будущие плагины), с публичным секретом ничего не стоит. Ждать, пока это станет дырой, не стали.

**Что сделано — главный замок и добавочная защита** (по итогам проверки, см. «Исправления по проверке»).

1. **Учебный режим — только явный** (`isLocalDev` в `apps/api/src/config.ts`): флаг `--dev` в командной строке API **и** `NODE_ENV` не `production` (не задан, `development` или `test`) **и** `ADMIN_URL` и `API_URL` после подстановки умолчаний указывают на loopback (`localhost`, `*.localhost`, `127.x.x.x`, `[::1]`). Флаг ставят только скрипт `dev` у `apps/api` (`tsx watch src/index.ts --dev`) и e2e; `start` его не ставит. Только в учебном режиме можно жить без своего `AUTH_SECRET` и заводить в пустой базе демо-сайт и владельца из `DEV_OWNER_*` (`devSeed` в конфиге). В любом другом случае, в том числе вовсе без переменных, без `AUTH_SECRET` конфиг не проходит, и API не стартует с объяснением: «Нужен свой AUTH_SECRET (от 32 символов, например openssl rand -base64 32). Без него API запускается только для разработки: pnpm dev (флаг --dev), NODE_ENV не production и адреса ADMIN_URL и API_URL на localhost». Учебный секрет, вписанный в `AUTH_SECRET` руками, вне учебного режима тоже не проходит, в проде — тем более. Адреса — второй замок внутри учебного режима: на сервере их задают всегда, иначе админка с настоящего домена не войдёт (Better Auth не примет её Origin). Команды терминала зовут конфиг с `dev: true`: сеть они не слушают, хеш пароля от секрета не зависит, а демо-сайт и владельца не заводят. Так `pnpm user:create` работает на свежем клоне без `.env`.
2. **Добавочная защита: на учебном секрете API отвечает только запросам к localhost с этого компьютера** (`prepareRequest` в `apps/api/src/client-ip.ts`). Решает адрес сокета, а не заголовок `X-Forwarded-For`, который пишет клиент, и имя в `Host`. Остальным — 403 «API запущен с учебным секретом и отвечает только на запросы к localhost с этого компьютера. Задай свой AUTH_SECRET». Прямой запрос из сети получает 403. Прокси на том же сервере соединяется с API с `127.0.0.1`, поэтому проверяется и `Host`: прокси, который передаёт настоящий `Host` (Caddy по умолчанию, `cms.example.ru`), тоже получает 403. Та же проверка закрывает подмену DNS (DNS rebinding), когда чужая страница ходит на `127.0.0.1` под своим именем. **Предел проверки:** nginx по умолчанию шлёт апстриму его собственный `Host` (`proxy_set_header Host $proxy_host`, то есть `127.0.0.1:4000`), Caddy с `header_up Host {upstream_hostport}` — так же, а прокси «для всех имён» передаёт `Host` клиента как есть, и клиент может написать `localhost`. Такие запросы проходят, поэтому эта защита не главная, а главный замок — явный флаг. Разработке она не мешает: админка ходит в API через прокси Vite с того же компьютера, рендерер и e2e — тоже. В лог при старте пишется, что API работает в учебном режиме.

Заодно cookie получают `Secure`, если `API_URL` начинается с `https://`, даже без `NODE_ENV=production`. Прод по-прежнему требует `AUTH_SECRET`, `ADMIN_URL` и `API_URL`.

Почему флаг, а не обязательный `NODE_ENV` или `production` по умолчанию. Переменную для `pnpm dev` и команд терминала кроссплатформенно не выставить без новой зависимости (`cross-env`) или `shellEmulator` для всех скриптов pnpm. Флаг в командной строке работает одинаково везде и без зависимостей, а случайно дописать `--dev` к команде запуска на сервере, в отличие от «забыть переменные», трудно.

Тесты: `config.test.ts` (без флага `--dev` API вовсе без переменных не стартует, и не помогают ни `NODE_ENV=development` или `test`, ни адреса localhost, ни учебный секрет руками; без флага со своим секретом работает, но без демо-сайта и владельца; демо-сайт по тому же правилу, что и владелец; сервер без `NODE_ENV` с настоящими адресами не стартует и с флагом; хватает одного адреса не на localhost; учебный секрет руками вне localhost и в проде не проходит; что считается loopback, а `localhost.example.ru` нет; со своим секретом вне прода работает, `Secure` по https; `loopbackOnly` только на учебном секрете; владелец для разработки только на localhost; пустой адрес — ошибка конфига) и `client-ip.test.ts` (loopback-адреса проходят, остальные и неизвестный адрес получают 403, подделанный `X-Forwarded-For: 127.0.0.1` не помогает; с `127.0.0.1`, но с чужим `Host` — тоже 403, со своим секретом `Host` не важен).

## Остальная безопасность и надёжность

- **`X-Forwarded-For` (21).** Перезапись вынесена из `index.ts` в `src/client-ip.ts` (`prepareRequest`, `serverFetch`) без побочных эффектов. Тесты: при `TRUST_PROXY=false` заголовок заменяется адресом сокета, при `true` остаётся. Есть и тест с настоящим сервером на временном порту: четыре попытки входа с разными «своими» `X-Forwarded-For` — 401, 401, 401, 429.
- **Продление сессии (29).** Тест сдвигает `sessions.expires_at` в базе в памяти: Better Auth продлевает сессию, и `Set-Cookie` с новым сроком доходит через наш маршрут. Ещё один тест проверяет, что протухшая сессия даёт 401 и стирает cookie.
- **Замок базы (26).** Pid пишется во временный файл, а замок ставится жёсткой ссылкой (`link` не перезаписывает файл и не оставляет окна, когда замок уже есть, а pid в нём ещё нет). Пустой или испорченный замок свежее 10 секунд считается занятым, старше — мусором после сбоя. Перед перехватом брошенного замка pid сверяется ещё раз. В сообщениях API и команд теперь есть путь к файлу замка и подсказка: если процесса нет или это не API — удали файл (pid на Windows переиспользуются).
- **Миграция 0002 (5).** Перед `CHECK` она сбрасывает и обратное полусостояние (заголовок без содержимого). Правка уже применённой миграции безопасна: мигратор Drizzle сравнивает только время миграций, а не хеш. Новые базы и базы до 0002 получают исправление, в применённых ничего не меняется.

## Отклонения и добавки

1. **`maxWorkers: 6` в `apps/api/vitest.config.ts`.** По умолчанию vitest запускает воркеров на один меньше, чем ядер (на машине разработки 19), и у каждого свой PGlite на сотни мегабайт. При 8 ГБ памяти и параллельной нагрузке воркеры падали на старте (код 0x80000003), а соседние тесты не укладывались в 30 секунд. Шесть воркеров — тот же порядок времени без падений.
2. **Сообщения Zod — в `@cms/schema`** (13, 23). `setupZodMessages` переехала из админки в `@cms/schema` и включается при старте API, в `createTestApi`, в `run` команд терминала и в MCP. Правило CONVENTIONS «одна схема — одно сообщение везде» теперь правда, а не преувеличение.
3. **`ExistingPageSlug`** (16) — мягкая схема адреса для страниц, которые уже есть (как до шага 2.1), рядом со строгой `PageSlug` для новых. Ею пользуются маршруты API и админка.
4. **Роль в e2e подменяется в браузере** (28). Участника в базе e2e не завести: команды не открывают базу, пока работает API e2e. Поэтому `client.spec.ts` подменяет роль в ответах `GET /api/me` и `GET /api/sites/:id` (`page.route`). Права так не проверяются, их проверяют тесты API. Проверяется то, что экраны слушаются роли.
5. **Рендерер без новых зависимостей** (30). Вместо vitest в `apps/renderer` (новая dev-зависимость и правка lockfile ради шести строк) запасной демо-сайт в dev проверен вручную: на временных портах `astro dev` без `CMS_SITE_ID` отдаёт демо-сайт и пишет предупреждение в лог, а `astro build` без него падает с подсказкой.

## Исправления по проверке

Проверяющий не принял шаг из-за блокера в замечании 25 и нашёл четыре мелочи. Исправлено всё.

### Блокер: API на учебном секрете можно было открыть наружу (25)

**Что нашли.** Первый замок пускал учебный режим, если не задано ничего: ни `NODE_ENV`, ни адресов, ни `AUTH_SECRET`. Второй замок (адрес сокета плюс `Host`) обходит прокси на том же сервере. nginx по умолчанию шлёт апстриму `Host $proxy_host`, и при `proxy_pass http://127.0.0.1:4000` API видит соединение с `127.0.0.1` и `Host: 127.0.0.1:4000`. Так же ведёт себя Caddy с `header_up Host {upstream_hostport}`, а прокси «для всех имён», который передаёт `Host` клиента, обходится запросом с `Host: localhost`. Проверяющий воспроизвёл это вживую: через такой прокси с адреса в сети прошли вход учебным владельцем из `.env.example`, `GET /api/sites` и `POST /api/sites`. Значит, утверждения README («не откроется … через прокси на том же сервере»), комментария в `config.ts` и этого плана были неправдой.

**Что сделано.**

- Учебный режим стал явным: без флага `--dev` у API его нет. Флаг ставят скрипт `dev` у `apps/api` (`tsx watch src/index.ts --dev`) и e2e (`pnpm --filter @cms/api exec tsx src/index.ts --dev`: через скрипт `start` pnpm мог бы принять `--dev` за свой флаг). `index.ts` разбирает аргументы через `parseArgs` из `node:util`: неизвестный аргумент — ошибка, а не молчаливый пропуск. `parseConfig` и `loadConfig` принимают `{ dev }`, `isLocalDev` требует флаг. Без него API без `AUTH_SECRET` не стартует, даже вовсе без переменных, и не заводит ни демо-сайта, ни учебного владельца. Решение кроссплатформенное и без новых зависимостей.
- Команды терминала зовут конфиг с `dev: true`. Им учебный секрет не опасен: сеть они не слушают, хеш пароля от секрета не зависит, демо-сайт и владельца они не заводят. Иначе `pnpm user:create` на свежем клоне требовал бы `.env`.
- Проверка `Host` осталась добавочной защитой. Её предел честно описан в README, `.env.example`, CONVENTIONS, комментариях `config.ts` и `client-ip.ts` и в «Решении по секрету» выше: nginx с `Host` апстрима и прокси «для всех имён» её обходят, поэтому `pnpm dev` на сервере не запускают.

Тесты в `config.test.ts`: «без флага --dev учебного режима нет». API без переменных не стартует с сообщением про `--dev`. Не помогают `NODE_ENV=development` или `test` с адресами localhost и `DEV_OWNER_*`, не помогает и учебный секрет, вписанный руками. Со своим секретом без флага API работает, но `devSeed` и `devOwner` выключены. Остальные тесты конфига идут с флагом, как `pnpm dev`. Вручную на временном порту (данные вне репозитория): `pnpm --filter @cms/api start` без переменных печатает ошибку конфига и не стартует. `pnpm dev` (`tsx watch` передаёт `--dev` скрипту) стартует в учебном режиме, создаёт владельца, отвечает 200 по `localhost` и 403 с чужим `Host`. Сам разбор флага в `index.ts` автотестом не покрыт: `index.ts` при импорте поднимает сервер и открывает базу. Его проверяют этот ручной запуск и e2e, которые без флага не стартовали бы.

### Мелочи

1. **Демо-сайт заводился по одному `NODE_ENV` (25).** Если на сервере заданы свой `AUTH_SECRET` и настоящие адреса, но не `NODE_ENV`, в пустую базу лёг бы опубликованный «Демо: ремонт квартир», а его снимок открыт без входа. Теперь демо-сайт и учебный владелец заводятся по одному правилу: `devSeed` = `NODE_ENV=development` и учебный режим (`isLocalDev`, то есть флаг `--dev` и localhost). `index.ts` смотрит на `config.devSeed`. Тест: «демо-сайт заводится по тому же правилу, что и владелец, а не по одному NODE_ENV» (с флагом и без, свой секрет и настоящие адреса, `NODE_ENV=test`, прод).
2. **Пустой `ADMIN_URL` или `API_URL` ронял конфиг `TypeError: Invalid URL`.** Zod 4 выполняет `refine` и после проваленной `z.url`, а `refine` звал `new URL('')`. Теперь сначала `URL.canParse` (и в `refine` у `Origin`, и в `isLoopbackUrl`), и пустая строка даёт обычную ошибку конфига у своего поля. Тест: «пустой адрес — понятная ошибка конфига, а не падение new URL», для обоих полей, в разработке и в проде.
3. **Ссылка на удалённый тест в `2.0-e2e.md`.** В «Исправлениях по проверке», пункт 3, теперь `packages/schema/src/zod-messages.test.ts`.
4. **Старое число e2e в «Итоге этапа 2».** В PLAN — 48 тестов (вместе с входом проекта `setup`), столько их после шага 2.6.

Итог: `pnpm check` зелёный (395 тестов), `pnpm e2e` — 48 из 48.
