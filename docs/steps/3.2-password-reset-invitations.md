# Шаг 3.2. Сброс пароля и приглашения письмом

## Цель

Первые настоящие письма на почте шага 3.1 (модули 1 и 10). Человек, который забыл пароль, сам получает одноразовую ссылку и задаёт новый пароль. Владелец приглашает участника на сайт по почте: тот по ссылке сам задаёт имя и пароль (или, если вход у него уже есть, просто подтверждает доступ), и пароль никому не передают руками. Требования раздела «Безопасность» модуля 10 выполняются: ссылки одноразовые, в базе только хеш токена, срок жизни ограничен (1 час и 7 дней), новый запрос сжигает старую ссылку, ответ на «забыл пароль» не выдаёт, есть ли такой адрес, а запросы ограничены по адресу и IP.

## Решения и почему

1. **Сброс пароля — на Better Auth 1.7** (сверено с документацией better-auth.com, разделы Email & Password и Options, и с кодом установленной версии). Эндпоинты `POST /api/auth/request-password-reset` и `POST /api/auth/reset-password`, наш код — в `sendResetPassword`. Настройки:
   - `resetPasswordTokenExpiresIn: 3600` — ссылка живёт час (`PASSWORD_RESET_TTL_MINUTES`; тот же срок уходит в письмо и в `expires_at` очереди).
   - `revokeSessionsOnPasswordReset: true` — после смены пароля все сессии пользователя удаляются.
   - **Только хеш в базе.** По умолчанию Better Auth пишет токен в `verifications.identifier` как есть (`reset-password:<токен>`). Включаем `verification.storeIdentifier` со своим хешером: в базе остаётся `reset-password#<SHA-256 всего идентификатора, base64url>`. Имя открыто, чтобы найти записи сброса пользователя (пункт ниже); сам токен из хеша не восстановить. Better Auth хеширует идентификатор и при поиске, и при погашении (`consumeVerificationValue`), так что одноразовость (запись удаляется атомарно при погашении) сохраняется. Но с хешером он ищет запись дважды: сначала по хешу, а не нашёл — по идентификатору как есть (запасной путь для записей, сохранённых до включения хеширования). Поэтому в базе на месте разделителя всегда `#` (`<имя>#<хеш>`, а у идентификатора без двоеточия — `#<хеш>`), а каждый идентификатор, который Better Auth собирает из присланного, начинается с постоянной приставки без `#` (`reset-password:`, `delete-account-`). Сохранённая строка с такой приставки не начинается, и запасной поиск не совпадёт с тем, что лежит в базе. Если включить плагин или эндпоинт, где идентификатор целиком задаёт клиент (номер телефона, адрес кошелька), это надо перепроверить (уточнено в «Мелочах после приёмки», п. 3). Кроме того, обёртка `POST /api/auth/reset-password` пускает к Better Auth только токен его формата (24 буквы и цифры, `ResetPasswordToken`). См. «Исправления по второй проверке», п. 1.
   - **Новый запрос сжигает старую ссылку.** Better Auth этого не делает. В `sendResetPassword` одной транзакцией: удаляются записи сброса этого пользователя, созданные раньше нынешней (`value = userId`, `identifier LIKE 'reset-password#%'`, `created_at` меньше), и письмо ставится в очередь (`enqueueMail` тем же `tx`). «Раньше нынешней», а не «все, кроме нынешней»: два одновременных запроса не убьют ссылки друг друга, выживет последняя.
   - Ссылка в письме ведёт в админку, а не в API: `ADMIN_URL/reset-password#token=…`. Токен во фрагменте (`#`), а не в пути или query: фрагмент браузер не отправляет на сервер, поэтому токен не попадает в логи статики админки и прокси и в `Referer`. Экран сразу убирает его из адресной строки (`history.replaceState`). Эндпоинт Better Auth `GET /api/auth/reset-password/:token` (токен в пути, а значит, в логе запросов) закрыт: 404.
2. **Одинаковый ответ и время.** Свой обработчик `POST /api/auth/request-password-reset` перед Better Auth: проверяет вход своей схемой (`ForgotPassword`: только `email`, без `redirectTo`), отвечает одним и тем же телом `{ "status": "sent", "message": "…" }` для любого адреса и выравнивает время ответа: не раньше 300 мс от начала запроса. Без выравнивания существующий адрес отвечает заметно дольше (запись токена, транзакция с письмом) — документация Better Auth тоже предупреждает о такой утечке по времени. Ошибка постановки письма (сбой базы) не меняет ответ: Better Auth ловит её в `runInBackgroundOrAwait` и пишет в лог.
3. **Лимиты сброса.** По IP — свой счётчик в обёртке: 5 запросов за 15 минут с одного IP (`RESET_REQUESTS_PER_IP`). Правило Better Auth для `/request-password-reset` — запасное и вдвое выше (см. «Исправления по второй проверке», п. 2). По адресу — свой счётчик в памяти (`createRateLimiter` в `src/rate-limit.ts`, экземпляр создаёт `createApp`, глобального состояния нет): 3 запроса за 15 минут на один адрес (в нижнем регистре). Счётчик считает **любой** адрес, есть он в базе или нет, поэтому 429 ничего не выдаёт. Лимит по IP проверяется раньше лимита по адресу (см. «Исправления по проверке», п. 1). Если запрос всё же отбил запасной лимит Better Auth, попытка адреса возвращается: отбитый по IP запрос в счётчик адресов не попадает ни в каком случае («Мелочи после приёмки», п. 2). Счётчики живут в памяти процесса, как и лимит входа Better Auth: при одном процессе API этого хватает, при нескольких — переносим в базу (записано в «Что осталось»). `POST /api/auth/reset-password` — 10 попыток в минуту с IP (токен 24 случайных символа подобрать нельзя, но перебор всё равно ни к чему).
4. **Почта выключена — честно.** `GET /api/password-reset` (открыт без входа) отвечает `{ "available": true | false }`. Экран «Забыли пароль?» при `false` сразу говорит, что сброс по почте недоступен, и как вернуть доступ: попросить владельца или на сервере выполнить `pnpm user:password --email …`. `POST /api/auth/request-password-reset` при выключенной почте — 503 `mail_disabled` для любого адреса (в очередь ничего не ставится, см. итог шага 3.1).
5. **Команда `pnpm user:password --email …`** — новый пароль скрытым вводом дважды или из `CMS_USER_PASSWORD` (как `user:create`). Меняет хеш пароля (или создаёт вход по паролю, если его не было), завершает все сессии пользователя и сжигает его ссылки сброса — так же, как сброс по почте. Это путь восстановления доступа без почты и для владельца, который остался без пароля.
6. **Приглашения — своя таблица `user_invitations`** (миграция `0008_user_invitations`): `id`, `site_id` (каскад), `email` (нижний регистр, CHECK), `role` (`editor` | `client`, CHECK), `token_hash` (SHA-256), `invited_by` и `accepted_by` (пользователи, `set null`), `created_at`, `expires_at` (7 дней, CHECK `expires_at > created_at`), `accepted_at`, `revoked_at` (CHECK: не оба сразу). Частичный уникальный индекс `(site_id, email) WHERE accepted_at IS NULL AND revoked_at IS NULL`: у адреса на сайте одно открытое приглашение.
   - Токен — как у токенов API: `inv_<id приглашения>_<32 случайных байта hex>`. Строка находится по id, хеш сверяется `constantTimeEqual`; в базе только хеш, сам токен есть только в письме (а в очереди — только до отправки и не дольше срока ссылки, правило шага 3.1).
   - Повторное приглашение того же адреса на тот же сайт отзывает прежнее (старая ссылка перестаёт работать) и шлёт новое — в одной транзакции с письмом.
   - Пригласить нельзя владельца админки (ему и так открыты все сайты) и того, кто уже участник этого сайта: 409 с путём до поля `email`. Сменить роль участника пока можно командой `pnpm member:add`.
   - Состояние для списка считается из полей: принято → «принято»; отозвано → «отозвано» (или «истекло», если отзыв пришёлся на уже истёкшее — так его отзывает повторное приглашение); `expires_at` прошёл → «истекло»; иначе «ждёт».
7. **Принятие приглашения.** Три запроса, все с токеном в теле (не в пути: путь попадает в лог запросов):
   - `POST /api/invitations/lookup` (без входа) — что за приглашение: сайт, роль, адрес, кто пригласил, срок и есть ли уже пользователь с этим адресом.
   - `POST /api/invitations/register` (без входа) — нового пользователя: `{ token, name, password }`. Одна транзакция: пользователь (`member`, почта подтверждена — ссылка пришла на неё), вход по паролю, доступ к сайту и отметка «принято». Если пользователь с этим адресом уже есть — 409: «войдите и примите». Админка потом входит этим паролем сама.
   - `POST /api/invitations/accept` (только после входа) — существующего пользователя: `{ token }`. Адрес вошедшего должен совпасть с адресом приглашения, иначе 403 с подсказкой, под кем войти. Токен API — 403.
   - **Одноразовость** держит один условный запрос: `UPDATE … SET accepted_at WHERE id = ? AND accepted_at IS NULL AND revoked_at IS NULL AND expires_at > now RETURNING`. Второй запрос с той же ссылкой (даже одновременный) строки не получит.
   - Ошибки ссылки: неизвестный или повреждённый токен — 404 `invitation_not_found`; принятое — 410 `invitation_used`, отозванное — 410 `invitation_revoked`, истёкшее — 410 `invitation_expired`. 410 Gone — новый код в CONVENTIONS: «ссылка из письма больше не действует». Тексты говорят, что делать дальше.
8. **Права.** Новое действие `members.invite` в таблице `src/auth/access.ts` — только `owner`: приглашать, смотреть список и отзывать. Редактор и клиент получают 403, токен — 403, чужой сайт — 404 (как везде, через `requireSite`). Редактору не даём: участник, который сам раздаёт доступ к сайту клиента, — решение владельца студии, и пока такой нужды нет. Если понадобится — одна строка в `access.ts` (записано в PLAN).
9. **Отзыв** — `DELETE /api/sites/:siteId/invitations/:invitationId`: 204, повторный отзыв — тоже 204 (время первого не сдвигается); принятое — 409 (доступ уже выдан, его убирают иначе); чужое или несуществующее — 404.
10. **Почта выключена — приглашения тоже 503 `mail_disabled`**, и в API, и в команде. Экран сайта показывает владельцу причину заранее (из `GET /api/mail`) и не даёт отправить форму.
11. **Команда `pnpm member:invite --email … --site … --role editor|client [--by <почта владельца>]`** — та же логика (`createInvitation` в `src/modules/invitations/service.ts`), письмо ложится в очередь и уходит, когда запустится API (команда работает, только пока API остановлен: замок базы). Без `--by` приглашает единственный владелец; если владельцев несколько, команда просит `--by`. Ссылку команда не печатает: её получает только адресат.
12. **Данные в письме — одной строкой.** Имя пользователя и название сайта проходят `toMailLine` (управляющие символы → пробел, обрезка до длины схемы): имя, заведённое когда-то с переводом строки, не должно ломать письмо сброса. Новые имена (`UserName` в `@averra/schema`) управляющих символов не принимают.
13. **Схемы входа — в `@averra/schema`** (их же используют формы админки): `UserName`, `PASSWORD_LENGTH`, `NewPassword`, `UserEmail`, `MemberRole`, `ForgotPassword`, `ResetPassword`, `NewInvitation`, `InvitationToken`, `InvitationLookup`, `InvitationRegister`, `InvitationAccept`. `NewUser` в API собирается из них.
14. **Админка.**
    - Без входа открыты `/login`, `/forgot-password`, `/reset-password`, `/invite`.
    - «Забыли пароль?» на экране входа → `/forgot-password`: почта → «Если такой адрес есть, письмо придёт…» (одинаково для любого адреса). Почта выключена — объяснение и как восстановить доступ.
    - `/reset-password#token=…`: новый пароль дважды → «Пароль изменён, входы на других устройствах завершены» и ссылка «Войти». Ссылка негодная — понятная ошибка и ссылка на новый запрос.
    - `/invite#token=…`: сайт, роль и кто пригласил; новому — имя и пароль дважды («Принять приглашение», потом вход и сайт); существующему — вход паролем прямо на экране или кнопка «Принять приглашение», если он уже вошёл; вошёл другой — «Выйти» и вход под нужным адресом.
    - На экране сайта у владельца — раздел «Участники»: форма «Пригласить участника» (почта, роль) и таблица приглашений с состоянием и «Отозвать» у ждущих.

## Критерии готовности

1. Сброс: письмо «Сброс пароля» уходит через очередь со ссылкой `ADMIN_URL/reset-password#token=…`; по ссылке пароль меняется; старые сессии пользователя больше не пускают; та же ссылка второй раз — 400 с русским текстом; ссылка старше часа — отказ; после нового запроса прежняя ссылка не работает; в `verifications` нет токена в открытом виде.
2. Ответ на запрос сброса для существующего и несуществующего адреса одинаковый (статус и тело) и не быстрее 300 мс; письмо уходит только существующему.
3. Четвёртый запрос сброса на один адрес за 15 минут — 429, и для существующего адреса, и для несуществующего; шестой запрос с одного IP — 429.
4. Почта выключена: `GET /api/password-reset` → `available: false`, запрос сброса — 503 `mail_disabled`, приглашение — 503.
5. `pnpm user:password` меняет пароль, завершает сессии и сжигает ссылки сброса (проверено через функцию репозитория).
6. Приглашение: владелец приглашает — 201, письмо со ссылкой `ADMIN_URL/invite#token=…`; новый пользователь по ссылке задаёт имя и пароль и видит только этот сайт с выданной ролью; существующий пользователь принимает после входа; не тот пользователь — 403; отозванное — 410; истёкшее — 410; повторное принятие — 410; неизвестный токен — 404; повторное приглашение отзывает прежнее; владельца и уже участника пригласить нельзя — 409; в базе только хеш токена.
7. Права: редактор и клиент — 403 на список, приглашение и отзыв; токен — 403; чужой сайт — 404; без входа — 401 (кроме открытых `lookup` и `register`).
8. Админка: «Забыли пароль?» → письмо → новый пароль → вход (e2e); владелец приглашает клиента → клиент по ссылке задаёт пароль → видит только свой сайт (e2e).
9. `pnpm format` чистый, `pnpm check` и `pnpm e2e` зелёные.

## Итог

Сделано по плану. Сброс пароля работает на Better Auth 1.7: письмо уходит через очередь `mail_outbox`, ссылка ведёт в админку (`/reset-password#token=…`) и живёт час. В `verifications` лежит только SHA-256 идентификатора: `verification.storeIdentifier` со своим хешером оставляет открытым только имя: `reset-password#<хеш>`. Новый запрос сжигает прежние ссылки пользователя в той же транзакции, что и постановка письма. После смены пароля все сессии завершаются. Запрос сброса для любого адреса отвечает одинаково и не раньше чем через 300 мс. Лимиты: 3 запроса за 15 минут на адрес (свой счётчик, считает и несуществующие адреса) и 5 за 15 минут с IP (после проверок — свой счётчик в обёртке, правило Better Auth только запасное). Без почты экран «Забыли пароль?» объясняет, как вернуть доступ, а `pnpm user:password` задаёт пароль из терминала. Приглашения хранятся в таблице `user_invitations` (миграция `0008`): токен `inv_<id>_<секрет>`, в базе только хеш, ссылка одноразовая (условный `UPDATE`), срок 7 дней. Повторное приглашение отзывает прежнее. Владелец приглашает и отзывает на экране сайта или командой `pnpm member:invite`. Новый человек по ссылке задаёт имя и пароль, а пользователь, у которого вход уже есть, входит своим паролем и принимает приглашение.

Проверки: `pnpm format` чистый. `pnpm check` зелёный: schema 100 тестов (было 90), tokens 2, blocks 11, api 393 (было 348), admin 86 (было 76), mcp 8. `pnpm e2e` и `pnpm e2e --shuffle` прошли, 54 теста, из них 4 новых. Новые тесты API зелёные и с `--sequence.shuffle`. Команды `user:create`, `user:password` и `member:invite` проверены руками на временной базе в scratchpad: удачные вызовы, нет пользователя, короткий пароль, нет сайта, владелец вместо участника, почта выключена. Новые экраны я посмотрел на скриншотах на десктопе и на телефоне. Для этого во временном конфиге Playwright вне репозитория на портах 4150 и 5290 поднимались свои API и админка со своей базой, после прогона серверы погашены.

### Отклонения от плана и добавки

1. **Пароль хешируется только для действующей ссылки.** Сначала маршрут `register` считал хеш (scrypt) до проверки токена. Так любой запрос с выдуманным токеном нагружал процессор на открытом маршруте. Теперь `registerByInvitation` получает функцию `hashPassword` и вызывает её после проверки ссылки. Тест проверяет, что по неизвестной ссылке и по ссылке с чужим секретом хеш не считается.
2. **Внутри транзакции нельзя спрашивать базу мимо `tx`.** PGlite ждёт конца открытой транзакции, и запрос через `db` повис бы навсегда. Почему не удалось принять приглашение, сервис выясняет уже после отката. Правило записано в CONVENTIONS.
3. **Приглашения и почта на экране сайта грузятся в загрузчике маршрута, а не после отрисовки.** Сначала раздел «Участники» спрашивал их через `useQuery`. Тест «сессия кончилась посреди работы» (`auth.spec.ts`) это поймал. Запрос уходил уже после показа экрана, получал 401 и уводил на вход раньше, чем тест кликал по странице. Теперь загрузчик сайта решает по роли из `meQuery` и грузит всё параллельно. Сам тест тоже поправлен: прежде чем стереть cookie, он ждёт заголовок экрана. Раньше он ждал только адрес, а адрес меняется до конца загрузки. Правило записано в CONVENTIONS.
4. **Скрытые подписи колонок растягивали страницу на телефоне.** `.visuallyHidden` позиционируется абсолютно и вставал за краем широкой таблицы вне прокрутки. У `.tableScroll` теперь `position: relative`. Таблица приглашений прокручивается вбок (`.wideTable`), а не переносит почту по буквам.
5. **Форма приглашения после успеха не ругается на пустую почту.** В `useFormErrors` добавлен `reset()`.
6. **Общие помощники.** `src/secrets.ts` (случайный секрет и SHA-256 в hex) теперь используют токены API и приглашения. `toMailLine` чистит имя и название сайта для данных письма. `insertUser`/`upsertMember` работают в чужой транзакции. Схемы почты, имени, пароля и роли переехали в `@averra/schema` и общие для API, команд и админки. У имени появилось правило «одной строкой».
7. **`ApiRequestError` в админке знает код ошибки** (`mail_disabled`, `invalid_token`, `user_exists`, `invitation_*`). По коду экраны решают, что показать.
8. **Комментарии e2e обновлены.** Участника в e2e теперь можно завести приглашением. Подмена роли в `client.spec.ts` и `mail.spec.ts` осталась: она проверяет, что экраны слушаются роли.

### Что не проверено тестами напрямую и что осталось

- **Лимиты в памяти процесса.** Свои счётчики (по IP и по адресу у сброса, на адрес и на владельца у приглашений) и лимит Better Auth живут в памяти одного процесса API. Память у них ограничена (не больше 10 000 ключей на счётчик), но при нескольких процессах их надо перенести в базу (у Better Auth есть `storage: 'database'`).
- **Выравнивание времени.** Порог в 300 мс закрывает разницу между существующим и несуществующим адресом, пока оба пути укладываются в порог. Если база будет отвечать дольше, разница снова станет заметной. Тест проверяет, что оба ответа не быстрее порога, но не меряет разброс.
- **Письмо со старой ссылкой, которое ещё в очереди**, после нового запроса всё равно уйдёт. Ссылка в нём уже не работает, а экран честно скажет, что она заменена новой. Отменять такие письма в очереди не стал.
- **Одновременное принятие** держит условный `UPDATE`. На PGlite запросы идут по одному, поэтому настоящая гонка двух соединений проверится только на PostgreSQL. Тест проверяет повторное принятие подряд.
- **Экран участников сайта** (список, смена роли, снятие доступа из админки) — «Потом». Пока роль меняет `pnpm member:add`. Давать редактору приглашать не стал: доступ к сайту клиента раздаёт владелец студии. Если понадобится, это одна строка `members.invite` в `access.ts`, записано в PLAN.
- **Вход по ссылке из письма и уведомление о входе с нового устройства** (модуль 10, «Позже») не делались.

## Исправления по проверке

Проверяющий нашёл один major и восемь minor. Исправлены все. Миграций нет: схема базы не менялась.

### Major

1. **Счётчик адресов сброса пароля рос без предела.** Лимит по адресу проверялся раньше лимита по IP: тот ставил Better Auth уже внутри `auth.handler`. Поэтому один клиент с одного IP, перебирая адреса, добавлял в `Map` запись на каждый запрос: IP-лимит отвечал 429, но адрес уже был учтён. Очистка включалась после 10 000 ключей и обходила всю `Map` на каждом запросе, а в пределах окна ничего не удаляла. Выходило O(n) на запрос и O(n²) в сумме: один клиент без входа нагружал память и процессор всего API. Что сделано:
   - **Сначала IP, потом адрес.** Обёртка `POST /api/auth/request-password-reset` сама проверяет лимит по IP (`resetLimits.byIp`, то же правило `RESET_REQUESTS_PER_IP`: 5 за 15 минут) и только потом учитывает адрес. IP определяется так же, как у Better Auth: `getIP` из `better-auth/api` с его же настройками. Если IP не найден, запрос идёт в общий счётчик, как у Better Auth. Запрос, отбитый по IP, в счётчик адресов не попадает. Правило Better Auth для `/request-password-reset` осталось как страховка.
   - **Предел памяти.** `createRateLimiter` помнит не больше `maxKeys` ключей (по умолчанию 10 000, это единицы мегабайт). Ключи лежат в `Map` в порядке последнего пропущенного запроса. Когда места нет, вытесняется самый давний ключ, как у Better Auth с его `MEMORY_STORE_MAX_ENTRIES`. Вытесненный ключ теряет свой счёт. Но чтобы вытеснить чужой живой адрес, нужно 10 000 новых адресов за 15 минут, а с одного IP пройдут только пять.
   - **Дешёвая очистка.** Благодаря порядку в `Map` очистка идёт с начала и останавливается на первом живом ключе. Каждый ключ удаляется один раз, так что в сумме это O(1) на запрос, а не обход всей таблицы. Отказ не освежает ключ: `set` существующего ключа не двигает его в `Map`.
   - Комментарий в `rate-limit.ts` и решение 3 выше поправлены.
   - Тесты. `rate-limit.test.ts`: предел ключей и вытеснение самого давнего; ключи с прошедшим окном уходят, живые остаются; 100 000 разовых ключей в одном окне дают ровно 10 000 в памяти и проходят за секунды (прежней очистке понадобились бы минуты). `password-reset.test.ts`: после исчерпания IP-лимита перебор адресов с этого IP получает 429, а у адреса из перебора все три попытки остаются целы. Текст 429 по IP — «…с вашего адреса».

### Minor

2. **Принятие приглашения перезаписывало роль.** Если между приглашением и принятием владелец выдал роль командой `pnpm member:add`, `acceptInvitation` молча её менял. Теперь существующий пользователь получает доступ через `addMemberIfAbsent` (`insert … on conflict do nothing`). Тот, кто уже участник, остаётся со своей ролью, а приглашение всё равно гасится: ссылка одноразовая. Новый пользователь (`register`) участником быть ещё не может, поэтому там `upsertMember` остался. Тест проверяет оба направления: client → editor и editor → client.
3. **Письмо приглашения обещало «задайте свой пароль» и тем, у кого вход уже есть.** Теперь письмо просит открыть ссылку и описывает оба случая: входа нет — по ссылке вы зададите имя и пароль; вход есть — войдите своим паролем и подтвердите доступ. Есть ли у адреса вход, письмо не знает, это скажет экран. Передавать такой признак в шаблон я не стал: за 7 дней он может устареть. Тест шаблона.
4. **Примеры шаблонов в предпросмотре были с `?token=`.** Теперь там `…/reset-password#token=example` и `…/invite#token=example`, как в настоящих письмах (правило CONVENTIONS). Тест: ни один пример не содержит `?token=`.
5. **Решение 11 расходилось с кодом по `--by`.** Исправлено: без `--by` приглашает единственный владелец, а если владельцев несколько, команда просит `--by`. README говорил верно, туда добавлено уточнение.
6. **Приглашения не чистились.** `invitationsRepo.cleanup(before)` удаляет закрытые приглашения: принятые — по времени принятия, отозванные — по времени отзыва, истёкшие — по сроку. Открытые не трогает. Срок — `MAIL_RETENTION_DAYS` (по умолчанию 30 дней), как у писем, и чистит их тот же обработчик очереди раз в час. Для этого у `startMailWorker` появилась опция `cleanupAlso` — что ещё чистить по тому же сроку; `index.ts` передаёт в неё приглашения. Обработчик работает и при выключенной почте, так что чистка идёт всегда. Принятые тоже удаляются: доступ уже выдан и хранится в `site_members`, а история «кто кого пригласил» старше месяца не нужна. Тесты: репозиторий (шесть приглашений в разных состояниях и разного возраста, удаляются ровно три старых закрытых) и обработчик (`cleanupAlso` получает границу «сейчас минус срок», в лог пишется, сколько удалено).
7. **У приглашений не было лимита.** У `POST /api/sites/:siteId/invitations` теперь два лимита: не больше 3 приглашений в час одному адресу на один сайт (`INVITES_PER_ADDRESS`) и не больше 50 в час от одного владельца (`INVITES_PER_INVITER`, на случай уведённой сессии). Сверх них — 429 `rate_limited` с понятным текстом. Счётчики — тот же `createRateLimiter`, свои на каждый экземпляр API. У команды `member:invite` лимита нет: её запускают на сервере, где и так есть доступ к базе. Тесты: четвёртое приглашение одному адресу — 429, на другой сайт — можно; 51-е от одного владельца — 429, у другого владельца свой счёт.
8. **`member:invite` могла молча поставить ссылку на localhost.** Теперь команда всегда печатает, на какой адрес админки ведёт ссылка: «Ссылка в письме ведёт в админку …». Сам токен не печатается. Если `ADMIN_URL` указывает на localhost, а почта идёт по SMTP, команда отказывает ещё до записи в базу: адресат такую ссылку не откроет. Если почта — файловый ящик (разработка), команда только предупреждает: запущена на сервере — задай `ADMIN_URL`, как у API, и пригласи заново, прежнее приглашение отзовётся само. Отказывать при файловом ящике нельзя: на компьютере разработчика localhost — правильный адрес. Логика вынесена в `inviteLinkNotice` (`cli/common.ts`), тесты — в `common.test.ts`.

Если не загрузились приглашения, в разделе ошибка и кнопка «Повторить». Если не загрузилась почта, в разделе пояснение, а форма продолжает работать: при выключенной почте API ответит 503, и форма это покажет. 401 по-прежнему уводит на вход через обработчик кеша. e2e в `invitations.spec.ts`: оба запроса подменены ответом 500, но заголовок сайта на месте, в разделе ошибка и рабочая кнопка «Пригласить», а после «Повторить» появляется список.

## Исправления по второй проверке

Проверяющий нашёл один blocker и один minor, исправлены оба. Миграций нет: схема базы не менялась, поменялся только формат строки в `verifications.identifier`.

### Blocker

1. **Строка из базы сама работала как ссылка сброса.** Better Auth 1.7.7 со своим хешером (`verification.storeIdentifier: { hash }`) ищет и гасит запись в два приёма: `identifiersToTry = [хеш, идентификатор как есть]` в `findVerificationValue` и `consumeVerificationValue` (`better-auth/dist/db/internal-adapter.mjs`). Это запасной путь для записей, сохранённых до включения хеширования. Наш хешер хранил `reset-password:<H>`. Если прислать `H` как токен, Better Auth соберёт `reset-password:<H>`, по хешу его не найдёт, а запасным поиском найдёт ровно эту строку. Значит, любое чтение таблицы `verifications` (бэкап, доступ к SQL на чтение) давало захват любого аккаунта: запрос сброса открыт, атакующий запускает его сам. Требование «в базе только хеш» было выполнено только на бумаге, а прежний тест проверял лишь, что в строке нет токена. Что сделано:
   - **Другой разделитель в базе.** `hashVerificationIdentifier` пишет `<имя>#<SHA-256 base64url>`, то есть `reset-password#<H>`. Двоеточия в сохранённой строке нет вовсе (в base64url его тоже нет), а все идентификаторы, которые собирает Better Auth, имеют вид `<имя>:<…>`. Запасной поиск никогда не совпадёт с тем, что лежит в базе, что бы ни прислали. `RESET_STORED_PREFIX` и `resetTokensOf` (сжигание старых ссылок, `user:password`) ищут уже по `reset-password#%`.
   - **Проверка формата токена до Better Auth.** Новая обёртка `POST /api/auth/reset-password`. Тело — строго `{ token, newPassword }`, токен — токен Better Auth: 24 латинские буквы и цифры (`ResetPasswordToken` в `@averra/schema`, на нём же построен `ResetPassword`). Иначе 400 `invalid_token` с тем же текстом, что у мёртвой ссылки, и до поиска записи запрос не доходит. В Better Auth уходит пересобранное тело и адрес без строки запроса, так что токен из `?token=` не берётся. Пароль по-прежнему проверяет Better Auth (тексты «Пароль слишком короткий» и т. д.).
   - **Варианты путей сброса мимо обёрток не проходят.** Сквозной маршрут `/api/auth/*` отвечает 404 на любой путь со словами `request-password-reset`, `reset-password` или `forget-password` (после раскодирования, без учёта регистра): `/reset-password/`, `//reset-password`, `Reset-Password`, `reset%2Dpassword` и т. п. Настоящие пути обрабатывают обёртки: они стоят раньше.
   - Записи старого формата (`reset-password:<H>`) могли остаться только в локальной базе разработки, где шаг проверяли руками. Они живут не дольше часа, и Better Auth удаляет истёкшие при каждом поиске, поэтому отдельной миграции нет.
   - Тесты. `modules/auth/password-reset.test.ts`: в базе `reset-password#<43 символа>`. Хеш из базы, вся строка из базы и `reset-password:<хеш>` в роли токена дают 400 `invalid_token` через API. Хеш и строка из базы в обход обёртки, серверным вызовом `auth.api.resetPassword`, дают `INVALID_TOKEN`. Пароль не меняется, а ссылка из письма после этого работает. Этот тест я прогнал и на прежнем хешере (с двоеточием): он падает, Better Auth меняет пароль по хешу. Ещё тесты: токен не того формата — 400; токен в строке запроса не берётся; варианты пути `reset-password` — 404, пароль цел. `auth/password-reset.test.ts`: двоеточия в сохранённой строке нет, `reset-password:<хеш>` с ней не совпадает. `@averra/schema`: `ResetPassword` принимает 24 буквы и цифры и отклоняет пустой, короткий, длинный токен, хеш и строки с `_` и `:`.
   - Решение 1, README («Сброс пароля») и CONVENTIONS теперь описывают запасной поиск Better Auth и объясняют, почему в базе `#`.

### Minor

2. **Лимит по IP считали два счётчика, и они расходились.** Правило Better Auth `customRules['/request-password-reset']` (5 за 15 минут) учитывало и запросы на кривые пути (`/request-password-reset/` и т. п.), которые до обёртки не доходили и получали 404. После них Better Auth отвечал 429 «Подождите 900 с» на запрос, который наш `resetLimits.byIp` пропустил и который уже попал в счётчик адресов. Выходило два разных текста 429, а фраза «запрос, отбитый по IP, в счётчик адресов не попадает» в этом случае была неверна. Что сделано:
   - Кривые пути до Better Auth больше не доходят (п. 1), так что его счётчик видит только запросы из обёртки, а их с одного IP не больше пяти.
   - Правило Better Auth стало запасным и вдвое выше нашего: `RESET_REQUESTS_PER_IP_BACKSTOP`, 10 за 15 минут. В нормальной работе оно не срабатывает. Убирать его совсем не стал: оно страхует на случай, если обёртку когда-нибудь обойдут.
   - Если запасное правило всё же сработает, обёртка отвечает тем же 429, что и наш лимит по IP («Слишком много запросов сброса с вашего адреса. Подождите N мин»), а не вторым форматом.
   - Тест: с одного IP по три запроса на пять кривых путей сброса (всего 15) — все 404. После этого у IP целы все пять запросов, а шестой получает 429 с нашим текстом. Формулировки в решении 3, README и CONVENTIONS уточнены.

## Мелочи после приёмки

Финальная проверка шагов 3.1–3.3: к этому шагу относятся пять замечаний уровня minor, закрыты все. Миграций нет.

1. **Тесты не держали две защиты обёртки `POST /api/auth/reset-password`** (3.2-1).
   - Проверка формата токена закреплена наблюдаемым отличием. Двенадцать запросов с токеном не того формата с одного IP получают 400 `invalid_token`, и ни одного 429. Дойди они до Better Auth, одиннадцатый упёрся бы в его лимит: 10 в минуту с IP. Мутация (проверка формата выключена) роняет этот тест, и только его.
   - Тест «токен в строке запроса не берётся» обещал больше, чем проверял: без `token` в теле запрос отбивала схема, до сброса строки запроса дело не доходило. Теперь вместо него два теста. «Тело без токена — 400 проверки» проверяет `code: 'validation'`. Второй следит за `auth.handler`: запрос с верным токеном в теле и `?token=…&callbackURL=…` в адресе меняет пароль, а в Better Auth приходит адрес без строки запроса. Мутация (без `url.search = ''`) роняет этот тест, и только его.

2. **Ветка 429 запасного лимита Better Auth** (3.2-2). Выбран вариант «вернуть адресу попытку»: при 429 от Better Auth обёртка зовёт `byEmail.refund(email)`. Тогда фраза README, CONVENTIONS и решения 3 «запрос, отбитый по IP, в счётчик адресов не попадает» верна без исключений. Оговорка в документации оставила бы исключение в коде, поэтому исправление лучше. Тест: счётчик Better Auth для IP набит десятью запросами мимо обёртки, а наш лимит по IP ещё свободен. Запрос через обёртку получает 429 с нашим текстом «…с вашего адреса. Подождите N мин», и у адреса после этого целы все три попытки. Без возврата попытки тест падает.

3. **Обоснование формата `verifications.identifier`** (3.2-3). Утверждение «идентификаторы Better Auth всегда с двоеточием» неверно: в 1.7.7 есть `delete-account-${token}` (`update-user.mjs`), и хешер хранит его как `#<хеш>`. Вывод и сама защита при этом верны. Комментарий к `hashVerificationIdentifier`, решение 1 и CONVENTIONS теперь называют настоящий инвариант. В базе на месте разделителя всегда `#`, а у каждого идентификатора, который Better Auth собирает из присланного, постоянная приставка без `#` (`reset-password:`, `delete-account-`), и сохранённая строка с неё не начинается. Добавлено предупреждение: плагин или эндпоинт, где идентификатор целиком задаёт клиент (номер телефона в `phone-number`, адрес кошелька в `siwe`), это нарушает, и перед его включением защиту надо перепроверить. Тест в `auth/password-reset.test.ts`: для `delete-account-…` и `reset-password:…` в сохранённой строке есть `#`, и она не начинается с их приставки.

4. **Обрезанная ссылка сброса называлась «устаревшей»** (3.2-4). Выбран первый вариант: экран `/reset-password` проверяет токен той же схемой `ResetPasswordToken` до формы. При неудаче он показывает её текст «Ссылка повреждена: откройте её из письма целиком» и ссылку «Запросить новую ссылку». Сообщение схемы, которое раньше нигде не показывалось, теперь работает, а запроса в API с заведомо негодным токеном нет. Убирать сообщение из схемы было бы хуже: человеку с обрезанной ссылкой честнее сказать, что ссылка повреждена. API на такой токен по-прежнему отвечает «Ссылка не действует…»: отличать «повреждена» от «устарела» на сервере незачем, человек видит экран. e2e в `password-reset.spec.ts`: по `/reset-password#token=AbCdEf123` — алерт с этим текстом и без «устарела», ссылка на новый запрос, формы нет, токен из адреса убран.

5. **Команда строже API со ссылками на localhost** (3.2-5). Выбран первый вариант — одно правило и предупреждение от API, — а не только запись в README.
   - Правило теперь в одном месте, `src/mail/link-warning.ts` (без Node API): `isLocalAdminUrl` и `localLinkWarning(adminUrl, status)`. Команда по нему отказывает, как и раньше (`inviteLinkNotice`).
   - API не отказывает, а предупреждает. При старте он пишет строку в лог, а `GET /api/mail` отдаёт `linkWarning` по нынешнему состоянию почты: SMTP могли задать в админке уже после старта. Страница «Почта» показывает предупреждение в разделе «Состояние».
   - Почему API не отказывает, как команда: в `pnpm dev` SMTP бывает настроен нарочно, чтобы проверить настоящую доставку себе, и ломать разработчику сброс пароля незачем. Команду же запускают ради одного письма, и слать ссылку на localhost по SMTP незачем. Это записано в README («Почта») и CONVENTIONS.
   - Проверка localhost (`isLoopbackHost`) переехала из `config.ts` в `src/loopback.ts`: теперь её подключают маршруты, а `config.ts` тянет Node API.
   - Тесты: `link-warning.test.ts` (localhost и его варианты; предупреждение только при SMTP, а с файловым ящиком, памятью и выключенной почтой его нет), `mail.test.ts` (`linkWarning` при SMTP из окружения и `null` с почтой в памяти). e2e: `mail.spec.ts` — предупреждение на экране по подменённому ответу и его отсутствие у файлового ящика; `smtp-settings.spec.ts` — после сохранения SMTP в админке предупреждение приходит в настоящем ответе API, а после удаления пропадает.
