# Шаг 3.3. Настройки SMTP в админке

## Цель

Сменить пароль SMTP или провайдера можно без доступа к серверу: владелец задаёт SMTP на странице «Почта». Настройки одни на всю установку и лежат в таблице `mail_settings` (модель готова к переопределению на сайт, оно появится вместе с формами). Пароль хранится в базе только зашифрованным AES-256-GCM ключом из отдельной переменной `MAIL_ENCRYPTION_KEY` и наружу не отдаётся никогда, даже зашифрованным. Менять настройки может только владелец и только с повторным вводом своего пароля. Кнопка «Проверить подключение» проходит те же шаги, что `pnpm mail:test`, по ещё не сохранённым настройкам. Если SMTP задан в окружении, главное — окружение, а админка показывает его только для чтения. Обработчик очереди берёт новые настройки без перезапуска API.

## Угроза, ради которой нужен повторный пароль

Письмо сброса пароля — ключ от любого аккаунта админки. Кто управляет SMTP, тот может получить это письмо. Сценарий без защиты:

1. У владельца уводят сессию: cookie утекла через чужой компьютер, вредоносное расширение браузера или незаблокированный ноутбук. Пароля атакующий не знает.
2. С этой сессией он открывает «Почта» и ставит SMTP своего сервера. Сертификат у сервера настоящий, например Let's Encrypt на его домен, так что проверка сертификата не мешает.
3. Он запрашивает «Забыли пароль?» для владельца или любого участника. Письмо со ссылкой уходит через его сервер. Атакующий задаёт новый пароль и получает постоянный доступ, который переживёт отзыв украденной сессии.

Ещё один путь без защиты — увести сам пароль SMTP. Проверка подключения с сохранённым паролем, направленная на чужой сервер, отдала бы ему пароль в `AUTH`.

Третий путь — подобрать пароль владельца через ту же сессию. Better Auth по умолчанию открывает по HTTP `POST /api/auth/verify-password`. Пометка `scope: 'server'` доступа не закрывает: router `better-call` закрывает только `SERVER_ONLY`. Лимит у этого пути — общий лимит Better Auth, 100 запросов за 10 секунд с IP. `POST /api/auth/change-password` тоже проверяет текущий пароль, с правилом Better Auth 3 запроса за 10 секунд с IP. Счётчик повторного пароля этих попыток не видел. Проверяющий подтвердил это на живом API: 30 неверных паролей подряд через `verify-password` не дали ни одного 429, а найденный пароль открыл `DELETE /api/mail/smtp`. См. «Исправления по проверке», п. 1.

Ещё один путь — разослать письма через ящик студии. «Проверить подключение» пароля владельца не просит. С сохранённым паролем SMTP она отправила бы проверочное письмо с логином, адресом и именем отправителя из запроса на любой адрес, и у такого письма проходят SPF и DKIM.

Что закрывает шаг:
- сохранить и удалить настройки можно только с паролем владельца, его проверяет Better Auth (`verifyPassword` серверным вызовом). Неудачных попыток не больше 5 за 15 минут на пользователя. Счётчик общий у всех путей, которыми вошедший проверяет свой пароль по HTTP: повторный пароль у настроек почты и смена пароля. `verify-password` Better Auth по HTTP закрыт. Через уведённую сессию пароль не подобрать быстрее, чем без неё: остаётся вход, а у него свой лимит (3 попытки за 10 секунд с IP, шаг 2.2);
- сохранённый пароль SMTP уходит только на сохранённый сервер. Если в проверке или при сохранении сменили сервер, пароль SMTP нужно ввести заново. В проверке подключения сохранённый пароль работает только с сохранёнными настройками целиком и только на почту самого владельца;
- изменение пишется в лог (кто, когда, какие поля) и уходит письмом всем владельцам.

Чего шаг не закрывает. Слабый пароль владельца подбирают входом, с уведённой сессией или без неё. Против этого работают лимит входа по IP и длина пароля (от 10 символов). Счётчик неудач входа на аккаунт закрыл бы и перебор с многих адресов. Но тогда любой, кто знает почту владельца, мог бы запирать ему вход. Решать это стоит вместе с 2FA (модуль 1, «Потом»).

Письмо идёт уже через новые настройки, поэтому против атакующего, который знает пароль владельца и поставил свой сервер, оно не защищает. Такой атакующий может письмо просто не доставить. Защита здесь — сам пароль. Письмо нужно для честного владельца: «это вы поменяли почту?».

## Решения и почему

1. **Таблица `mail_settings`** (миграция `0009_mail_settings`). В ней `id`, `site_id` (`NULL` значит вся установка), `host`, `port`, `security`, `username`, `password_encrypted`, `from_address`, `from_name`, `verified_at` (когда для этих настроек прошла проверка подключения, `NULL` — сохранено без проверки), `updated_by`, `created_at`, `updated_at`.
   - Уникальность `site_id` с `NULLS NOT DISTINCT`: строка на всю установку одна, потом будет не больше одной на сайт. Сейчас код читает и пишет только строку `site_id IS NULL`. Переопределение на сайт добавит строки, а не новую таблицу.
   - CHECK `(port, security)` — только `(465, tls)` или `(587, starttls)`.
   - CHECK формата `password_encrypted` (`v1.<версия ключа>.<iv>.<tag>.<шифротекст>`). Открытый пароль база не примет даже по ошибке в коде.
2. **Шифрование — AES-256-GCM на `node:crypto`** (сверено с документацией Node 24, `crypto.createCipheriv`).
   - Интерфейс `SecretBox` лежит в `src/crypto/secret-box.ts` без Node API: его видят маршруты, а их типы читает админка. Реализация `aesGcmSecretBox(key)` в `src/crypto/aes-gcm.ts`, её подключают `index.ts` и `testing.ts`.
   - IV — 12 случайных байт на каждое шифрование. Тег 16 байт, и длина задана явно (`authTagLength: 16`), иначе Node принял бы укороченный тег.
   - Контекст (AAD) — `mail_settings.password:installation`. Шифротекст, переставленный в другое поле или к другому сайту, не расшифруется.
   - В записи хранится версия ключа: первые 8 байт HMAC-SHA256(ключ, «averra-cms/mail-encryption-key-id») в hex. При будущей ротации по ней выбирают ключ из связки. Уже сейчас она отличает случай «ключ не тот» (`wrong_key`) от повреждённой записи (`corrupted`).
   - Ошибки расшифровки не падают наружу, а становятся состоянием «пароль не читается».
3. **`MAIL_ENCRYPTION_KEY`** — 32 случайных байта в base64, проверка в `config.ts`. Из `AUTH_SECRET` ключ не выводится: утечка одного не должна давать другого, а сменить секрет cookie можно и без потери пароля SMTP.
   - Ошибка конфига значение ключа не печатает. Подсказка, как сгенерировать: `openssl rand -base64 32` или однострочник на `node:crypto`.
   - В учебном режиме (`--dev` на localhost) без своего ключа берётся учебный `DEV_MAIL_ENCRYPTION_KEY`. Правила те же, что у учебного `AUTH_SECRET`: только учебный режим, в проде и вне учебного режима — ошибка конфига. Его варианты распознаёт `isDevMailKey`: пробелы, кавычки, регистр, url-safe base64, без `=`, часть строки, тот же текст в другой записи base64.
   - Нет ключа вне учебного режима — API работает. Настройки SMTP в админке тогда только для чтения, с объяснением, как сгенерировать ключ.
   - Ключ не тот — почта выключена с причиной «введите пароль SMTP заново», API не падает.
4. **Приоритет: окружение → база → по умолчанию.** Окружение решает само, если задан `SMTP_HOST` или явный `MAIL_TRANSPORT` (`smtp`, `file` или `off`).
   - Тогда настройки из базы не действуют, а админка показывает SMTP из окружения только для чтения, без пароля, с пометкой «задано на сервере».
   - Иначе берутся настройки из базы. Нет и их — как раньше: в учебном режиме файловый ящик, иначе почта выключена, и причина теперь называет и страницу «Почта».
   - `config.mail.fromEnv` говорит, решило ли окружение.
5. **Почта процесса — `MailRuntime`** (`src/mail/runtime.ts`, без Node API; фабрики SMTP приходят параметром). Он держит нынешнего провайдера и состояние. `reload()` перечитывает базу и пересобирает провайдера: расшифровывает пароль и создаёт `smtpMailer`.
   - Маршруты получают состояние функцией `mail.status()`, а не значением: сброс пароля, приглашения и `GET /api/mail` видят новые настройки сразу.
   - Обработчик очереди берёт провайдера перед каждым письмом (`mailer()` — функция у `processOutbox` и `startMailWorker`).
   - Смена настроек идёт внутри `exclusive()`: транзакция (настройки и письма владельцам), потом `reload()`. `mailer()` ждёт конца этой секции. Поэтому письмо «Настройки почты изменены», взятое обработчиком после коммита, уходит уже через новые настройки. Если провайдер сменился, пауза после сбоя сервера сбрасывается.
6. **Пароль только на запись.** Репозиторий отдаёт наружу view без `password_encrypted`. Пароль в нём — состояние `set` или `unreadable`.
   - Ответы API, логи и тексты ошибок пароля не содержат: ошибки SMTP проходят `maskSecrets`, а в лог идут только названия полей.
   - Пустое поле пароля при сохранении значит «оставить прежний». Это работает, только если прежний пароль читается и сервер не сменили. Иначе — 400 у поля `password`.
7. **Повторный пароль — `passwords.confirm`** (`src/auth/confirm-password.ts`): `auth.api.verifyPassword` с cookie запроса.
   - Неудачных попыток не больше 5 за 15 минут на пользователя (`createRateLimiter`), удачная попытка счёт не тратит: у лимитера появляется `refund`.
   - Счётчик один на все пути, которыми вошедший проверяет свой пароль по HTTP. Его создаёт `createApp` и отдаёт и почте, и обёртке смены пароля. `verify-password` Better Auth по HTTP закрыт (исправления по проверке, п. 1).
   - Неверный пароль — 403 `invalid_password` с путём `currentPassword`, не 401: 401 в админке уводит на вход. Лимит — 429.
8. **Схема настроек строгая и общая** (`@averra/schema`, `mail-settings.ts`): `MailSettingsFields`, `CheckMailSettings`, `SaveMailSettings`, `DeleteMailSettings`, `smtpModes`.
   - `z.strictObject`: лишнее поле (`rejectUnauthorized`, `tls`, `ignoreTLS`…) — 400. Скрытого параметра, который снял бы проверку сертификата, нет, и в TLS-параметрах nodemailer по-прежнему явный `rejectUnauthorized: true`.
   - Хост — имя или IPv4 (`z.hostname()`), без схемы, порта и пути. Приводится к нижнему регистру, точка в конце убирается.
   - Порт — только 465 или 587, вместе с режимом: `(465, tls)` или `(587, starttls)`.
   - Переводы строк и управляющие символы запрещены в хосте, логине (`singleLine`), адресе (`MailAddress`) и имени отправителя (`MailSenderName`). В пароле SMTP — тоже: перевод строки в конце пароля почти всегда ошибка копирования.
9. **«Проверить подключение»** — `POST /api/mail/smtp/check`: те же шаги, что у `pnpm mail:test` (`diagnoseSmtp`: DNS, соединение, TLS, вход, отправка проверочного письма на указанный адрес), по присланным, ещё не сохранённым настройкам.
   - Порт только 465 или 587 (схема), не больше 10 проверок за 15 минут на владельца (429). Сканером портов сервер не станет.
   - Тайм-ауты короче, чем у команды: человек ждёт ответа на экране.
   - Подсказки в сообщениях называют поля формы, а не переменные окружения (`origin: 'admin'` у `smtpMailer` и `diagnoseSmtp`).
   - Пароля владельца проверка не требует: она ничего не меняет. Поэтому сохранённый пароль SMTP в ней работает только с сохранёнными настройками целиком и только на почту самого владельца (`checkPasswordOf`). Тогда проверочное письмо — фиксированный текст от сохранённого отправителя (исправления по проверке, п. 2).
   - Успешная проверка возвращает `checkToken`: HMAC (Web Crypto, ключ процесса) от владельца, времени и отпечатка настроек вместе с паролем. Живёт 15 минут.
10. **Сохранение** — `PUT /api/mail/smtp`.
    - Нужен `checkToken` успешной проверки ровно этих настроек этим владельцем или явный `skipCheck: true` («Сохранить без проверки»). Нет ни того ни другого — 400. Токен от других настроек или устаревший — 409 `check_stale`.
    - `verified_at` пишется только по токену.
    - Ответ: view, список изменённых полей и сколько владельцев получили письмо.
11. **Удаление** — `DELETE /api/mail/smtp` с паролем владельца. Почта возвращается к окружению или к варианту по умолчанию. Нужно и для переезда настроек в окружение, и e2e: тест возвращает почту в файловый ящик.
12. **Лог и письмо.** После сохранения или удаления в лог API идёт строка: время, кто (имя, почта, id), какие поля (сервер, порт и шифрование, логин, пароль, адрес и имя отправителя), была ли проверка. Значений полей и пароля в ней нет.
    - Новый шаблон `mail-settings-changed` («Настройки почты изменены») ставится в очередь каждому владельцу той же транзакцией, что и запись настроек. Уходит он уже по новым настройкам (решение 5).
    - Если ничего не поменялось, письма нет. Если после удаления почта выключена, письма тоже нет: отправить нечем, а в очередь при выключенной почте не ставим (правило шага 3.2).
13. **Где правят настройки.** Править можно, только если окружение не решило (решение 4) и есть ключ. Иначе `check`, `PUT` и `DELETE` отвечают 409 `mail_settings_locked` с объяснением.
    - Права: только владелец (`requireOwner`, как вся почта). Участник и токен — 403, без входа — 401.
14. **Админка.** На экране «Почта» новый раздел «Настройки SMTP».
    - Окружение или нет ключа — данные только для чтения и объяснение.
    - Иначе форма: сервер, «Порт и шифрование» (465 — TLS сразу или 587 — STARTTLS), логин, пароль SMTP («задан, оставьте пустым, чтобы не менять», «не задан» или «не читается — введите заново»), адрес и имя отправителя.
    - Проверка: адрес для проверочного письма (по умолчанию почта владельца), «Проверить подключение» и список шагов ✓/✗.
    - Сохранение: «Ваш пароль от админки», «Сохранить» (если проверка не прошла или настройки после неё поменяли, кнопка объясняет, что сначала нужна проверка) и «Сохранить без проверки» с подтверждением. «Удалить настройки» — с паролем и подтверждением.
    - После сохранения поля паролей очищаются, а состояние почты и очередь перезагружаются.
    - Учебный ключ (`pnpm dev`) отмечен на экране: настоящий пароль от почты здесь не вводить.
15. **Тесты против настоящего SMTP.**
    - В тестах API — тестовый сервер шага 3.1 на свободном порту. Настройки и схема пускают только 465 и 587, поэтому `SmtpOptions.connectPort` (только код, как `ca`) направляет подключение тестового рантайма на его порт. Из API и окружения его не задать.
    - В e2e API — отдельный процесс. Тестовый сервер слушает свой порт `127.0.0.1:2587`, а API e2e подключается к нему через `DEV_SMTP_CONNECT_PORT`, только в учебном режиме (исправления по проверке, п. 5). Его CA создаёт `e2e/scripts/smtp-certs.ts` перед стартом API, и API e2e доверяет ему через стандартный `NODE_EXTRA_CA_CERTS`. Это добавляет корневой сертификат, а не снимает проверку.
16. **Команды.** `pnpm member:invite` учитывает SMTP из базы: при нём не отказывает «почта не настроена», а ссылку на localhost не ставит. `pnpm mail:test` по-прежнему проверяет только окружение (базу она не открывает, чтобы работать при запущенном API). Если окружение не решило, она говорит, что SMTP из админки проверяется кнопкой на странице «Почта».

## Критерии готовности

1. Шифрование: туда-обратно сходится. Каждое шифрование — свой IV. Другой ключ, подменённые шифротекст, тег или IV, укороченный тег, другой контекст — ошибка, а не мусор.
2. В `mail_settings.password_encrypted` нет пароля в открытом виде. Открытый пароль база не принимает (CHECK).
3. Ни один ответ маршрутов почты (`GET /api/mail`, `/smtp`, `/smtp/check`, `PUT` и `DELETE /smtp`, очередь, повтор, предпросмотр) не содержит пароля SMTP, его base64 и зашифрованной строки из базы. Лог тоже.
4. Без пароля владельца сохранить и удалить нельзя (400), с неверным — 403 `invalid_password`, база не меняется. Шестая неудачная попытка за 15 минут — 429, даже с верным паролем. Неудачи при смене пароля идут в тот же счёт, а `POST /api/auth/verify-password` отвечает 404 (добавлено после проверки).
5. Не владелец: редактор, клиент и токен — 403, без входа — 401. Это касается всех четырёх маршрутов SMTP.
6. Сохранить можно только с `checkToken` успешной проверки этих же настроек или с `skipCheck: true`. Без них — 400, с токеном от других настроек — 409.
7. Порт не 465 и не 587, пара порт и режим не та, лишнее поле, перевод строки или управляющий символ в хосте, логине, адресе или имени отправителя — 400, и соединения с сервером нет.
8. Проверка против тестового SMTP-сервера: успех (все пять шагов, сервер получил проверочное письмо); неверный пароль (сломан вход, пароля в ответе нет); недоверенный сертификат (сломан TLS). Одиннадцатая проверка за 15 минут — 429. С сохранённым паролем — только сохранённые настройки и своя почта, иначе 400 без подключения (добавлено после проверки).
9. Пустой пароль оставляет прежний. При смене сервера или нечитаемом прежнем пароле — 400 у поля `password`.
10. SMTP в окружении главнее базы: view `source: 'env'` без пароля, правка — 409, провайдер — из окружения, даже если в базе есть строка.
11. Нет ключа — правка недоступна (409), view объясняет, как сгенерировать ключ. Ключ не тот — почта выключена с причиной «введите пароль SMTP заново», API отвечает, новое сохранение с паролем чинит почту.
12. Смену настроек подхватывает обработчик очереди без перезапуска: письмо после смены уходит на новый сервер. Письмо «Настройки почты изменены» уходит каждому владельцу через новые настройки.
13. Конфиг: ключ — 32 байта base64. Короткий, длинный и не base64 — ошибка без значения в тексте. Учебный ключ и его варианты — только в учебном режиме. В учебном режиме без ключа берётся учебный, в проде без ключа API стартует, но правка закрыта.
14. e2e: владелец вводит настройки тестового SMTP-сервера, проверяет подключение, сохраняет с паролем, обновляет страницу. Пароль «задан», в DOM и в ответах API его нет. Письмо об изменении пришло на тестовый сервер, после теста настройки удалены.
15. `pnpm format` чистый, `pnpm check` и `pnpm e2e` зелёные.

## Итог

Сделано по плану. SMTP задаётся на странице «Почта», в разделе «Настройки SMTP». Настройки лежат в таблице `mail_settings` (миграция `0009_mail_settings`), одна строка на установку (`site_id IS NULL`, уникальность с `NULLS NOT DISTINCT`). Строки сайтов добавятся без новой таблицы.

Как это устроено:
- **Пароль.** Хранится только как запись AES-256-GCM: `v1.<версия ключа>.<iv>.<тег>.<шифротекст>`, со случайным IV, тегом явной длины 16 байт и контекстом в AAD. Формат держит CHECK в базе. Ключ — отдельная переменная `MAIL_ENCRYPTION_KEY`. Учебный ключ работает по правилам учебного секрета, и его варианты распознаёт `isDevMailKey`. Без ключа правка закрыта с объяснением, как его сгенерировать. С чужим ключом почта выключена с причиной «введите пароль SMTP заново», а новое сохранение с паролем её чинит.
- **Только на запись.** Пароль наружу не выходит: в ответах API есть только `set` или `unreadable`, в логе — названия полей. Пустое поле оставляет прежний пароль, но только для того же сервера.
- **Кто может менять.** Только владелец, с паролем, который проверяет Better Auth (`verifyPassword`). Неудачных попыток — не больше 5 за 15 минут, удачные не считаются. После проверки счётчик стал общим со сменой пароля, а `verify-password` Better Auth по HTTP закрыт: в первой версии лимит обходился (исправления по проверке, п. 1).
- **Проверка подключения.** Шаги те же, что у `pnpm mail:test`, а подсказки называют поля формы. Разрешены только порты 465 и 587, не больше 10 проверок за 15 минут. Сохранённый пароль SMTP в ней — только с сохранёнными настройками и на почту владельца (исправления по проверке, п. 2). Сохранить можно только с итогом проверки ровно этих настроек (HMAC, 15 минут) или явно «без проверки».
- **Источник настроек.** Порядок: окружение (`SMTP_HOST` или явный `MAIL_TRANSPORT`), потом админка, потом вариант по умолчанию. Если правит окружение, админка показывает настройки только для чтения, с пометкой «задано на сервере».
- **Новые настройки без перезапуска.** Их держит `MailRuntime`: маршруты спрашивают `status()`, обработчик очереди берёт провайдера перед каждым письмом. Смена идёт внутри `exclusive`, поэтому письмо «Настройки почты изменены» каждому владельцу уходит уже по новым настройкам.
- **Лог.** После смены в лог API пишется строка: время, кто, какие поля и была ли проверка.

Проверки:
- `pnpm format`: изменений нет.
- `pnpm check`: зелёный. schema — 117 тестов (было 100), tokens — 2, blocks — 11, api — 484 (было 411), admin — 91 (было 86), mcp — 8.
- `pnpm e2e` и `pnpm e2e --shuffle`: оба зелёные, по 56 тестов (было 55). Новый тест — `smtp-settings.spec.ts`. В перемешанном прогоне он шёл раньше `mail.spec.ts`, и тот всё равно увидел «SMTP не задан»: тест убирает за собой.

### Отклонения от плана и добавки

1. **Сертификаты тестового SMTP — отдельным модулем** `src/mail/testing/certs.ts`. `smtp.ts` их реэкспортирует, в `package.json` API появились экспорты `./testing/certs` и `./testing/smtp`. Скрипт e2e `scripts/smtp-certs.ts` берёт сертификаты оттуда, поэтому новых зависимостей у e2e нет. Вынести пришлось по такой причине. Импорт `smtp-server` при загрузке трогает хранилище корневых сертификатов Node, и процесс, запущенный с `NODE_EXTRA_CA_CERTS` до появления файла, писал в лог «Ignoring extra certs». Теперь скрипт сертификатов TLS не трогает, и предупреждения нет. Сам API читает файл, когда тот уже лежит на месте.
2. **Тесты, зависевшие от порядка.** `--sequence.shuffle` нашёл две такие старые зависимости, и я их исправил. В `media/disk-storage.test.ts` «корень не создаётся» теперь проверяется на своей папке. В `auth/auth.test.ts` у теста про чужой Origin свой адрес страницы. Третья — `modules/sites/routes.test.ts`: этот файл — сценарий из тестов, идущих по очереди (сохранить → опубликовать). Его я не трогал, он вне шага. В обычном прогоне он зелёный.
3. **`hookTimeout: 30_000` в `vitest.config.ts` API.** Под параллельной нагрузкой `beforeAll` в `outbox.test.ts` (база и миграции) один раз не уложился в 10 секунд по умолчанию. Один этот файл проходит за 3 секунды.
4. **В строке лога имя — одной строкой** (`toMailLine`). Имя, заведённое до схемы `UserName`, могло содержать перевод строки и подделать следующую запись лога.
5. **`pnpm member:invite` видит SMTP из админки** (`queuedMailTransport` в `cli/common.ts`). При таком SMTP команда не отказывает с «почта не настроена» и не ставит ссылку на localhost.
6. **Шаблон «Проверка почты» знает, кто его отправил** (`via`: команда или кнопка в админке). По умолчанию — команда, поэтому старые данные проходят схему.
7. **«Удалить настройки» проверяет и e2e.** Тест удаляет настройки кнопкой на экране с подтверждением, а в `finally` для надёжности ещё раз удаляет через API (ответ 404, если уже удалены).

### Что не проверено тестами напрямую и что осталось

- **Несколько процессов API на одной базе.** Каждый процесс перечитывает настройки сам: после сохранения — тот, что сохранял, и все — при старте. Второй процесс подхватит новые настройки только после перезапуска. Это как с лимитами в памяти: пока API один (PGlite), этого хватает. Для нескольких процессов нужен опрос `updated_at` в обработчике очереди.
- **Ротация ключа.** Версия ключа в записи уже есть: отпечаток, по нему видно «ключ не тот». Связки ключей (`MAIL_ENCRYPTION_KEY_PREVIOUS` и перешифрование при сохранении) пока нет. Сейчас ключ меняют так: новый ключ, потом пароль SMTP заново на странице «Почта».
- **«Сохранить без проверки» в e2e не нажимается.** Путь `skipCheck` проверяют тесты API, а подтверждение в браузере устроено так же, как у «Удалить настройки», которое e2e проходит.
- **Защита письмом.** Письмо «Настройки почты изменены» идёт по новым настройкам. Атакующий, который знает пароль владельца и поставил свой сервер, может его не доставить. От этого защищает сам пароль владельца, а письмо — для честного владельца (раздел «Угроза»).
- **Экран, когда SMTP задан в окружении или нет ключа,** проверен тестами API (view и 409). Вживую его посмотрел проверяющий, а экраны «нет ключа» и «ключ не тот» — ещё и я после исправлений (п. 6 ниже).

## Исправления по проверке

Проверяющий нашёл один major и шесть minor. Исправлены все. Миграций и новых зависимостей нет: схема базы не менялась.

### Major

1. **Лимит повторного пароля обходился через эндпоинты Better Auth.** Better Auth 1.7.7 открывает по HTTP `POST /api/auth/verify-password` («проверить пароль вошедшего»). Пометка `scope: 'server'` у него доступа не закрывает: router `better-call` не пускает по HTTP только эндпоинты с `SERVER_ONLY`. Это сверено с кодом установленной версии (`better-auth/dist/api/routes/password.mjs`, `better-call/dist/router.mjs`). Лимит у этого пути — общий лимит Better Auth, 100 запросов за 10 секунд с IP. `POST /api/auth/change-password` проверяет текущий пароль с правилом 3 за 10 секунд с IP. Наш счётчик (5 неудач за 15 минут) ни того, ни другого не видел, так что фраза «одной уведённой сессии этого мало» была неверна. Что сделано:
   - **`verify-password` закрыт.** Он записан в `disabledPaths` Better Auth (`CLOSED_AUTH_PATHS` в `auth/auth.ts`, по документации — «Disable specific auth paths»). Ответ 404 даже в обход наших маршрутов, прямо в `auth.handler`. Серверный вызов `auth.api.verifyPassword`, которым пароль проверяет `confirm`, работает: `disabledPaths` действует только на HTTP-запросы. Better Auth сверяет `disabledPaths` буква в букву, поэтому сквозной маршрут `/api/auth/*` сам отвечает 404 на этот путь в любом написании (`/verify-password/`, `Verify-Password`, `verify%2Dpassword`…). Так уже было сделано для вариантов путей сброса.
   - **Один счётчик неудач на все пути проверки своего пароля.** `createPasswordConfirmation` теперь создаёт `createApp` и отдаёт и почте, и `authRoutes`. У счётчика два метода: `confirm` (повторный пароль, как было) и `attempt(userId, check)` — одна попытка под счётчиком, когда пароль проверяет кто-то другой. Попытка учитывается до проверки. Её возвращают, если пароль не оказался неверным: попытка удачная или до пароля не дошла (кривой новый пароль, лимит Better Auth, сбой).
   - **Обёртка `POST /api/auth/change-password`.**
     - Тело строгое: `{ currentPassword, newPassword }`, новый пароль — по `NewPassword`, как везде.
     - Origin — только админка. Better Auth проверяет его и сам, но уже внутри попытки, а в тестах (`isTest`) не проверяет вовсе.
     - Сессию берём через `getSession` без продления, дальше — `passwords.attempt`: пароль меняет Better Auth, а неудачей считается только его `INVALID_PASSWORD`. Неверный пароль отвечает так же, как у почты: 403 `invalid_password` у поля `currentPassword`.
     - Остальные входы пользователя завершаются всегда (`revokeOtherSessions: true` ставит обёртка), как после сброса пароля. Этот вход получает новую cookie.
     - Ответ — `{ status: "changed", message }`. Better Auth отдал бы токен новой сессии и в теле, а ему место только в httpOnly-cookie.
     - Варианты пути — 404.
   - **Остальные пути к паролю.** Эндпоинты Better Auth, которые проверяют пароль, я нашёл по коду (`password.verify`, `validatePassword`). Это вход, смена пароля, `verify-password` и `delete-user`. Удаление пользователя выключено (`user.deleteUser` не задан) и отвечает 404 раньше, чем смотрит на пароль. Плагинов с паролем (2FA, username, phone-number) у нас нет.
   - **Вход** остаётся отдельным путём со своим лимитом по IP (3 за 10 секунд, шаг 2.2). Через уведённую сессию пароль больше не подобрать быстрее, чем без неё. Счётчик неудач на аккаунт у входа остановил бы и перебор с многих адресов, но позволил бы любому запирать владельцу вход. Это записано в «Угрозе» и в «Что осталось» ниже.
   - Раздел «Угроза», решение 7, критерий 4, README («SMTP в админке», API), CONVENTIONS («Доступ») и PLAN (модуль 10, «Безопасность») теперь описывают это как есть.
   - **Тесты** — новый `modules/auth/password-confirm.test.ts`:
     - `verify-password` — 404 с верным и неверным паролем во всех написаниях пути и прямо в `auth.handler`, а серверный вызов работает;
     - `delete-user` — 404 и с верным паролем, аккаунт цел;
     - неверный текущий пароль при смене — 403 у поля, пароль прежний;
     - удачная смена — новый пароль работает, старый нет, остальные сессии мертвы, у этого входа новая cookie, токена в теле нет, счёт неудач не потрачен;
     - пять неудач при смене пароля закрывают повторный пароль у почты, и наоборот; вперемешку — тоже пять на двоих; у другого пользователя свой счёт;
     - кривые пути, чужой Origin, запрос без входа, лишнее поле и короткий новый пароль до проверки пароля не доходят и счёт не тратят.
   - **Мутации.** Без `CLOSED_AUTH_PATHS` падают тесты `verify-password`. Без обёртки смены пароля падают четыре теста смены пароля. С отдельным счётчиком у почты падает тест общего счёта.
   - **Вживую** (API на порту 4171, база в scratchpad). `verify-password` в четырёх написаниях, с верным и неверным паролем — 404. Три неудачи смены пароля с разных IP (`TRUST_PROXY=true`) и две у почты — дальше 429 и там, и там, а вход при этом работает. С одного IP четвёртую попытку смены пароля раньше останавливает правило Better Auth (3 за 10 секунд), и такие 429 в наш счёт не идут.

### Minor

2. **«Проверить подключение» могла рассылать письма через ящик студии.** Проверка не просит пароль владельца, а сохранённый пароль SMTP в ней работал с логином, адресом и именем отправителя из запроса и на любой адрес `to`. Это до 10 писем за 15 минут на владельца с SPF и DKIM студии, и имя отправителя выбирал атакующий. Утверждение плана «письмо фиксированное» было неверным. Что сделано:
   - `checkPasswordOf` (`modules/mail/smtp-service.ts`). Пустой пароль в проверке работает только с сохранёнными настройками целиком: сервер, порт и шифрование, логин, адрес и имя отправителя. Иначе 400 у поля `password`: «Вы поменяли: … — введите пароль SMTP или сохраните без проверки».
   - Письмо с сохранённым паролем уходит только на почту самого владельца, иначе 400 у поля `to`. Обе проверки идут до подключения и до лимита проверок.
   - Сохранение с пустым паролем SMTP по-прежнему работает при смене любых полей, кроме сервера: там нужен пароль владельца.
   - В админке под «Куда отправить проверочное письмо» — подсказка, когда пароль сохранён и читается, а поле пароля пустое. Подсказка у поля пароля говорит, когда его вводить заново.
   - **Тест** в `smtp.test.ts`. Изменение каждого поля и чужой адрес дают 400 с текстом, а сервер не получил ни одного входа и письма. Своя почта в другом регистре — проверка идёт. С введённым паролем проходят любые поля и адрес. Сохранение с изменённым именем без пароля SMTP — 200. Мутация «без новых правил» роняет тест.
   - **e2e.** После обновления страницы проверка с сохранённым паролем на свою почту проходит, а на чужой адрес даёт ошибку у поля, и письма нет.

3. **Порядок «коммит → пересборка провайдера» в маршруте не был прикрыт тестом.** Новый тест в `smtp.test.ts` оборачивает `db.transaction`: сразу после коммита транзакции смены настроек обработчик спрашивает провайдера (`mailRuntime.mailer()`), ещё до пересборки.
   - Сохранение: ответ — уже новый SMTP 587, а не прежняя почта по умолчанию, и письмо о смене уходит через него.
   - Удаление: ответ — почта по умолчанию, а не прежний SMTP, и письмо об удалении уходит через неё.
   - Мутация из замечания (`saveSmtp` и `removeSmtp` без `runtime.exclusive`: транзакция, потом `reload()`) роняет этот тест, и только его. Без `exclusive` только у удаления — тоже.

4. **Ошибка базы печатала в лог параметры запроса.** `app.onError` писал `console.error(err)`. У `DrizzleQueryError` в тексте и стеке — `params: …`, а у причины из Postgres в `detail` — строка целиком.
   - Новый `src/log-error.ts`. Если в ошибке или в цепочке её причин есть ошибка запроса к базе, `errorForLog` пишет запрос с плейсхолдерами, сообщение и код ошибки базы и места в коде, без параметров и `detail`. Остальные ошибки идут как есть. `app.onError` пишет через него.
   - Тот же путь нашёлся у Better Auth. Сбой `sendResetPassword` (письмо сброса не легло в очередь) он ловит и пишет в лог вместе с ошибкой. В параметрах этой ошибки — данные письма с рабочей ссылкой сброса и её токеном. Я проверил на мутации, что без обработки ссылка `…/reset-password#token=…` в лог попадает.
   - Теперь у Better Auth свой `logger.log`: строка того же вида, что у его логгера по умолчанию. Текст идёт без параметров (`withoutQueryParams`), объекты — через `errorForLog`.
   - **Тесты.** `log-error.test.ts`: до обработки секрет в выводе есть, после — нет; ошибка базы глубже в цепочке причин; прочие ошибки — как есть. `smtp.test.ts`: запись в `mail_settings` падает в самой базе (CHECK, который не пропускает ни одной строки), ответ 500. В выводе консоли есть запрос, причина и места в коде, но нет ни зашифрованного пароля (`v1.<версия ключа>.`), ни `params:`, ни `Failing row`, ни логина и пароля SMTP. `auth.test.ts`: то же для письма сброса в логе Better Auth — нет `#token=`, `params:` и адреса.
   - Мутации (ошибка печатается как есть в `onError` или в логгере Better Auth) роняют эти тесты. Правило записано в CONVENTIONS («API»).

5. **e2e требовал порт 587.** На Linux порт ниже 1024 без root не занять, так что `pnpm e2e` упал бы там с EACCES.
   - Новая переменная `DEV_SMTP_CONNECT_PORT` (`config.ts`): в учебном режиме SMTP из админки подключается к этому порту того же сервера вместо 465 и 587. Вне учебного режима это ошибка конфига, в проде тоже. `index.ts` передаёт её в `adminSmtp` как `connectPort` и пишет о ней строку при старте, если окружение почту не решало.
   - e2e: тестовый сервер слушает `127.0.0.1:2587` (`smtpTest.port`), API e2e получает `DEV_SMTP_CONNECT_PORT`. В форме по-прежнему 587.
   - README (переменные, e2e, таблица портов), `.env.example` и CONVENTIONS (почта, тесты) обновлены.
   - Тесты `config.test.ts`: порт в учебном режиме; ошибка в проде, вне localhost и без флага; кривые значения. Вживую: API без `--dev` с этой переменной не стартует и объясняет почему.

6. **Тексты админки и строки при старте.**
   - Без ключа и с сохранённой строкой в базе экран говорил «Пароль: не читается — введите заново», хотя формы нет. Теперь — «задан, но без ключа MAIL_ENCRYPTION_KEY его не расшифровать».
   - Подсказка у поля пароля строится по причине из API. View отдаёт `passwordProblem` (`no_key`, `wrong_key`, `corrupted`, `format` или `null`), а `readPassword` у `MailRuntime` возвращает причину вместе с текстом. «Сменился ключ шифрования» — только при `wrong_key`, а повреждённая запись и запись не того формата называются как есть.
   - Предупреждение об учебном ключе API печатает при старте, только если окружение почту не решало: иначе SMTP из админки не действует и ключ ему не нужен.
   - Причина выключенной почты печаталась дважды: `MailRuntime` писал её при пересборке, а `index.ts` — при старте. Теперь её пишет только `index.ts`, а у `createMailRuntime` больше нет параметра `log`.
   - **Тесты:** `smtp-format.test.ts` (подсказка по каждой причине; без ключа — не «введите заново»), `runtime.test.ts` (`problem` у `no_key`, `wrong_key`, `corrupted`), `smtp.test.ts` (`passwordProblem` в view).
   - **Вживую** (админка на 5299): экран без ключа и экран с чужим ключом, с подсказками под паролем и под адресом проверки. Строки при старте API проверены с учебным ключом, со своим ключом и с SMTP в окружении. Причина выключенной почты теперь печатается один раз.

7. **«Сохранить» могло молча стать «без проверки».** Мутация сохранения теперь явно получает `SaveProof`: `{ checkToken }` или `{ skipCheck: true }`. Решает `proofFor` ещё до мутации. «Сохранить» без свежего итога проверки показывает ошибку и ничего не отправляет: подставлять «без проверки» не из чего. Правило записано в CONVENTIONS («Админка»).

### Что осталось

- **Лимит входа — по IP, а не по аккаунту.** Перебор пароля с многих адресов он не остановит. Счётчик на аккаунт дал бы любому способ запирать владельцу вход. Решать вместе с 2FA (модуль 1, «Потом»).
- **Токен сессии в теле ответа входа.** Better Auth отдаёт его в теле ответа `sign-in/email` для клиентов без cookie. Админка его не читает, а cookie остаётся httpOnly. В обёртке смены пароля токена в теле уже нет. Для входа это стоит решить вместе с обёрткой входа, если она понадобится (например, для лимита на аккаунт).
