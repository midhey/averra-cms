# Шаг 3.4. Формы и заявки

## Цель

На лендинге есть форма заявки, и она работает на статическом сайте без JavaScript. Посетитель заполняет поля, ставит согласие на обработку персональных данных и жмёт кнопку. Обычная HTML-форма уходит `POST` на публичный адрес API. API проверяет заявку по **опубликованной** версии блока, сохраняет её в таблицу `leads` и в той же транзакции ставит письма в очередь: владельцу или менеджеру сайта и, если посетитель указал почту, короткое подтверждение посетителю. Потом браузер возвращается на страницу, и CSS (`:target`) показывает «Спасибо». В админке у сайта есть раздел «Заявки»: список, карточка, «обработана», удаление и выгрузка CSV. Счётчик новых заявок виден в навигации сайта. Антиспам — ловушка и лимиты, без капчи. Персональные данные лежат не дольше срока, который задан в настройках сайта.

Шаг стоит на почте шагов 3.1–3.3: `enqueueMail`, шаблоны со схемой, состояние почты `MailRuntime`.

## Решения и почему

1. **Одна схема полей — и для браузера, и для сервера** (`packages/schema/src/forms.ts`). Тип поля выбирается из закрытого списка: имя, телефон, почта, текст, многострочный текст, выбор из списка, флажок. Для каждого типа одна запись правил: длина, шаблон телефона, тип `input`, `autocomplete`. Из неё `formFieldInput(field)` собирает HTML-атрибуты (`required`, `type`, `maxlength`, `pattern`, `autocomplete`, `inputmode`), а `leadValuesSchema(fields)` — Zod-схему заявки для сервера. Тест прогоняет образцы значений через обе стороны. Шаблон из `pattern` компилируется так же, как в браузере (`^(?:…)$` с флагом `v`), а результат сверяется с серверной схемой.
2. **У поля есть ключ** (`name`: латиница, цифры, `_`, до 32 символов). Он уникален в форме, и по нему поле узнаётся в заявке. Номер поля для этого не годится: поля переставляют. Имена служебных полей (`website` у ловушки, `consent` у согласия) заняты, схема их не пропустит.
3. **Ссылка на политику — поле блока (`policyUrl`), а не настройка сайта.** Поле обязательное, поэтому форму без политики не сохранить и не опубликовать: это держит схема блока, а не память человека. Нейронка через MCP видит его в схеме блока и заполняет сама. Отдельного экрана настроек сайта ещё нет (модуль 4). Когда он появится, поле можно сделать необязательным с адресом из настроек по умолчанию. Текст согласия — тоже поле блока, с разумным значением по умолчанию. В заявку он пишется вместе со ссылкой, номером опубликованной версии страницы и временем.
4. **Сайт остаётся без JavaScript.** Форма: `method="post"`, `action` — публичный адрес API (`CMS_API_URL` рендерера: тот же, откуда сайт берёт картинки), `application/x-www-form-urlencoded`. После приёма API отвечает **303** на страницу с якорем `#<id блока>-sent`. Элемент с этим id показывает CSS по `:target`, а форму рядом прячет. Страницу возврата API узнаёт так:
   - источник — из `Origin` (браузер шлёт его с каждой межсайтовой POST-формой), а без него — из `Referer`;
   - путь — страницы из адреса приёма (`/` или `/<slug>`): страница и так известна. Путь из `Referer` берётся, только если он указывает на эту же страницу (`/o-nas`, `/o-nas/`, `/o-nas.html`, `/o-nas/index.html`) — так сохраняется её точный вид. Сам по себе `Referer` ненадёжен: по умолчанию (`strict-origin-when-cross-origin`) в чужой источник браузер шлёт его без пути, только `https://сайт/` (исправлено по проверке, см. ниже);
   - браузер не прислал ни `Origin`, ни `Referer` (`Origin: null`, `no-referrer`) — API показывает свою страницу «Заявка отправлена».

   Перенаправление идёт на источник, который сам прислал форму, поэтому открытого редиректа здесь нет: чужая страница может отправить на наш адрес только себя же. Ошибки (форма не прошла проверку, лимит, слишком большое тело) — понятная HTML-страница от API. На ней список того, что не так, подписями полей, совет нажать «Назад» (браузер сохранит введённое) и ссылка на форму. Если клиент просит только JSON (`Accept` без `text/html`), ответ в формате `ApiError` — для скриптов и тестов. Скрипт для отправки без перезагрузки не делаем: без него всё работает, а лишний JS на сайте противоречит принципу 5.
5. **Неизвестные поля отбрасываются, а не отклоняются.** В заявку и письма попадают только поля опубликованного блока. Отклонять лишнее бесполезно: защиты это не добавляет, а боты шлют что угодно. Зато ломается честный случай: страница, открытая до публикации новой версии формы. Минимум данных (152-ФЗ) соблюдается: то, что форма не объявила, не хранится и не пересылается.
6. **Проверка — по опубликованной версии.** API ищет блок `form` с этим id в `pages.published`, а не в черновике, и снова проверяет его нынешней схемой блока: данные из базы идут в работу. Черновик на приём не влияет. Неопубликованная страница, удалённый блок или чужой сайт — 404 «Форма не найдена».
7. **Антиспам без капчи.**
   - **Ловушка**: скрытое от людей поле `website` (вне экрана, `aria-hidden`, `tabindex="-1"`, `autocomplete="off"`). Если оно заполнено, ответ тот же 303 «успех», а заявки и писем нет. Ответ неотличим от настоящего, и бот не узнает, что его поймали.
   - **Лимиты** (`createRateLimiter`, в памяти процесса): с одного IP — 5 отправок за 10 минут, на сайт — 100 за час. Сначала считается IP, потом сайт: по правилу CONVENTIONS ключ, который выбирает клиент, учитывается после лимита по IP. Тут лимит честный — 429 со страницей «Слишком много заявок, попробуйте через N минут». За одним IP бывает живой офис, и человек должен понять, что случилось. Лимит IP тратят все отправки, а лимит сайта — только заявки, которые будут сохранены (после ловушки и проверки схемой): иначе бот с многих IP, заполняющий ловушку, выбрал бы лимит сайта, и настоящие посетители получали бы 429.
   - **Размер тела**: не больше `LEAD_BODY_LIMIT` (`bodyLimit` до чтения тела), иначе 413. Предел считается из схемы: `FORM_MAX_FIELDS` (12) × `maxlength` многострочного поля (2000) × 9 байт (символ BMP вне кириллицы в urlencoded — `%XX%XX%XX`) + 16 КБ на ключи, ловушку и согласие, всего около 227 КБ. Честная форма, заполненная до `maxlength`, в него влезает всегда.
   - **Минимальное время заполнения — не делаем.** На статике честного способа нет. Метка, которую рендерер ставит при сборке, — время сборки, а не открытия страницы. Выдать метку при открытии можно только запросом к API в момент показа: через JS (его нет), через картинку с cookie (это сторонняя cookie, браузеры её режут) или так, чтобы саму форму отдавал API — `<iframe src="CMS_API_URL/forms/…">`, где подписанная метка стоит в скрытом поле. Вариант с iframe честный и без JS, но отклонён на этом шаге: высоту iframe без JS под содержимое не подогнать (поля, подсказки и сообщение об ошибке меняют высоту, будет скролл внутри блока или пустота), стили сайта (токены, шрифты) пришлось бы отдавать и из API, `:target` с текстом успеха работает внутри iframe, а не на странице, страница сайта перестаёт быть полностью статической (без API форма не видна вовсе), а API начинает отдавать HTML, который встраивают в чужие страницы (нужны `frame-ancestors` по доменам сайтов). Двухшаговая отправка с промежуточной страницей испортила бы форму людям. Остаются ловушка, лимиты и размер. Если реально начнут спамить, следующий шаг — необязательный скрипт с меткой, а для форм без неё — капча.
   - **CR/LF.** Однострочные поля (имя, телефон, почта, текст, выбор) с переводом строки или управляющим символом — ошибка (`hasHeaderBreak`), а не тихая чистка. Почта посетителя проверяется схемой `MailAddress` и только потом идёт в `Reply-To`. Тема письма пользовательского ввода не содержит.
8. **Хранение — таблица `leads`.** Поля: сайт, страница (ссылка, при удалении страницы — `NULL`) и её адрес, id блока, заголовок формы, данные — снимок `[{ name, label, type, value }]`. Подписи хранятся с заявкой: форму потом переименуют, а заявка должна читаться как была. Согласие: текст, ссылка на политику, номер опубликованной версии страницы, время. Статус `new` / `processed` и когда обработана, время создания. **IP не храним** (152-ФЗ: только то, что нужно). Для лимитов он живёт в памяти процесса, и его счётчик забывается через окно.
9. **Срок хранения** — настройка сайта `lead_retention_days`, по умолчанию 180 дней, от 7 до 1825. Заявки старше срока удаляет обработчик очереди писем раз в час, вместе с чисткой очереди (`cleanupAlso`, теперь с текущим временем — у каждого сайта свой срок).
10. **Письма — через outbox в той же транзакции, что и заявка.** Сбой записи письма откатывает и заявку: заявка без уведомления хуже, чем ошибка, которую видит посетитель.
    - **Владельцу или менеджеру** (`lead-new`). Адреса — настройка сайта `lead_recipients`; пусто — все владельцы админки. В письме все поля заявки подписями (подставляются через `html`…`` с экранированием, многострочный текст — с переносами), ссылка на заявку в админке. Тема — «Новая заявка с сайта «<название сайта>»». Название задаёт студия, а не посетитель, и оно проходит `toMailLine`. `Reply-To` — почта посетителя, если он её указал и она прошла схему. Подвал письма говорит, что «Ответить» напишет посетителю: общий подвал «отвечать не нужно» здесь был бы неправдой.
    - **Посетителю** (`lead-received`) — только если он указал почту, на сайте включено подтверждение (`lead_confirmation`, по умолчанию да) и этому адресу с этого сайта за последние 24 часа подтверждение ещё не ставилось (смотрим в `mail_outbox`). Текст фиксированный: в данных письма только название сайта. Ни имени, ни других полей посетителя в письме нет, поэтому форму нельзя превратить в рассылку своего текста на чужие адреса. Уходит только после ловушки и лимитов.
    - **Почта выключена** — заявка сохраняется, письма не ставятся. Раздел «Заявки» честно говорит, что уведомления не уходят и почему.
    - Telegram и вебхук в CRM — не в этом шаге, записаны в PLAN.md отдельным пунктом.
11. **Кто видит заявки.** Новые действия в `access.ts`: `leads.read` (список, карточка, CSV), `leads.manage` («обработана», удаление) и `leads.settings` (адреса уведомлений, срок, подтверждение). Все три даны **владельцу и клиенту сайта**. Клиент — это бизнес, чьи это заявки (оператор персональных данных по 152-ФЗ): он должен их видеть, обрабатывать, удалять по просьбе посетителя и решать, куда идут уведомления. **Редактор** делает контент, персональные данные посетителей ему не нужны. Если понадобится иначе, это одна строка в `access.ts`. **Токен API (MCP) заявок не видит** при любой таблице: это действия с персональными данными (`personalData` в `access.ts`), и `requireSite` отказывает токену в них отдельной проверкой (403). Чужой сайт — 404, как везде.
12. **CSV** — `;` как разделитель (так его открывает Excel с русской локалью), UTF-8 с BOM, каждое значение в кавычках. Защита от CSV-инъекции: значение, которое начинается с `=`, `+`, `-`, `@`, табуляции или возврата каретки, получает впереди `'`, и таблица не примет его за формулу. Колонки — дата, статус, страница, форма и поля всех форм по подписям.
13. **Метрика.** Цель на отправку формы без JS сайт не поставит. Цель на открытие страницы с `#…-sent` или серверная отправка цели — в шаге SEO и аналитики (модуль 4), записано в PLAN.md.

## Изменения по пакетам

- **`packages/schema`**: `forms.ts` — типы полей, `FormField`, правила по типам, `formFieldInput`, `leadValuesSchema`, служебные имена, `LeadSettings`, `LeadStatus`. Блок `form` (`blocks/form.ts`) в каталоге и союзе. Пометка `x-enum-titles` в `.meta()` даёт админке русские подписи вариантов.
- **`packages/blocks`**: компонент `Form` (`form/Form.tsx`, CSS Modules на токенах): поля по `formFieldInput`, ловушка, согласие со ссылкой, сообщение об успехе по `:target`. У `Page` новый необязательный проп `formAction(blockId)`. Без него (предпросмотр в админке) форма не отправляется.
- **`apps/renderer`**: передаёт `formAction` — адрес приёма в API по `CMS_API_URL`, id сайта и адресу страницы.
- **`apps/api`**:
  - миграция `leads` и настройки заявок в `sites` (`lead_recipients`, `lead_retention_days`, `lead_confirmation`) с CHECK;
  - модуль `src/modules/leads/`: `public-routes.ts` — открытый приём `POST /api/forms/:siteId/:slug/:blockId` (в списке открытых маршрутов `authenticate`), `routes.ts` — раздел админки, `repo.ts`, `service.ts` (приём в транзакции с письмами), `csv.ts`, `pages.ts` — HTML-страницы ответа;
  - шаблоны писем `lead-new` и `lead-received`. У шаблона может быть свой подвал (`footer` в `MailContent`);
  - права `leads.*` и запрет токену в `access.ts` и `middleware.ts`. В `GET /api/sites/:siteId` — `newLeads` (число новых заявок или `null`, если роли их не видно);
  - чистка заявок по сроку в обработчике очереди (`index.ts`).
- **`apps/admin`**: ссылка «Заявки» со счётчиком новых в навигации сайта. Экраны `/sites/:siteId/leads` (список, фильтр по статусу, выгрузка CSV, предупреждение о выключенной почте, настройки заявок) и `/sites/:siteId/leads/:leadId` (карточка, «Обработана» / «Вернуть в новые», «Удалить»). `SchemaForm` научилась флажкам (`boolean`) и подписям вариантов (`x-enum-titles`): без них блок формы не заполнить в редакторе.
- **`apps/mcp`**: ничего, кроме того, что блок `form` с примером сам появился в `list_blocks`. Заявок MCP не видит.
- **`e2e`**: `tests/forms.spec.ts`.
- **Документация**: README, CONVENTIONS, PLAN.md, этот файл.

## Хвосты почты (замечания последней проверки)

1. **Подсказка про Яндекс на 4xx.** `explain('send')` давал подсказку «адрес должен принадлежать ящику… у Яндекс 360 — совпадать с логином» на любой отказ `MAIL FROM`, в том числе на временный лимит «451 4.7.1 Too many messages». Теперь эта подсказка идёт только на 5xx. На 4xx текст другой: «Сервер временно не принимает письма от … (ответ 451: обычно это лимит писем отправителя). Настройки менять не нужно: письма подождут в очереди и уйдут позже». Лог обработчика тоже не говорит «это настройки»: «Виновато не письмо, а настройки почты или лимит отправителя». Тесты: 553 — подсказка про ящик, 451 — текст про лимит, без Яндекса и «Проверь MAIL_FROM».
2. **Вечный цикл `sendQueue` в `smtp.test.ts`.** Помощник крутил `processOutbox`, пока `claimed > 0`. При выключенной почте письма отпускаются и берутся снова, и тест висел. Теперь проход, который ничего не отправил (`mailOff`, `serverDown`, `aborted`), — конец, а больше 50 проходов — ошибка теста, а не зависание.
3. **Обрыв после TCP засчитывался шагу TLS с подсказкой про файрвол.** Выяснилось ещё одно: если сервер принимает TCP и сразу закрывает сокет, nodemailer всё равно доводит до колбэка `connect`. Проверка писала «✓ TLS установлен» и ломалась на входе с текстом про файрвол. Теперь `diagnoseSmtp` после `connect` проверяет, что соединение живо и зашифровано (`destroyed`, `secure`). Сбой после TCP объясняется отдельным текстом (`FailureContext.connected`): «…принял соединение и сразу закрыл его или ответил не как SMTP-сервер: проверь SMTP_PORT и SMTP_SECURITY» — без файрвола. Тест: TCP-сервер, который закрывает сокет, даёт `dns:ok, connection:ok, tls:fail` без «файрвол». Добавлен и положительный тест проверки в режиме TLS сразу: новая проверка `secure` не должна его ломать.
4. **Пауза 200 мс в `worker.test.ts`.** Тест «сервер не принял адрес отправителя…» ждёт не фиксированные 200 мс, а условие — запись лога о паузе «следующая попытка через 60 с». После неё проверяется, что отправка была одна.

## Критерии готовности

1. Блок «Форма» есть в каталоге (админка, MCP) с примером. Пример проходит схему, а форма без политики, с повторяющимися ключами полей, с `select` без вариантов или со служебным именем поля не проходит.
2. Опубликованная страница с формой — обычный HTML без `<script>`. У полей атрибуты из `formFieldInput`, есть ловушка и обязательное согласие со ссылкой на политику.
3. Отправка с выключенным JavaScript: 303 на страницу с `#…-sent`, посетитель видит текст успеха. Заявка появляется в админке, письмо владельцу (с `Reply-To` посетителя) и подтверждение посетителю лежат в файловом ящике.
4. Приём идёт по опубликованной версии: поле, которое добавили только в черновик, не принимается и не требуется. Неопубликованная страница — 404.
5. Ловушка: ответ как при успехе, заявки и писем нет.
6. Лимиты: шестая отправка с IP за 10 минут — 429; лимит сайта тоже работает, ловушка его не тратит. Тело больше `LEAD_BODY_LIMIT` — 413, честная форма до `maxlength` — нет. CR/LF в однострочном поле — 400. Без согласия — 400.
7. Транзакция: если запись письма падает, нет ни заявки, ни письма.
8. Письмо владельцу: все поля экранированы, `Reply-To` — почта посетителя, тема без ввода посетителя. Подтверждение посетителю без ввода посетителя, не чаще раза в 24 часа на адрес и сайт, только с почтой и включённым подтверждением.

Что получилось:
- **Схема полей** (`packages/schema/src/forms.ts`): таблица `fieldRules`, из неё `formFieldInput` (атрибуты браузера) и `leadValuesSchema` (сервер). Тест прогоняет образцы каждого типа, обязательного и необязательного, через «браузер» (атрибуты и `pattern` с флагом `v`, как его собирает браузер) и через сервер — ответы совпадают.
- **Блок «Форма заявки»** в каталоге админки и MCP, с примером. Компонент `Form` — чистый HTML: поля, ловушка, обязательное согласие со ссылкой на политику, текст успеха по `:target`. В редакторе форма заполняется обычной `SchemaForm`: ей добавлены флажок (`boolean`) и русские подписи вариантов (`x-enum-titles`). Пункты-поля в списке подписаны их подписью.

Ответ — 303 на страницу формы (`Origin` и путь из маршрута) с якорем или HTML-страница с CSP без скриптов. JSON — по явной просьбе.

### Отклонения от плана и добавки

- **Почте посетителя добавлен `pattern`** (`EMAIL_PATTERN`). Браузер для `type="email"` пропускает `anna@example` без точки в домене, а сервер (`MailAddress`) — нет. Без шаблона такая почта проходила бы браузер и упиралась в страницу ошибки. Тест согласованности это и поймал.
- **Хвост 3 оказался глубже.** Сервер, закрывший сокет сразу после TCP, nodemailer тоже доводит до колбэка `connect`. Проверка писала «✓ TLS установлен» и ломалась на входе с подсказкой про файрвол. Исправлено проверкой `destroyed`/`secure` после `connect` (см. «Хвосты почты»), добавлен положительный тест режима TLS сразу.
- **Сбой транзакции заявки** отдаёт посетителю HTML-страницу 500 «Заявка не сохранена», а не JSON общего обработчика ошибок: посетитель сайта смотрит на неё в браузере.
- **Подвал письма** стал настраиваемым (`footer` в `MailContent`). У «Новой заявки» с почтой посетителя общий подвал «отвечать на него не нужно» был бы неправдой. e2e «Почты» теперь проверяет подвал каждого шаблона.
- **MCP**: в правила для нейронки добавлена строка про форму (ключи полей, `policyUrl`, заявки через MCP не видны).
- **Счётчик новых заявок** приходит в `GET /api/sites/:siteId` (`newLeads`), а не отдельным запросом: экран сайта и так его грузит.

### Что не проверено тестами напрямую и что осталось

- Кнопка «Выгрузить CSV», форма настроек заявок и «Удалить заявку» в админке e2e не нажимаются. Их поведение проверяют тесты API (CSV с формулами, настройки, удаление, права). Карточку и «Отметить обработанной» e2e проходит.
- Лимиты заявок и счётчики в памяти одного процесса API: при нескольких процессах их придётся вынести в базу, как и остальные лимиты (`rate-limit.ts`).
- Подтверждение посетителю «раз в сутки на адрес» проверяется запросом к `mail_outbox` внутри транзакции заявки. Две заявки с одного адреса в одно мгновение теоретически могут поставить два подтверждения: PGlite выполняет транзакции по очереди, а на Postgres это стоит закрыть блокировкой на адрес, если понадобится.
- Список заявок в админке — последние 500, без постраничной выдачи: лендингу этого хватит надолго. Постраничную выдачу сделаем, когда упрёмся. CSV выгружает все заявки сайта: их не больше, чем живёт за срок хранения.
- Telegram и вебхук в CRM, цель Метрики — записаны в PLAN.md (модули 8 и 4). Свой SMTP у сайта для писем о заявках — по-прежнему «потом» в модуле 10.

## Исправления по проверке

Проверка, круг 1: одна major-ошибка и десять minor. Исправлено всё, кроме одного решения, которое оставлено на пользователя (пункт 6).

1. **major — возврат после отправки с неглавной страницы.** `returnUrl()` брал путь из `Referer`, а браузер по умолчанию (`strict-origin-when-cross-origin`) шлёт в чужой источник (сайт → API) `Referer` без пути. Посетитель со страницы `/o-nas` попадал на главную с `#…-sent`, не видел «Спасибо» и мог отправить форму ещё раз. Теперь источник — из `Origin` (без него — из `Referer`), путь — страницы из адреса приёма (`pagePath(slug)`). Путь `Referer` берётся, только если это та же страница (`/o-nas/`, `/o-nas.html` и т. п. — тогда сохраняется её точный вид). Ссылка «Вернуться к форме» на странице ошибки — тоже на эту страницу. Тесты: интеграционный с настоящими заголовками (`Referer: https://сайт/`, страница `o-nas`), полный `Referer` этой и другой страницы, ссылка назад со страницы ошибки; помощник `submit` во всех тестах шлёт теперь `Referer` без пути, как браузер. e2e без JavaScript на неглавной странице: адрес после отправки — `/<slug>#about-form-sent`, «Спасибо» видно, форма скрыта. README и решение 4 поправлены.
2. **NUL в многострочном поле давал 500.** Postgres не принимает `\u0000` в `jsonb`. Многострочное поле теперь отклоняет управляющие символы, кроме `\n` и `\t` (`\r` нормализуется в `\n` раньше), с сообщением «Без управляющих символов» — 400. Тесты: схема и маршрут (`\u0000`, `\u0007`, `\u001b` — 400; табуляция и переводы строк — 303).
3. **Поле с ключом `constructor` не отправлялось никогда.** Тело формы складывается в `Object.create(null)` и проверяется `Object.hasOwn`; снимок заявки берёт значение тоже только своим свойством. Правило записано в CONVENTIONS. Тест: форма с полями `constructor` и `tostring` принимается, пустое обязательное `constructor` — обычное «Заполните поле».
4. **Ловушка тратила лимит сайта.** Лимит сайта теперь берётся только для заявок, которые будут сохранены: после ловушки и проверки схемой. Лимит IP — по-прежнему первым и для всех отправок. Тест: десять отправок с ловушкой с разных IP не мешают двум настоящим заявкам, третья — 429 по лимиту сайта.
5. **Браузер и сервер по-разному принимали почту и пробелы.** Шаблон адреса теперь один — `MAIL_ADDRESS_PATTERN` в `packages/schema/src/mail.ts`: из него и `MailAddress` (сервер, заголовки писем), и `pattern` поля «Почта» в форме. Имя ящика — латиница, цифры, `_ ' + -`, точки только между ними (запятых, кавычек и скобок нет — адрес не разобрать как несколько). Домен — буквы любого алфавита и цифры, зона от двух знаков и с буквы: проходят `anna@пример.рф` и `anna@xn--e1afmkfd.xn--p1ai` (так IDN шлёт Chrome), не проходят `a..b@…`, `…@example.r`, `a!b@…` — и в браузере, и на сервере. Кириллический домен nodemailer сам переводит в punycode (проверено по его исходникам, `mime-node`). `z.email()` для адресов писем больше не берём. Обязательные однострочные поля без своего шаблона получили `pattern` «не одни пробелы» (`NOT_BLANK_PATTERN`). Осталось одно расхождение: обязательное многострочное поле из одних пробелов браузер пропустит (у `textarea` нет `pattern`), сервер ответит страницей ошибки — описано в README. Тест согласованности получил эти образцы и учитывает, что браузер сам обрезает пробелы у `type="email"`; интеграционный тест — IDN и punycode принимаются, письмо уходит на кириллический адрес.
6. **Клиент мог молча направить письма о заявках на свои адреса.** Сделан минимум из предложенного: при смене адресов уведомлений в той же транзакции уходит письмо «Адреса уведомлений о заявках изменены» (новый шаблон `lead-recipients-changed`) всем владельцам и прежним адресам: кто, когда, какие адреса теперь. Новые адреса письма о смене не получают. Без смены адресов (в том числе другой регистр) письма нет. В админке у поля подсказка, что о смене узнают владельцы и прежние адреса. **Не сделано и оставлено на решение пользователя:** запретить смену адресов клиенту (сейчас это может и владелец, и клиент — клиент оператор ПДн и решает, куда идут заявки) или подтверждать новый адрес по ссылке. Тесты: шаблон (поля, экранирование, пусто — владельцам, перевод строки в адресе отклоняется) и маршрут (клиент меняет — письмо владельцам и прежнему адресу, не новому; без смены — нет).
7. **Неверный комментарий к пределу тела, 413 на честный ввод.** Предел теперь считается из схемы: `LEAD_BODY_LIMIT = FORM_MAX_FIELDS × 2000 × 9 + 16 КБ` (~227 КБ). `FORM_MAX_FIELDS` — общая константа схемы, её же берёт блок формы. Тест: 12 многострочных полей по 2000 символов `…` (9 байт в urlencoded, больше 200 КБ) — 303; 50 000 символов — 413.
8. **Удаление заявки не трогало её письма.** В `mail_outbox` появилась ссылка `lead_id` на заявку с `ON DELETE CASCADE` (миграция `0011_outbox_lead_link`), её ставят оба письма о заявке. Удалили заявку руками или по сроку — удалились и её письма: неотправленные с копией полей и подтверждение с почтой посетителя. Цена: вместе с подтверждением удалённой заявки пропадает и отметка «этому адресу уже подтверждали» — после удаления заявки посетитель может получить подтверждение раньше суток. Срок хранения заявок не меньше 7 дней, так что по сроку это не случается. Тесты: удаление (письма этой заявки ушли, почты посетителя и комментария в очереди нет, письма другой заявки на месте) и чистка по сроку.
9. **Мусор в тестовых помощниках.** Двойной JSDoc в `smtp.test.ts` убран. Один помощник `sendQueue(api)` вынесен в `src/testing.ts`: останавливается на `mailOff`, `serverDown`, `aborted` и пустом проходе, а после предела проходов падает. Его берут `smtp.test.ts` и `leads.test.ts`.
10. **Зависший процесс vitest** (`vitest run src/mail/runtime.test.ts src/modules/mail/smtp.test.ts`, с 13:12) остановлен. После прогонов этого круга своих процессов node не осталось.
11. **Разбор «минимального времени заполнения»** дополнен вариантом, когда форму в iframe отдаёт сам API с подписанной меткой, и причинами, почему он отклонён на этом шаге (решение 7).
