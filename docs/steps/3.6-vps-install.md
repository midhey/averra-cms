# Шаг 3.6. Установка на VPS клиента

## Цель

Первая половина модуля 9: Averra ставится у каждого клиента на его VPS (решение 6 в PLAN.md), одной командой на чистый Ubuntu, и публикует сайт на том же сервере. «Опубликовать» в админке собирает статику Astro прямо на VPS и без простоя подменяет ею текущую версию сайта, которую отдаёт Caddy с SSL.

Обновления с откатом, бэкапы и обзор состояния установок — вторая половина модуля 9, следующим шагом.

На машине разработки нет Docker и PostgreSQL. Всё, что можно проверить без них, проверено тестами и живыми прогонами (см. «Итог»). Остальное, то есть сборку образов, Compose, Caddy с настоящими сертификатами и установщик на настоящем Ubuntu, владелец проходит по чек-листу «Проверка на живом VPS» в конце.

## Решения и почему

### 1. PostgreSQL в проде — node-postgres по DATABASE_URL

`DATABASE_URL` задан — API и команды работают с PostgreSQL через драйвер `node-postgres` (`pg`, `drizzle-orm/node-postgres`). Не задан — встроенный PGlite, как раньше. Выбор делает `dbTargetOf` (`apps/api/src/db/client.ts`), открывает базу `createDb(target)`. Миграции те же: мигратор Drizzle у обоих драйверов один (`dialect.migrate`), папка `apps/api/drizzle` одна.

Почему node-postgres, а не postgres.js: в коде есть сырые запросы `db.execute(sql…)` (выгрузка CSV, `exportLabels`), и они читают `.rows`. PGlite и node-postgres отдают одно и то же `{ rows }`, а postgres.js — массив строк. Тип базы в коде остаётся один (`Db`). Драйвер node-postgres приводится к нему явно, с комментарием, а совпадение держит интеграционный тест на настоящем драйвере.

Пул — 5 соединений: API один процесс, а на VPS с 1–2 ГБ у Postgres лишние соединения — лишняя память. Замок базы (`db/lock.ts`) берётся только у PGlite: Postgres держит API и команду одновременно, поэтому на сервере `user:create` и другие команды идут при работающем API (`docker compose exec`).

**Как проверено без Postgres.** `@electric-sql/pglite-socket` — сервер протокола Postgres поверх PGlite. Драйвер `pg` подключается к нему по TCP, как к настоящему Postgres: пул, транзакции, разбор типов (timestamptz, jsonb, bigint) — всё настоящее. Отличие одно: сервер выполняет запросы по очереди. Интеграционный тест `db/postgres.test.ts` гоняет через этот драйвер миграции, создание сайта, публикацию с историей (транзакция), снимок, приём заявки с письмами в той же транзакции, сырые запросы CSV и очередь писем. Тем же сервером проверен и собранный API целиком (см. «Итог»). Расширения PGlite, которые pglite-socket объявляет обязательными peer-зависимостями, помечены необязательными (`packageExtensions` в `pnpm-workspace.yaml`): они не нужны.

### 2. Прод-сборка API — esbuild в `dist/server`

`pnpm --filter @averra/api build` (`apps/api/scripts/build.ts`) собирает API и команды терминала в ESM для Node 24. В бандл входят наш код и пакеты рабочей области (`@averra/schema`, `@averra/tokens`): они экспортируют исходники `.ts`, а Node не снимает типы с файлов в `node_modules`. Остальные зависимости остаются внешними и ставятся как prod-зависимости: у sharp и PGlite бинарники и wasm рядом с пакетом. tsx на сервере не нужен.

Пути от `import.meta.url` (папка миграций, рендерер) верны и в исходниках, и в сборке, потому что глубина одна: `src/db/`, `src/publish/` и `dist/server/` лежат на два уровня ниже `apps/api`. Куски кода (`splitting`) кладутся рядом с точками входа, а не в подпапку. Скрипт сборки проверяет это по факту: от `dist/server` должны находиться `apps/api/drizzle` и сборщик рендерера.

Админка — обычная статика `vite build`, её отдаёт Caddy.

### 3. Образы — один Dockerfile, две цели

`deploy/Dockerfile`, контекст — корень репозитория:

- **`api`** — `node:24.22.0-bookworm-slim` (та же Node, что закреплена в проекте; glibc — под него есть готовые sharp и rolldown, без сборки из исходников). В образе только prod-зависимости API и рендерера: `pnpm install --prod --frozen-lockfile --filter "@averra/api..." --filter "@averra/renderer..."`, без vitest, drizzle-kit, typescript и Biome. API запускается собранным JS, без tsx; сами tsx и esbuild в дереве есть — их транзитивно приносят vite (tsx — его необязательный peer) и astro (esbuild — его зависимость) для сборщика сайта. Раскладка папок как в репозитории, поэтому пути `RENDERER_DIR`, миграций и пакетов рабочей области те же. Работает от `node`, код только для чтения. Писать можно только в тома (`/data/sites`, `/data/media`): код рендерера, который API запускает при каждой публикации, тоже за root. Кеши сборщика — в `/data/sites/.cache` (`astro/`, `vite/`), а `apps/renderer/.astro`, которую Astro не даёт перенести, — ссылка на `/data/sites/.cache/dot-astro` (см. «Мелочи после приёмки»). Есть HEALTHCHECK по `/api/health/ready`.
- **`web`** — `caddy:2.11.7-alpine` со статикой админки и `Caddyfile`. Работает от пользователя `caddy` (uid 1000), не от root: это единственный контейнер, открытый в интернет.

Секретов в образах нет: `.dockerignore` не пускает `.env`, `.data` и `node_modules`, а секреты приходят переменными из `.env` установки. sharp под linux-x64 ставит pnpm внутри сборки (нужный `@img/sharp-linux-*` по платформе). Образы собираются и под arm64 (buildx).

### 4. Compose и Caddy: сайт и админка, форма без CORS, медиа статикой

`deploy/compose.yaml`: `postgres` (данные в томе `postgres`, пароль из `.env`, небольшие `shared_buffers` и `max_connections` под 1–2 ГБ), `api` (наружу не открыт, только внутренняя сеть; `init: true`, `cap_drop: ALL`, `no-new-privileges`), `caddy` (порты 80/443, не root, `cap_drop: ALL` + `NET_BIND_SERVICE`, том сайтов только на чтение).

**Админка и API — один источник** (`ADMIN_DOMAIN`): Caddy отдаёт `/api/*` в API, остальное — статика админки с `try_files … /index.html`. `ADMIN_URL` и `API_URL` у API — оба `https://ADMIN_DOMAIN`, cookie без CORS и без `SameSite=None`.

**Форма сайта — на свой же домен.** Рендерер при публикации собирает сайт с `CMS_LINKS=relative`: `action` формы — `/api/forms/…` от корня сайта, и Caddy домена сайта передаёт этот путь (и только его) в API. Форма уходит на тот же источник, никакого CORS. Почему не прямо на поддомен админки: тогда сайт зависел бы от адреса API, а в `Referer` при межсайтовой отправке браузер срезал бы путь. Логика шага 3.4 за прокси работает без изменений. Caddy передаёт настоящие `Host`, `Origin` и `Referer` браузера, поэтому `returnUrl` возвращает посетителя на `https://сайт/страница/#…-sent`. `X-Forwarded-For` Caddy ставит адресом клиента и отбрасывает присланный клиентом: доверенных прокси перед ним нет (документация `reverse_proxy`). Поэтому у API `TRUST_PROXY=true`, и лимиты по IP считаются по посетителю, а не по адресу Caddy. Это проверяет тест `modules/leads/proxy.test.ts`: запрос на домен сайта через `prepareRequest`, лимит по IP и вариант без `TRUST_PROXY`, где все посетители слились бы в один IP.

**Медиа — статикой из релиза.** PLAN требует, чтобы в выкладку попадали только файлы, на которые ссылается страница. Так и сделано: после сборки API находит в HTML ссылки `/media/<id>/<ширина>.<формат>` и кладёт эти файлы в папку релиза (`release-files.ts`). Оригинал (`original.*`) наружу не попадает: шаблон ссылки его не пропускает. Caddy отдаёт их как статику с `immutable`, API в отдаче картинок сайта не участвует. Файл, который уже есть в прежнем релизе, связывается жёсткой ссылкой, а не копируется: файлы картинок под своим адресом не меняются, и пять хранимых версий не занимают пятикратно места. Сайт в релизе — полностью самостоятельная статика, её можно выгрузить архивом (принцип 8).

Заодно из `_astro` убирается то, на что не ссылается ни страница, ни её CSS и JS: Astro кладёт туда бандл React для островов (~220 КБ), даже когда страница его не грузит.

SSL: Caddy сам выпускает и продлевает сертификаты Let's Encrypt (`email` из `ACME_EMAIL`, тома `caddy_data` и `caddy_config`). HTML сайта — `Cache-Control: no-cache` (новая версия видна сразу), `/_astro/*` и картинки `/media/<uuid>/…` — `immutable`. У админки `index.html` и её экраны (`/`, `/sites/…`) — `no-cache`, `/assets/*` — `immutable`, а отсутствующий ассет — 404. Заголовки: HSTS, `nosniff`, `Referrer-Policy`, у админки `X-Frame-Options: SAMEORIGIN`.

### 5. Публикация на сервере — очередь, релизы, атомарная подмена

Включается переменной `PUBLISH_DIR`. Без неё, например в `pnpm dev`, публикация только меняет базу, как раньше.

- **Что запускает сборку:** «Опубликовать» и удаление опубликованной страницы (`modules/sites/routes.ts`). Ещё «Собрать заново» на экране сайта (`POST /api/sites/:siteId/build`, право `page.publish`). Сборка ставится после того, как публикация уже в базе. Сбой постановки в очередь публикацию не отменяет — он пишется в лог.
- **Очередь** (`src/publish/queue.ts`) — одна на установку, сборки идут **по одной**. Сборка Astro — самое тяжёлое на VPS, две сразу удвоили бы пик памяти. Тем более не бывает двух параллельных сборок одного сайта. Публикация, пока сайт собирается, заводит ещё одну сборку после текущей: снимок читается в начале сборки, и новая правка в текущую могла не попасть. Публикация, пока сборка только ждёт, новой не заводит. Это держит и база: у сайта не больше одной ждущей сборки (частичный уникальный индекс `site_builds_one_queued`).
- **Журнал** — таблица `site_builds` (миграция `0014_site_builds`): состояние, релиз, причина сбоя (хвост вывода сборщика), пиковая память, время. Хранятся последние 20 сборок сайта. После перезапуска API шедшая сборка помечается прерванной, а она и ждущие встают в очередь заново: пометка (`markInterrupted`) — до `serve()`, постановка в очередь (`resume`) — когда сервер слушает порт. Туда же — опубликованные сайты без текущей версии на диске: свежая установка или потерянный том.
- **Сборка** — отдельный процесс Node: `apps/renderer/scripts/build-release.mjs` (программный `build` Astro). Отдельный процесс — чтобы память уходила вместе с ним, зависшая сборка убивалась по таймауту (`PUBLISH_TIMEOUT_SECONDS`), а сбой не ронял API. Куча ограничена (`--max-old-space-size=PUBLISH_MAX_MEMORY_MB`). Сборщик получает только нужные переменные, секретов API (`AUTH_SECRET`, `DATABASE_URL`, ключи) у него нет, поэтому в его вывод, а через него в журнал и админку, они не попадут. Снимок сайта он берёт у этого же API по loopback. Пиковую память процесса он печатает последней строкой, и она идёт в журнал.
- **Релизы** (`src/publish/releases.ts`): `PUBLISH_DIR/<сайт>/releases/<время>-<хвост>/` и ссылка `current` на текущую. Сборка пишет во временную папку `.tmp-…`. Готовая переименовывается в релиз, потом рядом создаётся новая ссылка и **переименовывается поверх** `current`: на Linux `rename` атомарен, Caddy видит либо старую версию целиком, либо новую. Цель ссылки относительная, поэтому Caddy видит ту же папку под своим путём. Сбой на любом шаге до подмены удаляет временную папку, `current` не тронут. Хранятся `PUBLISH_KEEP_RELEASES` (5) последних, текущая не удаляется никогда, брошенные `.tmp-` чистятся. На Windows (разработка, тесты) папку-ссылку поверх существующей не переименовать: там старая ссылка сначала удаляется, на сервере этого кода не бывает.
- **Остановка API** прерывает идущую сборку (процесс сборщика убивается сразу), а не ждёт её до таймаута: `docker stop` даёт 10 секунд. Прерванная сборка соберётся при следующем старте.
- **Админка:** на экране сайта раздел «Сайт на сервере». В нём какая версия на сайте и когда собрана, сколько памяти заняла сборка, «Собирается…» (раздел сам опрашивает API, пока сборка ждёт или идёт), упавшая сборка с причиной в `role="alert"` и «Собрать заново» для владельца и редактора. Без `PUBLISH_DIR` раздела нет.

### 6. Установщик — `deploy/install.sh`

Bash, потому что на чистом Ubuntu нет Node. Флаги или вопросы: домен сайта, поддомен админки (по умолчанию `admin.<домен>`), почта (Let's Encrypt и вход владельца), версия образов, папка (`/opt/averra`). Справка — `--help`.

1. **Проверки:** Docker и `docker compose` есть и отвечают (`--install-docker` ставит пакеты Ubuntu `docker.io` и `docker-compose-v2`, без `curl | sh`). Порты 80 и 443 свободны, если их держит наш же Caddy — это повторный запуск, не помеха. DNS обоих доменов указывает на адрес сервера (`getent ahosts` против `hostname -I`; за NAT — `--public-ip`).
2. **`.env`** в папке установки: секреты из `/dev/urandom` (`AUTH_SECRET` и `MAIL_ENCRYPTION_KEY` — 32 байта base64, пароль Postgres — hex, чтобы не ломать `DATABASE_URL`). Файл создаётся с `umask 077` и `chmod 600` до `mv`, поэтому чужим не виден ни на миг. `.env` не выполняется через `source`, а читается как текст.
3. `docker login ghcr.io` по `--ghcr-user` (или `GHCR_USER`) и токену: его установщик спрашивает скрыто или берёт из `GHCR_TOKEN` окружения, в `docker login` — через stdin, `pull`, подъём `postgres` и `api`, ожидание `/api/health/ready` (до 3 минут).
4. Владелец — `user-create.js --if-missing` в контейнере. Пароль спрашивается скрыто или берётся из `AVERRA_OWNER_PASSWORD`: он уходит в контейнер переменной окружения, а не аргументом. Сайт — новая команда `site:create --print-id`, его id ложится в `.env` (`SITE_ID`): этот сайт Caddy отдаёт на домене сайта.
5. Подъём Caddy, итог: адрес админки и что дальше (SMTP в админке).

**Повторный запуск безопасен.** Секреты, если уже записаны, не меняются никогда: новый `AUTH_SECRET` выкинул бы всех из админки, новый ключ сделал бы нечитаемым пароль SMTP, новый пароль Postgres не подошёл бы к базе. Владелец и сайт второй раз не создаются (отметки `OWNER_EMAIL` и `SITE_ID` в `.env`, плюс `--if-missing`). Новые домены, почта и версия из флагов записываются, свои строки в `.env` сохраняются. Значения проверяются: домен (строчная латиница или punycode), почта, тег и имя образа. Они попадают в Caddyfile и `.env`, перевод строки или пробел недопустимы.

**Учебного режима на сервере нет:** в образе API запускается без `--dev`, в compose — `NODE_ENV=production`, а без `--dev` `config.ts` учебный секрет и демо-данные не открывает. Это проверяет тест установщика по Dockerfile и compose.

`--dry-run` показывает план и проходит проверки только на чтение (права на папку, Docker, порты, DNS): все проблемы сразу, код 1, если они есть. Файлов и контейнеров не трогает. Без прав на папку установки обычный прогон сразу отвечает «запустите через sudo». `--env-only` пишет папку и `.env` без Docker.

### 7. Как образы попадают на VPS — GHCR по тегу версии

Выбрано: образы собирает GitHub Actions (`.github/workflows/release.yml`) по тегу `vX.Y.Z` после `pnpm check`, под amd64 и arm64, и кладёт в GHCR: `ghcr.io/midhey/averra-api:X.Y.Z` и `averra-web:X.Y.Z`. На VPS `install.sh` скачивает их по `AVERRA_VERSION`. Workflow написан, но не запускался: в этом шаге ничего не пушилось и теги не создавались.

| | GHCR по тегу (выбрано) | Сборка на месте |
|---|---|---|
| Память VPS | не нужна: сборка pnpm + Vite на 1 ГБ легко падает по памяти | `pnpm install` и сборка админки на самом VPS |
| Время установки | минуты (скачать образы) | десятки минут на слабом CPU |
| Одинаковость | у всех клиентов один и тот же образ версии — проще обслуживать и откатывать | у каждого сервера своя сборка |
| Откат | сменить `AVERRA_VERSION` на прежнюю | пересобрать прежний коммит |
| Доступ | репозиторий приватный → на VPS токен GHCR только `read:packages`; он хранится в `~/.docker/config.json` (base64, не шифр) | на VPS нужен исходный код (deploy key) |
| Зависимость | от GHCR (GitHub) | от npm-реестра при каждой установке |

Запасной путь без GHCR — собрать образы на своей машине или в CI и передать их на сервер (`docker save | ssh … docker load`) или переопределить `AVERRA_API_IMAGE`/`AVERRA_WEB_IMAGE` на свой реестр (флаги `--api-image`, `--web-image`).

## Изменения по пакетам

- **`@averra/schema`:** `SiteBuildStatus` (`publish.ts`).
- **`@averra/api`:**
  - `db/client.ts` — `DbTarget`, `dbTargetOf`, `createDb(target)` на PGlite или node-postgres.
  - `config.ts` — `DATABASE_URL` (только `postgres://`/`postgresql://`, значение в ошибку не попадает), `PUBLISH_DIR`, `PUBLISH_KEEP_RELEASES`, `PUBLISH_TIMEOUT_SECONDS`, `PUBLISH_MAX_MEMORY_MB`, `RENDERER_DIR`.
  - Таблица `site_builds` (миграция `0014_site_builds`), `modules/builds` (журнал и маршруты `GET/POST /api/sites/:siteId/build`).
  - `publish/` — очередь, релизы, файлы релиза, процесс сборщика, сборка сайта.
  - Публикация и удаление страницы заводят сборку.
  - `index.ts` — база по цели, очередь сборок, `recover` после старта, прерывание сборки при остановке.
  - `cli/common.ts` — замок только у PGlite.
  - Новая команда `site:create`, у `user:create` — `--if-missing`.
  - `scripts/build.ts` (esbuild) и `start:prod`.
  - Зависимости: `pg`; dev — `@types/pg`, `@electric-sql/pglite-socket`, `esbuild`.

## Критерии готовности

1. `DATABASE_URL` → node-postgres, без него — PGlite. Миграции и весь путь API проходят на настоящем драйвере (тест на pglite-socket).
2. API запускается без tsx (`node dist/server/index.js`) из дерева только с prod-зависимостями. Админка — статика.
3. Dockerfile многоэтапный, без dev-зависимостей и секретов, не от root, с healthcheck; compose — Postgres в томе с паролем из `.env`, API во внутренней сети, Caddy с SSL; форма сайта уходит на свой домен.
4. «Опубликовать» → сборка на сервере → новая папка релиза → атомарная подмена `current`. Сбой сборки не трогает текущую версию и виден в админке. Сборки не идут параллельно, старые релизы чистятся. Пиковая память сборки демо-сайта замерена.
5. `install.sh`: проверки окружения, флаги и вопросы, `.env` с секретами и правами 600, ожидание готовности, владелец и сайт. Повторный запуск идемпотентен, учебный режим невозможен.
6. Выбран и описан путь образов (GHCR), workflow написан и не запускался.
7. README, CONVENTIONS, PLAN, этот документ с чек-листом живого VPS. `pnpm check` и `pnpm e2e` зелёные, `pnpm dev` работает как раньше (публикация на сервере в нём выключена).

## Проверка на живом VPS

Чистый Ubuntu 24.04, 1–2 ГБ памяти, два DNS-имени (A-записи сайта и `admin.` на IP сервера). Перед этим — опубликовать образы: тег `v0.6.0` → workflow `release` (или собрать и запушить руками, см. README).

1. **Образы.** Workflow прошёл. В GHCR есть `averra-api:0.6.0` и `averra-web:0.6.0` для amd64 и arm64. Размер `averra-api` разумный (ориентир — меньше 600 МБ). В образе нет `.env`, `.data` и dev-зависимостей: `docker run --rm --entrypoint sh averra-api -c 'ls /app/node_modules/.pnpm | grep -E "^(vitest|drizzle-kit|typescript|@biomejs)@"'` — пусто (tsx и esbuild там есть: их приносят vite и astro для сборщика, это не ошибка). `docker run --rm averra-api id` — `uid=1000(node)`, `docker run --rm --entrypoint id averra-web` — `uid=1000(caddy)`.
2. **sharp в образе:** `docker run --rm --entrypoint node averra-api -e "require('sharp')"` из `/app/apps/api` без ошибок. Загрузка картинки в админке работает (варианты AVIF/WebP режутся).
3. **Установка:** скопировать на сервер только `deploy/install.sh`, `deploy/averra.sh` и `deploy/compose.yaml` (команда — в README, «Установка»; не `scp -r deploy`: в папке `node_modules` пакета `@averra/deploy` со ссылками на инструменты разработки, около 120 МБ). Сначала `bash install.sh --site-domain … --email … --version 0.6.0 --dry-run` без sudo — «нет прав на запись в /opt/averra: запустите через sudo» в списке проблем. Потом `sudo bash install.sh --site-domain … --email … --version 0.6.0 --ghcr-user …`. Проверки проходят, токен GHCR и пароль владельца спрашиваются скрыто, в конце — адрес админки. `history | tail` — токена в истории нет.
4. `ls -l /opt/averra/.env` — `-rw-------`, владелец root. Секреты не выводились в терминал.
5. **Повторный запуск** с теми же флагами: «Секреты не менялись», владелец и сайт не создаются второй раз, вход в админку не слетел.

Владелец создан, вход с этим паролем работает: настоящий docker compose берёт значение `-e CMS_USER_PASSWORD` без `=` из окружения хоста, как подделка в тестах. `ps aux` во время прогона — пароля в аргументах нет.

6. **Проверки установщика:** с запущенным nginx на 80 — отказ «порты заняты». С доменом, указывающим не туда, — отказ с адресами. `--dry-run` в той же ситуации показывает обе проблемы сразу и ничего не меняет. **AAAA:** добавить домену сайта AAAA-запись на чужой IPv6 (например, `2001:db8::1`) при верной A-записи — отказ «не этого сервера: 2001:db8::1» с подсказкой про AAAA, и на сервере без своего IPv6 тоже (`dig` есть в образе Ubuntu; без него — `python3`). Удалить запись — проверка проходит.
7. **SSL:** оба домена открываются по https с сертификатом Let's Encrypt, http → https. `curl -I https://admin…` — HSTS, `X-Frame-Options`.
   - **Caddy не от root:** `docker compose exec caddy id` — `uid=1000(caddy)`. Порты 80 и 443 заняты им (`ss -ltnp`), сертификаты в томе принадлежат caddy. Если контейнер не стартует с «operation not permitted» на exec, убрать `cap_drop`/`cap_add` у caddy в `compose.yaml` и записать это сюда.

Сайт по https показывает страницу, картинки отдаются с `/media/…` (`Cache-Control: immutable`), HTML — `no-cache`. Страница с адресом `media` (`https://сайт/media/`) — тоже `no-cache`.
11. **Без простоя:** во время публикации гонять `while true; do curl -s -o /dev/null -w '%{http_code}\n' https://сайт/; done` — только 200.

После публикации в `/data/sites/.cache` есть `astro`, `vite` и `dot-astro`, а сборка прошла.
13. **Чистка релизов:** опубликовать 7 раз — в `/data/sites/<id>/releases` 5 папок. `current` указывает на последнюю.
14. **Перезапуск во время сборки:** «Опубликовать» и сразу `docker compose restart api`. После старта сборка помечена прерванной и прошла заново.

## Исправления по проверке

Проверяющий принял работу с двумя major и рядом minor. Исправлено всё, кроме `read_only` у API (ниже, почему).

**Major**

1. **Caddy (`web`) работал от root.** В цели `web` заведён пользователь `caddy` (uid 1000), ему отданы `/data` и `/config` (тома при первом подключении берут владельца отсюда), `USER caddy`. Порты 80 и 443 ему открывает file capability `cap_net_bind_service` у бинарника из официального образа. Её держат `cap_drop: ALL` + `cap_add: NET_BIND_SERVICE` в compose, а запасной путь — `sysctls: net.ipv4.ip_unprivileged_port_start: 0`. `no-new-privileges` у Caddy нет: он отключил бы эту file capability. Тест проверяет последний `USER` стадий `api` и `web` и права сервисов compose. В чек-листе — `docker compose exec caddy id`. Без Docker не запускалось: что Caddy поднимается от `caddy` и занимает 80/443, покажет живой VPS (пункт 7).
2. **`Cache-Control: no-cache` не ставился на `index.html` админки.** `header` выполняется раньше `try_files` и видит исходный путь (`/`, `/sites/…`), поэтому матчер `/index.html` срабатывал только на прямой запрос. Теперь `no-cache` стоит на всю ветку SPA. `/assets/*` — своя ветка с `immutable` и без `try_files`: отсутствующий ассет старой версии — 404, а не `index.html` под видом скрипта. Тест разбирает Caddyfile: заголовок в ветке с `try_files`, нет `header /index.html`, ветка ассетов без `try_files`. В чек-листе — `curl -I` по `/`, `/sites/x` и `/assets/nope.js`.

**Minor**

- **tsx и esbuild в образе.** Формулировки исправлены (Dockerfile, CONVENTIONS, README, этот документ): API запускается собранным JS без tsx, а tsx и esbuild приезжают транзитивно с vite и astro для сборщика сайта. В чек-листе ищутся только `vitest`, `drizzle-kit`, `typescript`, `@biomejs`. Исключать tsx из peer-разрешения vite не стали: это правка lockfile ради ~10 МБ, на безопасность не влияет — API его не исполняет.
- **Гонка при старте.** Пометка прерванных сборок (`markInterrupted`) теперь идёт до `serve()`, постановка в очередь (`resume`) — после. Вторая защита: очередь помнит сборки, идущие в этом процессе, и `buildsRepo.recover` их не трогает. На старом коде тест падает. Вживую — пункт 6 чек-листа.
