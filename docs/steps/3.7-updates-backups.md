# Шаг 3.7. Обновления, бэкапы и состояние установок

## Цель

Вторая половина модуля 9. Установок много, а студия одна (решение 6 в PLAN.md), поэтому обслуживать N установок должно быть скучно и безопасно:

- у установки есть номер версии из релиза, его видно в админке и в ответе состояния;
- бэкапы базы и медиа идут по расписанию и проверяются восстановлением, хранятся N последних, по желанию — зашифрованной копией во внешнем S3-совместимом хранилище; есть команда восстановления;
- обновление одной командой: бэкап → новая версия → миграции → проверка → откат при сбое (с восстановлением базы, если миграции успели примениться); миграции только совместимые вперёд, и это проверяет тест;
- студия видит состояние всех установок и обновляет их по списку серверов одной командой;
- клиент не заложник: сайт выгружается статическим архивом, а все данные сайта — полным экспортом.

На машине разработки нет Docker и PostgreSQL. Всё, что можно проверить без них, проверено тестами (скрипты на сервере — настоящим bash с подделками docker, ssh и прочих команд). Остальное — в чек-лист «Проверка на живом VPS» в конце. Что не запускалось, то так и названо.

## Решения и почему

### 1. Версия — из образа

`deploy/Dockerfile` принимает `ARG AVERRA_VERSION` (по умолчанию `dev`) и кладёт её в `ENV AVERRA_VERSION` образа `api`. `release.yml` передаёт её из тега (`v0.7.0` → `0.7.0`). API читает `AVERRA_VERSION` в `config.ts` (по умолчанию `dev` — разработка, e2e). Версия в образе, а не в `.env`: показывается то, что на самом деле запущено, а не то, что записано в файл.

Версию видит владелец в блоке «Состояние» админки и любой, у кого есть SSH и `averra.sh status`. В открытые маршруты (`/api/health*`) она **не** попадает: номер версии в открытом ответе подсказывает, какие уязвимости пробовать.

### 2. Состояние установки — маршрут для владельца, студия — через SSH

`GET /api/status` — только владелец админки (сессия), токену API (MCP) — 403. Ответ собирает `collectStatus` (`modules/status/service.ts`), он же печатает команду `status.js` в контейнере:

- версия; жива ли база и сколько миграций применено;
- последний бэкап и последний удачный: когда, чем кончился, проверен ли восстановлением, ушла ли копия во внешнее хранилище;
- последнее обновление: с какой версии на какую и чем кончилось (обновлено, откат, откат не удался);
- последняя сборка сайта (публикация) по всем сайтам и сколько сайтов сейчас с упавшей сборкой;
- почта: включена ли (и почему нет), сколько писем окончательно не ушло (`failed`), сколько ждут и сколько из ждущих — с ошибкой последней попытки (см. «Исправления по проверке»);
- свободное место на диске (тома сайтов и медиа, папка установки с бэкапами);
- `problems` — список того, на что смотреть (нет бэкапа больше двух суток, последний бэкап упал, мало места, письма с ошибкой, упавшие сборки, откат при обновлении). Список считает чистая функция `statusProblems` — одна для админки, команды и обзора студии.

**Чего в ответе нет:** адресов серверов, логинов и паролей SMTP, путей, ключей, данных писем. Только числа, времена и короткие причины, которые формирует сам код (тест проверяет, что секретов окружения в ответе нет).

**Как студия получает состояние.** Через SSH, а не новым токеном: `averra.sh status --json` на сервере выполняет `node dist/server/status.js` в контейнере API (команда читает базу напрямую, как `user:create`). Отклонённые варианты:

| | SSH + команда (выбрано) | Токен студии по HTTPS |
|---|---|---|
| Что нового открыто в интернет | ничего | маршрут через Caddy, принимающий токен уровня установки |
| Секрет | ключ SSH студии — он и так нужен для обновлений | ещё один секрет на машине студии, по токену на каждую установку |
| Работает, когда API лежит | да: `averra.sh` скажет «API не отвечает» и покажет бэкапы из файлов | нет — ровно тогда, когда нужнее всего |
| Цена | у студии должен быть SSH-доступ (он есть: установка и обновления) | новый вид токена, его выпуск, отзыв и хранение |

### 3. Бэкапы — `averra.sh backup` на хосте по таймеру systemd

Скрипт управления установкой `deploy/averra.sh` (bash: на сервере нет Node) ставится установщиком в `/opt/averra/averra.sh`. Бэкап делает хост, а не API: только снаружи контейнеров можно и снять дамп, и потом остановить API, подменить базу и поднять прежний образ.

Один бэкап — папка `/opt/averra/backups/<время UTC>-<вид>/`:

- `db.dump` — `pg_dump -Fc` из контейнера `postgres` (сжатый формат, восстанавливается `pg_restore`);
- `media.tar.gz` — том медиатеки (оригиналы и варианты картинок), снятый отдельным контейнером образа API с этим томом (`compose run --rm --no-deps`): бэкап не зависит от того, запущен ли API;
- `manifest.json` — версия, время, размеры, SHA-256 файлов, число миграций, итог проверки.

**Опубликованные сайты не бэкапятся:** это производные данные. API при старте сам собирает опубликованные сайты, у которых нет текущей версии на диске (шаг 3.6, `recover`), и берёт картинки из медиатеки. Поэтому восстановление, пока API остановлен, подменяет медиатеку восстановленной и очищает том сайтов, и только потом запускает API: сайт собирается заново из восстановленных базы и медиатеки (порядок — решение 6). Бэкап меньше, а сайт после восстановления совпадает с бэкапом. Служебные папки восстановления в томе медиатеки (`media/.averra-*`) в архив не попадают (`tar --exclude`).

**Проверка — восстановлением, а не только записью.** После дампа: `pg_restore` во временную базу `averra_verify` в том же Postgres с `--exit-on-error`, сверка числа миграций и наличия таблиц с исходной базой, удаление временной базы. Медиа — `gzip -t` и `tar -t` читают архив целиком. Базы лендингов — мегабайты, поэтому проверка идёт у каждого бэкапа, а не выборочно. Бэкап, который не прошёл проверку, помечается неудачным (`ok: false`) и в ротации не считается удачным.

**Ротация.** Хранятся `BACKUP_KEEP` (по умолчанию 7) последних удачных бэкапов, и ни один не старше `BACKUP_KEEP` дней (по времени в имени); чистка идёт после каждого бэкапа, удачного и нет; неудачные и брошенные временные папки удаляются; бэкап, который делается сейчас, не удаляется никогда. Права: папка бэкапов `700`, файлы `600`, владелец root.

**Расписание** — таймер systemd `averra-backup.timer` (каждый день в 03:30 со случайной задержкой до 30 минут, `Persistent=true`: пропущенный из-за выключенного сервера бэкап сделается при старте). Ставит его установщик. Почему не cron: `Persistent` и журнал в `journalctl -u averra-backup`.

**Одновременность.** Бэкап, восстановление и обновление берут один замок (`flock` на `/opt/averra/.averra.lock`): ночной бэкап посреди обновления не пойдёт.

**Состояние для API.** Итог каждого бэкапа и обновления скрипт пишет в `/opt/averra/state/*.json` (атомарно, через временный файл и `mv`). Папка смонтирована в контейнер API только на чтение (`/data/state`, `STATE_DIR`), API читает её при запросе состояния. Тексты ошибок в этих файлах — фиксированные строки скрипта, не вывод команд: в выводе `pg_dump` бывают параметры подключения.

### 4. Внешнее хранилище — rclone с шифрованием

По желанию (задан `BACKUP_S3_BUCKET` в `.env`) бэкап после проверки копируется в S3-совместимое хранилище (Yandex Object Storage и т. п.) образом `rclone/rclone:1.75.2` (точная версия, вышла 9 октября 2026). Ключи — `BACKUP_S3_ACCESS_KEY_ID` и `BACKUP_S3_SECRET_ACCESS_KEY` из `.env`; в контейнер rclone они идут переменными окружения (`-e VAR` без значения), а не аргументами.

**Копия шифруется** удалённым хранилищем `crypt` rclone (NaCl SecretBox: XSalsa20 + Poly1305 — с проверкой целостности; имена файлов тоже шифруются). Пароль — `BACKUP_PASSPHRASE`, его создаёт установщик (32 байта, как остальные секреты, не меняется при повторном запуске). Вне сервера дамп с хешами паролей, сессиями и заявками лежать открытым не должен. **Пароль нужно сохранить у студии** (менеджер паролей): умер сервер вместе с `.env` — без пароля внешняя копия не расшифруется. В хранилище — тот же срок: `BACKUP_KEEP` последних копий и не старше `BACKUP_KEEP` дней (чистка после каждого бэкапа, в том числе неудачного); сбой чистки виден в состоянии (`remote: cleanup-failed`); вторая линия — правило жизненного цикла бакета (README).

Сбой выгрузки не делает бэкап неудачным: локальная копия проверена. В состоянии он виден отдельно (`remote: failed`) и попадает в `problems`.

### 5. Персональные данные в бэкапах (152-ФЗ)

В дампе есть заявки (персональные данные посетителей), адреса пользователей админки, очередь писем. Срок хранения бэкапов конечен: не старше `BACKUP_KEEP` дней (по умолчанию 7) локально и во внешнем хранилище — по возрасту, а не только по числу, и после каждого бэкапа по таймеру, удачного или нет. Значит, удалённая в базе заявка (руками или по сроку сайта) живёт в бэкапах не дольше `BACKUP_KEEP` дней плюс сутки до следующего запуска таймера. Условия, при которых обещание держится: сервер включён (таймер), внешнее хранилище даёт удалять — сбой чистки там виден в «Состоянии установки»; обновление не брошено оборванным — его бэкап `pre-update` и отложенная база хранятся, пока `averra.sh update` не доведёт его (видно как `update_interrupted`, см. «Исправления по финальной проверке», п. 6); база `averra` на месте — без неё (откат кончился `rollback-failed`, рабочие данные под служебным именем) служебные базы по сроку не удаляются, пока человек не вернёт рабочую («Мелочи после приёмки», п. 3.7-2). Тот же срок у служебных баз с временем в имени: `averra_rolled_back_…` (откат обновления) и `averra_failed_restore_…` (восстановление, на котором не поднялся API, — в ней данные бэкапа); их удаляет та же чистка после каждого бэкапа, а пока они лежат, их видно в «Состоянии установки» (проблема `db_service_databases`). База `averra_before_restore` (прежняя рабочая база, если восстановление не смогло вернуть её на место) по сроку **не** удаляется: в ней рабочие данные, её разбирает человек — «Состояние» показывает и её. Итоговый срок хранения заявки — срок сайта + `BACKUP_KEEP` дней; это надо отразить в политике обработки персональных данных клиента (README). Внешнее хранилище для клиентов из РФ — в РФ (Yandex Object Storage, регион `ru-central1`), а копия зашифрована ключом, которого у хранилища нет.

### 6. Восстановление — `averra.sh restore <бэкап>`

1. Проверить бэкап (SHA-256 из манифеста, архив медиа читается целиком).
2. Распаковать медиатеку из бэкапа во временную папку на том же томе (`/data/media/.averra-restore`). Рабочая медиатека пока не тронута; не распаковалась — выход, ничего не менялось.
3. Восстановить дамп в **новую** базу `averra_restore` (`--exit-on-error`). Сбой здесь ничего не меняет: рабочая база не тронута.
4. Остановить API, переименовать `averra` → `averra_before_restore`, `averra_restore` → `averra` (имена баз меняются мгновенно). Если первое переименование прошло, а второе нет, первое возвращается (`averra_before_restore` → `averra`) и API снова запускается; не вернулось — скрипт честно говорит, что базы `averra` нет, под каким именем рабочая, и даёт команду возврата (а не «рабочая база не тронута»).
5. **Пока API стоит**, подменить медиатеку: прежнее содержимое тома переносится в `/data/media/.averra-before-restore`, распакованное — на его место (`mv` на том же томе — переименование, без копирования и без лишнего места; `find … -exec mv -t … {} +`, чтобы сбой любого переноса был виден кодом). Подмена — в две фазы, а имена того, что пришло из бэкапа, записаны заранее (`.averra-restore-names`). Прежнее содержимое не переехало целиком — уже перенесённое сразу возвращается, в корне ничего не удаляется. Не прошла вторая фаза — прежняя медиатека возвращается из соседней папки, а из корня удаляется только пришедшее из бэкапа. Затем прежняя база — на место, API запускается; сообщение говорит, что вернулось, а что нет и где лежит («Мелочи после приёмки», п. 3.7-1).
6. Том сайтов очистить, тоже без API.
7. Поднять API, дождаться `/api/health/ready`. API при старте сам собирает опубликованные сайты без версии на диске — уже из восстановленных базы и медиатеки. Поднялся — удалить прежнюю медиатеку (`.averra-before-restore`) и `averra_before_restore` (восстановление на месте человек подтвердил). Нет — остановить API, вернуть прежнюю базу, прежнюю медиатеку и `SITE_ID`, ещё раз очистить том сайтов (неподнявшийся API мог успеть что-то собрать) и поднять прежнее: прежние база и медиатека на месте. Неподнявшаяся база отходит под именем `averra_failed_restore_<время>` и удаляется по сроку бэкапов.

Почему так, а не «подменить медиатеку после готовности API» (как было до финальной проверки): API начинает собирать сайты, как только стартует, и берёт картинки из рабочей медиатеки. На новом сервере (`restore --from-s3`) она до подмены пуста — сборка падала бы на первой картинке, сайт оставался бы без версии, а скрипт писал бы «Готово». Повторная сборка после подмены — второй запуск API и лишнее окно, в котором домен отдаёт пустоту; подмена до запуска проще и закрывает гонку целиком.

Если база `averra_before_restore` или папка `.averra-before-restore` в томе медиатеки уже есть (прошлое восстановление не разобрано), скрипт отказывает до изменений и ничего не удаляет.

`--from-s3 <имя>` сначала скачивает и расшифровывает копию из хранилища. Восстановление спрашивает подтверждение (`--yes` — без вопроса): данные после бэкапа пропадут.

### 7. Обновление — `averra.sh update --version X`

**Обновление не бросается на полпути.** Команда `update` не делает обновление сама: она запускает процесс `averra.sh update-worker`, отвязанный от терминала и SSH, и показывает его лог (`/opt/averra/update.log`), пока он не кончится; её код выхода — его код. Отвязка — transient-службой systemd (`systemd-run --collect --unit=averra-update-<время>`, вывод — `StandardOutput=append:…/update.log`): она живёт вне сессии SSH, её не убьют ни SIGHUP при обрыве связи, ни закрытие сессии; без systemd — `setsid` (новая сессия без терминала). Процесс сам игнорирует `HUP` и `PIPE`. Значит, обрыв SSH во время `pnpm fleet update`, Ctrl+C у студии или закрытый терминал убивают только показ лога, а обновление доходит до конца — или до отката.

**Отметка хода.** Пока обновление идёт, в `/opt/averra/.update-run` (права 600) записано: с какой версии, на какую, время начала, шаг (`prepare` → `backup` → `switch` → `rollback` → `finishing`), имя бэкапа перед обновлением, число миграций до него, отложенная база. В `state/update-last.json` в это время — итог `in-progress` без времени конца. Если процесс всё же оборвался (перезагрузка сервера, `kill -9`), следующий `update` сначала **доводит прерванное**, а не отвечает «уже версия» по строке в `.env`:

- шаг `prepare` или `backup` (`.env` и `compose.yaml` ещё прежние): поднять прежнюю версию (API мог остаться остановленным на время бэкапа), итог прерванного — `failed`, затем обычное обновление;
- шаг `switch` (новая версия могла запуститься и применить миграции): копия прежнего `compose.yaml` (`compose.yaml.prev`) сделана до смены шага и отмечена в `.update-run` (`PREV_SAVED`) — откат берёт только её, а не файл от прошлого обновления; новая версия записана в `.env` (нет — процесс оборвался до запуска, и то, что поднялось бы, не новая версия: откат) и проходит проверку (API готов, API и Caddy держатся в `running`) — закончить обновление (новый `averra.sh`, итог `updated`); нет — откат по общим правилам (с восстановлением базы, если миграции прошли), код 1, обновление само не повторяется;
- шаг `rollback` — откат ещё раз (он повторяемый: имя отложенной базы запомнено; если она уже есть, а базы `averra` нет — откат оборвался между переименованиями, и рабочая база сначала возвращается на место; если есть обе — восстановление уже прошло и второй раз не делается);
- шаг `finishing` — только выгрузить внешнюю копию бэкапа и снять отметку.

Номер процесса (`.update-pid`) и итог (`.update-exit`) пишет только процесс, взявший замок; `update`, когда замок занят (идёт бэкап или восстановление), отказывает сразу, не трогая ни отметки, ни лог. Лог дописывается: каждый запуск начинается чертой `==== <время> update --version X ====`, на экран идёт только последний запуск, лог больше мегабайта уходит в `update.log.1`. Пока обновление не доведено, ротация бэкапов не удаляет его бэкап `pre-update` и отложенную базу: из них повтор откатывает.

Повторный `update` той же версии, пока процесс ещё идёт (например, `pnpm fleet update` после обрыва SSH), не запускает второй, а показывает лог идущего и отдаёт его код; другая версия — отказ. Процесс оборвался без итога — код 3 и подсказка повторить команду. В «Состоянии» `in-progress` дольше часа — проблема `update_interrupted` («похоже, оборвалось: повторите averra.sh update»); `averra.sh status`, когда API лежит, говорит «идёт обновление» или «обновление оборвалось» (поле `update` в JSON — для `pnpm fleet status`).

Решения по шагам:

1. **Подготовка без простоя:** скачать образы новой версии (`compose pull` с `AVERRA_VERSION=X`). Не скачались — выход, ничего не менялось.
2. Достать из нового образа `compose.yaml` и `averra.sh` этой версии (они лежат в образе API в `/app/deploy`): конфигурация установки меняется вместе с версией, а не отдельной ручной правкой.
3. **Остановить API и сделать бэкап** с проверкой (вид `pre-update`): с этого момента ничего не принимается, и бэкап — последнее состояние базы. Не удался — прежний API снова запускается, выход, ничего не менялось. Внешняя копия этого бэкапа выгружается в самом конце, когда сервис снова работает.
4. Запомнить число применённых миграций. Записать `AVERRA_VERSION=X` в `.env` (прежняя — в `AVERRA_PREVIOUS_VERSION`), новый `compose.yaml` (прежний — `compose.yaml.prev`).
5. Поднять новый API (`up -d api`): миграции применяет сам API при старте. Ждать `/api/health/ready` до `AVERRA_READY_TIMEOUT` секунд (по умолчанию 180). Это переменная окружения процесса, а не строка `.env`: `sudo AVERRA_READY_TIMEOUT=300 /opt/averra/averra.sh update …`.
6. Готов — поднять Caddy новой версии (админка) и проверить, что API и Caddy держатся в `running` (`compose ps --status running`, дважды с паузой). Всё так — записать новый `averra.sh`, итог «обновлено». Конец.
7. **Не готов — откат:** сначала остановить новый API (пока он перезапускается по кругу, он мог бы применить миграции сразу после подсчёта, и прежний образ встал бы на новую схему без восстановления базы), вернуть `.env` и `compose.yaml`; если число миграций изменилось — восстановить базу из бэкапа шага 3 (тем же путём, что `restore`, без медиа: их обновление не трогает). Рабочая база при этом **не удаляется**, а откладывается как `averra_rolled_back_<время>`: имя — в выводе, в `update-last.json` (`keptDatabase`) и в «Состоянии установки»; удаляется по сроку бэкапов. Поднять прежние API и Caddy, дождаться готовности. Итог «откат» (код выхода 1) или «откат не удался» (код 2, с инструкцией) — в `state/update-last.json`.

Сайт посетителям во время обновления отдаётся (Caddy и статика не трогаются до шага 6). Не принимаются заявки в окне между остановкой старого API (перед бэкапом) и готовностью нового: бэкап лендинга с проверкой — секунды; форма сайта получит 502. Данные, записанные новой версией до отката (она могла быть готова, а упал Caddy), не теряются: они в отложенной базе `averra_rolled_back_…`.

### 8. Миграции — только совместимые вперёд

Прежний образ должен работать на базе после миграций новой версии. Двух версий одновременно при обновлении нет: прежний API останавливается до бэкапа, а при откате новый останавливается до подсчёта миграций. Совместимость нужна там, где прежний образ встаёт на новую схему: откат, в котором база не восстановилась (итог `rollback-failed`, человек поднимает прежний образ), и откат руками на прежний образ без восстановления. Правило в CONVENTIONS:

- можно: новые таблицы, новые колонки с `DEFAULT` или без `NOT NULL`, индексы, снятие `NOT NULL`;
- нельзя одним шагом: удалить или переименовать таблицу или колонку, удалить индекс (уникальные индексы и ключи — опора `ON CONFLICT` прежнего кода: `users_email_unique`, `pages_site_slug_unique`, ключ `site_members`, `mail_settings_site_unique`), ограничение или другой объект базы (представление, последовательность, схему, функцию), сменить тип, добавить `NOT NULL` к существующей колонке или новую `NOT NULL`-колонку без `DEFAULT`. Это делается в два релиза: сначала новое рядом со старым (код пишет оба, читает новое), потом, когда старый код нигде не работает, удаление старого.

Проверку делает тест `db/migrations-compat.test.ts`: он разбирает SQL всех миграций и ищет опасные операции. Второй шаг двухшагового процесса помечается в самой миграции строкой `-- averra:compat <почему безопасно>` — без неё тест падает. Пометка действует только на инструкцию прямо под ней. Кроме удаления, переименования, смены типа и `NOT NULL` тест ловит `DROP DEFAULT`, новые ограничения (`UNIQUE`, `CHECK`, внешний ключ) и уникальные индексы на существующие колонки, `DROP TYPE` и `ALTER TYPE`, `DROP INDEX`, `DROP CONSTRAINT`, `DROP VIEW`/`SEQUENCE`/`SCHEMA`/`FUNCTION`/… и `DROP IDENTITY`/`EXPRESSION`, а любое другое `DROP` (кроме `DROP NOT NULL`) — правилом «удаление (не из списка)», чтобы новая конструкция SQL не прошла молча; ограничения на таблицу или колонки, которые заводит та же миграция, разрешены. Миграции до первого релиза (0000–0014): две из них (`0002`, `0007`) добавили `CHECK` к существующим таблицам — установок со старой схемой тогда не было, они перечислены в тесте закрытым списком (тест падает, если список разойдётся с найденным).

### 9. Несколько установок — `pnpm fleet`

Команда студии на машине разработчика (TypeScript, `deploy/src/fleet.ts`): список серверов — файл `~/.config/averra/servers.txt` вне репозитория (или `--file`, или `AVERRA_SERVERS`; пример — `deploy/servers.example.txt`), строка `<имя> <пользователь@хост> [port=…] [dir=…]`.

- `pnpm fleet status` — по очереди `ssh` на каждый сервер, `sudo -n /opt/averra/averra.sh status --json`, таблица: версия, база, бэкап, сборки, почта, место, проблемы. Код выхода 1, если где-то есть проблемы или сервер не ответил.
- `pnpm fleet update --version X [--only имя,…]` — по очереди, с остановкой на первой ошибке: что обновлено, на чём сломалось, что не трогали.
- SSH только по ключам: `BatchMode=yes` (пароль не спросят — откажет), `ConnectTimeout`. Ключ хоста проверяется как обычно (`known_hosts`): с `BatchMode` неизвестный хост — отказ, а не тихое согласие. Первый вход на сервер — руками, со сверкой отпечатка.

Исполнитель команд (`ssh`) подменяется в тестах: план обновления и разбор ответов проверяются без сети.

### 10. Экспорт — «клиент не заложник»

- **Сайт статическим архивом:** `GET /api/sites/:siteId/export/static` — ZIP текущей версии сайта на сервере (то, что отдаёт Caddy: HTML, CSS, картинки). Любой веб-сервер отдаст его как есть. Права — `site.read`, кроме токена API (публичное содержимое, но программе MCP архив не нужен). Без публикации на сервере (`PUBLISH_DIR`) или до первой сборки — 409 с объяснением.
- **Все данные сайта:** `GET /api/sites/:siteId/export/data` — ZIP: `site.json` (сайт, тема, настройки заявок, страницы с черновиками и опубликованными версиями, история, описание медиатеки, заявки с согласиями), оригиналы картинок `media/<id>/original.*` и `README.txt` с описанием формата. В нём персональные данные посетителей, поэтому право — новое действие `site.export` (владелец и клиент, как у заявок), токену API — 403 (`personalData`).

ZIP пишется потоком (`fflate` 0.8.3, без зависимостей, вышел в мае 2026): файлы читаются по одному, в памяти — один файл, а не весь архив; картинки и так сжаты и кладутся без сжатия. Предел ZIP без ZIP64 — 4 ГБ: экспорт больше 3,5 ГБ отвечает 413 с советом взять бэкап (у лендинга таких объёмов не бывает). Админка скачивает архив запросом и `Blob`, как CSV заявок.

## Критерии готовности

1. Версия из образа видна в блоке «Состояние» и в `GET /api/status`, в открытых маршрутах её нет.
2. `GET /api/status`: только владелец (участник — 403, токен — 403, без входа — 401); состояние базы, бэкапа, обновления, сборок, почты, диска и проблемы; в ответе нет секретов.
3. `averra.sh backup` делает дамп и архив медиа, проверяет их восстановлением во временную базу и чтением архива, пишет манифест и состояние, хранит `BACKUP_KEEP` удачных, по желанию выгружает зашифрованную копию в S3 и чистит там лишнее.
4. `averra.sh restore` восстанавливает через новую базу и переименование, рабочую базу при сбое не трогает.
5. `averra.sh update` проходит план из решения 7; откат образа при неготовности; восстановление базы — только если миграции применились; итог в `state/update-last.json`.
6. Тест совместимости миграций ловит удаление, переименование, смену типа и `NOT NULL` без пометки `averra:compat`.
7. `pnpm fleet status` и `pnpm fleet update` по списку серверов, остановка на первой ошибке.
8. Экспорт статики и данных — ZIP потоком, права, токену данные недоступны.
9. README («Обновление», «Бэкапы и восстановление», «Несколько установок»), CONVENTIONS, PLAN, этот документ с чек-листом. `pnpm check` и `pnpm e2e` зелёные.

### Отклонения от плана и добавки

- `SITE_ID` пишется в манифест бэкапа, и восстановление на новом сервере ставит его в `.env` само: иначе Caddy отдавал бы на домене пустой сайт, который завёл установщик.
- `openDb({ migrate: false })` у команд: `status.js` только читает базу и не применяет миграции (например, посреди отката).
- Помощники bash-тестов вынесены в `deploy/tests/bash.ts`, тест установщика пользуется ими же. `downloadCsv` в админке переписан на общий `saveResponse` (`src/download.ts`).
- `apps/api/.env.example` — `AVERRA_VERSION` и `STATE_DIR`.

### Что не проверено и что осталось

- Всё, что в чек-листе ниже: настоящие `pg_dump`/`pg_restore` в контейнере Postgres, `tar` в образе API, rclone с Yandex Object Storage, systemd, `flock`, обновление между двумя настоящими релизами.
- `read_only` у контейнера API — по-прежнему после замера на живом VPS (хвост шага 3.6).
- Выгрузка в админке скачивается через `Blob` (как CSV): архив целиком в памяти браузера. Для лендинга это мегабайты; если появятся сайты на сотни мегабайт картинок — скачивание ссылкой (админка и API на сервере — один источник).
- ZIP без ZIP64: выгрузка больше 3,5 ГБ отвечает 413 и советует бэкап.
- Новый Postgres-мажор обновлением не делается (правило в CONVENTIONS), процедуры для него нет.

### План

1. Откат обновления не теряет данные молча: окно между дампом и запуском новой версии закрыть, рабочую базу при откате не удалять, а откладывать с именем в выводе и состоянии; уже существующую `averra_before_restore` не удалять.

3. Список серверов студии — вне `deploy/`; на сервер копировать только нужные файлы; `servers.txt` — в `.dockerignore`.
4. Срок хранения бэкапов — по возрасту, после каждого бэкапа; сбои чистки во внешнем хранилище — в состояние.
5. Тест миграций: пометка на инструкцию, новые правила.
6. Обновление «удачно» только при работающем Caddy.
7. Тесты непокрытых веток восстановления.
8. Документация: имена файлов и переменных, `MAIL_ENCRYPTION_KEY` при переезде, переход с установки 3.6.
9. `pnpm fleet --file` — от папки запуска.
10. Кривой `BACKUP_KEEP` — в состоянии сразу; бэкап без запущенного API.

### Итог по пунктам

1. **Major, откат удалял данные после бэкапа — исправлено.** Два слоя. Первый: `averra.sh update` останавливает API **до** бэкапа (`compose stop api`), поэтому всё, что прежняя версия приняла, есть в дампе; бэкап не удался — прежний API поднимается снова, «ничего не менялось». Выгрузка в S3 вынесена в конец (`do_backup … 1` откладывает её, `finish_backup` делает после обновления или отката): сервис не стоит, пока копия едет в хранилище. Окно простоя — бэкап с проверкой (у лендинга секунды) и старт API; цена — форма сайта в эти секунды получает 502, честно, а не молча теряет. Второй слой: при откате с восстановлением рабочая база **не удаляется** — `restore_database` получил имя, под которым отложить прежнюю базу, откат использует `averra_rolled_back_<время UTC>`. Это важно, когда новая версия успела поработать (API был готов, а упал Caddy). Имя базы — в выводе с командой `psql`, в `update-last.json` (`keptDatabase`, схема `UpdateRun` с `default(null)` — файлы прежнего скрипта читаются), в «Состоянии установки» (проблема `update_kept_database`, неделю после отката) и в `averra.sh status`. Удаляется она по сроку бэкапов (`BACKUP_KEEP` дней, `rotate_backups`): персональные данные в ней не лежат вечно. `restore_database` больше не делает `dropdb averra_before_restore` перед переименованием: если база с таким именем есть, отказ с подсказкой, ничего не удалено. Финальная проверка нашла одну major и семь minor. Исправлено всё; что осталось как оговорка — ниже, с причиной. Docker, Postgres и VPS по-прежнему не запускались: скрипт проверен настоящим bash с подделкой docker, живые шаги — в чек-листе (пп. 7, 8, 26, 28, 29).

### План

1. Восстановление: медиатека подменяется, пока API остановлен, — до запуска API, который сразу собирает сайты; прежняя отходит рядом и возвращается при сбое. Тест на порядок, который падает на прежнем коде.
2. Откат обновления повторяем и при обрыве между переименованиями баз.
3. Шаг `switch`: копия `compose.yaml.prev` — до смены шага и с отметкой; тест на сверку версии в `.env`.
4. Подмена медиатеки без удаления прежней до успеха, честные сообщения; служебные папки — не в бэкап.
5. `update` при занятом замке не трогает лог и итог; номер процесса — после замка.
6. Ротация не удаляет бэкап и отложенную базу незавершённого обновления.
7. Причина неудачного обновления — в админке и в `status.js`.
8. README (поля `GET /api/status`, восстановление), решения 3, 6, 7, чек-лист.

### Итог по пунктам

1. **3.7-1, major, гонка при восстановлении — исправлено.** Новый порядок `cmd_restore`: распаковать медиатеку во временную папку (API работает, ничего не тронуто) → восстановить дамп в `averra_restore` → остановить API и поменять базы именами → **пока API стоит**, подменить медиатеку (`swap_media`: прежнее содержимое тома — в `/data/media/.averra-before-restore`, распакованное — на его место; `mv` на том же томе, без копирования) → очистить том сайтов → `SITE_ID` → `compose up -d` → готовность. API при старте собирает опубликованные сайты уже из восстановленных базы и медиатеки, на новом сервере в том числе. Поднялся — прежняя медиатека и `averra_before_restore` удаляются. Подмена не прошла — прежняя медиатека возвращается (`unswap_media`), прежняя база — на место, API поднимается, сообщение «медиатека не подменилась — прежние база и медиатека на месте». API не поднялся — остановить, вернуть базу, медиатеку и `SITE_ID`, ещё раз очистить сайты (неподнявшийся API мог успеть собрать что-то из восстановленной базы) и поднять прежнее. Почему подмена до запуска, а не повторная пересборка после неё: пересборка — второй запуск API и ещё одно окно, в котором домен отдаёт пустоту, а гонка остаётся у первого запуска. Подделка docker теперь выполняет `tar` и `sh` «контейнера» API над настоящими папками томов (`/data` → папка теста) и при каждом запуске API записывает, какие картинки лежали в медиатеке (`builds.log`). Тесты: «новый сервер с пустой медиатекой» — единственный запуск API видит `site/original.jpg` (на прежнем коде — пустую медиатеку: `build 0.6.0: `); порядок «переименование баз → подмена → очистка сайтов → `up -d`», между остановкой API и подменой запусков нет, после — медиатека как в бэкапе, без служебных папок. Тесты прогнаны на прежнем `averra.sh`: оба падают.
2. **3.7-2, откат не повторялся после обрыва между переименованиями — исправлено.** `rollback_update` первым делом смотрит на отложенную базу из отметки (`KEPT`): она есть, а `averra` нет — откат оборвался между переименованиями, рабочая база возвращается на место (`KEPT → averra`) и восстановление идёт заново; не вернулась — `rollback-failed` с именем базы и командой возврата, без совета `dropdb`. Есть обе — восстановление уже прошло (оборвалось до отметки `RESTORED`): второй раз не делается, а `dbRestored` и `keptDatabase` в итоге верные (раньше `keptDatabase` терялся). Ротация не удаляет базу из `KEPT`, пока обновление не доведено (п. 6). Тесты: процесс убит на `averra_restore RENAME TO averra` — повтор возвращает рабочую базу, откатывает (15 миграций, отложенная — 16), `rolled-back`; убит после обоих переименований без `RESTORED` — повтор без `pg_restore`, `keptDatabase` на месте. На прежнем коде оба падают (первый — `rollback-failed` с советом удалить базу с рабочими данными).
3. **3.7-3, шаг switch — исправлено.** `cp compose.yaml compose.yaml.prev` и отметка `PREV_SAVED=1` — до `PHASE=switch`; откат копирует `.prev` только при этой отметке, поэтому файл от прошлого обновления конфигурацию не откатит. Сверка версии в `.env` при доводке `switch` осталась и теперь закреплена тестом: процесс убит на `switch`, `.env` прежний, `compose.yaml` новый — повтор откатывает (`rolled-back`, `compose.yaml` прежний, `averra.sh` не заменён), а не пишет `updated`. Мутация «убрать сверку» этим тестом ловится (проверено). Второй тест: отметка `switch` без `PREV_SAVED` и `compose.yaml.prev` позапрошлой версии — откат его не берёт (на прежнем коде падает).
4. **3.7-4, подмена медиатеки удаляла прежнюю до переноса — исправлено** вместе с п. 1: прежняя медиатека не удаляется, а отходит в `.averra-before-restore` и удаляется только после готовности API; перенос — `find … -exec mv -t … {} +` (с `\;` сбой `mv` find проглатывал бы). Сообщения — по фактическому итогу: что вернулось, что нет и где лежит прежняя медиатека. Служебные папки не попадают в бэкап: `tar --exclude=media/.averra-*`. Оставшаяся от прошлого восстановления `.averra-before-restore` — отказ до изменений (как у базы `averra_before_restore`): молча её не удаляем. Тесты: подмена кончилась сбоем — прежние база и медиатека на месте, API ни разу не запускался на восстановленной базе; API не поднялся — медиатека прежняя (картинка, загруженная после бэкапа, есть, удалённая — не вернулась), прежний API пересобрал сайт из неё; оставшаяся папка — отказ, ничего не тронуто; архив бэкапа без `.averra-*`.
5. **3.7-5, `update` при занятом замке затирал лог — исправлено.** `cmd_update` пробует замок до запуска процесса (`flock -n`) и при занятом отказывает сразу: отметки, `.update-exit` и лог не тронуты; дескриптор с замком закрывается до запуска процесса, замок берёт сам процесс. Процесс пишет `.update-pid` и ставит запись итога (`trap EXIT`) только после `take_lock`: второй, проигравший замок, не затирает номер и итог идущего. Лог больше не обнуляется: каждый запуск дописывает черту `==== <время> update --version X ====`, на экран идёт только последний запуск (смещение последней черты), больше мегабайта — прежний лог уходит в `update.log.1`. Тесты: замок занят — код 1, лог и `.update-exit` целы, потом удачное обновление дописывает лог под чертой и не показывает прошлый; `update-worker` без замка не трогает `.update-pid` и не пишет `.update-exit`. Оговорка: два `update`, запущенные в одну и ту же долю секунды, оба проходят пробу замка; второй процесс тогда выходит, не взяв замок, а его команда может удалить `.update-pid` первого и через минуту сказать «процесс не запустился», хотя первый идёт (`averra.sh status` и `update.log` покажут ход). Закрыть это — передавать замок процессу или вести номер запуска; для ручной команды студии, которая и так идёт по серверам по очереди, не стоит сложности.
6. **3.7-6, ротация удаляла бэкап незавершённого обновления — исправлено.** Пока есть `.update-run`, `rotate_backups` не удаляет бэкап из `BACKUP` и базу из `KEPT`. Тест: `BACKUP_KEEP=1`, отметка отката, бэкап `pre-update` трёхдневной давности и отложенная база — плановый бэкап их не трогает (а более старый удаляет); отметка снята — следующий бэкап удаляет оба по сроку. Цена: если оборвавшееся обновление так и не довели, его бэкап и база живут дольше `BACKUP_KEEP` дней — это видно в «Состоянии» (`update_interrupted` через час, служебная база), и `averra.sh update` доводит его.
7. **3.7-7, причина неудачного обновления не показывалась — исправлено.** Общая функция `updateResultText` в схеме: подпись итога и, для `failed` и `rollback-failed`, причина из `UpdateRun.error` («не начато, версия прежняя: в образе нет compose.yaml или averra.sh»). Подпись `failed` стала нейтральной: «не начато, версия прежняя». У `rolled-back` причина повторила бы подпись — не добавляется. Ею пользуются админка (`describeUpdate`) и `status.js` (`statusLines`). Тесты: схема (все итоги), подпись админки, строка `status.js`.
8. **3.7-8, документация — исправлено.** README: в таблице API у `GET /api/status` — `checkedAt`, `db.serviceDatabases`, поля `update`, `updateUnreadable`; «Бэкапы и восстановление» — новый порядок (подмена медиатеки до запуска API, `.averra-before-restore`, отказ при оставшейся папке), служебные папки не в бэкапе; «Обновление» — лог дописывается, отказ при занятом замке. Здесь: решение 3 (сайт собирается из восстановленных базы и медиатеки, `--exclude`), решение 6 (шаги 5–7 и почему подмена до запуска), решение 7 (повторяемый откат, `PREV_SAVED`, замок, лог, ротация), описание тестов, чек-лист: пп. 7, 8 и 26 уточнены (сборка «собран» после восстановления, картинки, нет `.averra-before-restore`), новые пп. 28 (бэкап без служебных папок, отказ при оставшейся) и 29 (обновление при занятом замке, лог).

## Мелочи после приёмки

Финальная проверка шагов 3.5–3.7 оставила три minor-замечания к этому шагу. Исправлено всё; проверено на подделке docker (`deploy/tests/fake-docker.sh`) с настоящими `sh`, `find` и `mv` над папками томов — Docker и VPS на машине разработки нет.

1. **3.7-1, обрыв подмены медиатеки удалял непереехавшие прежние картинки — исправлено.** Раньше первая фаза `swap_media` переносила прежнее содержимое тома в `.averra-before-restore`, и если часть записей не переехала, `unswap_media` удалял в корне всё, кроме этой папки, — вместе с непереехавшими прежними картинками, а `cmd_restore` писал «прежние база и медиатека на месте». Теперь:
   - до подмены в `/data/media/.averra-restore-names` записываются имена того, что придёт из бэкапа (`ls -A .averra-restore/media`);
   - фаза 1 (прежнее — в `.averra-before-restore`) не прошла целиком — уже перенесённое сразу возвращается в корень, в корне ничего не удаляется, распакованная копия бэкапа убирается, код 4. Скрипт возвращает прежнюю базу, поднимает API и пишет «медиатека не подменилась — прежние база и медиатека на месте» — теперь это правда;
   - вернуть в фазе 1 не вышло — код 5: ничего не удалено, прежние картинки частью на месте, частью в `.averra-before-restore`. Скрипт так и пишет, называет папку и велит вернуть её содержимое в `/data/media`, базу не трогает и API не запускает: на половине медиатеки поднимать нечего;
   - фаза 2 (распакованное — на место) не прошла — код 1, прежняя медиатека целиком в `.averra-before-restore`. `unswap_media` удаляет в корне **только имена из списка** (пришедшее из бэкапа, оно есть в архиве) и возвращает прежнее; списка нет — не удаляет ничего. Так же после неподнявшегося API;
   - список удаляется вместе с `.averra-before-restore` после успеха (`drop_media_before`) или после возврата.

   Тесты (`averra.test.ts`, подделка `mv`, которая не переносит одну запись): папка `other` не переехала — после отказа прежняя медиатека целиком (`other/after.jpg` и обе картинки `site`), служебных папок нет, база прежняя, API работает; папка `other` не переехала, а уже переехавшая `site` не вернулась — `other/after.jpg` на месте, `site` в `.averra-before-restore`, сообщение не говорит «на месте», API не запущен. На старом коде оба теста падают (`other/after.jpg` удалялся). Прежние тесты подмены и неподнявшегося API проходят без изменений по сути.
2. **3.7-2, ротация могла удалить единственную копию рабочих данных — исправлено.** Если откат кончился `rollback-failed`, а рабочая база осталась под именем `averra_rolled_back_<время>` (базы `averra` нет), `update_finish` снимал отметку `.update-run`, и через `BACKUP_KEEP` дней ротация удаляла эту базу — ночной бэкап при этом падал, но ротация идёт и после неудачного. Теперь `rotate_backups` не удаляет служебные базы по сроку, пока базы `averra` нет (`db_exists averra` ответил 0), и пишет почему: в одной из них могут быть рабочие данные. Защита не зависит от того, каким путём база потерялась (неудачное второе переименование отката, `restore_database` с кодом 2, неудачный возврат после восстановления). Сообщения `rollback-failed` о базе под отложенным именем говорят, что срок хранения её не удалит, пока базы `averra` нет. Обещание по 152-ФЗ (решение 5, README) называет это исключение. Тест: базы `averra` нет, отложенная база трёхдневной давности и база неудачного восстановления при `BACKUP_KEEP=1`, бэкап падает — обе базы на месте, «Удалена база» в выводе нет; рабочую вернули — следующий бэкап удаляет отложенную по сроку. На старом коде тест падает.
3. **3.7-3, документация расходилась с кодом — исправлено.** PLAN.md: «медиатека подменяется, пока API остановлен (до его запуска)», а в обещании срока хранения — оба исключения. README («Персональные данные (152-ФЗ)») и решение 5: в условиях — «обновление не брошено оборванным — его бэкап `pre-update` и отложенная база хранятся, пока `averra.sh update` его не доведёт (видно как `update_interrupted`)» и «база `averra` на месте». Решение 6 описывает подмену в две фазы со списком имён.
