# Запуск Averra с сайтом Леры (le-english) — задание для агента

Задание для агента (Codex и т. п.), который разворачивает первую боевую установку Averra
с сайтом Vallex English. Агент делает работу по шагам. Отмеченное **[человек]** делает
владелец репозитория. Агент такое не делает: он просит и ждёт.

Сначала прочитай `AGENTS.md` в корне. Потом страницы документации `apps/docs/src/content/docs/`:
- `install/requirements.md`;
- `install/server.md`;
- `install/domains.md`;
- `install/mail.md`;
- `install/backups.md`;
- `install/checklist.md`.

Потом `examples/le-english/README.md`. Команды и флаги сверяй с кодом (`deploy/install.sh`,
`examples/le-english/import.ts --help`), а не с этим файлом: если они разошлись, прав код.

## Что спросить у человека до начала

- IP нового VPS и SSH-доступ: root или sudo, вход по ключу.
- Домен сайта и домен админки (по умолчанию `admin.<домен>`). Где управляют DNS.
- Почта студии: она нужна для Let's Encrypt и для входа владельца.
- Свежие данные с текущего сайта Леры. Лера правила контент после 4 октября, поэтому старая копия
  не годится:
  - `data/content.json`, файл вида `{ version, savedAt, content }`;
  - папка `public/` целиком или хотя бы `public/uploads/`.

  **`data/leads/` не брать.** Там заявки, то есть персональные данные. Их переносят отдельно и
  только с ведома Леры.
- Какую базу ставить (см. шаг 1).
- SMTP-ящик для писем и куда слать заявки: почта, Telegram.

Пароли и токены не передаются аргументами команд и не попадают в git, логи и чат. Пароль
спрашивается скрытым вводом или кладётся в переменную через `read -rs`.

## Шаг 0. Выпустить первую версию [человек + агент]

Релизов ещё нет: тегов в репозитории нет, образов в GHCR тоже. А `install.sh` требует
`--version` с опубликованными образами `ghcr.io/midhey/averra-api` и `averra-web`.

1. Агент: убедиться, что `pnpm check` и `pnpm e2e` на `master` зелёные.
2. **[человек]** Смёржить PR от release-please «release 0.1.0». Он создаст тег `v0.1.0`, а
   workflow `release` соберёт образы. Как это устроено — `dev/releases.md`.
3. **[человек]** Один раз сделать оба пакета GHCR публичными: Package settings → Change
   visibility → Public.
4. Агент: проверить, что образы скачиваются без входа:
   ```bash
   docker pull ghcr.io/midhey/averra-api:0.1.0
   ```

## Шаг 1. База данных — решение до установки

**По умолчанию — встроенная PostgreSQL из `deploy/compose.yaml`.** Её ставит установщик, и с ней
работают бэкап с проверкой, восстановление и откат при обновлении (`averra.sh`). Для первого
клиента рекомендуем её.

**Внешняя PostgreSQL сейчас не поддерживается.**
- `DATABASE_URL` в `compose.yaml` жёстко ведёт на контейнер `postgres`.
- `averra.sh` делает `pg_dump`/`pg_restore`/`psql` через `docker compose exec postgres`.

Подмена `DATABASE_URL` через `compose.override.yaml` даст рабочий сайт, но сломает бэкапы и откат.
**Так не делать.**

Если человек настаивает на внешней базе, сначала сделай отдельное изменение в коде, отдельным
коммитом `feat!:` и с тестами:
- в установщике — флаг или переменная для внешнего `DATABASE_URL` (пароль — не аргументом). Без
  неё сервис `postgres` не поднимается, а `depends_on` у API на него снимается;
- в `averra.sh` — бэкап, проверка бэкапа во временной базе, восстановление и откат через
  `pg_dump`/`pg_restore` по этому адресу. Клиентские утилиты PostgreSQL той же мажорной версии,
  что и сервер, должны быть в контейнере или на хосте;
- в `deploy/tests` — тесты на оба режима;
- в документации — `install/server.md`, `install/backups.md`, `dev/env.md`.

Ставить на прод только после зелёных `pnpm check` и тестов `deploy/`.

## Шаг 2. Пробная установка на поддомене

Сначала не на домене Леры: возьми поддомен, например `test.<домен студии>`, и
`admin.test.<домен студии>`. Пройди на нём `install/checklist.md` целиком, включая пункт про
память: VPS 1 ГБ или 2 ГБ. Только потом переходи к боевой установке. Найденные расхождения
документации и кода исправь в репозитории.

## Шаг 3. Установка

По `install/server.md`. Коротко:

```bash
# с машины студии: на сервер копируются только три файла
ssh root@<vps> mkdir -p /root/averra-deploy
scp deploy/install.sh deploy/averra.sh deploy/compose.yaml root@<vps>:/root/averra-deploy/
# на сервере: сначала проверка без изменений, потом установка (пароль владельца спросит скрыто)
cd /root/averra-deploy
sudo bash install.sh --site-domain <домен> --email <почта студии> --version 0.1.0 \
  --site-name "Vallex English" --dry-run
sudo bash install.sh --site-domain <домен> --email <почта студии> --version 0.1.0 \
  --site-name "Vallex English"
```

Пока DNS домена Леры ведёт на старый сервер, установщик откажет из-за DNS. Варианты:
- поставить с `--skip-dns-check` и переключить DNS в шаге 7. Сертификат выпустится, когда DNS
  разойдётся;
- сначала перенести DNS — тогда старый сайт сразу недоступен, это хуже.

**Выбери первый вариант и согласуй время переключения с человеком.**

После установки:
1. Войти в `https://admin.<домен>`.
2. Настроить SMTP («Почта», `install/mail.md`), SPF, DKIM и DMARC.
3. Включить Telegram-уведомления, если человек дал бота (`install/telegram.md`).
4. **[человек]** Сохранить `/opt/averra/.env` или хотя бы `BACKUP_PASSPHRASE` и
   `MAIL_ENCRYPTION_KEY` в менеджер паролей студии.

## Шаг 4. Перенос сайта Леры со свежими данными

Скрипт запускается с машины студии (Node 24, из `examples/le-english`) и ходит в API установки
как владелец. Свежие файлы Леры положи вне репозитория, например в `~/le-english-live/content.json`
и `~/le-english-live/public/`.

Пока DNS ведёт на старый сервер, адрес админки снаружи не открывается. Есть два способа:
- выпустить сертификат на временный поддомен админки;
- ходить через SSH-туннель.

Выбери, что проще в этой ситуации, и опиши в отчёте.

1. **Проверить новые данные на совместимость.** Сравни свежий `content.json` со старым
   (`content.default.json` из исходника и прежний `data/content.json`). Если у Леры появились
   секции или поля, которых нет в `examples/le-english/src/content.ts` и `blocks/`, допиши перенос.
   Затем:
   - `pnpm --filter @averra/example-le-english build`;
   - тесты примера;
   - отдельный коммит.

   **Ничего не должно теряться молча:** каждое поле из её контента должно оказаться на сайте или
   быть названо в отчёте.
2. **Сначала прогнать локально.** На `pnpm dev` с чистой базой запусти тот же импорт со свежими
   `--content` и `--public`. Сверь страницы с её живым сайтом скриптами `compare/shoot.mjs` и
   `compare/check.mjs`. **Заявки они шлют настоящие:** на не-localhost — только с `--send-leads`
   и с ведома человека.
3. **Перенос на установку** (пароль владельца — переменной или скрытым вводом):
   ```bash
   cd examples/le-english
   read -rs AVERRA_PASSWORD; export AVERRA_PASSWORD
   node import.ts --content ~/le-english-live/content.json --public ~/le-english-live/public \
     --email <почта владельца> --api https://admin.<домен> --origin https://admin.<домен> \
     --site-url https://<домен>
   ```
   Всё, кроме блоков, ляжет черновиками.
4. **Документы.**
   - **[человек]** Проверить реквизиты в «SEO → Организация». Скрипт берёт их из `legal` в
     контенте Леры.
   - **[человек]** Проверить тексты `/privacy` и `/consent` (лучше с юристом), удалить
     блок-пометку шаблона и опубликовать.
   - Без опубликованных документов `--publish` ничего не опубликует: так и задумано.
5. **Публикация** — тот же запуск с `--publish`. Если скрипт назвал правки в черновиках
   (`draftsBefore`), разберись с ними по README. Не добавляй `--publish-drafts` вслепую.

## Шаг 5. Проверка сайта действием

На установке, с JS и без JS, на ширине 375 и 1440 px проверь:
- шапку и мобильное меню;
- окно записи с любой кнопки «Записаться», а без JS — переход на `/zapis`;
- отправку заявки: одну тестовую, с ведома человека, потом удалить её в «Заявках»;
- что письмо или сообщение в Telegram пришло;
- FAQ, анимации, фото, 404;
- редиректы `/politika/` → `/privacy` и `/soglasie/` → `/consent`;
- отсутствие ошибок CSP в консоли.

Правила проверки такие же, как в `AGENTS.md`: действием, а не по скриншотам.

## Шаг 6. Бэкап до переключения

```bash
sudo /opt/averra/averra.sh backup
```

Убедиться, что бэкап проверен («Состояние установки»). По желанию — внешнее хранилище
(`install/backups.md`).

## Шаг 7. Переключение домена [человек + агент]

1. **[человек]** Согласовать время с Лерой. Старый сайт пока не выключать: он нужен для отката.
2. Перевести A-записи домена и `admin.` на новый VPS. AAAA — только на IPv6 этого сервера или
   никаких.
3. Дождаться сертификатов: `docker compose logs caddy`, `install/domains.md`.
4. Ещё раз пройти шаг 5 на боевом домене.
5. Если на старом сайте были адреса, которых нет в Averra, добавить на них редиректы. Список
   адресов старого сайта сверить с его `sitemap.xml`.

## Шаг 8. SEO и поисковики

1. «SEO»: адрес сайта `https://<домен>` (без `www`, если сайт был без него — как у старого
   canonical), описание, иконка, картинка для соцсетей, счётчики (Метрика). Домены счётчиков
   должны быть разрешены в CSP.
2. **Снять «Скрыть сайт от поисковиков»** (карточка «Индексация»). Новая установка скрыта по
   умолчанию — если забыть, сайт выпадет из поиска.
3. Проверить `https://<домен>/robots.txt`, `sitemap.xml` и canonical на страницах.
4. **[человек]** В Яндекс Вебмастере и Search Console переподтвердить права, если подтверждение
   было файлом на старом сервере, и отправить sitemap.

## Шаг 9. Сдача

- Добавить сервер в список установок студии (`install/fleet.md`).
- **[человек]** Пригласить Леру в админку ролью «Администратор сайта» (`admin/members.md`).
- **[человек]** Если меняется оператор персональных данных — уведомление в РКН (`install/personal-data.md`).
- Старый сервер выключить не раньше чем через неделю, когда в «Заявках» пошли заявки и нет жалоб.

## Готово, когда

- Сайт на боевом домене работает по HTTPS, и шаг 5 пройден на нём.
- Контент совпадает со свежим `content.json` Леры, а всё не перенесённое названо в отчёте.
- Заявка доходит до почты или Telegram.
- Бэкап проверен, `.env` сохранён у человека.
- Индексация открыта, sitemap отдан поисковикам.
- Все правки кода и документации закоммичены по `AGENTS.md`: Conventional Commits на английском,
  `pnpm format`, `pnpm check` и `pnpm e2e` зелёные.

Отчёт человеку — по-русски. В нём: что сделано, что проверено действием, что осталось за
человеком, какие расхождения нашлись.
